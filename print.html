Skyhook

Skyhook

Skyhook is a provider-neutral coding agent with a terminal interface and a programmable JavaScript workflow runtime. Use it interactively, automate work in headless sessions, or embed its Rust library in your own application.

Skyhook supports OpenAI Chat Completions and Responses, Anthropic Messages, Codex/ChatGPT subscriptions, and compatible local model endpoints. Tools work in local workspaces and on Linux and Windows targets reached over SSH or WinRM. The agent can call tools directly or use scripts to coordinate jobs and child agents through the same permissions and saved-output system.

  • Everyday use: learn the terminal interface, session management, and permissions.

  • Automation: run headless workflows or use JavaScript scripts.
  • Development: see setup, architecture, and embedding.

Installation

Skyhook runs on Unix and is built on Linux from a source checkout. It needs Rust 1.99 or newer, just, Zig on PATH, and the build tools listed under release builds. just setup installs the Rust-side tooling and names anything else that is missing.

git clone https://github.com/kryesh/skyhook.git
cd skyhook
just setup
just install   # release shims and both applications, installed into ~/.local/bin

The first build compiles the V8 JavaScript engine from source, which takes several CPU-hours.

This installs skyhook, the general-purpose coding agent, and skyhook-security, the security research companion. Both support the terminal interface and headless execution and embed the same shims. Make sure ~/.local/bin is on PATH.

just install builds for this machine’s own target, against its C library. just install x86_64-unknown-linux-musl installs a static build instead.

For a local-only build without Zig, run cargo build --locked --release -p skyhook-apps instead and use target/release/skyhook or target/release/skyhook-security. just build builds both applications in target/debug. Connecting to a remote target without an included shim returns an explicit missing-shim error.

Both applications use the ordinary Skyhook provider configuration and credentials. The companion also reads security.yaml; use security.example.yaml as a starting point and adjust its model assignments to match your config.yaml. See security configuration for discovery rules and research settings.

See development setup for contributor commands and shim builds for the build matrix, artifact layout, and native shim-only builds.

Continue with your first session.

Your first session

After installing Skyhook, create a configuration directory. The default location is $XDG_CONFIG_HOME/skyhook or ~/.config/skyhook:

config_dir="${XDG_CONFIG_HOME:-$HOME/.config}/skyhook"
mkdir -p "$config_dir"

Create config.yaml in that directory with a provider and model you can access. For example:

providers:
  openai:
    codec: "responses"
    dialect: "openai"
    base_url: "https://api.openai.com/v1"
    api_key:
      env: "OPENAI_API_KEY"
    models:
      default:
        model: "gpt-5.6"
        max_context: 1050000
        max_output: 128000

Use a model identifier supported by your account and set its token limits explicitly; Skyhook does not detect them automatically. You can choose smaller budgets. For model limits, other providers, a keyless local server, or Codex OAuth, see providers and models and authentication.

From a source checkout, you can instead copy the comprehensive example and edit it before running:

cp config.example.yaml "$config_dir/config.yaml"

The full example configures several providers; remove unused providers and models or supply their required credentials.

Start from the project directory you want to work on:

export OPENAI_API_KEY=...
skyhook --prompt "inspect this repository"

Skyhook opens a full-screen terminal interface. --prompt submits an initial message; --script workflow.js starts a JavaScript workflow in the same interface. Both remain open for inspection and follow-up input after the work finishes. These interface modes require an interactive terminal. Use skyhook batch with -p/--prompt or -s/--script for headless execution with redirected input/output support and automatic exit; see Headless execution.

The first sent message or explicitly run script creates the session. Use --workspace PATH to select another workspace. Normally, <workspace>/.skyhook/config.yaml overlays the selected user configuration, entry by entry. Use --config path.yaml to load only that file instead, with no user/workspace config merging. See configuration layering, including its workspace trust boundary.

To inspect configuration or available skills without a session or API credentials:

skyhook dump config  # Effective YAML on stdout; diagnostics/source paths on stderr.
skyhook dump skills  # Winning skills, frontmatter, and asset tree.

Both return nonzero on errors; skills can still list valid entries when other entries fail. See dump for compatible options. After a session, skyhook stats SESSION_ID reports its token usage, model requests, delegation, and tool calls (see stats).

Actions with effects outside the workspace require approval. See permissions and capabilities before using --approve-all; it bypasses tool approvals, not capability gates.

Next, learn the terminal interface, session and context behavior, or headless execution. All command-line options are summarized in the CLI reference.

Terminal interface

Conversation and inspector

User messages appear on the right and assistant messages on the left. Tool previews show their remote execution target after the tool name, such as exec @lab-monitoring; local calls omit @root. Expand a tool call to inspect its arguments, output, or failure details. Scripts, commands, file content, and diffs have syntax highlighting. Click an expanded body to collapse it, or drag to select text. Copying code preserves its contents without visual padding or newlines added by wrapping. Language-labelled code blocks in messages and reasoning receive syntax highlighting once their closing fence arrives; open blocks keep a consistent plain code style while streaming.

The agent tree appears above the composer while children are active or a child agent is being viewed. Click an agent to inspect its conversation without mixing its output with other agents. Each agent and tab retains its reading position and expanded rows. Agents using the wait tool show Waiting rather than Running tools. Tree rows show @target for remote agents and their own token totals, context usage and time: output · input (uncached) · context · time. The time is how long a busy agent’s current turn has run; once it isn’t busy, how long a child ran its job, or how long the root agent’s last turn took. Agent call previews show the child’s target even while queued or running; an omitted target inherits the caller’s target. Completed final replies identify the model that answered in a footer below the reply, with how long that response took and, when tool rounds came first, how long the whole turn took.

The composer always sends to the root agent. While root is busy, Enter queues a follow-up for its next model request, without interrupting the current request or tools. It does not wait for the entire turn to finish. /queue edits/removes input that has not yet been consumed. Selecting a queued message to edit pauses automatic queue delivery and moves it into the composer; merely opening the queue or deleting an item does not pause it. While the edit is open, nothing queued is sent, including messages held for /retry, whatever else happens. Submitting the edit puts it back in its place, however the messages around it change meanwhile, and the messages behind it go with it when the queue resumes; Enter on an empty draft, or /resume, discards the edit and leaves the message as it was. Interruption, a failed turn, submission or delivery errors, and session-start failures also pause queue delivery; a failed turn’s error is shown in the conversation. /resume clears that pause, as does normal composer Enter (even with an empty draft); slash commands do not automatically resume the queue. If Skyhook cannot write a session’s journal, that session stops as if the process had crashed: its queued input is dropped and its conversation shows why. It stays open to read until you close it, and reopening it continues from what was saved. Queued input lives only in the running interface. Each open session keeps its own queue, which keeps delivering while you look at another session and is discarded when its session is closed.

/retry continues failed or interrupted turns without duplicating their original prompts, and resends, as one batch on the bottom bar’s model and mode, queued messages a failure or interrupt paused; a queue paused while you edit a message stays paused. After a session interruption it resumes all interrupted children automatically, regardless of which agent is selected. Parents with pending waits stay in those waits. On a reopened session that has not run anything yet, /retry always starts it and continues whatever it left unfinished, or reports that there was nothing. Automatic model retries display the attempt number, a countdown to the next attempt, and every failed attempt’s diagnostic, oldest first, in one error block; consecutive attempts that failed the same way share one line, such as attempts 3–17 RateLimited: …. A final failure starts expanded and a pending retry collapsed, while /details and exports expand them all. An expanded block shows every error whole. Partial output from the failed attempt clears when the next attempt starts, and partial output a failed or interrupted turn left clears when the agent’s next turn begins, as reopening the session shows it; successful replies have no retry labels. Retries continue until success or cancellation for transient model failures.

The inspector provides Conversation, Requests, and Jobs tabs. Switching agents keeps the selected tab, while reading positions and expanded rows remain separate for each agent and tab. However long a conversation grows, its whole history scrolls and the scrollbar spans all of it: what is far from view is read as the view nears it, with Loading… at its edge until it arrives, and it arrives without moving what you are reading. Drag the scrollbar to move through the history quickly. Requests include compaction requests, numbered from 1 for each agent, with when each was sent, token summaries, and how long each took; transient retries appear under the same request and number, which reads Retrying while the next attempt is pending. Full request bodies are available in the session log, not rendered in the UI. Status messages, such as interruptions and errors, appear in the conversation and are saved with the session, but are not sent to the model. Startup warnings (skills, configuration, connections and MCP servers) describe this installation rather than the session, so the terminal shows them but does not save them. Unsaved notices appear where they arrived in the conversation and scroll away as it grows. Feedback on an action, such as an attached file, an export, or a setting that could not be saved, shows briefly on the notice line instead. An export finishes even if you switch away from its session meanwhile.

An expanded job card shows a summary of the job’s output: the preview the model sees, with what it left out, and the file each field past 4 MiB is kept in, to open there. Reading it does not acknowledge the agent’s pending notifications. Select a job and press c to confirm, then request cancellation (useful for background jobs, since interrupting already cancels the foreground tool). Intermediate child-agent messages and terminal job notifications appear as expandable Job event cards. Earlier progress messages remain readable after the job completes or resumes. Child-agent messages and answers, and question prompts and option descriptions, render as Markdown, both in cards and in the question prompt. Remote output becomes available as it is transferred to the host. An expanded job card loads its output while it is on screen and follows what a running job writes.

Provider-supplied reasoning streams in a separate expanded block and collapses when answer text starts or the response finishes. Click a multi-line block or press Enter when selected to reopen it, including after resuming a session. Single-line reasoning stays inline without an expand/collapse control and is not selectable, even when it wraps in a narrow terminal. A heading or wholly bold or italic line followed by a blank line starts a new reasoning section, titled by that line and collapsible like any multi-line block; only the section still streaming stays expanded. A title with nothing under it stays inline. Spinners indicate that work is still active, and a counter at the end of the row shows for how long. The working indicator counts the whole turn, across model requests and tool rounds; streaming reasoning counts from its request. Running tool calls count up and keep their duration once finished; expanding one shows when it started. A running tool waiting for input keeps its status symbol while its counter runs, and a retry counts down to its next attempt. Copied and exported text includes finished durations but not running counters.

Model selection and UI state

Models are named provider/model and listed in configuration declaration order. For a new session, selection uses --model, then the most recently submitted configured model, then default_model, else the first model of the first provider. The starting mode is chosen the same way: --mode, then the mode of the most recently submitted message if it is still configured, then default_mode. Batch jobs ignore the remembered mode. /model (or Ctrl+X M) selects the model for subsequent user messages in the current session. Selection stays in the UI until a message is sent; cancelling the picker or leaving without sending does not change the session’s recorded model. Each submitted message captures its model, including queued messages. Queued messages are submitted together as one batch, in order, including their attachments. The batch cannot be split across requests; the last message’s captured model is used for that request. A batch is saved whole or not at all: if the session cannot take its model, mode or attachments, the turn it reached fails with why, queue delivery pauses, and every message in it stays queued for /retry, which tries the batch again on the model and mode the bottom bar shows, in place of the ones the messages captured; messages already on their way join the batch. Removing a message from the queue withdraws it, unless /retry is already submitting it. Once every held message is withdrawn, the batch no longer waits: a turn the batch began rests with nothing to continue, while one it stopped mid tool loop stays failed and /retry continues it without the batch. Interrupting while /retry sends the batch returns its messages to the queue, paused: nothing is sent until you resume the queue, submit another message, or /retry. A session closed before then drops the batch. Tool follow-ups, retries, compaction, and /retry retain the active turn’s model. The bottom bar shows the choice for the next message; reply footers identify the model that actually answered. Resumed sessions retain their last applied model, unless --model names another: the session switches to it at startup, before any message or startup script, rather than for the next message as /model does. /models is an alias for /model. A session whose recorded model is no longer configured still opens, with a startup warning, and is never moved to another model on its own. A message sent to it stays queued and the model picker opens: the model chosen there becomes the session’s, then the message is sent. Children whose own model is gone restart on it too.

The interface stores the last submitted model and mode and the sidebar setting in the workspace’s .skyhook/state.json (skyhook-security in .skyhook/security-state.json), beside its sessions, without changing the model configuration. Session titles are saved with their history.

A sidebar beside the conversation shows the application’s name, then the session’s title; click the title to rename the session. Below, it lists the MCP servers the viewed agent can use, with their startup status, and the viewed agent’s todos, with the viewed agent’s capabilities pinned to its bottom. For the root agent of a new session these are what the mode of the next message grants, so cycling modes changes them. Once the root agent runs, choosing a mode for the next message that changes what it runs, including its own mode after the configuration redefined it, previews the change: a green + marks a server that mode would add, and a server it would remove is greyed out. A section with nothing to list is left out, title included. The sidebar is shown by default; Ctrl+X B or /sidebar toggles it. Host-defined capabilities show the titles their product declares; a foreign session’s recorded capabilities fall back to their namespaced names. Long labels are shortened with …. A foreign view-only session shows Recorded capabilities, not grants from the current product’s modes or MCP configuration, and its title cannot be renamed. Terminals narrower than 100 columns hide it without changing the saved setting.

The bottom bar uses this format:

default · openai/fast (gpt-5-mini) · 3f9c2a7d…       8.4k · 200k(31.2k) · 42% (54k/128k)

The left side is the mode, the configured provider/model name with its API model ID in parentheses when the two differ, the working directory (prefixed view-only for another product’s session), and the session ID. The statistics are session output tokens, session total input tokens (uncached input), and the selected agent’s context occupancy as the last response that reported its prompt counted it (tokens/model capacity). Session totals include children and compaction; a count a provider did not report adds nothing. Context includes instructions, tools, history, runtime state and that response; it is not cumulative usage. It appears as — until a response reports its prompt, including after compaction.

Renaming opens a prompt of its own, ahead of pending questions and permissions, with the title you set ready to edit, or empty while the title is automatic; the composer and its draft are left alone. Enter saves the title, and saving it empty returns the session to its automatic title. Esc cancels the rename. A draft has nothing to rename until its first message is sent.

When options carry previews, the focused option’s preview stands beside the options in a wide terminal and under the option in a narrow one. Text written on the last choice is another answer, and text written on an option is a comment on the ticked ones. For answering agent questions from a script, see jobs and agents.

Product-provided views and actions

An embedding product can add read-only tabs after the built-in inspectors. Cycle them with the same tab shortcuts or click their headers. Their data refreshes in the background, so loading a view does not block typing, switching sessions or resizing the terminal. A view that takes the whole screen may keep the agent tree: in a column beside it on a terminal at least 100 columns wide, headed by how many agents run and in which modes, or below it on a narrower one. There, Tab and Shift+Tab move between the view and the agents, ↑/↓ step through the agents without leaving the view, and clicking an agent or pressing Enter on it opens its conversation, as choosing it from the Agents palette does.

Headless execution

Use skyhook batch with exactly one prompt or script:

session_id=$(skyhook batch -p "Review this repository" --capabilities read,agents)
skyhook batch -s workflow.js --approve-all
skyhook batch -p "What does this service do?" --mode readonly
skyhook batch --resume "$session_id" -p "Summarize the findings"

A batch job runs in the default mode, in the one --mode names, or with the exact --capabilities list. Headless mode does not require a terminal or read answers from stdin. It creates or opens the session, prints only its session ID followed by a newline to stdout, and flushes that line before executing the prompt or workflow. It then exits automatically. The ID lets external programs locate and follow the normal session logs under <workspace>/.skyhook/sessions. Headless mode uses only the selected workspace’s history, just like the terminal UI. Resumed runs print the existing session ID.

Assistant output, script console output/results, startup warnings, and execution diagnostics remain in the session logs; they are not printed to stdout or stderr. Warnings about the configuration itself, such as a skipped config file, are the exception: they go to stderr, before any error that stops startup. The process exits successfully when the submitted operation and shutdown succeed. On failure or interruption it exits nonzero and prints the error to stderr; stdout still carries only the session ID. A failure before a session can be opened produces no session-ID line. If Skyhook cannot write the session journal, the session stops as if the process had crashed: the error says so, and no final status is recorded. Explicit --help and --version retain their normal output.

The submitted root turn or workflow defines completion. A workflow must explicitly await background work it needs completed; outstanding jobs are cancelled, and child agents interrupted, during shutdown. Interrupt and termination signals also trigger cleanup and journaled status rather than a terminal prompt.

A batch job never has human interaction. Root ask is unavailable (also inside scripts and with bg:true). Child agents can still ask their owning parent agent. The root is instructed as a delegated agent: it completes the prompt’s task and returns the result, answering its children’s questions itself rather than ending its turn to ask. Operations requiring human approval fail immediately; ordinary automatically allowed operations still work. --approve-all (or config approve_all: true) bypasses tool approvals but does not enable questions.

exec never has stdin connected or a controlling terminal, so ordinary /dev/tty prompts cannot stop the job waiting for terminal input. An inherited SSH_AUTH_SOCK is preserved. Remote commands apply the same capability restrictions. This is still not an OS sandbox against deliberately programmed subprocesses that establish their own external interaction mechanisms.

See the CLI reference for argument combinations and permissions for the capability/approval distinction.

Sessions and context

Session lifecycle

Startup and /new open an empty draft without creating a session or its files. The session is created when you send the first message or explicitly run a script. Resuming an existing session still opens it immediately.

Use --resume SESSION_ID to reopen a session. The CLI stores session logs and looks for saved sessions only in <workspace>/.skyhook/sessions, where --workspace selects the workspace (default: the current directory). It does not search parent or sibling workspaces. Sessions written by an incompatible earlier session format cannot be reopened and are left out of /sessions, as are a product’s own sessions whose product data, such as Skyhook Security’s research, an incompatible earlier version wrote.

Skyhook’s file tools never open a database this process holds open: searches skip an open session’s session.db and its -wal, -shm and -journal files, and reading, replacing or removing them, or removing a directory that contains them, is refused. To inspect a live session from outside, open it read-only without its shared memory index changing, for example sqlite3 'file:.skyhook/sessions/<id>/session.db?mode=ro&readonly_shm=1'.

The terminal keeps several sessions open at once. /new opens a draft beside the current session, and /sessions lists the open and saved sessions: the current session first, then the other activated sessions, those still working first, then every other session by most recent activity. An open session is activated once it has run here: a new session from its first message, a reopened one from the first action that changes it. Activated sessions are shown in bold. Opening a session and closing it again with nothing running does not count as activity. The current session is marked >. Open sessions show their live status, and saved ones how they would resume: idle, interrupted, or failed. Opening a saved session changes nothing in it until you act on it, by sending a message, continuing it, or anything else that is saved with it; notices about it meanwhile are shown, not saved. A session closed idle with results still waiting for its main agent is listed and opens as idle, as described below. A lock marks a session that was held open when the list was shown, by another Skyhook instance or because it was still closing here. Choosing one that was closing here opens it once it has closed; one another instance holds cannot be opened until that instance closes it, and choosing it says so. A saved session whose status cannot be read shows no status symbol. Each row’s id, event count, mode, last activity time, and creating host sit at the right. When a row is too narrow, they give way from the left, id first and host last, so titles keep at least 30 columns; longer titles are cut short with …. Choosing an open session switches to it, choosing a saved one opens it alongside. Sessions you switch away from keep working, and the notice line reports when one of them has a pending question or permission request or has failed. A session you switch away from with nothing running, nothing waiting on you, and nothing typed or queued is closed, so other Skyhook instances can open it; it stays in the list as a saved session. /close shuts down the current session only; quitting shuts down all of them.

Sessions created by another Skyhook product are labelled with their host and view-only in history and the terminal header. You can inspect agents, requests, jobs and saved output, copy text, and export the conversation. The composer, rename, model/mode selection, continuation, interruption and job cancellation are unavailable; reopening and closing never activate these sessions. Use the creating product to continue or change them.

A session is named after the first message you send it. Rename it with /rename (Ctrl+X L) or by clicking its title in the sidebar. A title you set stays until you change it, whatever the session does later, and renaming starts from it; renaming a session with an automatic title starts empty, and saving an empty title returns the session to its automatic title. A session without a title is listed by its first message. Model selection and UI state are described in the terminal guide.

Interrupting a session stops active model requests and cancels foreground tools, scripts, and questions. Nothing asks a model again until you continue with /retry or send new input: results that arrive meanwhile wait, and reach their agent with its next request. A response already recorded when the interrupt lands stands. Delegated child agents, including ones that had yet to start, retain their conversations and continue with /retry; parents waiting on their work keep those waits. Sending new input breaks those waits at every depth: the session proceeds, and each retained child remains interrupted in the background, where /retry can still continue it. Cancelling a job an interrupted agent is waiting on lets that agent go on with the result. Background jobs otherwise keep running, except those owned by a cancelled script. Explicit job cancellation stops work for good. Closing a session interrupts it the same way and cancels its other running jobs: child agents that were running, or already interrupted, can still be continued after it reopens, as can a delegation it stopped before the child started, which asks for approval again. Closing a session does not change its last activity time: as after a crash, work that closing cuts short ends when the session last did something. A session whose journal Skyhook cannot write stops the same way, as if its process had crashed, and reopens as one would.

Child agents must finish or cancel their owned work before completing. The root agent may leave background services running while the session remains open, but they do not survive shutdown or a process restart. On resume, unfinished jobs are marked interrupted and job IDs are not reused. Requests, jobs, and tool calls the previous process left running are recorded as ending when it last did something, so their durations stop there and reopening a session does not change its last activity time. Retained child agents can be resumed; ordinary process and tool jobs cannot. Pending child replies and job notifications remain available after resume and reach their agent with its next request: reopening a session does not start one. A session reopened with any waiting for its main agent resumes interrupted once it runs, so /retry delivers them as a new message would. See jobs and agents for delegation, notifications, and cancellation from scripts.

Conversation compaction

Skyhook uses the current model to summarize older conversation when context grows large. The continuation is intended to preserve the task, instructions, plans, findings, unfinished work, and where to resume. Recent conversation and the original calls for active work remain in context; historical tool calls are not executed again. Compaction also reconciles the agent’s todo list against the conversation without changing child-agent lists.

A successful model response triggers automatic compaction when:

U = input tokens + cached input tokens + output tokens
U >= 0.9 × (max_context - max_output)

This is the completed response’s reported usage, not cumulative session usage. Skyhook does not estimate token counts, so without reported usage there is no automatic trigger. Compaction runs before executing tool calls from that response. The summarizer sees the entire latest response and its pending calls, explicitly marked as not yet executed. It reconciles the current todo list with the conversation and any pending todo changes; its reconciled list takes priority over direct pending todo replacements. Those direct replacements fail as superseded, so they cannot overwrite that list. Todo reads and replacements invoked through scripts run normally; a scripted replacement can update the reconciled list. The original calls and their results are included in the first normal post-compaction request; the summary does not consume those future results. If compaction fails, the turn ends and those calls are recorded as not executed. A text-only response returns at once; the compaction it triggers runs before the agent’s next model request, also after the session is closed and reopened. A compaction that is interrupted, or whose summaries could not be used, stays due and runs again before the agent’s next request, for example when you continue. One that fails for another reason, such as a provider error, is not tried again, and the next request is sent without it. Switching model or mode clears a due compaction: from then on, the new model’s reported usage decides.

The provider still decides whether a request fits. A recognized context-overflow error can trigger compaction and retry, including for an oversized initial request or new tool output. Normal requests keep the configured max_output. Compaction requests can use a smaller output limit when less context space remains, and a summary the provider rejects as too large is retried with half the output reserve, then with about the older half of the summarized history left out. After an overflow, compaction keeps only the latest exchange beside the summary. The context meter in the terminal shows the last reported occupancy. Configure model limits to match the endpoint you use.

Compaction does not execute tools. It can retain selected job results as well as recent conversation; full saved results remain accessible through jobs. Older details depend on the summary: original messages remain in the session log, but there is no agent-callable history tool. A validated summary can still be incomplete or inaccurate.

Invalid, truncated, cancelled, or unsaved summaries leave the preceding context and todos active. Every valid, successfully persisted summary installs a checkpoint and its reconciled todos, even if the replacement context is not smaller. The terminal reports compaction start, the reported occupancy that triggered it, and failures without printing the summary. Eligible compaction failures, such as a truncated or invalid summary, have a bounded retry policy, separate from transient model failures, which retry until success or cancellation. A refused summary is not retried. See model failure recovery.

For persistence and request reconstruction internals, see library architecture and embedding.

Permissions and capabilities

Approval policy

--approve-all or approve_all: true bypasses approval prompts. Subject to the granted capabilities, the default CLI auto-allows reads and agent operations, as well as writes inside the root workspace and inside the workspace of a remote target, whose connection is approved before anything reaches it. Execution, HTTP requests, remote connections, target changes, and writes outside those workspaces require approval. When the interactive capability is granted, questions appear in the interface. Otherwise operations needing human input fail immediately; approve_all bypasses tool approvals but never restores questions. A command’s password prompt (from ssh or sudo) fails unless the environment Skyhook was started with names an askpass helper (SSH_ASKPASS, SUDO_ASKPASS), which commands inherit unchanged. Skyhook’s own SSH connections type the target passwords their targets configure.

Filesystem tools and command cwd accept absolute paths or relative paths including ... The workspace is a base directory, not a security boundary. Filesystem path authorization and human approval are distinct: the default CLI read policy auto-allows reads even when their canonical paths are outside the workspace. Do not rely on a confirmation prompt to protect outside-workspace reads. Outside-workspace writes require confirmation, and remote access has its own approval requirements. Permissions name paths as text, so an operation naming a path that resolves to one that is not valid Unicode is refused rather than approved under an approximate name, and a session does not start in a workspace whose path is not valid Unicode.

A path counts as outside the workspace when resolving it leaves the workspace: it ends outside, or passes through an outside directory or symbolic link on the way, even if it ends back inside. Whether such a path exists is revealed only once its operation is approved. When it does not exist, the operation is refused without a prompt, exactly as if the user had denied it, unless the approval policy would allow the operation without asking; then it fails as not found. A missing path inside the workspace fails before approval. On the session host, a child agent’s workspace is checked like a path when the child starts: outside the workspace, it follows the rules above; inside, a missing one is created before the child starts, which needs the launching agent’s write capability and is authorized as a write to it. On another target the workspace must already exist, and resolves there when the child starts. The child works in the directory its workspace resolves to, and its relative paths resolve from there. On the session host, its job shows the workspace joined to the agent’s workspace, with any .. and a trailing separator kept. remove refuses the root workspace, the agent’s workspace, and any directory containing either.

Choose Allow once to approve only the current operation. When offered, Allow proposed scope saves the displayed grant for later operations while the session stays open; reopening the session asks again. Inspect Details before granting it. Path grants apply only to the approved target and access mode. Directory grants cover descendants; read and write grants remain separate. A session reads back the output it kept in spill files as it reads its own database, the file a fetch body was returned in among them, whether or not it was reopened since. Process execution remains subject to confirmation on each invocation. These defaults apply to the CLI; library hosts can supply a different approval policy.

Approval controls and pending/granted approval details remain user-facing. Agents see an ordinary queued job while authorization is pending. A prompt is withdrawn once nothing waits for it, as when its operation is cancelled or its session stops. A denial preserves its reason and marks the rejected operation with code: "permission_denied"; it does not undo work that a containing script already performed. Agents must not circumvent a denial through another tool or route. For programmatic failure handling, see the JavaScript response contract.

A host capability name is <namespace>.<name> (lowercase ASCII letters, digits and underscores, each component starting with a letter).

Per-agent depth restrictions narrow the result. Enable target support by including "targets" in a mode.

Modes

A mode is a named permission preset. The root agent runs in one mode at a time:

# The mode a new session starts in; "general" when omitted.
default_mode: "readonly"

modes:
  readonly:
    capabilities: ["read", "network"]
    instructions: "Investigate and report. Do not change anything."
    hint: "Look things up without changing anything"

  # Built in, and listed first. Declare it only to change what it grants.
  general:
    capabilities: ["read", "write", "exec", "network", "agents", "mcp"]

capabilities is required, and default_mode must name general or a declared mode. Optional instructions are added to the system prompt of an agent running in the mode; they guide the model, whereas capabilities are enforced. An optional hint offers the mode to agents starting a child: the agent tool lists each hinted mode whose capabilities the caller holds itself, with those capabilities and the hint. A mode without a hint cannot be given to a child. A workspace config that declares a mode replaces the whole definition of a user-config mode with that name; modes it does not name are kept, in declaration order.

--mode NAME selects the starting mode; without it the terminal starts in the mode last used in that workspace, and a batch job in default_mode. In the terminal, Tab/Shift+Tab in the composer (or /mode) choose the mode the next message is sent in; the footer shows it. Cycling modes only makes that choice: it never changes the session. A change takes effect with that message and forfeits the provider’s prompt cache for the next request. Child agents keep what they start with: the capabilities and instructions of the mode their parent chose for them, or otherwise the capabilities their parent holds and no mode instructions. Background jobs and scripts already running keep their capabilities too. A session can only hold capabilities that some configured mode grants, and MCP servers start under that union, so switching modes never starts or stops a server. Approvals granted earlier stay granted but cannot be used while the mode lacks their capability.

A resumed session continues in the mode it was last in, as the current configuration defines it: the configuration decides what a reopened session’s modes grant, more or less than before, and a batch session reopened in the terminal gains interactive. Opening a session whose modes the configuration has since changed or removed shows a warning and changes nothing. The change applies with the next work that runs the root agent: a prompt, retry, continue, script or job delivery. A root agent whose mode was removed moves to the default mode. Child agents it already started keep what they started with, within what the configuration still allows. The session’s history keeps every definition of a mode it used, so earlier entries still show what they ran under. Because general is always present, redeclare it with a narrower list if the terminal should never be able to switch to its default capabilities. Continuing a failed or interrupted root turn also applies a newly chosen mode.

Capabilities gate both tool discovery and invocation, including JavaScript. Approval policies and cached grants cannot restore a missing capability. Ungated orchestration tools remain available even with an empty set. These gates are not an OS sandbox: allowing exec lets a command access files or the network independently of the corresponding built-in tool gates. Disabling network removes fetch, not model-provider traffic or trusted MCP transport setup; disable mcp to prevent MCP connections. Per-server MCP requirements are additional gates, not grants.

See headless execution for noninteractive commands and authentication, execution targets for route approvals, and MCP for trusted server startup and per-server gates.

Sessions retain the application that created them, separately from their title and mode. Other applications can inspect them and read their statistics from the shared session directory, but cannot activate, rename, or otherwise change them. Reopening a session in its creating application is required to resume work.

Execution targets

Include "targets" in a mode’s capabilities (or a batch job’s --capabilities allowlist) to grant the target capability. It is not enabled by default. Without it, agents cannot use target-management tools or select another target, including from JavaScript.

Targets are named entries in the top-level targets mapping, and session tools can add or replace targets without modifying YAML. Skyhook never reads SSH configuration files: a target’s host, user, port, authentication, and options come only from its own definition. Aliases, ProxyJump, identities, and other settings in ~/.ssh/config or /etc/ssh/ssh_config do not apply.

When user and workspace config are layered, a workspace entry replaces the whole target with the same name; it does not inherit user SSH, authentication, or routing settings. Targets with other names are retained. Repeat any required settings in the replacement entry.

targets:
  bastion:
    host: "bastion.example.com"
    transport:
      ssh:
        user: "gateway"

  build:
    host: "build.internal"
    workspace: "/srv/project"
    via: "bastion"
    transport:
      ssh:
        key: "~/.ssh/build_ed25519"
        password: {env: "BUILD_KEY_PASSPHRASE"}
        forward_agent: true

  legacy:
    host: "legacy.internal"
    transport:
      ssh:
        user: "deploy"
        password: {command: ["pass", "show", "legacy"]}

  database:
    host: "db.internal"
    origin: "build"
    transport:
      ssh:
        # Reach the host through a gateway using the deploy user's own SSH key on build.
        options: { ProxyCommand: "sudo -n -u deploy ssh -W %h:%p gateway.internal" }

The built-in root is the session host—the machine running the main Skyhook process. It is not configured as a target and always identifies that machine, including when an agent’s current target is remote. Named targets give their transport and its settings under transport: ssh, or winrm (see WinRM targets); an SSH target with no settings is written transport: {ssh: {}}. A target’s os declares its operating system, "linux" or "windows", by default "linux" for ssh and "windows" for winrm; see Windows targets. Skyhook starts the target with the commands of the system declared, so declare it correctly. A target whose shell runs them and names the other system, such as a Windows host whose SSH default shell is a POSIX one declared "linux", fails to connect with the target declares os linux but runs windows; one whose shell cannot run them fails with that shell’s own error.

Routing: origin and via

  • origin names the target that starts the SSH or WinRM connection; it defaults to root. Key paths, CA files, password sources and agents belong to the origin.
  • via names an SSH target to jump through with native ProxyJump, within that same connection. Jump hosts need no shim. A via target must have the same origin, so its key paths are never interpreted on another machine. Omit via, rather than naming the origin, to connect directly from the origin. A WinRM target is never a jump and takes no via: it connects directly from its origin.
  • One SSH connection types at most one password: of a target and the targets it reaches through via, only one may set password. A route needing two is refused when the target is configured or added. Use origin instead of via for the later of the two, or a target between them: every target can be an origin, and each origin starts SSH connections of its own.
  • A configured origin or via names another configured target, from any configuration file merged into the effective configuration; one naming no configured target is refused when the configuration loads, with the names it could take instead.

Both may be set: origin: "build" with via: "gateway" makes build run SSH through gateway, where gateway also has origin: "build".

Registering targets never connects to them; registrations are session-wide.

await tool.target_add({name: "database", host: "db.internal", origin: "build",
  transport: {ssh: {key: "~/.ssh/database"}}});

SSH settings

SSH settings live under transport.ssh. Every setting is optional. options values must be strings; quote numeric-looking values, for example ServerAliveInterval: "15". Each host is given 30 seconds to connect, after which OpenSSH’s own error is the connection error, unless the target’s options set ConnectTimeout.

passwordWith key, that key’s passphrase. Without key, the target authenticates with a password and offers no keys. See passwords.

How a target authenticates follows from key and password:

  • password without key: OpenSSH’s password authentication; no keys are offered. A server that allows only keyboard-interactive authentication, as some PAM setups do, cannot be reached with a password.
  • key, with an optional password for an encrypted key: that key alone.
  • neither, including a target with no SSH settings at all: only keys already in the origin’s SSH agent: the one it inherited or was forwarded, otherwise Skyhook’s private agent there if an earlier connection started it, or on Windows the agent service. The connection fails if there is none; see agents.

OpenSSH’s default key files (~/.ssh/id_*) are never offered.

Passwords

A password takes any credential form: a literal, {env: NAME}, {command: "..."} or {command: ["program", "arg"]}, or {file: path}:

ssh:
  user: deploy
  password:
    command: ["pass", "show", "deploy"]

The source is read on the target’s origin, the machine that starts its SSH connection: an environment variable is that machine’s, and a command runs, or a file is read, there, exactly as key paths are interpreted there. It is read again for every connection and never kept.

A password is never included in tool results. A resumed session reads a configured target’s password from the configuration again, and warns of a target the configuration no longer defines as the session started with it, whose connections fail until it does. A target added with target_add is saved in the session log with its password as given, so a literal one is stored there in plain text; prefer another form.

A connection’s password is given once, to OpenSSH on the origin, which never asks about a host key, so it reaches no server but the target’s. A rejected password fails the connection with OpenSSH’s own reason, and any later prompt fails it, reporting the prompt that was answered. A password that cannot be read fails the connection with an error naming the target and the source’s problem, never the password. On a Windows origin with OpenSSH for Windows 8.1, a password or passphrase with non-ASCII characters may not be typed reliably.

Tools run as the same user as Skyhook, so they can read a password file or run a password command too. Keep password files out of workspaces, and give them mode 600: Skyhook refuses a file other users can read. On a Windows origin, the file’s access list must allow only you, SYSTEM and Administrators, as for an OpenSSH private key there; see credentials.

The account needs permission to use WinRM’s command shell. Administrators have it. Other accounts need Execute in the WinRM service’s root security descriptor (its RootSDDL); membership of Remote Management Users alone is not enough. To grant that group Execute, add the ACE (A;;GX;;;S-1-5-32-580) to the descriptor, for example in an elevated PowerShell:

$sddl = (Get-Item WSMan:\localhost\Service\RootSDDL).Value
Set-Item WSMan:\localhost\Service\RootSDDL -Value ($sddl -replace 'S:', '(A;;GX;;;S-1-5-32-580)S:') -Force

winrm configSDDL default edits the same descriptor in a dialog.

A WinRM target connects from its origin, root by default, which can be any target, including a Windows or Linux SSH target or another WinRM target; it is never a via jump and takes none. A Windows origin finds a Kerberos KDC with its own DNS client. WinRM delivers output in batches about half a second apart, so a tool call takes noticeably longer over WinRM than over SSH.

Windows targets

A target with os: "windows" runs Windows 10 1809, Windows Server 2019 or later. Over SSH it runs OpenSSH Server with its default shell, cmd.exe; over WinRM its WinRM service. Skyhook needs Windows PowerShell 5.1 there, which those releases include.

targets:
  winbuild:
    os: "windows"
    host: "winbuild.internal"
    workspace: 'C:\src\project'
    transport:
      ssh:
        user: "builder"

Paths on a Windows target are Windows paths, such as C:\src\main.rs, and tools accept / or \ between their parts. A relative workspace is in the user’s profile directory (%USERPROFILE%). An exec command given as a string runs in Windows PowerShell 5.1 without a profile; an argument list runs its program directly.

Agents

Each origin authenticates with the SSH agent it already has: on root, the one Skyhook inherited in SSH_AUTH_SOCK; on a remote origin, the agent forwarded to it, if its own connection forwards one. Only an origin without one gets a private agent that Skyhook starts there when a connection needs it, and keys from key targets are loaded into that private agent as they are used. An inherited or forwarded agent is never modified: a key is offered directly and not added to it. On root, exec receives the private agent’s SSH_AUTH_SOCK only when Skyhook inherited none. Private agent state is discarded when its origin’s session or connection ends and is not restored when resuming a session.

A Windows origin uses the agent in its SSH_AUTH_SOCK, or else the OpenSSH Authentication Agent service while it runs, and never starts a private agent there: that service keeps the keys added to it across logons, so Skyhook adds none. Without either, a target offering only agent keys, or one that sets forward_agent, fails to connect from that origin, while key and password targets connect as usual. A Windows origin connects with OpenSSH’s ssh.exe, which must be on its search path.

The agent service does not sign for a logon made with an SSH key rather than a password. From a Windows origin reached that way, targets offering only agent keys fail while the service runs, and so does a key target whose key the service also holds.

A connection forwards its agent only when its target sets forward_agent: true; remote commands then receive SSH_AUTH_SOCK, so commands such as git, ssh and ssh-add can use the same identities. Without it remote commands get no agent from Skyhook.

target_add requires the write capability as well as targets. It also requires the exec capability and its approval when it sets ssh.options, which can run commands, or a password that is not a literal: an environment variable, a file and a command are all read on the origin, outside any workspace. Configuration files are trusted like MCP commands.

Host keys are checked against the origin user’s ~/.ssh/known_hosts and the system-wide /etc/ssh/ssh_known_hosts, so record each host’s key there before connecting; options can name another file with UserKnownHostsFile, or accept unknown keys with StrictHostKeyChecking: accept-new, or any key with no. An unknown host key fails the connection with OpenSSH’s reason, such as Host key verification failed.: StrictHostKeyChecking: ask, OpenSSH’s default, acts as yes, and UpdateHostKeys: ask as no.

Using targets

Use targets to list each target’s host, type, os, via, origin and how it authenticates without connecting. Registering a target does not change the agent’s location.

Target-aware tools, including agent, use these rules:

  • Omitting target uses the calling agent’s target and current workspace.
  • Setting target: "root" uses the session host and its configured session workspace.
  • Setting another named target uses its configured workspace, except that explicitly selecting the calling agent’s current named target retains that agent’s workspace override.

Workspace-inheriting tools such as write, replace, and remove use the calling agent’s target and workspace without accepting a target selector; a write source names its own target, so a file can be copied between machines. Host/session tools such as jobs, todo, wait, and targets still run on the session host. agent selects a child’s future execution location; launching the child and running its provider remain host operations. An explicit agent.workspace takes precedence over the selected base; relative overrides resolve against that base.

Diagnostics identify the operation and its subject, with the execution target when applicable. A working-directory override is separate from the target’s configured workspace: an absolute cwd must exist on the selected machine, not on the session host. A connection, session-storage, or saved-output inspection failure is not necessarily a failure of the command on the remote machine.

Prefer these named targets to manually running ssh. A tool that needs a route requests approval before any probe, authentication, or shim deployment. The request shows every target the connection passes through, origins and jumps first, each with its host and the user it logs in as. A route grant applies across tools and workspaces, so reconnecting an unchanged route needs no new approval. Changing a target or any hop in its route invalidates every grant naming it: an operation still waiting for approval or a connection asks again about the new definition, and one already running over the old route finishes there, but any further approval it asks for is refused.

Tools run on a target through Skyhook’s shim, a program the first connection installs there as ~/.cache/skyhook/shims/<sha256>, or under $XDG_CACHE_HOME when that is set (on Windows, %LOCALAPPDATA%\skyhook\shims\<sha256>.exe). A shim that starts removes the others there that nothing has used for a day. A session keeps one connection to each target, shared by every call there.

JavaScript orchestration and the session log stay on the host; nested tool calls use the selected target and workspace. For remote execution internals and shim builds, see remote transport and shims.

Instructions and skills

Instructions

Skyhook loads at most one user instruction file and one file in the exact resolved workspace directory. It does not walk workspace ancestors for instructions. --workspace PATH selects that workspace; --config selects only YAML configuration and does not suppress instruction discovery.

Within each directory, filenames are checked in this order:

  1. AGENTS.md
  2. agents.md
  3. Agents.md
  4. AGENTS.MD

The first existing filename is selected. If reading it fails, Skyhook does not try a lower-priority spelling in the same directory. A readable empty file counts as selected, so it does not trigger fallback either. An instruction file must be a regular UTF-8 file of at most 1 MiB; a larger file or one that is not a regular file is skipped with a startup warning, and other read failures stop startup.

For user instructions, Skyhook first checks $XDG_CONFIG_HOME/skyhook, then falls back to $HOME/.config/skyhook if the first location is absent or fails. It never loads both user files. If no fallback succeeds, all non-missing user-file errors are reported. Missing optional files are fine; an unreadable selected workspace file is an error.

For example, on a case-sensitive filesystem:

$XDG_CONFIG_HOME/skyhook/agents.md  # Selected user file if AGENTS.md is absent.
$HOME/.config/skyhook/AGENTS.md     # Not loaded when the XDG selection is readable.
/project/AGENTS.md                 # Not loaded for workspace /project/app.
/project/app/AGENTS.md             # Selected workspace file, even if empty.
/project/app/agents.md             # Ignored when AGENTS.md exists, even if unreadable.

User instructions are supplied before workspace instructions, with their source identified. If both locations select the same file, it is loaded only once. Root and child agents share these instructions.

Host-owned skills

Host-owned skills are exposed through the skill tool, which is offered only when at least one skill was discovered. Unlike instructions, skill discovery reads ~/.agents/skills and .agents/skills directories along the workspace ancestry, with the nearest workspace definition winning when names collide. Discovery happens at startup; restart Skyhook to discover newly added skills. Skills are discovered and read on the session host only: an agent whose location is a remote target is offered the same skills, and .agents/skills directories on that target are not read. A skill directory contains SKILL.md and optional supporting files, conventionally grouped in scripts/, references/, and assets/:

.agents/skills/release/
├── SKILL.md
├── assets/
│   └── logo.png
├── references/
│   └── template.md
└── scripts/
    └── release.py

Skill YAML frontmatter may contain arbitrary metadata, but its values must be JSON-compatible: mappings with string keys, sequences, strings, booleans, finite numbers, and null. Duplicate or non-string keys, custom tags, non-finite numbers, and YAML << merge keys are rejected. Anchors and aliases are supported with bounded expansion. A description must be a string; a skill with any other non-null description is skipped with a warning.

Loading and copying assets

The examples below assume the release skill layout shown above.

All skill arguments are optional and nullable; native calls supplying null behave like calls omitting those fields. Without name, the call lists available skills; path requires name.

await tool.skill(); // {kind: "list", skills: [{name, description}]}
await tool.skill({ name: "release" }); // Complete SKILL.md, assets tree, and location
await tool.skill({ name: "release", path: "references" }); // Directory subtree
await tool.skill({ name: "release", path: "references/template.md" }); // Original text
await tool.skill({ name: "release", path: "assets/logo.png" }); // Attached image

Results have a kind discriminator: list, skill, directory, text, image, or binary. Base skill results contain location, complete content, and, when the skill has other files, an assets text tree that includes nested files but excludes the already-loaded root SKILL.md. Directory results use the same tree format, rooted at the selected path. Trees mark symlinks without descending through them. Long trees and asset text are saved in full and can be paged using jobs.

Text assets (including JSON, YAML, source code, and SVG) are returned unchanged, never executed. Supported raster images are attached with metadata, and one that does not decode is an error. Other binary files return metadata rather than raw binary or base64 content. Paths inside a skill must be relative and cannot escape its root. Use path: "." to browse the root.

Skills live on the session host. location is {path, target: "root"}, the skill directory’s absolute path there, so ordinary tools can reach its files. target is included only for agents with the targets capability; an agent on a remote target without it cannot reach the session host, so its results have no location. Copy an asset with write’s source, which also delivers it to an agent working on a remote target:

const { location } = (await tool.skill({ name: "release" })).unwrap();
await tool.write({
  path: "tmp/release.py",
  source: { path: `${location.path}/scripts/release.py`, target: "root" },
});

An agent on the session host can omit target.

A mixed-file test workspace includes its hidden .agents/skills/mixed-assets/ directory. Its tests exercise native calls, explicit nulls, asset discovery, UTF-8 and binary files, image attachments, and path containment.

Security research

skyhook-security is a companion application built from the same library and terminal host as skyhook. It researches a selected part of a target: a codebase, or without source a deployed service or API, a network daemon or a binary, recording the flaws it finds, how each entry point reaches them, the vulnerability candidates they support, reviews, and empirical validation attempts. It is not a sound static analyzer: a flaw, route or candidate is a research hypothesis, not proof that a path is executable or a vulnerability exists. Reports identify assumptions and coverage gaps.

Configuration

The companion reuses the ordinary user and workspace config.yaml: providers, model settings, credentials, execution targets, and MCP servers are not copied into another file, and skyhook auth manages the same credentials. Additional settings live in security.yaml, with the same user-directory discovery and workspace overlay rules; the workspace file is .skyhook/security.yaml. --security-config PATH selects one explicit security file and disables discovery for that file alone; --config PATH independently selects the ordinary configuration. skyhook-security dump config shows the effective shared configuration with security modes, model hints, and merged MCP entries applied, without opening a run or session. The embedded modes’ instructions render for each agent, so the dump leaves them out.

Model assignments refer to the configured provider/model names, not the identifiers sent to a provider. A model can serve several roles, and several models can serve one role. Assignments become model-selection hints rather than mandatory bindings: orchestrators choose appropriate models when delegating, and unassigned models are not offered as explicit delegation choices. The roles are orchestrator, explorer, validator, environment, poc, and reporter; a role is not a mode name. A session that starts with no role hints configured reports it as a diagnostic.

Research pipeline

The root orchestrator drives the pipeline through delegated research modes; the research store holds one graph of what the agents found and derives the work each part of it still owes. target maps the code, binaries and interfaces into components, mapping what it cannot read by what its material shows, and records the deployment premises your request settles, among them one per actor’s intended capabilities, per build or configuration option and per platform the code branches on, and each interface in scope under a short name; when your scope includes dependencies, it records each locked version a published advisory affects as a flaw at its manifest entry. Under a live policy, when the map records interfaces, the orchestrator arranges an environment serving them before paths, under ask once you approve its scope. paths has an entries child record the entries of each file and of each interface an environment serves as paths, the input states taken in there, and the other states its code reads or writes, with each path’s accesses. It then merges paths recording one entry and states recording one storage, links the input states no child placed, and completes each path from the target’s first code the input reaches through every stage that handles it.

The components recorded outside scheduled work, by target and paths with its entries children, are the run’s scope. A path is in scope while its entry step lies in one of them, by the step’s component or the component owning its file. target records the exclusions in your request as failing deployment premises and maps none of the excluded code. Every task begins with the scope: the mapped components, their interfaces, and the deployment premises, failing ones as excluded, and records no component, path or candidate for a route entering outside it, such as a language binding. What later work records beyond the scope anyway stays recorded but owes nothing, and neither does what only such paths reach: a state only they access, a flaw only they step through that no candidate starting in scope holds, a premise only such work relies on, and a candidate whose first action is one. A state an in-scope path accesses too is checked as before. The synthesis and the Research page count the paths and candidates outside the scope.

After paths, one scheduler runs every phase together within workers: each subject starts as soon as its own prerequisites are met rather than when a whole phase ends. Ready work starts in pipeline order — sweeps, probes and checks, settles and chains, reviews, tests, reports — and later work waits only on earlier-stage work, ready or running, that touches it; unrelated later work fills the remaining slots. Sweeps, checks, settles, chains and reviews go out in bundles, one child each: the sweeps of the paths keyed on the same state, a path’s key being the handed state it reads or writes that the most paths access (the instance handle its caller supplies or receives), else the instance state the most paths access, ties going to the lowest-numbered, so every call on one instance goes together (a path accessing neither is swept alone, and paths sharing only another state stay in their own bundles); the checks of a handed state and of the instance states written on the paths accessing it, so a value handed back is checked with what its producers leave in the instance the next call resumes from (an instance state goes with the handed state its writer paths access that the most paths access, and alone when they access none); a path’s settles (its own premises, those of the flaws on it, and what each rests on) or chains, where work on a stage several paths share goes with the lowest-numbered one and a premise goes with the path of the premises resting on it; and the reviews of one root flaw’s candidates. Work on a node that running work is about waits for it, so one agent works a node at a time and the next starts with its findings in view.

Every scheduling fact is in the store, so running the scheduler again, after a stop, a crash or a resume, continues where the last run stopped. The orchestrator runs one at a time.

A child beginning a task is told what changed of each subject’s work since the subject’s previous task in that phase, if any, and while it works, with its next request, of what other agents changed of what its work rests on since it began: each change once, as a digest per changed subject, so it can re-read them before deciding. A check marks its state with at least one premise its clearing relies on: a recorded one, such as the deployment premise for a documented contract, or a general claim its accesses do not show, settled by another agent; a mark naming none is refused. A handed state’s check also rests, for each value a caller acts on, on a premise naming a condition that yields it beyond the one its name suggests, since a write site does not show every condition upstream that leads there. A check of a state checked before examines only the accesses changed since and the pairs cleared on a premise that failed or was contradicted, and the whole state again after an edit or a merge into it. Its own changes and its helpers’ are left out, and the root, which works no task, is told nothing. A task also names, for each subject, the result of its phase proposed outside it (below), for it to decide, and a check the decided premises of the flaws leaving its state wrong, each with the task deciding it and how much evidence it carries, for what it finds to contradict.

The research graph holds nodes of a few kinds, each with a title and a body:

  • A component is implementation, by the files and named interfaces it owns; its body notes its concurrency: what runs its code, the state it shares, and what serialises access to it.
  • A state is the storage one invariant relates, by its scope; per-call temporaries are not states. An input state is data an actor writes that the target takes in, with its trust (untrusted, authenticated, local or privileged) and the read defining it: a location defines one input state, so recording another there returns the one recorded, and merging one frees its location for the state it merged into. Configuration read at startup is trusted as the operator, and a CI job others can trigger as whoever can trigger it. A handed state is written by the target and carried by the caller into later calls, such as a status or a cursor; an instance state is one object’s fields across its calls; a stored state outlives the caller’s interaction and is read by other flows, such as a session or a record, each read of it trusted as its least-privileged writer path’s input. A state’s scope is fixed when it is recorded.
  • A path is one scenario: an entry on the target’s public interface (a route, handler, job, exported function) followed through every stage that handles it, as ordered steps through components, each at a location with a note, and its accesses: each read or write of a state, at its location. One state can be accessed by many paths.
  • A premise is a prerequisite: internal state or logic a flaw needs to reach unintended state, or a path needs to carry input there, stated as that need and never as the code’s safety guarantee (a guarantee the code does not enforce is a flaw). A failing premise contradicts the candidates resting on it. It is code-scoped, about the target’s own logic and decided by reading or observing it, or deployment-scoped, decided by you, and holds, fails, or is undecided. A premise may rest on others: the general claims its decision, either way, relied on, each a premise of its own, settled apart.
  • A flaw is a local defect at a location in a component, with an optional CWE, the premises it depends on, the states it leaves wrong (a status reported wrongly leaves its handed state wrong), and a status: suspected, confirmed (a verified defect with no chain to an observable consequence found so far) or refuted. An invariant enforced only where it may not run in deployment (a debug assertion, client-side validation) or only by convention (a bound, a progress guarantee, a status meaning, a lifetime) is a suspected flaw, its premise that something can violate it, worked like any other; an obligation documented for a trusted caller is a flaw only in a caller that skips it, while a check left to an untrusted client or peer is the target’s flaw.
  • A candidate is an ordered chain of flaws to an observable vulnerability, its first flaw its root, through its actions: the paths its scenario performs, in order, the first where the attacker starts. A path may repeat, as in a race with itself. Candidates sharing a root flaw are its group, tested and reported together; a candidate merged into another adds, after the other’s own actions, each path it performed as often as it did beyond the other.
  • A finding is a root flaw’s report.

A location is a code region (file and lines, in its function), an address range of a binary image at its link base (in its symbol), or an operation of a recorded interface in that interface’s own terms (a route template, a method, a message type), at one of its fields when narrower. A location names an interface, never an address, so it stays the same across deployments. Evidence is a location with a stance on one node: it supports, contradicts or gives context; one made in an environment names it. Each result is decided by the work owning it: a code premise’s status by its settle or by the review of a candidate whose chain rests on it, a deployment premise’s by you, recorded outside every scheduled task, a flaw’s by its chain, and a candidate’s assessment and verdict by its review. Work belongs to the outermost task it was recorded within, so a helper’s records count as its parent’s. Recorded anywhere else, a status, assessment or verdict is a proposal: the decided one keeps standing, a proposal that differs from it disputes it and owes its owner’s work again, and one that agrees changes nothing, nor does one repeating a proposal its owner’s work answered, until an edit, a merge, a dispute or another change that work rests on asks it again. Node views and the Research tab show a pending proposal beside the result, with the event, task and agent that recorded it. Contradicting evidence after a premise’s decision or a flaw’s judgement disputes it too, and owes its settle or chain again; an edit of its substance since reads it as undecided or suspected until it is decided or judged again. Any agent may raise a candidate, a flaw or a premise at any time, left unsettled for the work that checks it (except a deployment premise your request settles), and merge a duplicate of any kind but a finding into the node it repeats, which takes its edges; restating what is recorded changes nothing. A state, path or component recorded in error is retracted with set_status and a note: it shows as retracted but owes no work, holds none back and leaves every count, and the premises a retracted path relies on stand in no candidate’s chain, until marked recorded (a path unswept) again. Retracting or restoring a path owes the reviews and reports of the candidates performing it again.

Candidates are assessed with a CVSS 4.0 base vector (CVSS-B) scored for the impact if every premise of its chain holds; the native scorer applies the shortlist threshold. A candidate’s review scores it first: one scored below the threshold needs no verdict, and one a review moves below it keeps its verdict, but no report covers either. The review has a trace child, which neither begins work nor judges, trace each shortlisted candidate through the source, from the attacker’s entry along every action to the stated effect, recording each check, branch or bound that stops the input as contradicting evidence, or as an undecided code premise when it rests on a general claim; a returning review traces only the steps whose records changed. The review decides each code premise its verdict needs. A build option, configuration or deployment other than the default, behaviour of the caller, client or deployment beyond supplying attacker input, or a race window the attacker must win, makes Attack Requirements present and is a premise. Attack Vector, Privileges Required and the other exploitability metrics come from what the attacker must hold or face before the first action, plus anything a later action needs that no earlier action supplied; access or privilege gained during the scenario is never a prerequisite. A score rests only on what the candidate’s premises establish: a condition that would raise a metric becomes its own candidate, the same chain with that condition as a premise, so the root’s report leads with whichever validates. A review records validated (every premise holds), disproved (a chain flaw is refuted or a code premise fails), excluded (a deployment premise fails, so the deployment keeps a real finding out of reports) or unproven (a premise stays undecided). An assessment counts until the candidate itself is edited or merged outside its review, or a proposal disputes it. A verdict counts while nothing its review rests on changed after it and the statuses it claims stand: none of its chain’s premises undecided or failing and no chain flaw refuted for validated, a code premise failing or a chain flaw refuted for disproved, a deployment premise failing for excluded, and a premise undecided for unproven. A premise decision, contradicting evidence or a material change of the candidate, its chain, a path it performs or a state that path accesses owes the verdict again, unless made within its review, as does an access recorded or removed of a state its flaws leave wrong or its paths read where one of its flaws sits (in that flaw’s function, or at its location when it names none); an access of any other state, on its paths or another’s, owes nothing, and neither a decision nor an access re-scores a candidate. A candidate’s confidence is conjectured while a premise of its chain is undecided or contradicts it, established otherwise, confirmed while a positive verdict stands, and demonstrated once its settling test (its latest test that is not pending, recorded at its standing verdict) is confirmed and its chain uncontradicted. A validated candidate no more severe than a demonstrated one of its group is noted rather than tested.

Deployment premises stand for what only you can answer. target records the ones your request settles as holding or failing, among them the obligations the target’s documentation places on a trusted caller such as an embedding application: a broad request admits what that documented contract permits, and anything an untrusted client or peer can send, so breaking a trusted caller’s documented obligation fails unless you include it, and what the documentation leaves unsaid holds. In an interactive run the orchestrator then puts that profile to you as one question before research starts and records your answers; while a question to you is open, the scheduler starts no reviews, and the rest of the work goes on. Agents rest a deployment condition on each recorded premise it combines, raising a new one only for a single condition none covers. One raised later and left undecided is never settled by an agent: it holds back the reviews resting on it and is listed in the synthesis as asked. A status an agent sets on one within scheduled work only proposes it, and is asked too. When the scheduler returns, the orchestrator puts the asked premises, and those an unproven candidate rests on, to you as one question, records each answer as the premise holding or failing, which sends their candidates back to review, and runs the scheduler again. A batch run has no one to ask: the orchestrator answers its agents’ scope questions from your request, and the premises it leaves undecided stay asked and are listed in its final summary.

The synthesis a scheduler run ends with lists the work each phase owes and has running, each exhausted subject with its last agent’s reply, the deployment premises asked of you, the candidates left unproven with their undecided premises, the components no path reaches, the interfaces paths without code wait on an environment for (under live: no, every interface such a path enters on), and how many paths and candidates lie outside the scope. After each return the orchestrator also has a settle agent review the loose ends it lists, the premises of exhausted settles and those an unproven candidate rests on: each gets a proposed status, what would settle it, or what reopens it. Exhausted work is terminal: the orchestrator closes the run once a pass changes nothing, with nothing owed or held, every answer you gave recorded, and that review moving nothing. It then always writes the current reports out and lists exhausted work as incomplete and each root flaw without a current report as having none. Every agent that records a conclusion (a premise decided, a flaw judged, a verdict, a test result) checks the code around it for flaws or candidates it implies. All of this is agent-discovered evidence and analytical conclusion, not a symbolic proof or a substitute for empirical validation.

Runs and sessions

Each security session is one analysis run: the session keeps the run’s research beside its journal, so a review today can be followed by environment preparation, empirical validation, and reporting later, in the same session, without repeating discovery.

skyhook-security --prompt "Focus on request routing and access control"
skyhook-security runs            # list security sessions; -w DIR selects another workspace
skyhook-security runs SESSION    # the run as the Research tab shows it, every section open in full

# Continue a run: resume its session.
skyhook-security --resume SESSION --prompt "Extend the analysis to the admin interface"

The orchestrator runs the stages your instructions call for: a new session analyzes the workspace from target selection onward, and a resumed one continues from its records, whether the instructions extend the analysis, prepare an environment, validate, test or rewrite reports. Fresh work is always owed; settled or exhausted work is owed again only once something it rests on changed. A resumed run keeps its shortlist threshold, live policy and workers; a --workers flag resizes it once its work resumes, and --live and --shortlist apply only to a new session, so each is refused with --resume. A headless resume is refused only when the run’s own policy is ask, whatever the configuration says. Only the root agent knows the live policy, and under no every agent’s instructions leave out live work. The shortlist threshold is applied by the store alone; no agent is told it.

In the terminal, a new session opens with a scope panel at the top of the root agent’s conversation: the shortlist threshold, the live policy, and the workers, prefilled from security.yaml, flags, then the defaults. Edit it while writing the instructions in the composer: Shift+Tab moves between the fields and the composer, ←/→ change a choice, digits edit the workers. The first message sends the panel’s values with it; with no instructions the session starts with “Analyze the workspace.” Once the run has started the panel stays in view, frozen; a session that fails to start leaves it editable for the next try. A reopened session shows the panel frozen with the values its run runs under, including a --workers resize that applies once its work resumes.

The Research tab (] from Jobs, or click its header) takes the whole screen below the tab strip and views the root agent again, so the status beside it is the session’s own. It opens on a dashboard of the run: its threshold, live policy and workers, when this window opened the session and how long ago (reopening starts it again), the synthesis, a pipeline showing where each phase stands (what it owes, has running and has exhausted), and panels for coverage (states, paths swept and unswept, uncovered interfaces, paths outside the scope, components reached or mapped only, premises undecided, asked and disputed, flaws by status), candidates by status, and the tasks running and exhausted in each phase. Below it, sections list the candidates, findings, paths, running tasks, task history, flaws, premises, components and states, each most relevant first: candidates by standing (demonstrated, validated, shortlisted, unproven, unassessed, then the rest); findings by their best score; paths unswept first; flaws confirmed first; premises awaiting your answer first; states checked across calls (instance and handed) first. Within each group, rows with work running come first, then work owed, then work exhausted, then none; candidates and flaws then by score. Each path, state, premise, flaw and candidate shows what it owes and its last task, and opens to its latest tasks. Running tasks (their agent’s job still live) and the task history (jobs that ended) are listed apart, each newest first, with their phase, state (as their agent’s job stands), when they began or ended, subjects and the first line of their brief; a task opens to its whole brief, its agent’s reply and the records the agent wrote. Click a section’s header, or choose it with ↑/↓ and press Enter, to open it; a record opens the same way to its detail, a candidate to its whole scenario: actions, chain, premises, assessment, verdict, tests and evidence, with an assessment or verdict that no longer stands marked stale. A candidate whose assessment or verdict no longer stands keeps the group it last reached, marked stale (shortlisted (stale), say), until it is assessed or reviewed again. A candidate another one takes precedence over shows whom it waits behind as ↑ and that candidate’s id: noted ↑545 when a demonstrated member of its root group reports the root, test ↑545 under what it owes while its group’s test, or the test of a premise blocking it, goes to the more severe one first; its detail lists its root group and what it waits on. A candidate whose demonstration is under way shows as proving, and as test abandoned once the agent running it ended without recording an outcome. An open section lists its first 50 records, most relevant first; its last row loads 50 more. The page scrolls as one, updates while agents work, and keeps what you opened. While agents run, they stay in view beside the page on a wide terminal, or below it on a narrow one; click one to open its conversation.

The orchestrator receives the run’s state with each request: run, live policy, workers, the plan’s line (such as “owed: 4 sweep, 2 settle; 3 running; exhausted: 1 chain; asked: 1; uncovered: 1”), and the artifacts directory. The agents it starts receive no run state; their briefs name the IDs of their work, and each agent that runs or builds anything gets a working directory of its own under artifacts/, so parallel work never collides. A new session (Ctrl+X N) starts as the command line would, on the model selected where it was opened when the command line’s configuration offers it, and otherwise on its default.

For automation, batch takes the same choices as flags over the security.yaml defaults:

skyhook-security batch --prompt "Review the HTTP header parser" --live no --shortlist medium
skyhook-security batch --resume SESSION --prompt "Review the upload paths" --workers 2

The run’s files live in its session’s directory under .skyhook/sessions/: test artifacts belong under artifacts/, and the current reports are written under reports/. Sessions share .skyhook/sessions with skyhook, so skyhook stats covers them; a session created by the other application opens view-only (see sessions).

Live work and reporting

Live work is any interaction with a running target: probing it, settling or reviewing what only observation decides, and demonstrating findings. It happens only in an environment, a running instance an agent prepared (a container started from a binary or image) or a deployment you authorised, which records the interfaces it serves and their addresses. A prepared environment is a template: each agent copies it into its own working directory and runs its own instance there. A deployment cannot be copied, so its instructions say how agents share it, and are the rules of engagement: addresses, identities by reference, rate, what live work may change and must leave alone, and the window. Under ask the orchestrator records an environment for a deployment only once you approve its scope; under yes it takes the scope from your request, never broader. The store schedules around environments and enforces nothing: Skyhook’s approvals do, fetch per origin and exec per invocation. exec is not a sandbox, and batch live work needs approve_all; with live: yes against production, that is your choice.

Under live: no no live work is owed: interfaces are never probed, and paths on them are listed as uncovered, while a binary is still analysed by reading its disassembly. Under yes or ask a path without source code is probed once an environment serves its interfaces; a probe that needs what its environment lacks, such as an identity, leaves the path unswept for a later environment.

Under live: no no demonstration is owed. Under yes or ask each validated scenario that is not noted owes one until a test settles it, its root group’s most severe first; with ask, an interactive run asks after analytical review which findings to demonstrate, and each one declined is recorded as such. Declining does not reject a finding: its report remains confirmed and empirically untested, with the reason. A code premise two settling looks left undecided is tested too, through the most severe unproven scenario resting on it, the others waiting on what that test decides: the PoC agent runs the review’s demonstration plan or a bounded one of its own and proposes the premise’s status from what it observes, which its settle decides, sending its candidates back to review, or records what it tried as context and the test as unavailable, leaving them unproven. Such a test settles premises only: once a review validates its candidate, the scenario owes a demonstration of its own. A PoC agent makes an environment change the scenario’s premises admit itself, through an environment agent when the change is reusable; an environment recorded within its work is prepared for its candidate, without making its test owed again. A test waiting on you is recorded as pending and stays owed until you resolve what it waits for, which lets it resume; one the environment cannot run is recorded as unavailable and reported as untested with its reason. An inconclusive run is not a result: the PoC agent refines its approach, delegating helpers as it needs, until it confirms or disproves the scenario. A test is recorded as failed only with evidence that the scenario does not work as formulated, which goes on the chain flaw or premise it bears on: that evidence sends the candidate back to review, and the scenario is reported, or withdrawn, by the verdict review then records. A test other than a declined one stands only while what it demonstrated is unchanged since its work began: a verdict of another value, even one recorded while the test ran, unsettles it, and a re-validation after its chain or actions change owes a test of its own; a restated verdict with nothing it rests on changed keeps its test. An unavailable or failed test is owed again once a later environment is recorded for its candidate or for none in particular; a declined one stands, across new verdicts too, until you ask for it. A confirmed test stands while its chain is uncontradicted. A race, a check apart from its use or a measured difference such as timing is demonstrated over a fixed number of trials with a control run as often, both success rates in the test’s note, a measured difference confirmed only beyond a threshold stated before the runs; a win that needed the window widened counts only when the window exists in the unmodified build, with the rate without widening reported. A confirmed test is expected to record an attack artifact and a control run on the same build, each a distinct regular file under the run’s artifacts/ directory reached without a symbolic link; the report shows a confirmation that lacks one. Execution uses ordinary approvals and capabilities: prefer a disposable container or a deliberately configured target, and keep live validation within the authorized environment.

A root flaw is reported once its group owes no review or test, by a report agent who writes one markdown report: summary, analysis, impact, remediation, reproduction citing test ids and artifacts, and a section per other scenario. The report is owed again whenever what its scenarios rest on changes after it was written, or its group’s reportable scenarios are no longer the ones it covered. reports/ holds only the current reports, rendered from the run’s store; each root flaw with one has a folder, reports/<root>/:

  • README.md: front matter, the title, a generated table of the scenarios (candidate, paths, chain, vector, score, severity, status, confidence and test), then the reporter’s report;
  • finding.json, the machine-readable record the Markdown is rendered from;
  • test-<id>/ for each scenario’s settling test: its artifacts under attack/, control/, observation/, harness/ and notes/ by their own names (numbered -2, -3 when two share one), with test.md, test.json and SHA256SUMS.

reports/index.md and index.json list every current report with its severity (the most severe of its scenarios) and its headline scenario’s own severity, score, vector and confidence, labelled apart since a demonstrated headline may be less severe than an untested variant. reports/hardening.md, linked from the index while it has entries, lists the confirmed flaws no report covers, with each one’s title, location and CWE, in two groups: those no validated candidate holds, with why no chain was found, which are not scored or tested; and those whose most severe validated candidate is assessed below the run’s threshold, with that candidate and its severity. None are reported, and index.json lists them under hardening, each with its reason. Every page opens with a small front matter its text repeats, and links only by relative path.

The orchestrator writes reports/ once it closes the run. The directory is the run’s own: anything else placed there is removed, a root’s folder is replaced when what renders has changed, and a generation with nothing changed changes nothing. An artifact is copied only while it matches the digest its test recorded; one that changed keeps the root out of reports/ and is reported.

These files are guarded by path name, not against another program writing in the session directory at the same moment. A replaced folder is moved aside before the new one moves in, so a reader in between, or after a crash there, finds that root’s folder missing until the next generation. An artifact, and reports/ itself, is refused when reached through a symbolic link, but a link put in place between that check and the read or write is followed. Keep other programs out of a run’s session directory while it runs.

Configuration overview

Skyhook uses YAML configuration.

File selection and layering

With --config path.yaml, Skyhook loads only that file. It does not search for or merge user or workspace configuration, even if the explicit file fails to load. The contents are always parsed as YAML, regardless of the filename suffix.

Without --config, Skyhook:

  1. Tries $XDG_CONFIG_HOME/skyhook/config.yaml, when that environment variable is set.
  2. On any read, YAML parse, or structural error, tries $HOME/.config/skyhook/config.yaml. At most one user file is selected; the two user files are never merged.
  3. Overlays <resolved workspace>/.skyhook/config.yaml if it exists. --workspace PATH selects the workspace; otherwise it is the invocation directory. No ancestor workspace configurations are loaded. An unreadable or invalid workspace file is an error.

Automatic discovery uses only config.yaml, not config.yml.

Missing optional user files are fine: a complete workspace-only configuration can be used. A broken user file is not silently treated as missing if no fallback succeeds. The effective configuration must be valid; defaults are applied after merging.

The workspace file overlays the user file key by key, and each key’s value is replaced whole. The exception is the named maps providers, modes, targets, and mcp. These merge by name, and each entry comes whole from the last file that defines it. A workspace entry replaces the user entry of the same name without inheriting its omitted fields, and entries with other names stay available. For example, a workspace providers.openai must repeat the dialect, endpoint, credentials, and every model it keeps. A replaced entry keeps its position in the user file’s order. Entries only the workspace defines come after the user’s.

An explicit null is a value, not a deletion: providers: null or providers.openai: null makes the configuration invalid rather than removing entries.

Example: user models, workspace targets

Keep providers, with their models, in the selected user config.yaml:

providers:
  openai:
    codec: "responses"
    dialect: "openai"
    base_url: "https://api.openai.com/v1"
    api_key:
      env: "OPENAI_API_KEY"
    models:
      default:
        model: "gpt-5.6"
        max_context: 1050000
        max_output: 128000

targets:
  bastion:
    host: "bastion.example.com"
    transport: {ssh: {}}

  build:
    host: "old-build.internal"
    via: "bastion"
    transport:
      ssh:
        key: "~/.ssh/old-build"

Then use this <workspace>/.skyhook/config.yaml:

modes:
  general:
    capabilities: ["read", "write", "exec", "targets"]

targets:
  build:
    host: "new-build.example.com"
    transport: {ssh: {}}
    workspace: "/srv/project"

The effective configuration retains providers.openai, with its default model, and targets.bastion. A named mode or target is replaced whole, not merged: modes.general grants exactly the listed capabilities, and targets.build uses the new host and workspace, with default authentication/routing behavior: neither the old key nor via: "bastion" survives. If a route or key is needed, repeat it explicitly in the workspace entry.

Trust boundary: workspace configuration is full configuration, not a restricted project hint. It can change approvals, modes, provider credential commands, and MCP server startup. Review it before starting Skyhook in an untrusted checkout.

YAML syntax and strings

Each file must contain a single YAML document with a mapping (object) at its root. Empty or comment-only documents, null roots, and sequence or scalar roots are rejected. An empty mapping ({}) is a valid no-op workspace overlay, but an empty effective configuration is invalid.

Values must be JSON-compatible: mappings with string keys, sequences, strings, booleans, finite numbers, and null. Duplicate keys, non-string keys, custom tags, non-finite numbers, multiple documents, and YAML << merge keys are rejected. Anchors and aliases are supported with bounded expansion. YAML merge keys are unrelated to Skyhook’s file layering.

Quote values that must stay strings, especially numeric-looking SSH options and environment values: ServerAliveInterval: "15" and WORKERS: "4", not unquoted numbers. Actual numeric settings such as max_context remain numbers.

For multiline instructions or shell-command strings, a literal block scalar preserves line breaks:

modes:
  readonly:
    capabilities: ["read", "network"]
    instructions: |-
      Investigate and report.
      Do not change anything.

|- omits the final newline; use | if the string should end with a newline. Folded blocks (> or >-) turn ordinary line breaks into spaces, so use them only when that is intended. MCP start_command remains a sequence of argument strings, not a shell-command block.

Paths and environment

Relative MCP cwd values resolve against the directory of the source file defining that value. A user-defined cwd keeps its user-file base when other MCP fields are overlaid; a workspace-defined cwd uses the workspace config’s directory (<workspace>/.skyhook), not the workspace root. An MCP server without cwd, from either file, starts in the session workspace rather than the directory skyhook was launched from.

The CLI always stores and discovers sessions in <workspace>/.skyhook/sessions, including headless execution and resume. Remote paths resolve on the selected execution target. The workspace is a base directory, not filesystem isolation.

The CLI loads .env from the invocation directory, with existing process environment variables taking precedence. Neither --workspace nor --config changes that location. See authentication.

Inspect without starting a session

skyhook dump --workspace /path/to/project         # Same as dump config
skyhook dump config --workspace /path/to/project --approve-all
skyhook dump config --config ./standalone.yaml    # Explicit file only

These commands write resolved effective YAML to stdout and source paths/diagnostics to stderr. They apply defaults and applicable CLI policy overrides without requiring API credentials, starting MCP servers, or making network requests. Exit status is zero for a valid dump and nonzero if valid configuration cannot be produced. See dump for selectors and incompatible options.

Configuration errors

A refused configuration is reported in full: a line saying which stage of loading failed, then one line for each refused value, in the order the files write them. Each line starts with file:line:column, at the file that wrote the value, which for a merged configuration may be the user file or the workspace one, and names the value by its full path from the document root, such as providers.openai.models.default.max_context or modes.readonly.capabilities[1].

  • An unknown key is refused with every key valid in its place, and an unknown value with every value it could be.
  • A mapping missing required keys is refused with every one it is missing.
  • A name that selects nothing configured, such as a target’s via or origin, or a host capability the running application does not declare, is refused where it is written, with the names it could be instead. A user file may name what the workspace file defines; the merged configuration must define it.
  • A default_mode or default_model that names nothing is refused once the application has finished configuring itself, with the names it could be instead and no file position: an application may add modes of its own, which default_mode may name.

Diagnostics never quote the file, so they cannot reveal credentials written beside the refused value.

Configuration areas

  • Providers and models: named API connections, full model IDs, context/output limits, reasoning replay, and connection recovery.
  • Authentication: environment variables, secret-manager commands, .env, and Skyhook-owned Codex login.
  • Permissions and capabilities: approve_all, modes, and their exact capability allowlists.
  • Execution targets: SSH and WinRM destinations, origins, routing, and authentication.
  • MCP servers: trusted local server startup and imported tools.

Providers and models

A provider entry names an endpoint and the models served through it, under models. Everywhere a model is chosen or recorded—--model, the /model picker, the agent tool, default_model, session history and skyhook stats—it is named provider/model from the two keys, so neither key may contain /. The model field inside a profile is the identifier sent on the wire and stays free-form. default_model selects the model a new session starts with when neither --model nor the model last submitted in the workspace chooses one; without it, the first model of the first provider is used.

Every provider names a dialect, the server’s wire conventions. Each model selects a codec, either directly or from its provider’s defaults: chat_completions, responses, or messages. The codec is the API family; base_url names the shared API root and Skyhook appends /chat/completions, /responses, or /messages for the selected model (/codex/responses for a codex provider). Different models on one provider may use different supported codecs:

Request settings are flat: put shared defaults beside models, and model-specific values directly beside model.

Service tier

service_tier selects the backend’s tier ID, such as priority, flex, or ultrafast, on any dialect and codec, as a provider default or beside model. It is unset by default and sent exactly as written. Check that the endpoint and model accept the tier before selecting it. Faster tiers can cost more or use more of a subscription; see ChatGPT speed.

Responses settings

Any dialect serving codec: "responses" accepts two optional settings, as provider defaults or beside model. A backend serving Responses need not accept them; check that the endpoint, model, and account support a setting before selecting it. Other codecs refuse a selection, so a model that switches away from Responses must clear inherited ones with null.

  • reasoning_summary is the detail of the reasoning summaries requested: "auto" (every dialect’s default), "concise" or "detailed", or null to request none.
  • access_programs.cyber requests a cybersecurity access program: standard, daybreak_blue, or daybreak_red; unset by default. The model and account must be eligible for the program; it does not grant entitlement, and other safeguards still apply. Some models take a different wire value from the approval it needs: gpt-6-astra and gpt-6.1-sol take daybreak_blue but require Daybreak Red entitlement. See the Daybreak guide.

Explicit caching

explicit_caching: true, as a provider default or beside model, switches a chat_completions or responses request to explicit prompt caching (prompt_cache_options: {mode: "explicit"}) on every dialect but codex, which refuses the setting: the backend caches only at the breakpoints Skyhook marks, never on the changing runtime state, so later requests can reuse the prefix. Both mark the end of the stable history and the point where each earlier request’s history ended, and Chat also the stable system prompt, up to four breakpoints a request: the newest history boundaries are kept. A dialect that already marks breakpoints with cache_control on Chat (openrouter, and litellm behind anthropic) places the same marks with that field. On openrouter Responses, cache_ttl applies to automatic caching only; explicit marks are cached for the backend’s default lifetime. Neither marks the history of a request with no reusable prefix, such as compaction. Left unset, the backend’s automatic caching is unchanged. messages refuses the setting. Check that the endpoint and model support it; see the prompt-caching guide for supported models and pricing.

astra:
  model: "gpt-6-astra"
  max_context: 1050000
  max_output: 128000
  service_tier: "priority"
  access_programs:
    cyber: "daybreak_blue"
  explicit_caching: true

Image limits

Images of up to 8 MiB are stored as attached, except that an animation, and any GIF, is stored as a PNG of its first frame (an APNG’s default image, which may lie outside its animation), re-encoded as a smaller JPEG if that PNG would exceed 8 MiB. An image with very large dimensions can be refused when attached, whatever the model’s limits. Before a request, an image whose longest edge or encoded size exceeds the model’s limits is fitted: it is downscaled to the edge limit, keeping its aspect ratio, and re-encoded as PNG (unless it is a JPEG) if that is within the size limit; otherwise it is re-encoded as JPEG and made smaller until it fits. An image within the limits is sent unchanged, the stored original is kept, and the model is not told that an image was fitted. An image that cannot be fitted, such as one whose stored data no longer decodes, is sent as a short note saying so, and the request proceeds. Each dialect sets defaults:

Dialectmax_edgemax_bytes
anthropic8000 px7.5 MiB (10 MiB as base64)
openai, codex6000 px8 MiB
compatible, litellm, openrouter4096 px3.5 MiB

image_limits replaces either limit, as a provider default or beside model; a limit left out keeps the default, and image_limits: null restores both. max_bytes is at most 8 MiB, since no image is stored larger, and max_edge at most 65535 px, the largest JPEG; a larger value is refused. The limits are per image: a service rule that depends on how many images a request holds, or on their total pixel area, is not applied. Changing a model’s limits from its dialect’s defaults changes the images earlier reasoning saw, so signed reasoning from before the change is not replayed afterward.

local:
  model: "vision-model"
  image_limits:
    max_edge: 2048     # longest edge, in pixels
    max_bytes: 2097152 # encoded size, in bytes

A server that deviates from its dialect’s presets can select placements at either level:

  local:

    dialect: "compatible"

    output_limit: "max_tokens"                   # or null for none
    reasoning_replay: "reasoning"                # the assistant-message key; or null
    cache_key:                                   # one location, a list of them, or null
      - body: "cache_salt"

    models:
      thinker:
        model: "served-name"
        max_context: 131072
        max_output: 32768
        reasoning_effort: "reasoning_effort"

The selectable dimensions are output_limit, reasoning_effort, reasoning_replay and tool_stream (Chat Completions only), cache_key, and user_id. Every one but cache_key is a field path. Each selection names one location or a nonempty list of distinct locations, and the value is written at every one. A selection left out inherits, and with nothing to inherit keeps the preset for the model’s effective codec and dialect settings; an explicit null places nothing. Changing codec does not discard inherited selections: set null for any the new codec has no place for, or replace them.

A field path is dot-separated (metadata.user_id); cache_key and user_id carry the conversation identity. Paths must not name a field the codec writes itself (such as model or messages) or one the dialect adds (such as OpenRouter’s routing provider and models), and no two may overlap, including one inside another (reasoning and reasoning.effort), within one selection or across two. A cache_key header must not be accept, content-type, or a header the codec sends itself (such as anthropic-version on messages). A reasoning_replay field moves the provider’s replay to other keys in the same form. Messages requires an output limit, so output_limit: null is refused there, as is reasoning_effort: null everywhere.

Context and output budgets

Every model profile requires max_context and max_output. Both must be positive, and max_output must be smaller than max_context. Prompt/history, reasoning, and generated text share the context window. Automatic compaction is triggered by a response whose reported input, cached input, and output tokens reach 90% of max_context - max_output. Compaction precedes tool execution, or, after a final answer, the agent’s next request. The summarizer sees the pending calls, and their results reach the first post-compaction request intact; a pending todo replacement is superseded by its reconciled list. A max_output of at least 50% of max_context produces a startup warning for that model, whether or not it is selected: reserving that much output space leaves most of the window unused for input. The configuration remains valid. Normal requests retain their configured output limit; compaction requests reduce it when necessary to fit the remaining context space. Use the model’s published limits or your server’s actual configured limits, whichever is lower. You can deliberately choose smaller budgets for cost, latency, or available memory. However, using Skyhook with less than approximately 128k tokens of max_context is not recommended: instructions, tool definitions, conversation, and compaction all need room. This is guidance, not an enforced minimum.

state_mode controls how per-request runtime state (date, active jobs, and todos) reaches the model. dynamic (the default) sends a fresh state with each request; the model sees only the current one. persist keeps each state in the conversation, at the cost of keeping every one in context until compaction; a state the latest kept one already shows is not repeated. Use it for models that bind signed reasoning to the exact earlier conversation (such as Claude Fable 5.1) when the provider cannot hide earlier state, for example Claude reached through a Chat Completions or Responses proxy. Use it too where a large state (many jobs or todos) defeats prompt caching: chat_completions and responses cannot hide an earlier state, so under dynamic each request leaves out the previous one’s, and a provider that reuses only where an earlier request ended, as codex does, then reuses little of the history. none sends no runtime state, except to a compaction summary, which needs the current todo list to reconcile it. See runtime state for what the model receives.

A dialect’s state_role selects how runtime state is sent:

  • system uses the protocol’s harness role: a system message on messages, a system or developer message on chat_completions, and a developer message on responses. Through anthropic, or litellm with an Anthropic upstream on messages, a dynamic state is a turn-scoped system message: the model reads it for one request, and afterwards it costs no input tokens but stays in the conversation, so models that bind thinking to the exact earlier conversation (Claude Fable 5.1, Opus 5.5, Sonnet 5.5, Haiku 5.5) keep it with dynamic state. It needs a model that supports mid-conversation system messages (Claude Opus 4.8 and later, Fable, Sonnet 5.5, Haiku 5.5; not Sonnet 5). Other dialects send plain system messages and drop superseded state, as user does. On messages, a state with no valid place, such as right after an assistant turn, is not sent.
  • user sends state as user content, joining the user turn before it or as a turn of its own, for servers without a harness role mid-conversation, such as many open-model chat templates. Superseded state is then dropped, which changes the end of the conversation between requests. During a tool loop each state is a new user turn, so a chat template that keeps reasoning only for the latest user query drops the loop’s earlier reasoning after it, whatever the state_mode. For such models, enable the template’s option to keep earlier reasoning (Qwen’s preserve_thinking, for example).

anthropic defaults to system, as does litellm for messages behind an Anthropic upstream; openai and codex always use it, and compatible, openrouter and every other litellm combination default to user. Changing a provider’s state_role changes the conversation earlier reasoning was produced in, so that reasoning is not replayed afterward. Through anthropic, or litellm with an Anthropic upstream on messages, set reasoning to a level other than off on models that bind thinking: only then does Skyhook ask the service to drop a thinking block whose earlier conversation changed, rather than reject the request.

Model failure recovery

For every provider, transient/network failures retry until success or cancellation, with no attempt limit. This includes connection failures, interrupted streams, timeouts, rate limits, temporary server errors, an expired credential from a command or file (authentication), and a response with neither visible text nor a tool call, such as reasoning alone. Other authentication, billing (exhausted quota, credit, or spend limit, however the service reports it), invalid-request, and malformed-response errors stop the request instead of retrying. So do refusals, and a response cut off at max_output with nothing to act on, which reports that the output limit was reached.

A valid server Retry-After hint—delay-seconds or an HTTP-date—sets the delay, even when it exceeds 30 seconds. Past dates mean no delay; malformed or ambiguous headers fall back to the default backoff. Without a valid hint, delays grow exponentially: 1s, 2s, 4s, 8s, 16s, 30s, then remain at 30s. The backoff restarts when a new request is prepared, including after compaction. Cancellation interrupts the wait.

Retries resend the same request: queued input and notifications wait until that response completes. Completed tools are not rerun, and partial tool calls from failed attempts are never executed. The failed partial response is discarded. The interface and session records may show retry status, but agents receive only the successful response or a terminal failure.

Context-window overflow triggers compaction rather than resending an oversized request indefinitely. Recovery stops after three context failures for one response; an invalid summary also has a separate three-attempt limit. Transient failures during summarization follow the same unlimited retry policy and do not consume either limit.

This prevents duplicate Skyhook tool execution, not duplicate provider inference: the provider may have processed the interrupted request, and additional usage may be incurred. Usage reported before interruption is retained; unreported provider usage remains unknown. Retries also cannot guarantee that tools hosted by the provider will not repeat side effects.

Reasoning history and local-server compatibility

On chat_completions and responses, a model’s reasoning is an effort level: none, minimal, low, medium, high, xhigh or max. On messages it is a thinking mode (off or adaptive) or an effort level under adaptive thinking: low, medium, high, xhigh or max. A value the codec does not accept is refused when the configuration loads, with the accepted values listed.

Responses and Codex automatically request reasoning summaries, even when no model reasoning effort is configured. Anthropic requests summarized thinking when reasoning enables thinking; with reasoning unset, the model’s default applies and may omit thinking text. Skyhook displays only the reasoning text or summaries the service returns, not otherwise-private reasoning. Support varies by provider, model, and compatible server.

Skyhook saves returned reasoning and automatically reuses it with the same API and model. Signed or encrypted reasoning is reused only with the same provider, endpoint, and configured routing or tenant identity; switching to another configuration omits it from requests without deleting the saved history. Readable reasoning is reused across those changes. A proxy changing the upstream behind an unchanged alias cannot be detected automatically. Signed thinking cannot be reused across compaction or mode switches. Visible summaries cannot replace private reasoning state the service requires. Reasoning the service did not sign or encrypt is still replayed, until signed or encrypted reasoning from the model appears in the context; from then on only that is sent. Services that accept only reasoning they signed or encrypted never get the rest: anthropic, openai and codex on responses, and litellm behind Anthropic and on responses.

Standard Chat Completions has no portable request-side reasoning field. Compatible Chat providers replay their returned reasoning under reasoning_content by default. A server that spells the key differently selects it with reasoning_replay: "reasoning"; reasoning_replay: null keeps reasoning local. The openai dialect never replays on Chat, since the official API rejects unknown message keys; litellm behind an anthropic or bedrock upstream replays the thinking blocks the proxy returns, and openrouter replays its reasoning_details; signed ones are bound to the exact conversation like Messages thinking. A response with readable reasoning_details keeps those as its reasoning, in place of any plain-text reasoning it also streamed; a response without them keeps its plain text, which openrouter replays under its reasoning field. Once signed reasoning appears in the context, only signed thinking blocks are sent, a turn’s reasoning_details are sent whole, in order, only if one of them is signed, and plain-text reasoning stays local. Responses and Messages replay native reasoning automatically; a Responses reasoning item that restates its summary as content, or the reverse, is kept once, as its final item states.

Reasoning is replayed with its owning assistant turn, including turns that only call tools. Server-side tool and reasoning parsers/templates must be configured appropriately. Chat requests send max_output as max_completion_tokens; a server that only honours max_tokens sets output_limit: "max_tokens".

Connection timeouts

Every provider accepts startup_timeout_secs and read_idle_timeout_secs settings, each a whole number of seconds from 1 through 86400 (both default to 600 seconds); null is refused, so leave one out to take its default. Startup is a deadline for each HTTP attempt, while read-idle resets after each response-body chunk. For example:

providers:
  local:
    codec: "chat_completions"
    dialect: "compatible"
    base_url: "http://127.0.0.1:8080/v1"
    startup_timeout_secs: 600
    read_idle_timeout_secs: 600

Each retry gets fresh deadlines, so these settings do not limit the total time spent on a response. Cancel the request to stop waiting; the server may continue processing if it does not honor disconnects. See model failure recovery for retry behavior.

skyhook dump config writes the resolved timeouts, so a dump shows the defaults an entry left implicit.

Authentication

Credentials

A configured value that may hold a secret—a provider’s api_key and fixed headers, MCP headers, and an SSH or WinRM target’s password—is a credential. It takes one of these forms:

FormValue
"text"The text itself.
{env: NAME}The environment variable NAME, which must be set and nonempty.
{command: "..."}The standard output of shell text run with the shell of the machine that uses the credential: /bin/sh -c, or Windows PowerShell 5.1 on Windows.
{command: ["program", "arg"]}The standard output of a program run directly, without a shell.
{file: path}A file’s contents.

A map names exactly one source; any other key, or a second source, is refused with the sources a map can name. A command’s output and a file’s contents lose one trailing line ending (\n, then \r). A command runs with standard input closed and standard error discarded; its standard output is limited to 64 KiB, and it must exit successfully with UTF-8 output that is not blank. A file path is absolute on the machine that reads it (/ on Linux; a drive root such as C:\, or a \\server\share path, on Windows) or starts with ~/ (your home directory); the file must be a regular file of at most 4 KiB, owned by you and accessible to nobody else (chmod 600), and hold UTF-8 text that is not blank. On Windows, as OpenSSH for Windows requires of private keys, the file’s owner and everyone its access list allows must be you, SYSTEM, Administrators or TrustedInstaller. Errors name the setting, the kind of source (and an environment variable’s name) and its problem, such as api_key from env PROXY_TOKEN: not set, never the value, a command’s text or output, or a file’s contents.

providers:
  anthropic:
    codec: "messages"
    dialect: "anthropic"
    base_url: "https://api.anthropic.com/v1"
    api_key:
      env: "ANTHROPIC_API_KEY"
    # Alternatively:
    # api_key: "sk-ant-..."
    # api_key:
    #   command: "op read 'op://Private/Anthropic/api-key'"
    # api_key:
    #   command: ["pass", "show", "anthropic"]
    # api_key:
    #   file: "~/.config/skyhook/anthropic-key"
    headers:
      x-title: "skyhook"
      x-proxy-token:
        env: "PROXY_TOKEN"

A literal secret is stored in plain text in the configuration file, and skyhook dump config prints it. Prefer another form for secrets. Commands are trusted host configuration, executed on the machine that uses the credential with Skyhook’s environment there; they do not run through tool approval. Use a noninteractive secret-manager command that writes only the secret to stdout. Do not put literal secrets in command strings or commit them to configuration files.

API keys

api_key and headers are provider-only: all models in that provider instance share their credential resources, even when their codecs or request settings differ. A LiteLLM virtual key is sent as a bearer token for every codec, including messages.

Environment-variable values the provider sends are resolved when it is built and must be present and nonblank. They are used as they are, not trimmed: a value with a trailing newline fails, naming the provider and field. A command runs, and a file is read, only on the first model request that sends its value, not when configuration is loaded or a conversation is opened. The value is trimmed of leading and trailing whitespace and newlines, then kept in memory for the provider’s models to share; a failure is not kept, so the next request tries again. When the server refuses a kept value with HTTP 401, the value is discarded and the next request runs the command, or reads the file, again. If the refused value had been accepted before, as when a short-lived token expires, the model request is retried automatically; a value refused on its first use fails the request. A value that is empty or not a valid header value fails the request without including it in the error. A command has no timeout of its own and runs before the HTTP startup timeout begins. Cancelling the request terminates the command’s own process, not necessarily its descendants. Provider commands run in Skyhook’s process working directory, not an agent’s workspace or remote target.

Environment files

At CLI startup, Skyhook loads .env in the invocation directory before constructing providers. Existing process environment variables take precedence. A missing file is ignored; Skyhook does not search parent directories, the --workspace directory, or the configuration file’s directory. Loaded variables are also inherited by credential commands and other local child processes. Neither inherited host environment variables nor .env values are automatically forwarded into remote target processes; remote commands use the remote machine’s environment. Managed SSH routes disable SendEnv, SetEnv, and X11 forwarding. Local SSH authentication/proxy helpers still use the host environment; Skyhook’s SSH-agent forwarding is configured separately.

For example, in the directory from which you run skyhook:

ANTHROPIC_API_KEY="your-key"

Keep .env out of version control and restrict its file permissions. The CLI supports normal dotenv quoting, comments, export declarations, and variable interpolation. A malformed or unreadable file fails startup without printing its contents.

Codex subscription login

A codex provider uses Skyhook-owned OAuth credentials, one login per provider. Name the provider as it is configured: for a provider named codex, run skyhook auth login codex for browser authorization or skyhook auth login codex --headless for device authorization. skyhook auth status codex reports that provider’s local login status without contacting the service, so it cannot tell whether the service still accepts the login. skyhook auth status codex --check also presents the credentials to the service with the provider’s headers, refreshing them first if a request would, and reports the plan and rate-limit use it returns. It fails when the provider is not logged in or the service rejects the credentials. The check reads the account’s usage, which runs no model and spends no quota; that endpoint is not publicly documented by OpenAI, so what it reports may change. Several codex providers can sign in to different accounts or issuers independently. Login does not require the provider to have models.

When the provider sets auth_url, login and token refresh use that issuer instead of https://auth.openai.com. base_url likewise replaces the ChatGPT backend root, https://chatgpt.com/backend-api. Requests go to codex/responses beneath it, and --check to wham/usage, so a mirror serves both beneath one root. auth_url must use HTTPS (HTTP only on a loopback host) and carry no credentials, query, or fragment; a path prefix is kept. Skyhook never imports, reads, or modifies the official Codex client’s credential files.

Credentials are kept in a credentials/ directory next to the configuration file that defines the provider, as <provider>.json. For a provider in the user configuration that is ~/.config/skyhook/credentials/ (or under $XDG_CONFIG_HOME/skyhook). For a provider the workspace configuration defines, it is <workspace>/.skyhook/credentials/; keep that directory out of version control. For --config path.yaml, it is beside that file. Skyhook creates the directory when you first log in, readable only by you, and refuses to use one that grants any access to other users.

To sign a provider out, delete its credentials/<provider>.json while no session is using it. Nothing is revoked on the server, so this is also how to clear credentials for a provider you have removed from your configuration.

A provider name becomes a file name, so it must contain no NUL character and be at most 250 bytes. On a case-insensitive file system, such as macOS by default, names that differ only in case (Work and work) share one credentials file; give such providers distinct names.

Stored credentials are bound to the issuer that granted them. When a provider’s issuer differs, requests fail without sending them and name the command that signs it in again. That command selects the provider’s configuration file with -c, so it signs in the same entry the session used wherever you run it.

MCP servers

Configure Model Context Protocol servers in the top-level mcp mapping, with one named mapping per server. It defaults to empty: no MCP connections, tools, or MCP prompt guidance are added unless servers are configured. Skyhook supports stdio and Streamable HTTP; legacy HTTP+SSE transport is not supported.

mcp:
  files:
    transport: "stdio"
    start_command: ["my-mcp-server", "--root", "/srv/project"]
    capabilities: ["read"]
    cwd: "mcp-work"                  # Relative to its config file's directory; default: workspace.
    env: { LOG_LEVEL: "warn" }        # Environment overrides for the launched process.
    startup_timeout_secs: 30         # Default; whole seconds from 1 through 86400.
    call_timeout_secs: 120           # Default; whole seconds from 1 through 86400.

  service:
    transport: "streamable_http"
    url: "http://127.0.0.1:8080/mcp"    # Full MCP endpoint, not an API root.
    capabilities: ["read", "write"]
    headers:
      Authorization: { env: "MY_MCP_AUTHORIZATION" }
    # Optional local startup fallback, only when the endpoint is unreachable:
    # start_command: ["my-http-mcp-server", "--port", "8080"]

Connections and credentials

start_command is an argument vector, not shell text; its first element must name a nonempty executable. Stdio requires it and rejects url and headers. Streamable HTTP requires an absolute HTTP(S) url. It connects first, and only starts the optional command if the endpoint is unreachable—not on authentication, protocol, or other server errors. cwd and env apply only to start_command; HTTP connections without a startup command must omit them. Relative cwd is resolved against the directory of the source configuration file that defines the value, not the agent workspace. Each server entry comes whole from one file, so a user server’s cwd is relative to the user file’s directory and a workspace server’s to <workspace>/.skyhook. Without cwd, the command runs in the session workspace, whichever file defines the server; MCP commands always run on the session host, never on a remote target. Timeouts must be positive whole seconds. Unknown settings and invalid transport combinations are rejected. Environment values must be strings; quote numeric-looking values such as WORKERS: "4".

HTTP headers maps header names to credentials: a literal, {env: NAME}, {command: "..."} or {command: ["program", "arg"]}, or {file: path}. The complete value is sent as the header (for example, MY_MCP_AUTHORIZATION can contain Bearer ...). Invalid or repeated header names, blank values and invalid literals are refused with the configuration. An environment value is read, a command run and a file read when the connection starts; a missing, blank or invalid value, or a failed command or unreadable file, prevents that server’s connection from starting. Prefer env, command or file for secrets, and do not put them in start_command arguments or literal env values.

Trust and permissions

Trust boundary: configured startup commands are trusted configuration, including commands from a workspace .skyhook/config.yaml overlay. Review workspace config before use. They run during session startup without a model tool-approval prompt, only on the local root/session host—not on selected remote targets. Only configure commands and endpoints you trust. Child agents share the session’s MCP connections rather than starting their own servers.

The session must hold the global mcp capability before any MCP server is launched or contacted, and before any MCP tool can be exposed or invoked. Each server’s capabilities sequence defaults to [] and adds requirements to that global gate. Valid names are read, write, exec, network, targets, agents, interactive, and mcp, and any capability the application itself declares, such as skyhook-security’s. An agent must hold all listed capabilities to see or call a server’s tools; otherwise those tools are hidden from both the model catalog and JavaScript access. Servers whose requirements exceed the session’s capabilities are not contacted or launched at all. Nonempty lists also request those permissions through the normal approval policy, scoped to the MCP server/tool rather than a filesystem workspace. The implicit global mcp requirement is availability-only and introduces no approval prompt. approve_all never bypasses missing capabilities. An omitted or empty per-server list requires only global mcp and produces no permission prompt. MCP transports do not implicitly require exec or network; startup commands and endpoints remain trusted host configuration.

Using imported tools

Skyhook imports tools only, not MCP prompts or resources. At startup it initializes each server and discovers its tools, then freezes that catalog for the session lifetime; later catalog-change notifications do not add or replace tools. A server that fails startup/discovery is warned about and skipped rather than preventing the session from starting. The terminal interface’s sidebar shows each server’s startup status.

Imported tools are available to the model and through tool builders inside script. Use the exact advertised name and schema rather than deriving them from the server’s tool name. Names usually look like mcp_filesystem_write_file, but may have a suffix to avoid conflicts; each tool’s description is the server’s own. Arguments may appear at the top level or under an arguments object so they do not conflict with common Skyhook arguments such as bg. Tools with invalid or unsupported input schemas are warned about and skipped individually.

Call a tool with tool[name](...). Calls return the common JobView envelope; the MCP payload (content, plus optional structuredContent and isError) is in .result. Images use the usual saved-output image handling, and server-reported errors retain their output in failed jobs.

Calls can be cancelled and run in the background as built-in tools can. Skyhook bounds the size of what discovery returns, and each message a server sends at 64 MiB; a larger stdio message is discarded, the call it answered ends at its call timeout, and the server keeps serving other calls. Skyhook does not replay a call with an uncertain outcome after a connection failure. Cancellation cannot undo effects that already occurred on the server.

Scripting introduction

Every script call gets a fresh JavaScript environment. Run the example below from a Skyhook source checkout (or adapt the paths to your project). Tool calls are lazy: reusing one builder executes it once, while constructing an equivalent new builder creates a new call:

// Every direct JavaScript call is a JobView; use unwrap for the native payload.
const packageFile = (await tool.read({ path: "Cargo.toml" })).unwrap();
const matches = (await tool.search({ pattern: "TODO", path: "src" })).unwrap();

const readme = (await tool.read({ path: "README.md" })).unwrap();

// Builders can be awaited independently (and can still be batched with Promise.all).
return { packageFile, matches, readme };

A workflow file runs in the same runtime:

skyhook --script workflow.js
# Run headlessly and exit when the workflow and shutdown finish:
skyhook batch --script workflow.js

There is no Node.js environment or recursive script call. Calls use the same tool schemas, capabilities, approvals, and saved-output behavior as direct tool calls. Read the JavaScript reference for supported globals, serialization, concurrency, result wrappers, and failure handling.

For delegation and background work, continue with jobs and agents. The tool reference, HTTP reference, and saved-output reference describe the individual contracts.

Jobs and agents

Delegation and child input

Child agents retain their conversation for follow-up work. Send instructions with control({job: id, send: instructions}), directly or as tool.control(...) in a script; the call completes, without a result, once the input is accepted. A running child receives the input at its next model-request boundary, without interrupting its current request or tools. Children do not need receive() for these updates.

A retained child whose job is completed, failed, or interrupted resumes under the same job and agent identity, including after a session restart. New instructions are appended to its existing conversation. Explicitly cancelled children and non-agent jobs cannot be resumed. jobs({job}) then exposes the latest run’s saved result, not an archive of earlier results; the child conversation and messages already delivered to the parent remain intact. A final reply whose completion the parent had yet to receive when the child resumed, as when input races that reply, arrives as a message event instead, unless a script already received it as the call’s result.

After a session interruption, retry resumes every retained failed/interrupted child without selecting them individually. A child-only retry leaves a parent waiting on work untouched and does not add a root model request. Retrying without an instruction continues the same history without adding a synthetic message.

A child’s result is {messages?, reply}: reply is its final reply. A background child’s earlier visible text replies arrive as message events without waiting for the child job to finish. Events carry kind: "message", the child job id, optional name, and text. They reach the parent at a model-request boundary, not by interrupting an in-flight request. Pending messages survive session restart. Reading a background job’s output does not consume its message events.

Message delivery does not mean the child has finished: completion also requires its owned work and queued inputs to be resolved. A completed background child’s notification carries the final reply in .result.reply; earlier replies are not concatenated into it. A foreground child’s earlier visible replies are not message events: its result saves them in messages, oldest first, each {text, at} with at the RFC 3339 UTC time it was made. Like any large result, a long messages is shortened in the call’s view and listed in presentation.truncated; read the rest with jobs({job, field: "/result/messages", start, unit: "elements"}). Replies a session restart cuts off from a call whose child still ran arrive as message events. messages is absent when there are none. The parent cannot make another model request until its foreground calls return.

When a child asks, the model’s own foreground call blocked on it moves to the background, so the model’s turn goes on and it can answer. That call is either its own agent call, which returns the child’s job:

{"id": 12, "state": "waiting_input", "presentation": {"notice": "This child agent asked a question, ..."}}

or its foreground script call, when the script’s tool.agent(...) waits on the child, which returns the script’s job, {id, state: "running", presentation: {notice}}. The script keeps running, and its completion arrives as a job event. A script’s own tool.agent(...) call never moves: in a foreground or background script it keeps waiting until the child finishes and resolves with the child’s result.

The question goes to the child’s parent agent, the agent whose model or script made the call, never the script itself or a further ancestor. It arrives as the same job event a background child’s question produces, after the replies the child made before it, as message events, in the same delivery: a parent parked in wait wakes for it. A child the model’s own call let go of is then a background job: its later replies arrive as message events and its completion as a job event. A script’s tool.agent(...) result saves in messages only the replies not delivered as message events. Nothing repeats a reply.

Child names are scoped to their caller: A and B may each create a child named worker, but all scripts owned by A share A’s child-name scope. A child retains its name even after termination; send follow-ups to its existing job instead of launching a duplicate. A launch that created no child holds no name: of two launches taking one name at once, the first to start its child keeps it.

Each model-facing ask contains one question: {header, prompt, options?, multiple?}.

  • header is a short title, up to 24 characters. It is the question’s tab in the terminal and the key its answer is filed under, so it must be unique among the questions asked together.
  • prompt is Markdown.
  • Each option is {label, description, recommended?, preview?}. Labels must be distinct. A question taking one answer may recommend at most one option; one with multiple: true needs options and may recommend any number. preview is Markdown shown beside the focused option, for comparing concrete artifacts such as code or config.

Independent concurrent calls are merged by the runtime. A child question batch changes its stable agent job to waiting_input; answer that job with control({job: id, send: answer}). For a merged batch, use control({job: id, send: {"Auth method": answer, "Deploy": answer}}); the keys are the headers in the waiting job’s questions output. A lone question also takes its answer keyed under its header. An answer to a question taking one answer is a string (a suggestion label or free-form text), or {"answer": "selected label", "comment": "user text"}. An answer to a question with multiple: true is a list of labels and free-form text, or {"answers": [...], "comment": "user text"}. An answer of another shape is refused, and nothing of that reply is delivered. A single question returns its answer directly; a merged batch keeps each answer under its header. Root-agent questions go to the host interface instead of a parent agent. ask also accepts optional bg (boolean, default false). With bg: true, the call returns job metadata immediately so the agent can continue independent work. Use jobs({job}) to inspect the pending question and eventual answer; the ask job also accepts control({job: id, send: answer}). Omitting bg or passing false keeps the usual foreground wait. Multiple outstanding child question batches are combined on the stable agent job; parents may answer a subset keyed by header, and unanswered questions remain pending. Headers must be unique across that child’s outstanding questions. Background questions are still owned jobs: children must await or cancel them before finishing.

agent accepts an optional depth delegation budget. It defaults to zero, making the launched child a leaf. The value must be less than the caller’s own available depth; once no depth remains, agent is omitted from both model tools and script bindings. Its optional workspace accepts relative or absolute directories for both local and remote children. Relative overrides resolve against the workspace selected by the target rules. Children receive a fresh conversation, shared session instructions and host-owned skills, and their parent’s active model, including model switches and restored session selections. An explicit child model overrides the inherited model, and mode runs the child in a mode in place of the caller’s capabilities. Both take only entries configured with a hint, and mode only those granting nothing the caller lacks; an input with nothing to offer is absent. This applies equally to local children, remote children, and deeper descendants. Agents on the same target share files; a workspace override creates no filesystem isolation. Children must finish or cancel all owned jobs and descendants before their agent job completes. Only root agents may leave background services running after answering.

Job lifecycle and cancellation

Background-capable tools accept an optional bg argument. Calls use the common JobView contract; a background launch reports the job as launched, running and without a result, even if it has already finished. A loaded literal null result is result: null. A child question has state: "waiting_input"; jobs({job}) returns its questions, headers included, in presentation.question, regardless of its size.

Jobs normally follow queued → running → completed, optionally cycling through waiting_input → running; failed, cancelled, and interrupted are terminal alternatives. A jobs({job}) read acknowledges the question or result it returned, suppressing duplicate automatic notification; an outcome that arrives after the read is still notified. Explicit reads remain repeatable, and jobs itself never waits; see waiting for background work. Unanswered questions do not expire. Send answers to the stable child-agent job ID.

Cancellation cascades through descendant jobs and agents and terminates managed command process groups locally and remotely. It is a request: use jobs({job}) to confirm termination. Deliberately detached processes and unreachable remote hosts limit cleanup. Command timeouts are optional; omission or null means no deadline. Explicit timeouts of 1–3600 seconds terminate execution, retaining captured output. A nonzero command exit is a normal result; see tool result shapes for process payloads.

Job names

agent, exec, and fetch accept an optional name describing the work. Names must use lowercase kebab-case: start with a letter, then use lowercase ASCII letters, digits, and single hyphens between nonempty words. Examples include inspect-config, run-tests, and build-v2. Names are descriptive labels and do not replace job IDs. Tool job names need not be unique; child-agent names must be unique within their caller’s scope, as described above.

return tool.exec({command: ["cargo", "test"], name: "run-tests", bg: true});

Names appear in active-job state, job envelopes (including notifications and inspection), and durable job records. They survive session resume. Omitted or null names leave jobs unnamed; invalid names are rejected before execution. JavaScript builders also support .name("run-tests").

Long foreground calls

A model’s foreground call of a tool that accepts bg (exec, script, fetch, MCP tools and agent, but never ask) can move to the background by itself, so a long call does not hold its agent indefinitely:

  • Once the calls of one model response have run 30 seconds, a pending event moves them: another background job of the agent finishing or asking, or input for the agent (your queued message, or a parent’s follow-up to a child). An event that arrives sooner waits until then; a call that ends first returns its result as usual. A child’s progress reply is not an event here.
  • After 3 minutes the calls move anyway, except a child agent’s, which reports through its own replies and questions.

Every still-running foreground call of the response moves together. Each returns its job ID in state running with a notice saying why it moved; the job then behaves exactly like one launched with bg: true: jobs({job}) reads its output so far, and its result arrives as a job event. Calls inside a script are not moved on their own: the script’s call moves as a whole, and the calls it waits on keep waiting.

Waiting for background work

Launch with bg: true, do independent work, then yield for events and inspect status. wait resolves when the agent can act: if other foreground work is still running, it keeps waiting; otherwise any pending event resolves it. Each notification resolves a given caller’s wait once, without consuming the notification content. The next model request receives the accumulated events together. A wait timeout ends the wait, not the job. A child must finish or cancel all owned work before it can finish; root background services remain managed by the live session. In headless mode, shutdown cancels and drains outstanding work, so workflows must await work they need completed.

const job = await tool.exec({command: ["cargo", "test"], name: "run-tests", bg: true});
let status = await tool.jobs({job: job.id});
while (["queued", "running", "waiting_input"].includes(status.state)) {
  await tool.wait({timeout: 300});
  status = await tool.jobs({job: job.id});
}
return status;

To request cancellation, use await tool.control({job: job.id, cancel: true}), which completes without a result, and inspect the job until its state is terminal. Wait events can concern other jobs; they do not prove this job finished. See saved job output for inspection and pagination, and runtime state for todos and active-job snapshots.

Configuration dump

The config dump writes the resolved effective configuration as YAML to stdout. It follows normal file selection and layering, including explicit-file-only behavior for --config, and includes defaults (such as the built-in general mode) plus any --approve-all override. Source paths and diagnostics go to stderr, so redirected stdout remains YAML. It exits with status 0 when a valid config can be produced, and nonzero otherwise; it does not require provider credentials to validate configuration.

The dump includes literal values stored in configuration, such as a literal api_key or header value and MCP environment entries; treat its output as potentially sensitive. Environment-backed values are not expanded and credential commands are not executed. Diagnostic control characters are escaped for safe terminal display.

Skills dump

The skills dump uses the same skill discovery as a session, independently of model configuration. It works without a model config or API credentials. The output is a tree of winning skills (after name precedence), including each source path, effective summary, complete YAML frontmatter, and nested assets in sorted order. Symlinks are marked and not followed; asset contents are not executed.

Skill parse and asset traversal errors go to stderr, while valid skills are still listed on stdout. Exit status is 0 when discovery and asset inspection succeed, or nonzero if errors were reported, even if stdout contains some valid skills. This does not change skill search locations: ~/.agents/skills plus .agents/skills along workspace ancestry. See instructions and skills.

Stats

skyhook stats SESSION_ID reads a saved session and reports where its tokens went, how its model requests ended, what each agent delegated, and which tools it called. Like --resume, it finds the session in the selected workspace’s history (<workspace>/.skyhook/sessions). It needs no configuration, credentials, or terminal, and it can read a session another process still has open. Sessions from other Skyhook products share this history; all report formats identify the creating host, and --list includes a Host column.

  • tree lists the agents as tree would, each line carrying that agent’s figures, followed by a one-line total.
  • json writes one JSON document with every figure: per agent, its outcome (a failure as {"kind", "provider", "message"}, with provider only for a provider failure), start and final finish times (a resumed child counts only its last completion), usage, request counts (requested, completed, failed, interrupted, attempts), compactions, jobs created by role, and calls, errors, and unanswered calls per tool; plus per-model and per-tool totals and the session totals.

JavaScript runtime

Supported globals and concurrency

Scripts run in V8 with the standard ECMAScript built-ins, including Intl, Temporal and Uint8Array.fromBase64, .fromHex, .toBase64(), and .toHex(). WebAssembly and Atomics.waitAsync are not available. Scripts compute in UTC whatever the host’s time zone, so local-time Date methods and Intl and Temporal defaults use UTC; an explicit timeZone still applies. The runtime adds:

  • performance.now() for measuring elapsed milliseconds;
  • queueMicrotask(callback), which ignores the callback’s return value;
  • await sleep(ms) for asynchronous waits, resolving to undefined. The delay must be a number of milliseconds from 0 to 1800000 (30 minutes); fractional values are accepted, and any other value throws a TypeError at the call. Sleeps stop when the script is cancelled, and unawaited sleeps do not keep it alive;
  • setTimeout, setInterval, clearTimeout and clearInterval, passing extra arguments to the callback. A missing, negative or NaN delay is 0; a delay above 30 minutes throws the same TypeError as sleep rather than firing early. Timers due at the same time run in the order they were set. Pending timers do not keep the script alive. An exception a timer or queueMicrotask callback throws, or a rejection of the promise an async one returns, is written to the console as Uncaught … without ending the script;
  • TextEncoder and TextDecoder, for UTF-8 only: encoding writes an unpaired surrogate as U+FFFD, and a decoder for any other label throws a RangeError. {fatal: true} makes malformed input a TypeError, and ignoreBOM keeps a leading byte-order mark; {stream: true} is not supported;
  • atob and btoa, which throw an error named InvalidCharacterError for input that is not base64, or for characters above U+00FF, and a TypeError without an argument;
  • structuredClone(value) for values V8 can serialize, cycles included, such as Map, Set, Date, RegExp, errors, ArrayBuffer and typed arrays. Functions, symbols, the runtime’s own objects (URL, URLSearchParams, TextEncoder, TextDecoder and WorkPool) and other values it cannot clone throw an error named DataCloneError, as does a non-empty transfer option, and a copy whose buffers exceed the ArrayBuffer storage limit throws a RangeError;
  • URL, with URL.canParse and URL.parse, and URLSearchParams, following the WHATWG URL standard: an invalid URL throws a TypeError, as does a missing required argument, and a URL’s searchParams and search stay in step;
  • new WorkPool(concurrency).map(items, worker) and .run([fn1, fn2, ...]) as async iterables yielding {index, value} results in completion order, or {index, error} with the thrown value for a task that threw; remaining items continue. run requires exactly one array of functions, each called with no arguments—not variadic arguments. Invalid run arguments, and a map worker that is not a function, throw before any task starts. Early iterator closure stops scheduling and drains running work;
  • .feed(next, worker, {wake}) for work that becomes ready over time: whenever a slot frees it calls await next(running, free) (a Map of running keys to their items, and how many slots are free), starts the returned items whose key (a string or number) is not already running, and yields {key, item, value} or {key, item, error} as each completes. Items beyond the free slots wait and start, in order, before next is called again. It ends when nothing is running and next starts nothing. An optional wake function (such as receive) is called while work runs and raced alongside it: each value it resolves yields {wake: value}. A wake still pending when the feed ends is released, so the input it would have taken goes to the next receive();
  • await receive() waits for the next JSON value sent to the script’s own job ID with control({job: scriptJobId, send: value}); the script must be launched with bg: true. Values arrive in order. Calling release() on a receive you no longer await hands its value, taken or not, to the next receive(). This is script input, not child-agent input: agents receive owner updates automatically.

For example, pass the task functions to run in one array:

const results = [];
for await (const {index, value} of new WorkPool(2).run([
  async () => 1,
  async () => 2,
  async () => 3,
])) {
  results.push({index, value});
}
return results;

Memory limit

Each script call has a 512 MiB JavaScript heap limit for its objects and strings, and separately up to 512 MiB of ArrayBuffer and typed-array storage at once. Freed memory restores capacity; neither is a cumulative allocation, execution-time, or token budget.

An ArrayBuffer or typed-array allocation beyond its limit throws a RangeError, which scripts can catch. Exceeding the heap limit ends the script, which cannot catch it, with the error “JavaScript heap limit (512 MiB) exceeded”, and the call fails even if the script went on to return. Keep headroom for temporary allocations during result conversion and serialization.

This is not a total process-memory limit. Rust-side tool results, host bookkeeping, and other native allocations are outside the budget, and concurrent script calls each have their own allowance.

Saved output and serialization

A result field that holds JSON, such as a command’s JSON stdout, arrives as the decoded value. JSON.parse given an already-decoded object or array returns a copy of it, so parsing such a field works whether it arrived as text or as the value.

Read or search saved command output with tool.jobs({job: commandJobId, field: "/result/stdout"}). A jobs read returns the existing JobView for that job; it does not add another wrapper. Field-selected output is a job view, not a raw string: the page is in presentation.preview, as lines of text, elements or members of JSON, or query matches, with pagination metadata alongside it. Field, pagination, search, and query selections omit image attachments; whole-output reads can attach saved images.

JobView response contract

Direct model calls and JavaScript tool calls return the same JobView envelope:

id?: number
state?: string
result?: JSON
error?: string
meta?: JobMetadata
presentation?: Presentation

Tool results omit absent fields and empty lists at every level. Scripts read a field the response’s schema declares but it lacks as null: r.id, r.state and r.meta are null on an ordinary completed call, and an absent stdout is null. The model’s views stay sparse. Fields inside a paged jobs({job}) result are not filled, since a page may omit them.

A completed call with nothing more to read or resume (no truncation, page, capture, question, notice, or retained child that input resumes) omits id and state. result is the native tool payload. It is present exactly when the job has a result, and a loaded literal null result stays result: null. A tool with nothing to return, such as tool.control({job: id, send: value}), completes without a result. meta is absent on an ordinary successful foreground call. Background handles, listings, inspections, and failures carry meta with what the caller does not already know: tool and name except in the response to the caller’s own foreground call, parent, target, and workspace only when they differ from the calling agent’s own, and code for a denial. A pre-admission failure lacks id, as does a call the runtime could not make at all: a tool that is no longer available, or a call interrupted while the session was not running, is answered with this same failure shape.

presentation is absent when a successful foreground response has no truncation, page, capture, question, or notice. When present, it groups preview, shape, truncated, captures, question, and notice, each present only when it has content, and precedes result. Read a text page as r.presentation.preview.lines and a question as r.presentation.question, {questions}. Presentation never shortens a question. A script never sees a question its tool.agent(...) child asks: the call keeps waiting for the child’s result while the question reaches the script’s agent as a job event, and a foreground script’s own call moves to the background so that agent can answer (see delegation). Truncation entries keep their source paths rooted at /result/....

JavaScript receives complete data; model views may shorten fields as described in saved job output. A field kept in a spill file is read whole into the script like any other, so a large one counts against the heap limit. A returned tool response keeps its own fields whole in the script’s own preview, and its result is previewed as a direct read of that result would be; a page a jobs read returns is a presentation already and stays whole. A value taken out of a response, such as response.result, is shortened like any other returned value. Tool descriptions give a call’s response as JobView<T>: the envelope, with the native result T at .result. A successful jobs({job}) read of a failed target is still a successful tool invocation returning that failed JobView; response.unwrap() checks the observed job state and can therefore throw for that view.

response.unwrap() and native results

Use response.unwrap() synchronously when a completed native payload is needed:

const data = (await tool.read({path: "README.md"})).unwrap();

It returns response.result when the response is completed (an absent state means completed), or null when the job has no result, and throws for failed or pending responses; the thrown error has error.response containing the envelope and error.output equal to its .result, plus error.job and error.code when the response has an id or denial code. The method is non-enumerable and runtime-only: Object.keys, JSON serialization, logging, returning, and saving the envelope retain plain JSON. Nested payloads, JSON copies, and receive() values are not decorated.

jobs({job}) reads already return views, so read their result, presentation.preview, presentation.captures, or pagination rather than unwrapping them. A script’s whole-output jobs({job}) read holds the target’s complete result, never a preview: previews apply only to what reaches the model, such as the script’s own returned value. Operational tool failures are failed views rather than JavaScript throws; programmer, serialization, receive, and sleep errors still throw.

The runtime does not provide Node.js APIs or fetch. Scripts cannot import modules, including the runtime’s own.

Script results and failures

Every script result payload is {value: <JavaScript return>, console?: <captured text>, failure?: <details>}. Scripts without a return have value: null, silent scripts have no console, and failure is absent unless a failure has details. In a script JobView, the payload is at /result and its return is at /result/value; logs are at /result/console.

console.log(...values) captures space-separated text, formatting objects as JSON. A running script’s captured text can be inspected with tool.jobs({job: scriptJobId, field: "/result/console"}). These inspections read the currently available output; they do not subscribe to future writes or wait for script completion.

There is no fixed console-capture size cap. Disk capacity and I/O failures still apply. Automatic previews can shorten displayed output without discarding captured output; use paging, search, or queries to inspect more. The 16 MiB limit applies to JavaScript source, not console capture.

On a script execution failure, the saved script payload is {value, console?: <captured text>, failure?: <details>}, where value is null unless only the returned value’s conversion failed; the enclosing JobView is failed and carries its error: the thrown error’s message and stack, or the JSON of any other thrown value. The message leads with the error’s name unless it is plain Error. Stack frames are line L:C positions in the submitted body’s own lines and columns, or end of source for a syntax error where input ended early; frames outside the body are left out, and the callers an await resumed are shown as at async frames. Console text belongs to the script result, not job metadata.

failure holds a thrown error’s other properties: its cause and enumerable properties, such as the job and code of an unwrapped failed response, whose full view tool.jobs({job}) reads. It is absent when there are none, so use the enclosing JobView’s state and error to determine whether execution failed. Automatic previews can shorten it.

Returned values convert to JSON:

  • As in JSON.stringify, an undefined member is omitted, a top-level undefined, an undefined array element or a non-finite number becomes null, a toJSON method’s result stands in for its object (a date becomes its ISO string, a URL its href), and other objects become their own enumerable string-keyed properties.
  • Where JSON.stringify would throw or lose data, a value takes its natural form: a BigInt becomes its decimal string, a typed array an array of its elements, an ArrayBuffer, SharedArrayBuffer or DataView an array of its bytes, a Set an array in insertion order, a RegExp its text such as "/x+/g", and a boxed primitive its value. A Map becomes an object when its keys are strings or finite numbers that stay distinct as names, and an array of [key, value] entries otherwise.
  • Promises, builders and other thenables anywhere in the value are awaited.
  • An Error becomes an object of its name, message, cause and other properties.
  • An unpaired surrogate in a string becomes U+FFFD.
  • Anything else is a problem at its path, such as $.items[2]: functions, symbols, WeakMap, WeakSet, WeakRef and FinalizationRegistry objects, cycles, unpaired surrogates in keys, nesting deeper than 100, and a member whose getter or toJSON throws or whose promise rejects, reported with its error’s message.

Conversion runs after the body returns, so the body’s own try/catch cannot catch its problems. A value with problems still fails the script, with an error listing them by path, but its saved value keeps everything else, with null in place of each problem; captured console text is kept as on any failure.

Tool arguments convert the same way when the builder is made, so a problem throws at the call: undefined properties are omitted, while undefined array elements, promises, builders and unpaired surrogates are problems too. The converted argument must be an object.

Builder execution and policy

A builder takes its tool’s arguments as one object; omitted values receive the tool’s normal defaults.

Awaiting a builder executes it immediately. Returning builders recursively executes independent branches concurrently. Only returned values expand: inside the body, await {a: builder} awaits the object, not its members, so await each builder or use Promise.all. Calls use the same capabilities, approvals, path access checks, and saved-output behavior as direct tool calls. Scripts cannot invoke the script tool recursively.

Failed tools retain any partial output (including captured process output on timeout) in the failed JobView’s .result; JavaScript operational failures do not reject the builder promise. Use response.unwrap() when failures should throw rather than be handled as data. Programmer and serialization errors are not operational tool failures and still reject/throw.

See scripting introduction for lazy-builder examples and jobs and agents for background work and child input.

Built-in tools

read, search, glob, exec, fetch, write, replace, remove, script, targets, target_add, skill, jobs, control, wait, ask, todo, and agent. Calls use the common JobView envelope; native payloads are in .result. skill is offered only when skills were discovered.

exec({command}) runs a string with the target’s shell (/bin/sh -lc, or Windows PowerShell 5.1 on a Windows target), or an array as a program and arguments without shell parsing: exec({command: "cargo test 2>&1 | tail"}) or exec({command: ["cargo", "test"]}). A stream over 4 MiB is kept in a file on the target that ran the command (spill files).

jobs() lists the current agent’s active jobs, excluding the listing call and its containing script. jobs({all:true}) includes completed history. A listing returns {jobs, older}: the newest limit jobs (100 by default), oldest first, and how many older ones it left out, omitted when none were. The listing payload is in the envelope’s .result. jobs({job}) reads that job’s saved output and status immediately; it never waits for new output or completion. It returns the existing queried view, not another wrapper, and accepts the output selections field and limit, with start and pattern for text or JSON, offset and context for text, and unit and query for JSON. all cannot be combined with job, and the other selections require job unless they restate their defaults. control({job, send}) delivers JSON input to a job and control({job, cancel: true}) cancels it and its descendants; each completes without a result, and a null send counts as absent.

Use wait({timeout?: seconds}) (or await tool.wait(...) in scripts) to yield until an agent event or a timeout, then inspect the relevant jobs. The returned view’s .result is {reason, waited_s}: reason is "event", "timeout" or "cancelled", and waited_s counts the whole seconds waited. A cancelled wait is a failed view that still carries this result. A supplied timeout is a whole number of seconds from 1 through 1800 (30 minutes); an omitted or null timeout waits the full 1800, so an agent waiting on work that never reports regains control. An event does not guarantee a particular job has completed; inspect its current status. See waiting for background work for when a wait resolves.

See the JavaScript response contract for response.unwrap(), serialization, and operational-failure behavior. In this reference, tool.jobs({job}) and other inspection calls return views for reading their presentation fields; use the task-specific contracts below for their payloads.

Reading and replacing text

read({path}) reads a regular file or lists a directory. A file is text when it is valid UTF-8 without NUL bytes; any other file is attached if it decodes as a supported image (PNG, JPEG, GIF or WebP) and rejected otherwise. A text file of at most 4 MiB is captured as it is read. A larger one is not copied: the result shows its first lines, and each later read of its content reads the file as it is then (spill files). replace({path, old, new, count?}) edits files of at most 64 MiB, both before and after the replacement; old and new together are at most 4 MiB, as is write content. In a file whose every line break is CRLF, each line break in old and new, \n or \r\n, stands for \r\n, so the file keeps its endings. Files with LF or mixed endings are matched and edited exactly as given, and write always stores its content exactly.

Creating files with write

write({path, content}) atomically creates or replaces a UTF-8 file, creating missing parent directories first, for example write({path: "reports/run/summary.md", content: "..."}). As in the operating system, .. cannot follow a directory that does not exist yet, so missing/../file fails.

write({path, source: {path, target?}}) copies another file’s bytes exactly, including binary files of any size. Supply exactly one of content or source. The destination is always in the caller’s target and workspace. The source is read on its own target: the caller’s when target is omitted, or the named one, which requires the targets capability and follows the same workspace rules as any target selection. One approval covers reading the source, connecting to its target, and writing the destination, except that a remote source path outside that target’s authorization root is approved separately when its target requests it. A copy between machines passes through the session host, and the destination is replaced only once the whole copy has arrived. For example, an agent on a remote target can copy a file from the session host with write({path: "tool.bin", source: {path: "/srv/tools/tool.bin", target: "root"}}).

HTTP requests with fetch

fetch is an HTTP request tool, available directly and as tool.fetch(...) in scripts. It runs on the selected execution target: DNS, TLS, proxy discovery, uploads, and downloads all happen there. Relative paths use that target’s workspace; no files are implicitly copied between machines. Like exec, it supports name, bg, cancellation, and saved job output.

// Read a web page as markdown, without its HTML boilerplate.
const page = (await tool.fetch({url: "https://example.com/article"})).unwrap();

// Send JSON to an API. HTTP 4xx/5xx are responses, not tool failures.
const response = (await tool.fetch({
  url: "https://api.example.com/items",
  method: "POST",
  body: {kind: "json", value: {name: "example"}}
})).unwrap();

// Duplicate query parameters and request headers are supported.
const search = (await tool.fetch({
  url: "https://api.example.com/search",
  query: [["tag", "rust"], ["tag", "http"]],
  headers: {Accept: "application/json"}
})).unwrap();

// Send a file as the raw request body, without base64-encoding it in model context.
const upload = (await tool.fetch({
  url: "https://api.example.com/upload",
  method: "PUT",
  headers: {"Content-Type": "application/gzip"},
  body: {kind: "file", path: "dist/archive.tar.gz"}
})).unwrap();

// Save a download on the execution target. An existing file is kept unless save_to.overwrite is true.
// A large transfer needs a longer deadline, or none: timeout: null.
const download = (await tool.fetch({
  url: "https://example.com/archive.tar.gz",
  save_to: {path: "archive.tar.gz"},
  timeout: null
})).unwrap();

// Explicitly opt out of certificate validation for a development HTTPS server.
// This permits untrusted certificates and enables interception; never use casually.
const development = (await tool.fetch({url: "https://localhost:8443/health", insecure: true})).unwrap();

Request options

Only url is required. method defaults to GET and accepts standard methods and valid custom HTTP method tokens. query is an ordered array of string pairs, appended to any existing URL query. The default User-Agent is Skyhook/<version>; an explicit User-Agent header overrides it. Header values can be strings or arrays of strings. auth accepts {kind:"bearer",token:"..."} or {kind:"basic",username:"...",password:"..."}; arbitrary authentication schemes can use headers. Do not combine auth with an Authorization header or embed credentials in URLs.

body has exactly one tagged source:

  • {kind:"text",value:"..."} for UTF-8 text.
  • {kind:"json",value:...} for any JSON value, including null.
  • {kind:"form",fields:[["key","value"],...]} for URL-encoded forms with repeated keys.
  • {kind:"base64",value:"..."} for inline binary data.
  • {kind:"file",path:"..."} for a regular-file upload as the raw request body. The file is streamed from where it is; a redirect that sends the body again reads the file as it is then.

Multipart form-data encoding is not supported. File bodies can set their media type through the Content-Type request header; they are not interchangeable with multipart uploads.

Responses and extraction

Responses include the status, the received byte count (size), the elapsed milliseconds (duration), and a tagged body: page, unreadable, json, text, base64, file, or empty. Followed redirects add their history (redirects), whose last location is the final URL. Response headers is absent by default; set include_headers: true to return a map of repeated header values. This option does not affect the headers request-header map.

response_format chooses how an inline body is returned:

  • auto (the default): HTML is read as markdown (below). A textual body that is JSON is read as that value, following the JSON output rules: the body is then {kind: "json", value}. A body served as HTML that does not begin like HTML is textual, so JSON labelled as HTML is still read as JSON. Other textual bodies are decoded into body.text, and binary bodies, including any that open with control bytes text never holds whatever their media type, are base64 in body.data.
  • readable: like auto, but reads any textual body served as HTML as a page, and also reads a body as HTML when it looks like HTML but was served as another media type, such as text/plain.
  • text: any body decoded as text exactly as sent, including HTML and JSON.
  • base64: the response entity bytes.

HTTP decompression is automatic; these are not raw wire bytes. Character decoding honors BOMs, HTTP charsets, and HTML meta charsets where applicable. Without an Accept header, auto sends text/html,application/xhtml+xml,application/json;q=0.9,*/*;q=0.8, as a browser asks, so sites that answer other requests with an empty page or a non-HTML variant return their HTML, while APIs that serve no HTML still return JSON; readable sends text/html,application/xhtml+xml;q=0.9,*/*;q=0.8. save_to: {path, overwrite?} saves the response to the file at path on success instead of embedding the payload, creating missing parent directories, and ignores response_format. An existing file fails the call unless overwrite is true. save_to is offered only to agents with the write capability. Errors or cancellation do not replace an existing destination.

A body over 4 MiB with no save_to is not returned inline either. The target that fetched it writes it to a new file in its spill directory and the result names it: body: {kind: "file", path, bytes}, the same shape save_to returns, with the bytes as sent and no response_format applied. Read it with read, process it with exec, or move it with write({path, source: {path}}): the session reads that file without asking while it stays open. A fetch whose spill file cannot be created fails; a failed or cancelled fetch leaves no file.

HTML is returned as {kind: "page", title, byline?, site_name?, language?, scope, markdown}. scope is article when the page has a readable main article, and markdown holds only that article. Otherwise it is page, and markdown holds the whole page body without scripts, navigation, form controls, footers, and hidden elements. Markdown keeps headings, absolute links, lists, code blocks, and tables with a header row, but not images embedded as data; other tables read as their text. A table cell spanning several columns or rows is repeated in each, so every value stays under its header. Extraction does not execute JavaScript or fetch linked assets. HTML that cannot be read is returned as {kind: "unreadable", reason, text} with its decoded source in text. reason is too_large (over 10 MiB of HTML, 50,000 elements and parse errors, 256 levels of nesting, or 20 MiB built while converting it), no_text (for example a page rendered by JavaScript), or parser_failed. Extraction never fails the call: the status, headers, and redirects are always returned.

Automatic job presentation may shorten a result over its preview budget: the body, and also long header values and redirect lists, recording what it cut; retrieve the complete saved payload using jobs({job}) fields such as /result/body/markdown, /result/body/text, /result/body/value, /result/body/data or /result/headers. JavaScript calls still receive the complete payload for processing.

Limits and failure diagnostics

The default total timeout is 30 seconds; timeout: null waits without a deadline. connect_timeout is 10 seconds, at most 3600, and max_redirects cannot exceed 20. max_bytes is unset by default; when given it fails a response whose decoded body is longer, whether returned or saved. It never applies to an upload. Limits apply while streaming, including to decompressed data; exceeding a limit fails rather than reporting an incomplete body as successful. Model-visible preview truncation is independent: retrieve saved results with jobs({job}). Cancellation and timeouts cannot undo server-side effects, and requests are not automatically retried.

Transport and processing failures are ordinary failed jobs with no result: in scripts, a failed JobView rather than a rejected promise. The error names the operation in progress (for example send HTTP GET https://example.com, receive HTTP response body, or the download path), then the cause: an I/O kind (such as connection refused), with its OS error code when the system classified it no further, or a fixed message such as the TLS handshake failed or response exceeds max_bytes. A failure after the request was sent notes that the request may have executed; a save_to failure that left its destination untouched also reports that it is unchanged, unless it created directories to hold it, which remain. Failure messages never copy underlying error text, query strings, credentials, headers, or bodies; URLs are reduced to their origin. A response’s duration is measured inside fetch on the execution target; it does not include connection startup or initial tool approval.

HTTP 4xx/5xx responses still complete normally: a 405 establishes HTTP connectivity, not successful ingestion. Permission denial and cancellation retain their separate semantics.

Redirects, proxies, and security

redirects is safe by default (follow GET/HEAD), follow to follow other methods too, or manual to return the redirect response. max_redirects defaults to 5. A call is approved for the origin it names; the redirects it follows need no further approval. Cross-origin requests do not inherit sensitive request headers, and HTTPS-to-HTTP redirects are rejected. Redirect method rewriting follows HTTP conventions; 307/308 preserve method and body. proxy selects an explicit HTTP proxy; otherwise fetch uses the target’s proxy environment. HTTPS, here and for every other connection Skyhook makes, trusts the bundled Mozilla root list plus the system’s CA store when one is present. insecure defaults to false. Setting it to true disables HTTPS certificate validation for that invocation only; it does not disable authorization or permit HTTPS downgrade redirects.

All requests require the network capability and approval, not just filesystem read permission. File uploads additionally require read, and downloads require write, including paths inside the workspace. Loopback and internal-service URLs are supported; this is a general-purpose network tool, not an isolated browser or a network sandbox. Returned content is untrusted data. There is no ambient shared cookie jar: set Cookie explicitly and use include_headers: true to inspect repeated Set-Cookie headers when needed. Arguments, response bodies, and headers can contain secrets and are subject to the normal session/job persistence rules; do not assume HTTP credentials are omitted from session records or that insecure makes authentication safer.

Saved job output

Tools execute once and save their complete results. A file read captures a snapshot, which later retrieval does not reread; a text file over 4 MiB is the exception, read where it is each time (see Spill files). Search and glob capture their complete result sets. No output is cut or evicted to fit a size: a result field over 4 MiB is kept in a file instead of in the session. Storage failures are reported as failures, with retained partial output marked incomplete.

Tool result shapes

See the JavaScript JobView response contract for the envelope, metadata, presentation group, and unwrap() behavior. This page focuses on saved output and the task-specific payloads below. A failed or pending view remains an ordinary response.

Search and glob patterns filter eligible files without overriding hidden-file or ignore settings. Nulls in tool payloads are preserved; fields a tool has no value for are absent. Process results contain exit: {code}, or exit: {signal} when a signal killed the process, and the stdout and stderr streams that produced output; scripts read an absent stream as null. A stdout holding JSON is read as that JSON; see JSON output. Completed agent calls return their complete answer string without automatic truncation. Child questions return {questions:[{header,prompt,options?,multiple?}]}, their answers keyed by header.

Directory reads return grouped entries with file sizes, for example: {kind:"directory",entries:{files:[{name:"main.rs",bytes:4096}],directories:["lib"]}}. Groups are files, directories, symlinks, and other, with sorted names; empty symlinks and other groups are absent, and scripts read them as null. Search returns {matches:{"src/main.rs":["12: matching text"]}}, preserving source whitespace. Files are searched in parallel and come back in no particular order; each file’s lines stay in order. An empty search result has matches: {}. A matched line longer than 1 KiB comes back as the text around its match, ending (line truncated, N bytes). A file or directory the search cannot read is skipped and listed by path, as skipped: [{path, reason}] with reason unlisted, unopened or unread; the other files’ matches stay, and matches is then incomplete. targets returns each target’s routing and authentication metadata; fields a target does not set are absent. target_add completes without a result. All defaulted input fields are optional in tool schemas.

By default, hidden entries (including .git) and ignored files are excluded. hidden: true includes hidden entries, while no_ignore: true independently disables ignore files. Searches rooted in subdirectories inherit ancestor ignore rules; explicitly requested paths remain accessible.

Diagnostics

Diagnostic messages identify the failed operation and its subject, such as a path, argument, job, or output field. Workspace-operation failures include the applicable execution target; host/session failures are not attributed to the caller’s remote target. “On session host” is shown when the viewing agent is on a different target and omitted for an agent on the host. Inspecting a job’s saved output connects to no machine, with one exception: a read that needs bytes the job’s target keeps in a file (Spill files) reads them on that target. A retrieval failure concerns saved output, while a retrieved execution error retains the original operation’s context.

Structured job diagnostics are rendered for the viewing agent, exposing target aliases only when that viewer’s capabilities permit them. This is not a general redaction guarantee for saved output. A jobs output read made with broader capabilities saves its already-rendered view as ordinary JSON. Later reads of that saved snapshot with narrower capabilities retain the earlier JSON unchanged, as do reads of script results that copy it. Arbitrary returned JSON is not inspected for diagnostics or target aliases, and already-committed model messages are not rewritten.

An error does not by itself establish that an operation had no effects. A command may have started before output capture failed, a file replacement may have committed before a durability check failed, and a recursive removal may have deleted some entries. Messages distinguish known pre-execution failures from known or uncertain later effects. Do not automatically retry a mutation merely because its result is a failed job.

Outcome distinctions still matter: a nonzero process exit is a completed command result, an HTTP error status is a normal HTTP result, and a wait timeout ends only that wait. A read of a missing or inaccessible path is a failed job like any other tool failure, except that a missing path outside the workspace is refused like a denial unless the approval policy allows the operation without asking (permissions). Policy denials, operating-system access failures, cancellation, and interrupted execution remain distinct.

JSON output

Process stdout and MCP text content blocks are checked once when the job finishes, and a textual HTTP body when it arrives. When the whole text is one JSON object or array, or two or more objects or arrays in a row (JSON Lines, or concatenated output such as jq prints by default), the value replaces the text; a sequence becomes an array. stdout and MCP text then hold the value, and stdout’s result type reads string | object | JSON[]; an HTTP body becomes {kind: "json", value} (response_format: "text" keeps it as text). Scripts and the model both receive the value, and page or query it as JSON.

The text stays text when it is anything else (a lone number or string, or JSON with other text around it), is unfinished (cut off or cancelled output), nests deeper than 64 levels, repeats an object key, or holds a number that double-precision floating point cannot represent as written. A number qualifies when the shortest decimal that reads back as its nearest double has the same value as written: 0.1, 1.0 and 1e30 do; integers above 2^53 such as 9007199254740993, over-precise decimals, and out-of-range numbers such as 1e400 do not.

Automatic previews

JavaScript receives complete result data. The model’s automatic view of a finished result is a preview:

  • Text fields, strings reached only through objects of at most 100 members, such as stdout, file content, or body.text, each keep at most 200 lines or 16 KiB (16384 bytes), whichever comes first, counting UTF-8 content bytes before JSON escaping. Together they keep at most 64 KiB; later strings are shortened like everything else.
  • Command streams, the stdout and stderr text fields of exec, keep both ends within those limits: their first whole lines, up to 60 lines and 30% of the bytes, then a marker line such as … lines 61–4860 omitted …, then their last whole lines, up to 140 and the bytes the first lines left. The marker line is not part of the output and is not counted. A stream whose last line alone is over those bytes keeps only its start, like other text fields. An exec response a script returns keeps both ends of its streams in the script’s result too.
  • Everything else shares one 8 KiB preview budget, which also counts the shape and truncation records below. When it is exceeded, strings keep their first 256 bytes; if every element then fits, all are kept. Otherwise arrays keep their first elements, with one count shared by every array at any depth: the largest that fits, and at most 10. Objects with more than 100 members keep their first members in source order the same way; smaller objects keep all of theirs, or when that does not fit, none. When even a single sample does not fit, strings get shorter, then deeper levels are left empty. Values holding complete fields keep the path to them.

Fields a tool declares complete are never shortened and are not counted: skill instructions and child agent answers. Errors and child questions sit outside result and are also complete, including those of tool responses a script returns. A response can therefore exceed the budget; it does not limit response size.

A presentation is never shortened again: a jobs listing, or a jobs read’s preview or page, reads the same however it is presented later. A script’s jobs read holds the whole result instead, so wherever that view is presented again, returned from the script or read as the jobs call’s own saved output, its result is previewed as a direct read of it would be, while the view’s own fields stay whole.

presentation precedes result. When arrays or objects were cut, presentation.shape describes the whole result: objects list each member’s shape under its own name, and a member only some objects have includes absent, as in "boolean|absent"; arrays are [count, element], with "min..max" when lengths vary and [0] when always empty; types that vary are joined as "string|null", or {"|": [...]} when one is a container; objects with more than 100 members read {"*": value, "#": count}. A shape over half the budget collapses its deepest levels to "{…}" and [count, "…"].

presentation.truncated lists each cut in its own unit:

  • {field, total_lines, next_start, next_offset?} for a string, with the exact position to continue from; next_offset is present only when that position is inside a line.
  • {field, total_lines, next_start, tail_start} for a command stream shown around a marker line: lines next_start up to, but not including, tail_start were left out.
  • {field, shown, total_elements, kept?} for an array.
  • {field, shown, total_members, kept?} for an object.
  • {field, cuts} for further cuts within field, beyond the first 32 listed.

kept lists the index ranges shown, as [[first, last], ...], when a complete field inside an array or object keeps an element beyond the leading ones; such records are always listed. Reading a cut array or object continues at its first value not shown: start is one-based, so without kept that is shown + 1, with unit elements or members. Finished jobs with incomplete captures include an Output incomplete; captured fields remain readable with jobs({job, field}). notice. These rules also apply after session resume and to completed remote jobs.

Script result presentation

The enclosing script’s .result is {value, console?, failure?}; silent scripts have no console. Ordinary tools have no console field. Existing JobViews such as tool.jobs({job}) reads are not wrapped again.

Presentation never changes the full saved return value. Default script output retrieval returns the composed script payload; explicit field selections read saved script data. Logging and returning the same data explicitly produces both outputs.

Paging, searching, and querying

Explicit jobs({job}) selections return a view whose presentation.preview is one page of the selected field, in that field’s own unit:

FieldSelectorsPage
Text: a string, a number, boolean or null, or a capture that is live or unfinishedstart, offset, limit, pattern, contextlines, total_lines, next_start, next_offset
A JSON object or arraystart, unit, limitelements or members, total_elements or total_members, next_start
A JSON object or array, filtered by pattern or querystart, unit, limit, and pattern or querymatches, total_matches, next_start

start and limit page lines of text or values of JSON, and pattern filters either. unit names what start counts, as the page it continues names its values: lines, elements, members or matches. A start past 1 on JSON requires it, and any unit must match the field’s pages: a capture read as lines while its job ran can be JSON once it finished, and a line position does not apply to it, so such a read is rejected and the field is read again from start: 1. offset and context apply only to text, and query only to JSON; using them with the other kind of field is rejected with an error naming the field’s kind. Selectors that only restate their defaults (start: 1, offset: 0, context: 0) select nothing, so they are accepted with either kind of field. Job metadata is never truncated.

// Read part of a text field, search it, and continue a long line.
jobs({job:42, field:"/result/stdout", start:300, limit:80})
jobs({job:42, field:"/result/stderr", pattern:"(?i)error|warning", context:2})
jobs({job:42, field:"/result/stdout", start:22, offset:54, limit:100})
// Page a JSON array, then continue at the returned position.
jobs({job:42, field:"/result/stdout/items", start:201, unit:"elements", limit:50})
// Keep the elements whose JSON mentions a name.
jobs({job:42, field:"/result/stdout/items", pattern:"\"api-[0-9]+\""})
// Select within JSON.
jobs({job:42, field:"/result/stdout", query:"$.items[?@.status.phase == 'Failed'].metadata.name"})

field is a JSON Pointer: /result/content selects a file’s content, /result/stdout and /result/stderr select process streams. For scripts, /result/console selects captured console text and /result/value selects the JavaScript return; append pointer segments for nested data, for example /result/value/items. The empty pointer "" selects the whole saved output, the members of {"result": ...}. limit is 1–1000 lines, values, or matches (default 100). Output inspection returns immediately; it does not wait for new output.

Text pages

start is one-based (default 1); offset is a zero-based UTF-8 byte offset within that starting line (default 0). context is 0–20 surrounding lines (default 0), and positive context requires pattern. Pages hold up to 32 KiB of JSON-encoded line content; field is omitted when it is the field the model asked for. next_start is absent when no continuation remains, and next_offset is present only when the next position is inside a line. lines has one entry per returned line (or fragment of an oversized line): a string for a plain read, and {line, text} with the one-based source line number for a search. Empty fields have zero lines; a final unterminated line counts, and a trailing newline does not add an empty line.

Pages prefer whole lines; oversized lines are split at UTF-8 boundaries. The page budget may return fewer lines than limit: use the returned position rather than computing start + limit. Offsets beyond a line or inside a UTF-8 character are rejected. A start past the available lines returns an empty page with the total. Regex matching is case-sensitive unless inline flags override it. Matching supports lines up to 64 MiB and reports an explicit resource error for larger lines; ordinary paging can still read those lines.

For closed fields, a missing next_start means no selected content remains. For running fields, total_lines describes currently captured output, and the numeric next position can be retried after yielding with wait, even when no content is currently available. Unavailable output omits total_lines; known empty output retains zero. Repeat the field, regex, and context when continuing a search; overlapping match context is reconstructed from saved text. Live searches defer incomplete lines and context windows until more output arrives or capture closes. A wait timeout never stops the original job.

JSON pages

start is the one-based first element or member (default 1), so element /items/0 is start: 1; past 1, unit is elements or members, or matches on a page filtered by pattern. A page holds whole consecutive values in source order within 32 KiB, member names and text included, so it may return fewer than limit: continue at next_start, which is absent at the end. A first value that is not whole within the page is sampled as a preview is, within the page budget, with the page’s shape and truncated records at that value’s own pointers, for scripts and the model alike; select those pointers to read further into it. A member name longer than the page budget is still shown whole.

pattern keeps the elements or members whose compact JSON text matches, with text’s regex rules: a member’s text is its name, a colon and its value, and strings appear JSON-escaped. The kept values are {at, value} matches like a query’s, with total_matches counting all of them in the field; start and next_start are positions among the field’s elements or members, so a search continues as a text search does. Like a query, a pattern reads the field into memory, up to 64 MiB of JSON text.

Queries

query is a JSONPath (RFC 9535) query over the selected JSON field: $ is that field. Filters can use length(), count(), value(), and regular expressions with match() (the whole string) and search() (any part), as in $[?search(@.title, '[Ee]ncoder')]. A query that does not parse is rejected with this filter form. Matches are {at, value} in document order, duplicates included, where at is the match’s pointer in the saved output, ready to use as field. They page by start with unit: "matches", counting matches from 1, with total_matches counting all of them. Numeric comparisons use double precision. When nothing matches, the page carries the filtered field’s shape, which shows the member names a query or pattern can use.

A query reads the selected field’s JSON into memory, up to 64 MiB of JSON text; a larger field is rejected, so query a field within it. This limits a query’s input, not its evaluation: once it starts, a query runs to completion, and queries that repeat selectors can produce many duplicate matches.

Spill files

A session’s database holds at most 4 MiB of one result field. A larger field is kept in a file, on the machine that produced it, and reads as a field the database holds does: the same preview, pages, searches and queries, and whole in a script. A fetch body is the exception, returned as a file. This section tells the session’s user where the files are.

FieldWhere its bytes are
fetch body over 4 MiB, without save_toA new file on the target that fetched it; the result names it as body: {kind: "file", path, bytes} (HTTP)
exec stdout or stderr over 4 MiBA new file on the target that ran the command, holding the whole stream as text
search matches, glob paths, script console and returned values, MCP text, over 4 MiBA new file on the session host
read of a text file over 4 MiBThe file itself, where it is; nothing is copied

New files are written to the spill directory of the machine that holds them, one directory per session: ~/.cache/skyhook/spill/<session id>/, or under $XDG_CACHE_HOME when that is set; on Windows, %LOCALAPPDATA%\skyhook\spill\<session id>\. The directory and its files are readable by their user alone; a session directory that already exists as a link, one other users can enter, or one whose path is not Unicode, is refused rather than used. Spill files are not part of a session and Skyhook never removes them, neither when a session ends nor later: delete the directory when its contents are no longer wanted. A session opens, resumes and replays without them.

The TUI’s job card shows each field kept in a file, as <field> · file on <target> · <bytes> bytes with the file’s path under it, to open there.

When the directory cannot be created or written, the call that needed the file fails, and the session goes on: a fetch fails; a command’s call fails with the output it had sent; a stream to the session host fails its call with the 4 MiB it had, marked incomplete; and a job whose result holds a part that cannot be kept fails with no result saved. The failure says why, such as storage full, and on which machine: the file it could not keep belongs in that machine’s spill directory. A fetch body or a command’s stream appears only when it is whole: a fetch that fails, or a fetch or command that is cancelled part way, leaves none, while a command stopped by its timeout leaves the file of what it had written, which reads like any other.

What a read of such a field does depends on who holds the file:

  • Session-host files are read as the database is. A detected JSON value stays JSON.
  • A command’s stream is plain text, never read as JSON. The session keeps the first 4 MiB as they arrived and the last 16 KiB and line count the target reported, so previews show both ends and total_lines as for any stream, with no connection. Anything more, a page of its middle, a pattern search, a query or pattern over the result that contains it, or a script’s whole view, is read from the file across the connection to the target, as far as the target counted when it wrote it.
  • A referenced file is counted once, on its target, when the read first opens it, which is one pass over the file there; a file that is not UTF-8 text throughout fails the read, as a smaller one does. total_lines is the count taken then, on every later page: it is not taken again. Each page shows the file as it is when paged, so after the file changes a page shows the changed file beside the first count, and a start past the file’s end returns an empty page. What a preview or page already showed stays as recorded.

While a command whose stream passed 4 MiB still runs, its target reports the stream’s latest 16 KiB and its line count so far, at most four times a second and once more when the stream ends before the command does: a page of the running field reads its first lines and its latest ones, with the running total_lines, and an empty page for the lines between, which are readable when the command ends. The latest lines are those that begin within the reported 16 KiB; a longer last line reads from its beginning, as far as the first 4 MiB hold it.

A read across the connection can be cancelled like any call, and a target that is slow to answer delays no other read of saved output. A page reads from its first line; a pattern is matched on the session host, so a rare pattern in a large remote file reads much of it across the connection. A query, or a pattern over a result, reads the field into memory within their 64 MiB limit, and a script’s whole view is bounded by the script’s memory.

The files written for a session, a command’s stream, a fetch body and the session host’s own, are its saved output: it reads them without asking, before and after a resume. A stream is read as the database is, and a fetch body’s path is handed to its caller, which reads that one file with read or as a write source. Reading one on another machine uses that target’s connection, which is approved as any connection to it is. A referenced file is not the session’s: each read of it through jobs resolves the path again and asks what a read of it by the caller would ask, so a grant held for the file answers it and a resumed session, which holds none, asks again. Any other read that names a file in a spill directory is an ordinary read of a path outside the workspace.

A file on a target is on the machine the call reached: the target, and every target its connection passed through, as the session defined them then. Those definitions are the session’s own, kept through a resume whatever the configuration says since. Once target_add redefines one of them the same name may reach another machine, so a field kept in a file there reads as saved output for <field> is no longer available, and a fetch body’s path there is a path like any other.

Saved bytes that cannot be read, because a file is gone, cannot be opened or read, is no longer a regular file, holds less than was saved, or its target cannot be reached, fail the read with saved output for <field> is no longer available. The rest of the job stays readable: a preview shows a command’s stream or a referenced file from what the session holds, and a session-host field as empty, listed in presentation.captures as incomplete. The job card shows why a session-host file cannot be read (not found, permission denied, not a regular file, shorter than was saved).

Persistence and live output

Reads are repeatable and survive session resume, except where a spill file was changed or removed since. Finished jobs with retained partial output have an Output incomplete; captured fields remain readable with jobs({job, field}). notice, including when viewing the final captured page.

The view’s presentation.captures lists captures that are not a finished part of the result, live, unfinished, or abandoned output, even without a structured result:

[{"field":"/result/console","complete":false}]

complete: false means the capture is still live or incomplete; in particular, a partial JSON capture must not be treated as a valid JSON value. A finished job lists no capture that took nothing. Select a descriptor’s field to page or search its retained bytes as text. Capture descriptors survive failures, cancellation, and session resume even when there is no structured result containing those fields. Empty or absent result fields are not fabricated to represent partial captures.

Local captures, including script console output, can be read while running. Remote captures become available as they are transferred; inspecting already-transferred output does not require reconnecting to the remote machine.

The TUI’s job card shows the structured result and previews any available captures not represented there. This exposes both process streams while live and preserves stderr and exit status on completion. While a job runs, each capture shows its latest lines, up to 20 within a page’s bytes, and follows them as output arrives. Under the preview the card shows each file a field is kept in, with its target and size; the rest of a truncated field is the model’s to read with jobs.

Recorded model requests keep the previews, pages, and notifications the model actually saw; they are not regenerated from saved output.

Todos and runtime state

Todo lists

Every agent has an ordered advisory todo list. todo() reads the caller’s list; todo({items:[...]}) replaces the whole list and completes without a result; an empty array clears it. todo({status:[...]}) sets every item’s status, one per item in list order, keeping the text; it must give exactly as many statuses as the list has items. Each item has text and a status of pending, in_progress, or completed. Multiple items may be in progress. Unfinished items do not prevent an agent from finishing.

Any agent allowed to delegate can seed a child with agent.todos. The task prompt remains required; seed items use the same {text, status} format as todo.items and appear in the child’s runtime state before its first model request:

return tool.agent({
  prompt: "Implement the requested change and report the validation results.",
  name: "implement-change",
  todos: [
    {text: "Inspect the implementation", status: "in_progress"},
    {text: "Make the change", status: "pending"},
    {text: "Run relevant checks", status: "pending"}
  ],
  bg: true
});

The child owns subsequent edits; items and status are exclusive. Reads return {items}. An agent without todos has an empty list. Inside the child, progress can be updated with the same tool:

return tool.todo({items: [
  {text: "Inspect the implementation", status: "completed"},
  {text: "Make the change", status: "in_progress"},
  {text: "Run relevant checks", status: "pending"}
]});

or, keeping the text, with only the statuses:

return tool.todo({status: ["completed", "in_progress", "pending"]});

Lists persist with the session, including completed and interrupted child lists. Resume preserves recorded statuses. For Rust host observation, see embedding.

Prompt context

Each agent’s system prompt ends with a <context> block of key:value lines: its workspace; its target, with that machine’s host and any via and origin, when it may choose targets; os, the operating system of the machine its target names, with the shell its shell commands run in, os:linux shell=sh or os:windows shell=powershell-5.1; and tz, that machine’s time zone, with the zone’s offset from UTC when the prompt was built, such as tz:Europe/Berlin +01:00. The zone is the one that machine’s clock follows: the zone its TZ names, else its system zone; a TZ that gives a rule rather than a zone name shows only the offset, such as tz:+09:00.

Launching a child on a remote target connects to it first, approved like any tool call on that target: a denied or unreachable target fails the agent call without starting a child. Every timestamp an agent sees, such as the state’s time and a child reply’s time, is in UTC, and scripts compute in UTC.

Per-request state snapshot

The model profile’s state_mode controls whether and how the model receives a fresh <state> snapshot with each request.

The snapshot shows the current time in UTC, to the second, active jobs, and the caller’s todo list. Empty job and todo sections are omitted. This is a compact model-facing view, not the JSON returned by job or todo tools; scripts should use those tools to inspect state. Dynamic snapshots are still recorded with model requests; this mode is not a data-retention control. It does affect prompt caching: see state_mode for when persist keeps more of the history cached.

Reading job progress

Job rows identify the job, parent, tool, optional name, state, age, and child-agent progress. Directly visible jobs have - as their parent; nested active child agents identify their immediate parent job. Ordinary tool jobs are not shown as nested children.

age_s is elapsed whole seconds since creation, including time queued or waiting for input. Child-agent jobs report the child’s selected target and workspace once initialized. Location overrides are shown only when they differ from the snapshot’s current execution location. Omitted locations refer to that current location, not to the parent row’s overrides. Targets are omitted when target capabilities are unavailable.

Child-agent turns and tool_calls counters describe that agent alone, not its subtree:

  • A turn is a complete, recorded assistant response, including responses containing tool calls. Failed or incomplete attempts, retries, and compaction requests do not add turns.
  • Tool calls count jobs launched by that child, including calls inside its scripts, but not work owned by its descendants.
  • Counters remain cumulative across retained-child follow-ups and session resume.

Todos retain their original order, including completed items. For example:

<state>
time:2026-09-05T09:41:22Z
in_progress:
  Make the change
pending:
  Run relevant checks
job parent tool name state age_s turns tool_calls
7 - exec run-tests running 12 - -

9 8 agent - waiting_input 4 1 0
</state>

Here, job 9 uses the snapshot’s current location, not job 8’s workspace override. Only unfinished todos appear; todo reads the whole list. With no active jobs or unfinished todos, only the time remains. A todo’s text is shown as written unless it would break a line or read as a heading or the job table’s column line, when it is quoted as a JSON string.

Development setup

Prerequisites

  • Rust 1.99 or newer via rustup, and just on PATH.
  • Zig 0.15 or newer on PATH (or CARGO_ZIGBUILD_ZIG_PATH) for release builds and the remote shims; debug builds and tests do not need it.
  • python3 on PATH for the test suite, whose MCP tests run a scripted server.
git clone https://github.com/kryesh/skyhook.git
cd skyhook
just setup

just setup adds the rustfmt and clippy components and every shim target, and installs cargo-zigbuild, cargo-nextest, and mdBook with cargo install. It then checks for Zig and what release builds need, and names whatever is missing. See remote transport and shims for shim profiles and artifacts.

Release builds

just build-release [target] builds both applications into target/<target>/release on a Linux host; only x86_64 hosts have been tested.

  • Without target, it builds for this machine’s own target (just --evaluate native_target prints it), using the host’s C library and name resolution.
  • just build-release x86_64-unknown-linux-musl or aarch64-unknown-linux-musl builds a static binary with musl’s own resolver.

Targets of other architectures fail before building.

The first build for a v8 version and target compiles V8 from source, taking several CPU-hours and a few gigabytes under target/v8; later builds reuse it. To build offline, keep target/v8 and the cargo registry from an earlier build. The build needs, on PATH:

  • clang and clang++ at least as new as the clang major that V8 version’s Chromium build pins, with their compiler-rt builtins; the build stops with the required version if the installed one is older;
  • from the same LLVM, ld.lld, llvm-ar, llvm-nm, llvm-readelf and llvm-objcopy, and llvm-config for its libclang.so;

Library architecture

The skyhook crate is the library. The terminal and batch front end is a host of that library, not a separate agent implementation. Provider protocols, terminal interaction, and local or remote execution meet at shared runtime boundaries.

See embedding for host API and replay contracts, remote transport and shims for execution transport, and jobs and agents for delegation behavior.

Crate layout

Each crate is crates/<directory>, and depends only on crates above it in this list.

  • skyhook-macros (macros) and skyhook-base (base): generic primitives with no role of their own, each at one path, which every crate and host imports from base directly: enums spelled once (NamedEnum, and Kinds, which names a data enum’s variants so a journal dictionary and the data it classifies cannot drift apart), checked newtypes, the size limits tools share, digests, and blocking work run off the async workers.
  • skyhook-media (media): images, attachments and the content-addressed blob references the journal and providers record. It decodes in memory and touches no files.
  • skyhook-worker (worker): the code that runs wherever tools execute. It holds the operations a tool call runs on a machine, each one call answering with typed facts, never rendered text; the facts a failure carries; the Target trait the host runs every operation through, on the session’s own machine or over a connection; the protocol and the loop a shim serves it with; and the origin role, the SSH and WinRM streams a machine opens to further targets. It builds for Linux and Windows, and every platform difference stays inside it.
  • skyhook-tools (tools): the target tools as specs: each tool’s schemas, its admission, the paths it resolves, the one operation it builds and how it renders that operation’s events and end into its result, with argument validation, output captures and the one renderer of diagnostics. It starts no operation and touches no machine.
  • skyhook-schema (schema): the proc macro that builds the session journal’s schema image at compile time.
  • skyhook (skyhook): everything that needs a session: the agent runtime, providers, the journal, the tool catalog, policy and admission, the host-only tools, the target registry, and the protocol client that connects to shims and deploys them.
  • skyhook-security (security) and skyhook-apps (apps): a product and the front ends; see products and hosts.
  • skyhook-shim (shim): the binary a remote target runs. Of the workspace it links only the worker and base, so the compiler keeps host-only code (the session database, providers, the agent runtime, the JavaScript engine, tool schemas and rendering) out of every shim.

A worker wire type that a tool’s schema or the configuration’s embeds, such as a command line or a credential, derives JsonSchema in the worker beside its one definition, so its doc comments there are model- and config-facing text written for every schema that embeds it; what differs per use, such as whose shell runs a command, the embedding field says.

Products and hosts

Products are libraries; the applications are one package of front ends over them.

skyhook            core library: the configuration type, the product API (skyhook::product),
                   launch, approvals and the plain Skyhook product
  ↑
skyhook-security   the security product, on the library crates alone
  ↑
skyhook-apps       the terminal, command line, configuration files and batch jobs; the
                   skyhook and skyhook-security binaries

A product implements skyhook::product::Product: an Identity (host name, session schema, display name, capabilities, whether the root’s mode is fixed), its own launch options with any settings of its own already parsed, a configuration edit applied before admission, and a SessionFactory that prepares each of its own sessions and may ask for a scope form before the first message. Any host can serve it.

Core’s launch module is what any front end opens sessions with: the product’s edit of the configuration the front end hands in (HostConfig, the library’s Config with the launch’s own approve_all), root-mode admission, model and mode selection by attendance, the approval policy and the prompt channel to whoever attends a session (interaction), prompt attachments, and session listing through the store. It takes values, never the paths to read them from; the front end keeps any remembered choices and supplies the shim catalog.

skyhook-apps (crates/apps) is the terminal application: the TUI, clap admission, .env loading, the configuration files, batch jobs, the auth, dump and stats commands, the saved UI state, termination signals and the embedded shims. Its two binaries each dispatch their own command line, and the security binary adds its options, its security.yaml, its runs command and its look.

Configuration files are the applications’ own (skyhook_apps::config): discovery of the user and workspace files or the one a command line names, their layering, and the diagnostics of files passed over. Typed LayeredConfig schemas share one loader: config.yaml is HostConfig, checked against the host capabilities of the product it is loaded to run, and a product’s file is a schema its binary declares.

Each file is read into a tree of nodes (skyhook_base::decode) that places every value at its file, line and column, and layers merge on those trees. One pass then decodes the merged tree through the Decode trait and collects every refusal at the position of the value it refuses. A type’s own validation and the checks of what the parts say of each other (target routes, undeclared host capabilities) run in that same pass; the default mode and model are checked when the configuration is sealed, after the product’s edits. A type that also crosses a serde boundary, such as a target’s settings as a tool’s arguments, keeps its serde form for that boundary.

Sessions carry the creating host’s name; another host’s session opens view-only, and the library refuses to activate it. All products share .skyhook/sessions, the shims and the capability rules; see products and launching their sessions.

Security research product

skyhook-security (crates/security) owns its settings (SecurityConfig, which a host parses and hands in with the launch options; the terminal layers security.yaml into it), embedded research modes, each replaced whole by a configured mode of its name, instructions and a persona rendered from templates with the run’s live policy in their context, model-role hints, the research tools, a report writer, and the research tables it keeps in each of its sessions’ own session.db beside the journal as a session extension. A session is the run: it records the run as it opens, with the live policy it keeps, and a resumed session continues it. The run’s test artifacts and its reports live in the artifacts/ and reports/ subdirectories of the session directory. The security guide describes the research behaviour. This section says what the store records, what is derived from it and who may write it; each table and derivation is documented where it is defined, in crates/security/src/store.

Recorded. The store is one graph and one audit log.

  • Every object is a node of one kind (component, path, state, premise, flaw, candidate, finding) with a title, a body and a detail row of its kind sharing its id. A location (a code region, an address range of a binary image, or an operation of a named interface) has the same shape. Edges join detail rows. A path’s steps, a candidate’s chain of flaws, whose first is its root, and a candidate’s actions are ordered lists, each set whole.
  • A duplicate of any kind but a finding merges into a live node of its kind. merged_into is one hop and a merge repoints the duplicate’s edges to the survivor, so readers never resolve merges; a merged path keeps its steps, and a merged candidate its chain and actions, as history. An id argument naming a merged node resolves to the survivor at the boundary.
  • Inventory recorded in error is retracted rather than deleted: a path is unswept, swept or retracted, and a state or component recorded or retracted. Nothing derived reads a retracted node, and setting its status back restores it.
  • Every write is one event by the journal’s agent row, with the actor’s note. event_node names each node the event bears on with the strongest of four ordered effects (concerns, disputes, standing, changed): a write names its direct marks, and one rule carries them along the graph as it stands after the write.
  • Premise and flaw statuses, assessments and verdicts are histories of rows keyed by the event recording each, and each row records whether the work owning that result recorded it. The standing result is the latest owned one. A different result recorded elsewhere is a proposal: it disputes its node and owes the owning phase its work again, and replaces nothing.

Derived. Scheduling is derived; nothing is planned, and no aggregate is stored.

  • What a phase’s work on a node rests on is that phase’s arm of one relation (bearing). Its latest event on the node is the work’s basis, and the work is owed while its result predates its basis. A phase’s own work on a node, its helpers’ included, never moves what it rests on.
  • Work started is a log. A task belongs to the journal job of the agent that began it, and names each subject with the basis it began on, several subjects for a bundle. A task has no end of its own: it is live while its job is, and its work is done when its subject no longer owes the phase.
  • A subject is offered while its phase owes it, no task of it is live, and fewer than two of its tasks began at its current basis. startable pages the offered work in pipeline order, each entry with the ready work its agent takes with it, leaving out what running work or earlier-stage work holds back, and admitting tests by the run’s live policy, the user’s approvals and the pending tests the user unblocked.
  • The run’s scope is the components recorded outside every task. What only paths entering elsewhere reach owes no work, and stays recorded.
  • Candidate standing and confidence, the synthesis and the run’s facts are views over the results, the task log and the state of the agents’ jobs.

Told. The root agent receives the run’s facts as host state with each request; the agents below it get none, and what they need travels in their briefs. The Research tab renders the same facts as a page of typed blocks, which the host lays out. The facts depend on the state of agent jobs, which changes without a research write, so a cached read of them is read again when a job moves as well as when research is written. An agent with tasks is told of others’ changes to its subjects as a host event: one bounded digest for each changed subject, of the events of the bearing relation after the task began and after the agent’s cursor, leaving out those the agent or one beneath it recorded. Nothing is stored for this: the subscription is the task log. Beginning a task returns the same digests for each subject a task of that phase worked before.

Reported. reports/ is a projection of the store, which research_generate renders from the store alone: a folder for each root flaw whose finding reports its scenarios as they stand, replaced as a whole when what renders changed, with a folder for each test the report states whose artifacts are copied only while they match the digest the test recorded, beside a hardening list of the confirmed flaws no finding’s scenario holds.

Permitted. Each research action is a tool, and the host capabilities gate which an agent is offered: security.research recording research, with security.verdict a verdict; security.verdict with Write a report; security.test a test; security.scheduled beginning assigned work; and security.coordinate scheduling (research_startable) and report generation. The store refuses nothing but boundary parsing, unknown ids and integrity, so unwanted work is prevented by not scheduling it. Read-only tools, the host state and host events read beside the session’s one writer; a tool whose work is mostly files (recording a test, generating reports) takes the session’s files turn rather than the writer’s.

Configuration and provider entries

config is the configuration a host parses from text it holds (Config::from_yaml), decodes from a tree (config::process) or builds in code (Config::builder); it admits it, resolves model selections, and builds the model catalog. It does not interpret provider entries. An entry’s ConfigHome is where the host says it was defined, beside which its Skyhook-managed credentials live; one a host leaves unfiled keeps them in the user’s Skyhook directory. provider::dialect owns the entries (RawProviderConfig, ProviderSettings, ProviderModels): each dialect module declares its provider-only Options (connection rules and any Skyhook-managed Login, which refuses an api_key) and its inheritable request settings. Request defaults and model settings are typed partial declarations (provider::settings) that keep inheritance intent until admission resolves each model into a complete, independently validated codec and transport profile. The shared Request also carries service_tier, a body field on every codec, explicit_caching for Chat and Responses, and the Responses-only selections (reasoning_summary, access_programs); admission refuses an effective one on any other codec, and a dialect refuses one its service does not take (Codex refuses explicit_caching). Each dialect’s Responses preset declares its summary default. Its image_limits replace the per-image limits each dialect declares in its profile.

Provider boundary and lifetime

provider::Provider is a shared factory. open_context(id) creates an independently owned ProviderContext for one conversation without making a model request; invoke(&mut self, request) returns an owned asynchronous response stream that does not borrow the context. A startup failure is the stream’s first and only item. Providers may send the context identity as cache-affinity metadata. Custom providers implement both traits. The three inference API families live under provider::codec: each codec encodes requests and decodes native streams under a typed dialect that names the conventions varying between servers of that family (field placements, tool-name rules, schema constraint, replay spelling, terminal-event shape), while the codec keeps the correctness rules and reads error bodies with its API’s own codes. Vendor modules under provider::dialect own provider-only settings, the codecs they speak and the dialect presets for each, credentials (header values layered on the shared secret::Credential), and the transport conventions (fixed headers, per-turn session headers, body fields the vendor takes whatever the codec, and typed readers that map their servers’ own error codes and wording onto error kinds); configured models run through provider::http::HttpProvider. Shared request, message, and response types live under provider::protocol.

Each model runs as its own HttpProvider at its codec’s endpoint under the shared API root; the models of one provider build share its HTTP client, credential sources, command generations, and OAuth state.

Images are admitted only when they decode whole (media::Image) through image’s own decoders, with an allocation limit that also covers an animation’s canvas, and turned upright by their EXIF orientation. The journal keeps a still PNG, JPEG or WebP as attached; an animated PNG or WebP, and any GIF, is kept as its decoded default image or first frame, fitted to the stored size. An HttpProvider context fits each image a request references to its profile’s limits once, and keeps the outcome (media::Prepared) while the context still references the image: a fitted copy, or the reason none could be made. Codecs read these through a read-only view and encode a copy with its own format, or an omitted image as a text part giving the reason, so an image that cannot be fitted never fails the request. Only a fault in Skyhook’s own fitting work, such as a panic, fails it, as ProviderErrorKind::Internal.

The runtime retains the provider context across turns, tool work, questions, retries, and compaction. A child whose invocation has resolved, with nothing left for it to take, parks: its loop and context are released, and the input that resumes it opens a fresh context under the same identity from its history. A model change prepares its replacement before committing the selection and preserves journal history. Reselecting the current model keeps the current context. A mode change also replaces the prompt and tool surface and invalidates earlier bound reasoning. A host’s persona renders into every agent’s prompt; a resumed agent keeps its recorded prompt until a mode change rebuilds it. A root reopened under a ceiling that changes the grant its prompt was rendered for, such as a host without the user, changes into its own mode under the new grant as its next work starts. Resume opens a fresh provider context under the same context identity, or none for a root whose model the configuration no longer has: the session still activates for writes, and only running the root fails with UnknownModel until a selection, or activate_on, which journals the switch in the activation commit, moves it to a configured model. A child whose own model is gone restarts on the root’s committed model, journaled as it starts. continue restarts retryable children in one commit, then claims and admits the root’s held batch in one step, so nothing withdraws from it meanwhile and a refused batch is held again unchanged while the children run on.

Prompt text is embedded Tera templates (prompts). An agent’s prompt renders when its contract is fixed, as it starts or changes mode, from its typed context (role, available depth, capabilities, mode and the context lines: workspace, target, and the operating system, shell and time zone the target’s machine reports), to which a host’s Prompts add the fields of its own section. Only a root granted Interactive takes the root role; a root no one can ask is instructed as a child, working its task to a result. One render path serves both: a mode whose instructions are a host template (Instructions::Template) renders them for the agent entering it into an Edition, the text the journal records; the system prompt then places the host’s persona, rendered for the agent, that text and the workspace’s instruction files around the library’s parts, and the journal keeps the prompt as rendered. A journal holds text, never a template name, so resume and replay need no templates, and drift compares the mode as it renders now for the reopened root with its recorded edition. A host’s Templates register beside the library’s; each template is checked against its context, refusing a top-level name it does not define: a host’s read the agent’s context and the section’s fields, and only the system template reads the parts placed around an agent’s context. A script a template shows the model is a verbatim source, included as written.

Each harness is built for one identity::HostName, the application creating sessions; the session stores that origin and exposes it through its summary, stats and SessionStarted. Another host’s session can be opened for reading, and the activation boundary refuses to run or change it with HarnessError::HostMismatch. Host identity does not partition the shared session root.

A host’s ResumeHook (agent/resume.rs; its contract is in embedding) is ordered by the core. Each call waiting on it joins a set in the core, in the change that also arms what leaves it, so a call abandoned as it joins leaves too. An interrupt empties that set in the same change that stops turns, counting what it withdrew, and so does the shutdown transition. A call is let in only by leaving that set in a core change after the hook finished, whether it succeeded or failed, so an interrupt that lands as the hook finishes still withdraws it.

The session owns the durable conversation (session::Message): user text and attachments, job events (child replies and presented job views), parent input and compaction summaries, assistant items, tool results, and the agent’s state (date, live jobs, todos, and a host-supplied section) as a message of its own. Providers receive it rendered: state becomes a context state entry and job events runtime text, so the provider layer knows nothing about jobs or todos, and those renderers are part of the session format.

Providers receive complete provider-neutral requests; they do not privately replay failed submissions. A response_schema must be transmitted as a structured-output constraint or rejected with InvalidRequest, not silently ignored or replaced with prompting. Input images must be encoded or rejected explicitly; generated image outputs are not supported. Reasoning replay carries provider/model provenance: replay from another model or API is omitted from encoding, and so is sealed (signed or encrypted) replay from another provider configuration, without deleting the durable transcript.

History, transient state, and caching

A ModelRequest carries its context as one ordered list of typed entries: messages, and runtime state the harness wrote, with how long the state stays in the model’s view (StateLifetime). A profile’s state_mode sends each request’s own state (current, dynamic), commits it to the conversation unless it equals the latest committed one (persisted, persist), or omits it (none). Everything before the first current state is a prefix later requests extend under the same context settings until compaction replaces it. Only a state whose request produced no response later drops out of it, since nothing is bound to it.

The journal records each request’s tail. The projection gives each committed response the state its request sent, the request of the attempt that completed with it, and later requests send it again before that response as superseded state, back to the latest checkpoint or mode switch (where bound reasoning ends). A superseded state never reaches the model, so the model always reads only the latest dynamic state. Each codec places state in its dialect’s StateRole: the protocol’s harness role, or user content where a server has none mid-conversation; never inside tool output. A Messages dialect may make system-role state turn-scoped, which lets that codec resend superseded state hidden from the model and keep the conversation unchanged for reasoning bound to it; every other placement omits superseded state, so the wire request stops extending the previous one where that state was, which persist avoids. A state not followed by a response or the end of the context is omitted everywhere: its request produced nothing bound to it.

history_lifetime communicates cache reuse without prescribing a provider implementation:

  • extends is the default: later requests extend this history.
  • detached marks one-off settings, such as a compaction summary request, with no reusable history prefix under those settings.

Messages, Chat dialects that send cache_control, and Chat and Responses under explicit_caching (prompt_cache_options: {mode: "explicit"}, marked with prompt_cache_breakpoint) mark cache breakpoints: the cached segments of the system prompt (on Messages and Chat), the end of the history prefix, and the point before each earlier assistant response in it, where each prior request’s prefix ended, so that prefix stays reusable. Each dialect caps the breakpoints of one request, system segments included, at four by default, the documented limit of each codec’s API (four cache breakpoints on Messages, four cache writes per explicit-cache request on Chat and Responses); over the cap, the oldest history breakpoints are left out, and a request whose system segments leave no room for its history is refused. Responses sends cache_control top-level instead, so the server places the breakpoint itself, and only under automatic caching; Chat and Responses otherwise use automatic prefix caching. A detached request marks no history, and the current state and the rest of the request carry no marker. Responses sends every tool output as a text-block array in explicit mode, so it can carry a marker; Chat gives that form only to a tool output it marks.

Request, response, and recovery lifecycle

  1. At a request boundary, the runtime applies accepted input and model/mode selections, every batch queued by then committed with its selection as one submission, refreshes history from the journal, and builds the request. Shared settings are recorded in model_context; model_requested freezes the exact history range and inline tail.
  2. Each provider invocation gets a model_attempt_started record for that logical request. The stream carries display-only Deltas for blocks, cumulative Usage snapshots, and one terminal End holding the Completion: the complete items in position order and how the response ended (an answer, tool use, or a cut). Only a completion built for tool use carries tool calls, so nothing else can authorize execution. LiveResponse gives the runtime and observers the same provisional view of the deltas until the end arrives. Observers then see each response settle as committed or failed, keyed by the journal sequence it produced.
  3. Only an accepted response becomes model-visible history. Its message, usage, and outcome commit together before tool dispatch. The response’s calls are then planned concurrently and their jobs created together, in call order, in one commit: after a crash either every job of the response exists or none does, and a call that fails planning settles without a job and without affecting its siblings. Each tool result commits as its call finishes; request projection merges results back into the original call order. This preserves completed work after a crash without making completion order part of the next model request.
  4. Once a tool exchange is closed, the runtime can compact history or build the next request. An agent with no further work returns to its idle loop rather than discarding its context, until, as a child, it parks.

The session core keeps each agent’s newest request with its RequestPhase, the calls its responses left without results and whether its input awaits the model; that is what turns, activity, resume settlement and the observation read, and session::Turns folds each agent’s turns. The fold also decides what presenting a record reads beyond it (session::Fact): the request an answer committed under, the call a result answered, and that a failed turn ended on its request’s failure. The core folds requests and each agent’s state as records commit, and writes their rows, with what it decided of answers and failed turns, in that transaction, so request pages, statistics, the session list, agent summaries, compaction’s retention and opening a session read lifecycles from those rows rather than deriving them again.

The core admits every command by the session’s SessionPhase (viewing, running, shutting down, failed, closed) in one table in session/core/phase.rs, which also decides when what a command journals is dated. A reopened session is only viewed until the first call that changes it activates it (agent/activation.rs), and shutdown stops a session as a crash would (SessionHandle::shutdown, agent/handle.rs); the host contract for both is under interruption, continuation, and shutdown.

Interrupt, continue and new input read three facts the core keeps, and nothing else: the session’s flow (open or paused), each agent’s turn (Turn in agent/agents.rs), and whether each child invocation has begun. stop_turns, redirect and interrupt_tree in agent/interrupt.rs decide each agent from them. A busy turn an interrupt stops stays stopping until its loop has unwound the work it took: nothing claims it, or what it would hold, and continue and new input wait for that (settle_interrupts), so one agent never runs two commands at once. The host’s observation is a display, never an input to that decision.

Transient recovery belongs to the runtime, not the provider or transport. It classifies normalized ProviderErrorKind values rather than error-message text: rate limits, timeouts, transport failures, and unavailable servers repeat the frozen logical request. Input and selection changes wait for the next request boundary. The failed stream is dropped before backoff; server retry hints take precedence over capped exponential delays. Recovery remains cancellable and continues until success or interruption. A failure is journaled with its retry and backoff, so a request never reads failed while it retries, and one a crash leaves retrying reopens interrupted. The request fold keeps its retried failures as runs of consecutive identical failures, written with its state, so an endless retry holds only its distinct changes.

A retry starts a fresh live response while retaining the attempt audit records and any reported usage. A stream that fails or closes before its end never authorizes tool execution, and transient recovery does not rerun completed tools. An expired credential from a command or file is transient: the provider discards it on a 401 and the retry fetches a fresh one, and so is a completed response with no nonblank text or call, unless it is a refusal or an output cut. Other authentication failures, invalid requests, and protocol errors do not enter this retry loop. Context-window recovery and unusable compaction summaries have their own bounded recovery path; a checkpoint that breaks a journal invariant is not retried. Which cut or empty responses commit is decided in agent/turn.rs.

Compaction and context accounting

The journal is authoritative; compaction replaces the model-visible projection, not old records. Automatic compaction is decided from a completed response’s reported occupancy, at 90% of max_context - max_output. Every size it uses is one a provider reported. Summarization is a separate journaled request with a structured response schema and no callable tools. Its checkpoint installs the replacement history and the reconciled todos in one commit, which is refused when it would overwrite newer todo state, and replay uses the stored continuation rather than rerunning the summary.

An agent’s context (agent/context.rs) opens with its history, read from the journal by index: its latest checkpoint with the retained sources, then its records after the frontier folded by Projection::apply, the fold that goes on to apply the records the core feeds it, and reads its history again after a checkpoint. The occupancy it compacts for is the core’s. Compaction retains from that history, with indexed reads of the agent’s requests completed since its checkpoint and of the exchanges its live calls opened, so neither reads the whole journal. agent/compact/ owns the summary request and how it shrinks after an overflow (mod.rs), the summary’s structured continuation, its schema, parser and attempt (summary.rs), the retained tail (retention.rs), and the checkpoint (checkpoint.rs). The user-visible behavior is under conversation compaction, and the durable reference contract under model-call reconstruction.

Tools, jobs, and execution

ToolRegistryBuilder registrations are typed; only MCP tools register a server-supplied JSON schema. Typed registrations generate input and output schemas, and a unit registration completes its job without a result; registry metadata also supplies compact result documentation to the model and JavaScript runtime. Both call paths use the same executor, capability checks, authorization coordinator, and job supervision rather than separate tool implementations. Every call is admitted once, before authorization: a typed registration may declare an admission step that turns its parsed input into the value its handler receives, so its checks run at the boundary rather than in the handler. The admitted value names its path arguments, which are resolved in place, and derives its permissions, so an inadmissible call never asks for approval. It may also choose the schema its job’s result follows, which presentation and scripts read and tool descriptions leave out, for a tool whose result shape varies by action. A target’s paths are op::TargetPath text everywhere the host holds them, in arguments, locations, diagnostics and the journal; their components come from the target’s resolution, and a path that resolves to one that is not text is refused with the target’s own bytes, undecoded. Path admission (skyhook_tools::path) resolves a requested path where the call runs: relative to the workspace, through existing symbolic links, as the tool will use it (an existing entry, a write target, or a removal). The resolved path, not the spelling the caller gave, is what the call asks permission for, over the exact file or a directory’s descendants. A relative path continues the workspace’s own resolution, so every entry looked up on the way counts. A path refused outside the authorization root (one that does not resolve, or a removal of the root, the workspace or a directory holding either) is asked for as the path it would be, under a decision that may not ask anyone, and fails only once allowed, so no prompt or error reveals what lies outside. A capability the caller lacks makes the tool unavailable rather than denied.

A call’s paths (its input’s, its source’s and its job’s workspace) resolve in one step, each on the machine holding it, before its permissions are assembled and approved. A call whose paths are all on the session host resolves as it is planned, so a path that fails to resolve fails it before its job exists, and it is approved once. A call that opens a connection is approved for its routes alone before anything connects, and its job runs from then on; once connected, its paths resolve, and the rest of its permissions are approved together. Either request is skipped when held grants already cover it.

A connected call whose paths would need no permission of their own inside its target’s authorization root, and that reads no source and places no job, is pre-approved when the request it makes once they resolve inside the root is allowed without asking anyone; that request is then the call’s own, so no later decision can refuse what the pre-approval allowed. A pre-approved call builds its operation once and sends it in a contained call, which resolves its paths: when every one resolves inside the authorization root, the target performs the operation on their resolutions in that call; otherwise it holds the operation and answers with the resolution, the call is approved as any other, and the held operation then performs on that resolution, or is cancelled. Containment is the one decision a worker makes for the host, read from the resolution it already computes, so a link or .. that leaves the root holds the operation. A call stopped while its operation may be performing ends with its effects unknown, unless it may only read.

Capability::Host(HostCapability) extends the built-in permission vocabulary with namespaced namespace.name identifiers a host declares on its builder; ceilings, modes, native tools and MCP requirements may only use declared names, and every authorization gate treats them like built-ins. The journal records capability names as data, so another host’s names read back without its declarations. Session database formats are clean breaks without migration.

The executor coordinates host-owned jobs and their persistence. A job’s lifecycle (queued, awaiting approval, running, waiting for input, finished), its startup lease and its single completion owner live in job/lifecycle.rs and job/supervisor.rs. A tool may declare a source argument, a TargetedPath on any target: the executor selects its location like a tool target, authorizes the read with the call, and opens it for the call’s context. A host tool whose input places its job elsewhere, such as a child agent’s target and workspace, has that location selected before the job exists, so every view of the job reports it; a local workspace is resolved and authorized there as one of the call’s paths, while a remote one is resolved by its worker as the job’s connection opens, and refused there when it cannot be used. A job shows that workspace as written, .. kept and no link followed, so no view of it reveals or misstates what lies outside; the job runs where it resolves. Workers run operations only: the host keeps tools, job ownership, policy decisions and saved output, so remote workers never become second agent runtimes. See remote transport and shims for connections, streaming and shutdown.

Tool failures are structured diagnostics: a typed cause plus the operation, subject, site, known local effects, and, as a separate fact, whether a sent request may have executed, which only the sender raises, as it sends. Operations fail with the worker’s facts where they fail, naming what only they know; tools annotate the rest, such as which argument failed, and skyhook_tools::diagnostic owns the one renderer. Facts chosen nearest the failure win, and each boundary (planning, dispatch, rendering) only fills what is still unset: a failure carries a partial context in process and is resolved once, when it is persisted or rendered. A target that could not be reached, or whose connection failed under a call, fails with a connection cause that names what kept it: SSH, WinRM, the protocol, deployment, a setting the worker refused, a password the configuration no longer gives, or the startup. The remote client keeps that fault typed beside the facts its call reports until the call ends. A failure an origin reports names the machine it happened on. Diagnostics are persisted with the job and rendered per viewer; saved job output describes what a viewer sees.

Saved output and model-visible presentation are separate. A finished result is saved once, as a compact document with its large parts in captures (job/output/saved.rs), and read back through bounded streaming readers, which the tools crate’s JSON detection builds (skyhook_tools::output::json). The large parts are written before the finish, staged: no reader lists them until the finish that references them commits, so that transaction stays small whatever the result’s size. A finish that prepares its output again, as a stale finish retries, replaces what it staged before at the same field, and opening a session removes those a finish never committed. A capture’s rows hold at most 4 MiB. Past that the bytes are in a file and the capture names it (session::db::output::CaptureBytes): one the session moved its rows to in the session host’s spill directory, one a command’s target wrote its whole stream to, or a file a read named. The first is read by the same reader as rows, and one that fails its reader is that field’s loss alone: the snapshot marks the field unreadable and what it was showing is made again (job::output::Saved::reading). The other two are on the job’s target, where job/output/files.rs reads them through the read operation: a page from its first line, and whole, installed as the field’s value, for a read that needs the field whole. The call that reads carries its reach to that target (job::output::Reach): the executor’s connects as any call does and authorizes a file a read named as a read of it; a stream the target wrote is the session’s own, read as its database is. A run that keeps a file on its target records the route its connection was admitted along, each target as a row of its journaled revision (job_output_route), and the spill files that target created for its result (job_output_spill), in one step of the session core before its output is saved (SessionStore::keep). A capture’s file carries that route (session::TargetFile) and is reached only along the same one; a spill file is the session’s own to read (session::OwnSpills, which opening a session loads) while its route stands. A saved output is resolved on one of the session’s readers and a target’s file is read only once that reader is let go, so a target that is slow to answer delays no other read. Host inspection tells where a field’s bytes are (job::FieldFile). Spill files are outside the session directory. A spill that cannot be kept is a typed failure of the call or job that needed it (skyhook_worker::fs::spill::SpillError). JavaScript receives complete results, while the journal retains the exact previews delivered to the model. Saved job output documents the user-facing limits.

How a preview shows each field is saved with the result (job/output/projection.rs): what its schema declares, complete fields and text keeping both ends, joined with what its producer marks. Whether a value is shortened again follows one rule for every tool: a presentation already is marked complete at its root; anything else is raw data, previewed by its fields’ presentations. A jobs listing, and a view fitted for a model or paging a field, are presentations. A script’s whole read of a result is raw data: its view carries that result’s saved presentations, while its own fields stay whole as the view’s schema declares. Scripts receive each response with the presentations its job saved, and these follow the values a script returns, so a view returned by a script, or read again as the jobs call’s own saved output, shows its result as a direct read would.

The script tool’s runtime lives in tool/javascript. Each script runs in a fresh V8 isolate on a thread of its own, started from a per-process snapshot of the embedded runtime modules (tool/javascript/js), so one snapshot serves every mode: the runtime’s install receives the mode’s tools. The isolate’s heap and its ArrayBuffer storage are each limited to 512 MiB; reaching the heap limit ends the script, and neither limit caps Rust-side bridge or job memory. engine.rs owns the V8 platform, the snapshot and the memory limits, isolate.rs the script’s isolate and event loop, and runtime.rs supplies its tool calls and console. The web globals rest on host functions: V8’s own UTF-8 and serialization for text coding and structuredClone, and the url crate’s WHATWG parser and form encoding for URL and URLSearchParams. The submitted body is compiled as its own module, so failure reports keep only its frames. Calls the script left unawaited are aborted when it ends; on cancellation, the calls in flight are driven to their end first. One conversion turns tool arguments and returned values into JSON at the host boundary (bridge.rs), where the host fills a response’s declared absent fields with null from the schema its job stores.

Child messages and job notifications commit to the parent’s history together with their acknowledgment, as a model call’s result does with the outcome it reports, so an event that never reaches committed history stays pending for delivery (agent/wait/delivery.rs, job/delivery.rs). A host’s events join only the delivery before a request, read under the turn’s cancellation: the agent’s cursor is journal state, a pointer from agent_state to the message holding its latest host event, moved by that commit, and nothing that decides whether an agent has work to take or a wait has resolved reads them. A foreground child’s replies stay queued for its call instead. Its completed result saves them: the finish drops them from the queue, and journals only while the replies queued are those its prepared output saves, preparing the output again otherwise (job/lifecycle.rs). A call let go of before it returns, or returning anything else, leaves them to delivery (job/entry.rs). A question is the owner’s, whoever waits on the job: while it is pending, it and the replies queued before it are pending for the owner together, and a foreground wait keeps waiting for the outcome. Folding the ask record also releases the model-level foreground call blocked on the job, the job’s own or that of the script whose calls wait on it, which then returns the job unfinished, presenting and acknowledging neither (job/persistence.rs, job/delivery.rs). A turn moves its response’s blocked foreground calls aside the same way (agent/foreground.rs): past the event threshold, once its agent has input or a background job’s outcome or question pending, or at the limit, it journals their release in one commit whose live change marks each job with what moved it, which the call’s returned view reports (JobManager::move_calls). A child’s final answer stays its job’s result until its owner acknowledges that completion; a restart before then supersedes the result and queues the answer as a reply (job/entry.rs), which a read of the superseded result, such as a script’s own call, acknowledges in place of the restarted invocation’s delivery. A job’s read holds the result in the change that captures it, before its output is collected: until that job ends, the reply is held from its owner’s notifications, and a notification read before a hold landed commits nothing. What a waiting job asks is part of its phase, each question by the ask job waiting for its answer: an ask’s end retires its question in the same commit, which asks the rest again or lets the job run on, and a reply is accepted into each ask’s mailbox at most once, so a repeated reply answers nothing again (job/questions.rs).

Process tools leave stdin unconnected, capture stdout and stderr, and detach from the controlling terminal (the worker’s local/exec.rs). A program that prompts fails unless the environment Skyhook inherited provides a way to answer; only Skyhook’s own SSH processes get a terminal, which types configured target passwords; see authentication.

Session core and transaction boundaries

Each durable session is one SQLite database, session.db, holding the append-only, normalized event ledger beside its blobs, saved job results and captures of at most 4 MiB each (a larger field is a spill file, which a session never needs to open, resume or replay); schema/src/session.sql documents the tables and the few JSON columns, and sets the format the journal’s identity carries. The schema proc macro runs that DDL in an in-memory database at compile time and embeds the serialized result: creating a session writes those bytes as its file (or copies them into memory), creates any product tables over them, and only fills the dictionaries, whose rows come from Rust enums. Closing any descriptor of a file releases every POSIX lock the process holds on it, SQLite’s included, so one registry under one lock (skyhook_worker::fs::live) records both each database the process has open (its file, -wal, -shm and -journal, by identity and by name) and every handle another in-process opener holds (fs::OpenFile, by identity). An opener refuses a live database’s file and holds the file its name reaches under the lock, then opens outside it, so concurrent opens never queue on each other’s syscalls; a descriptor that reached another file by then is decided about under the lock, and one of a live database’s is parked on that database until its last connection closes. A database registers before SQLite opens it, waiting at most the busy timeout for handles on its files to close; replacing or removing a file decides and acts under the lock, and removing a tree reserves it under the lock, so no database registers inside it, then removes it outside; walks pass over live files. Each open session has one core thread (session/core/mod.rs) that owns the only writer and the one in-memory fold of what live work reads of the journal (each agent’s newest request, the resident jobs and agents, todos and targets, the next sequence and the last activity, never the records themselves) and, never journaled, each running agent’s turn and inbox, the question asks each issuer is batching, and every registered wait.

Commands run on that thread in order. Each plans against the current state: a Plan names the entries it journals, the output it saves with them, and what it changes live. The writer journals them in one transaction. In that transaction it folds them into the state, refusing a transition the state does not admit, and writes the current-state rows of the jobs, requests and agents they changed; the ledger stays the only source of history and exports. No reader sees the state ahead of the journal or a record the state does not reflect, and a rule a concurrent change can break, such as the stale-todos check on a compaction checkpoint, is decided against the state it commits to.

The commands already queued when the core takes one run with it as a group, and one sync of the write-ahead log after the last makes the group durable; the core never waits for more to arrive. Each command still plans against the state the ones before it leave and commits its own transaction, so a refused plan leaves the rest of the group as it would be without it. What a command leaves to happen once it commits, such as its reply, the waits it resolves and its deferred effects, runs after the sync: until then the state and observers may reflect a commit, but nothing the session does in response has happened. A failed sync stops the session; each command of the group that committed, and any drain or close behind it, reports that failure. A stopped session holds what reopening it reads, so a transaction that failed leaves nothing of its fold. A committed record is shared, not copied, by the observation stream, the agent contexts and every observer, and an agent’s context is fed only the records of its own agent that its history folds.

One user-visible operation is one plan. A submission is admitted when its messages commit, a queued batch commits with its model and mode selection in one transaction, and the commit that ends a turn also closes the calls it left without results and journals the failure that ended it, right ahead of the turn’s end, which is how the request ledger tells a turn that failed on a request from one that failed before any. The core’s turn state is the single authority for model work: an interrupt changes it in the core, and every commit that starts work (a request, a model attempt, a response, a delivery, queued input, a compaction, or a job a model call starts) is refused unless the agent’s turn is busy. A turn’s cancellation token decides nothing; it only aborts the I/O in flight, such as a provider stream or a process.

A registered wait declares the agents and jobs it reads, and decides from the state alone before it takes anything. A change decides again only the waits whose agents or jobs it touched, repeating while what they take touches more, and every wait on a session-wide change (phase, flow, activation or a resume withdrawal); each agent’s activity is likewise read again only when the change touched that agent. A wait nobody awaits stands until it decides: a question batch is presented by one once none of its issuer’s other asks is left to join it or end, so dropping any one ask presents the rest regardless.

Resident set

The core holds only the resident set, so what it holds and what a change, a request or a tool call reads of it are bounded by live work, not by the session’s history. A job is resident while it is unfinished or interrupted, has a delivery or a reply pending, is a child that input can resume, or launched a resident job; the resident jobs are indexed by owner and by parent. A job let go of keeps a cancellation requested of it that the journal does not record for the rest of the session, so a job created under it is cancelled whenever it is made; a reopen forgets it. Every agent’s state is held; its contract and the children it has started are held while it is the root or its loop runs, and read from the records its state names as its loop starts. A job that leaves the set is let go with its indexes and handles: a job holds its input mailbox and cancellation token only while it can still run, and what runs an agent job again is built only as it restarts. Whatever addresses a job by id reads it as the core last held it, from its status row, which is final once the core lets the job go. Opening a session reads the state rows and a few counts by index; nothing is folded from history.

Parking

A child’s loop runs only while it has something to do or something to deliver to. Once its invocation has resolved, its turn is idle or failed with nothing queued or held, it owns no live, interrupted or pending job and none of its children runs, it parks in the change that finds it so. The next change that needs it (input to its job, a continue that restarts it, or the restart of a job it owns) starts its loop again, and that of each parked child above it, in that same change, so an agent never runs two loops and none parks between that check and the work it was started for. It starts as its journal leaves it: under the contract it ran under, with the children it started, stopped on its failure if its last turn failed, and with a fresh context opened at a request boundary under the same identity, so continue and input go on as they would have had it never parked. A child whose job was cancelled, or whose cancellation was requested, is not started again, and its name stays its owner’s. A cancellation requested of a finished child’s job itself (the jobs tool or the host’s cancel_job) is journaled, so it holds after a reopen too; a reopen forgets one that an interrupt, an abandonment or a close requested of a finished descendant.

Log and reads

The ledger is only appended to: the store’s writer offers no update or delete of a ledger or dictionary row. A write the journal cannot take stops the session as a crash does. Commits do not sync the log; the core syncs it once per group of commands. SQLite’s automatic checkpoint copies the log into the database as it grows, and the last connection to close copies and removes it. A read holds its snapshot for that read alone, so the log stays bounded by what commits during the longest read. A writer lock excludes competing session owners, not read-only inspection.

Reads that do not belong to the core, such as job output, the blobs a request sends, an agent’s history, history pages, request reconstruction, the title, the session list, statistics and exports, run on read-only connections, each in one snapshot, so they never wait on the writer’s transactions; a session held in memory reads through its writer’s connection instead. A session keeps a fixed few read connections, each on a thread of its own, and a read waits for one rather than opening another. Reads are async, and one waiting for a connection holds no thread. The core reads on a connection of its own, so its reads never wait behind other reads. The pool and the turn it takes are db primitives; the journal and the security store each supply how their readers open. The library turns SQLite’s allocation statistics off for the process before its first connection: counting takes one global mutex, which would serialise readers that otherwise run in parallel.

Observation

Observation is a host view of durable records, the jobs the session state folds from them, and live state; it is not a second source of conversation history or job state. An observation copies only what the core holds live: the phase, each agent’s newest request and activity, the resident jobs, the responses of each agent’s latest turn, context gauges, and each agent’s transcript length and usage. It costs the same however long the session is, and since the core reports the jobs it lets go of, an observer holds what the core holds. History is read in pages on read-only snapshots, by index. A page reads at least what the observation applied, and every later record is an update at the next ordinal of its agent, so a host placing updates by ordinal misses nothing and repeats nothing; a lagging host observes again and reads its pages again, never the history. Live updates the journal does not carry, such as streamed deltas and capture notices, never wait on the core’s commands, its state lock or the database, only on the observation’s lock, which a commit takes after COMMIT to fold its records into the views and publish them, and a subscriber holds while it copies the views. A capture write notifies observers of its run once, then again only after something reads that run’s output or the run finishes; a streamed delta likewise notifies observers of its response once, then again only after something reads that response or a record of its agent applies, or a new observation copies the views. A burst of writes or deltas costs a bounded number of updates, so a token stream alone never makes an observer lag.

Source: agent runtime, providers, host tools, target tools, and sessions.

Terminal history window

The terminal shows the viewed agent’s tab from a window of its history, so drawing reads only memory and what the terminal holds is bounded by the view, not by the history. Each tab is one run of a list loaded a page at a time from either end: the conversation’s entries by ordinal, keeping only the kinds it can show, so a run of records that never show costs reads but nothing held, each page with the facts presenting it reads, which later updates extend, so an entry shows the same whatever else is loaded; requests, an owner’s jobs, and a card’s children. Loads run off the event loop, at most one in flight above the view and one below, and land as work; what is not loaded past either end of the run shows as a loading row. The conversation’s scrollbar spans the transcript’s records, each entry’s rows its own record and records that show nothing none, so what loads or is let go moves it only when a load finds an end of the transcript, which the entry nearest that end then reaches; a list’s spans the rows it loaded. What streams after the last record spans one record more, as its reply will once committed, so the thumb moves through a long reply as it streams. Rows that show no record lie where the next one starts, and a position there finds the first of them, so the start of the track shows what precedes the first entry. The track maps a position to the record there, whatever the view shows. A position beyond the run (the scrollbar, Home, End) reads there instead, at once, in a window of its own: what the one it replaces had in flight lands unused, and until the position is laid out, scrolling moves it rather than the rows shown. A reading position is an anchor (an entry key and rows into it, and the tab’s own entry it belongs to: a transcript entry, a request or a root job, or the start or end where it belongs to none), never a row, so it is found again whatever a new page, width or recovered observation lays out; the children still to read where it belongs load whatever their distance, and it is given up only once a page read where it lies shows it is not there. Entries beyond a fixed budget on either side of those the view needs (what it shows and those up to the next entry each way that shows, so scrolling reaches the next row) are let go with what presenting them read, and with the outputs of the cards they show. A job the session lets go of, and a request a newer one replaces, keep the view they were left with while the window shows them, whatever order that and the pages reading them arrive in. A frame lays out only what the window holds, and the sidebar asks the session what the viewed agent holds only once an agent’s start or mode change, or the chosen agent or mode, changes it, so a frame never waits on a commit. A session out of view keeps only its live part and its agents’ summaries.

Terminal transcript selection

The terminal lays out transcript entries into rows. Each row’s layout separates what it paints as decoration (wrap continuations, code padding, disclosure glyphs, spinner gutters, diff markers, table borders and padding) from the source text it shows. A row’s source is described by spans: which logical line they belong to, which bytes of that line’s text, and which bytes of the row show them. A table cell is a logical line of its own, so the fragments of a wrapped cell share one line. Spans also keep the source that a row shows differently or not at all, such as a cell’s trimmed separators, a replaced wide grapheme, or an empty cell.

A selection is anchored to source, not to rows: each end is an entry key, a logical line identity within that entry, and a byte in that line’s text. Line identities come from the source and do not depend on width, but they are identities only. A Markdown line is identified by its source position; within a tool document, also by all the text before its Markdown block. A tool document or plain line after an entry’s header is identified by all the text before it, so inserting a line gives every line below it a new identity; the header’s own text is the entry’s state, so it takes no part. Document order is the order in which the layout first shows each line, which reads a table’s cells row by row even when their fragments interleave on screen. Endpoints, copying and highlighting all read the same spans. Copying joins each selected line’s parts in that order, one line per table cell. Each layout of an entry orders its lines once, when a selection first needs them, so dragging across a long entry reads only the rows of the lines it selects.

Whenever entries are laid out again (new text, a reply settling, a resize), the selection is re-resolved against the new rows. It survives only if its endpoints still exist and the text they select is unchanged; otherwise it is dropped rather than moved to other text.

Embedding

The skyhook crate is the Rust library. Hosts supply configuration, a workspace, model selection, and interaction handlers rather than depending on terminal UI state. See library architecture for responsibility boundaries and the internal request lifecycle. Session and agent identifiers are skyhook::identity. The tools’ vocabulary, such as diagnostics, target names and execution locations, comes from skyhook-tools, types the library shares with the remote shim, such as operations, credentials and job identifiers, from skyhook-worker, and generic primitives, such as enums::NamedEnum and bounded::Bounded, from skyhook-base; a host depends on them beside skyhook.

Configuration and model hints

skyhook::config::Config is the configuration: public sections a host parses or builds, then seals with into_runtime(). The library reads no configuration file; where a configuration comes from is the host’s own.

  • Config::from_yaml(text) parses one document the host holds and refuses every bad value in it, each at its line and column. Each section also parses on its own (RawProviderConfig, Mode, TargetConfig, McpServerConfig) with skyhook::yaml::parse.
  • A host that layers or merges files reads each with skyhook::yaml::read(text, file) into a tree of nodes that remember where they were written, merges the trees, and decodes the result with skyhook::config::process, which reports each refusal at the file, line and column of the value it refuses. Its check is the host’s: Config::refusals is what from_yaml checks, and takes the host capabilities a product declares.
  • Config::builder() builds one in code from Config::default(), what an empty document configures. It declares the named entries (provider, mode, target) and selects among them (default_model, default_mode); build() refuses what sealing would. Every other setting (mcp, max_child_depth) is a public field.
  • Config::validate() runs the same checks on a configuration a host edited or merged.

The mode and model new sessions start with are checked when the configuration is sealed, not when a document is parsed, so a host may declare the mode or configure the model a document names before it seals.

use skyhook::config::{Config, mode::Mode};
use skyhook::provider::dialect::RawProviderConfig;
use skyhook::yaml::parse;

let local: RawProviderConfig = parse(
    "{dialect: compatible, codec: chat_completions, base_url: 'http://127.0.0.1:8080/v1', \
     models: {main: {model: served-name, max_context: 128000, max_output: 4096}}}",
)?;
let review: Mode = parse("{capabilities: [read]}")?;
let mut config = Config::builder()
    .provider("local".parse()?, local)
    .mode("review".parse()?, review)
    .default_model("local/main".parse()?)
    .build()?;
config.max_child_depth = 2;
let runtime = config.into_runtime()?;

A provider entry’s public home (ConfigHome) says where it was defined: File(path) keeps its Skyhook-managed credentials in credentials/ beside that file and names the file in login hints; Unfiled, what parsing and building leave, keeps them in the user’s Skyhook configuration directory. An MCP server’s relative cwd resolves against the directory of the file its node was read from, and stays as written for a document read without one.

Before sealing a Config, hosts can edit a configured model’s profile through model_profile_mut(&ModelRef), which returns ConfigError::Model for an unknown provider or model. Clearing a hint removes that model from the choices offered to agents, not from the configured catalog. Hosts can also assign the public default_model: Option<ModelRef> before calling into_runtime(), which validates the selection. Edits affect the new runtime generation only, not previously sealed configurations.

Products and launching their sessions

A product is a library on skyhook alone. It implements skyhook::product::Product with its own Options type for what a launch takes beside the configuration, any settings of its own included as the host parsed them, and an Identity: the HostName its sessions are tagged with, the schema of those sessions (see below), display name, a RootMode (Switchable, or Fixed to keep the root in the configured default mode), and the HostCapabilityDeclarations its modes grant, which every session the product opens declares, another host’s included. skyhook::product::Skyhook is the plain coding-agent product. Any host can serve it.

A front end opens a product’s sessions through skyhook::launch:

  • launch::configure(&product, options, HostConfig, workspace, &ExecutionRequest, Attendance) takes the configuration the front end read or built (launch::config::HostConfig: a Config with the launch’s approve_all, which also deserializes from a document carrying that key), applies the product’s edit and canonicalizes the workspace. The request (launch::request::ExecutionRequest) names a session to resume and an explicit root model. The returned host’s warnings are what the product said of its configuration, for the front end to show.
  • launch::startup::prepare(host, &request, &PermissionRequest, remembered, catalog) admits the configuration and selects the root’s model and mode: the explicit ones, else the front end’s remembered choices while configured, else the configured defaults. PermissionRequest is a mode or a batch job’s exact capabilities; catalog is the shim catalog remote targets bootstrap with. Persisting the remembered choices is the front end’s own.
  • Launch::create(Opening, &Interface) creates or resumes a session in the workspace’s .skyhook/sessions, with the product’s factory for its own sessions and view-only for another host’s. Interface::Batch denies whatever needs approval; Interface::Attended carries a skyhook::interaction::UiInteraction, whose receiver gets each approval, question batch and rename as a Prompt with a one-shot reply.
  • skyhook::attachment::read_attachment reads a workspace file as a prompt attachment, and SessionStore::read_each reads every saved session of a workspace a few at a time, for a session list.

The skyhook and skyhook-security binaries are thin front ends over these, in the skyhook-apps package; product options join their shared command line at the root, under batch and for dump config.

The extension points are:

  • Product::configure(&self, &mut Config, Options, SessionContext<'_>).await returns Configured: the product’s warnings of the configuration it was handed, each complete as a host shows it, and an Arc<dyn SessionFactory>. It edits the configuration before runtime admission (product settings, model defaults, modes, MCP entries); a product’s own settings arrive parsed in its Options. A front end that inspects configuration calls it directly and serializes the result, as dump config does; a session runs with it.
  • SessionFactory::form(&self, SessionContext<'_>) -> Option<ScopeForm> is the scope a new session’s draft is written with (skyhook::product::form): choice and integer fields with defaults, and a message used when the draft is submitted empty. The terminal shows it at the top of the root’s conversation beside the composer, sends its values with the first message and freezes it once the session starts; a failed start leaves it editable. The values reach prepare in the context’s Opening::New. Batch runs pass no form.
  • SessionFactory::prepare(&self, HarnessBuilder, SessionContext<'_>) returns HookFuture<'_, PreparedSession>: the customized builder and an Arc<dyn SessionExtension>. SessionContext holds the canonical workspace, its attendance (Attended at a terminal, Batch with nobody to ask), and its Opening: New with the form’s answers, if any, or Resume(SessionId). A draft calls it on first submission; the host tags the builder with the product’s host name and schema and calls it only for the product’s own sessions, so a foreign session opens view-only with no extension.
  • SessionExtension::opened(&self, &SessionHandle, SessionContext<'_>) -> HookFuture<'_, ()> runs before the first input; associate a new session with its product resources here, and finish a setup an interruption left undone. A reopened session may only be viewed, so change nothing else. Failure shuts the session down.
  • SessionExtension::scope(&self, &SessionHandle) -> HookFuture<'_, Option<ScopeForm>> is the scope a session runs under in this launch, as the factory’s form holding those values, including what a resume hook changes once its work begins. The terminal reads it after opened for a session it opens rather than starts from a draft (a resume, or a switch to another session) and shows it frozen at the top of the root’s conversation. The default is none.
  • What this launch changes about a reopened session’s work (as the security product applies its --workers) goes in a skyhook::agent::ResumeHook registered on the prepared builder with HarnessBuilder::resume_hook; the library runs it before that session’s first work (see Interruption, continuation, and shutdown).

Hooks before opened create no sessions and write nothing to stdout; a batch run prints the session ID first. A product that keeps its own data in each session declares it as Identity::schema, a session::Schema the host passes to HarnessBuilder::session_schema: the harness creates every session from it and checks the tables’ format on every one of its own it reopens. Schema::extended(image, seed) takes the tables as a ProductImage and a function that fills their dictionaries in a new session (Seeding::Fill) and checks them on an open (Seeding::Check). ProductImage::layered(ddl, format) runs the product’s DDL over the journal’s image as each session is created and records the format. A plain host passes Schema::JOURNAL. SessionStore::summary, given the host and its schema, refuses one of the host’s own sessions that check would refuse, so the session switcher leaves it out and --resume refuses it before prepare, as for an earlier session format; other hosts’ sessions are still listed, view-only. The harness hands host state and the resume hook the tables as an ExtensionDb on the session’s own writer and read pool; tools reach them through ToolContext::extension(), and the extension’s terminal hooks through the session (SessionStore::extension()); a write whose commit failed reports Unconfirmed, since it may have committed. Another host’s harness opens such a session without them; ExtensionDb::inspect reads them read-only without opening it. Files of the product’s own go in subdirectories of the session directory, whose work takes turns through ExtensionDb::filing as the tables’ writers do through writing. HookFuture is a boxed Send future returning Result<T, skyhook::product::Error>.

Per-session views and actions

SessionExtension::views() returns the stable titles of the session’s read-only views. In the terminal they are tabs after Conversation, Requests, and Jobs, sharing their keyboard cycling and clickable headers, and each takes the frame below the tab strip, keeping only the footer, any prompt awaiting an answer and the live agents: a column beside the page on a terminal at least 100 columns wide, the usual band below it on a narrower one.

refresh(view, SessionHandle, Disclosed) -> HookFuture<'_, Arc<page::Page>> loads views()[view] off the UI thread, as the extension’s own session sees it; returning the same Arc for an unchanged page spares the host laying it out again. A Page is a list of typed blocks: Facts (label and value pairs), a Pipeline of stages, Panels of labelled values and meters, and Sections, collapsible tables of records that each open to their detail. Cells carry a Tone and a Weight, not a colour or a font. The host lays the page out with its own theme, reflowing panels and dropping section columns by priority as the width shrinks, and owns disclosure and scrolling, so a product needs no terminal code. Disclosed says which sections are open, how many of their records to supply (Disclosed::PAGE at a time), and which records are open, each with how many of its detail’s continued entries to supply, likewise a page at a time: supply records and detail only for those, and mark a detail that has more entries than it shows. The host reads the shown view about once a second and again at once when the viewer opens or closes something. Futures must be cancellation-safe. Sanitize untrusted text before returning it.

Foreign sessions remain view-only: the host hides the composer and title editing and withholds the commands that would write, while inspection, transcript copy and export remain available. SessionHandle::host() identifies the recorded origin and is_view_only() reports whether this harness may activate it; library activation checks remain authoritative.

Constructing a harness and session

The configuration-backed entry point is:

let model = config.into_runtime()?.select_model(&name)?;
let harness = HarnessBuilder::configured(&model, workspace, host)?
    .build()
    .await?;
let session = harness.new_session().await?;

into_runtime() admits an immutable configuration generation, including any edits the host made to the Config; select_model(&name) binds the host’s explicit choice, a ModelRef parsed from provider/model, to that generation. Admission and selection precede provider construction, credential lookup, and workspace access. HarnessBuilder::configured(&model, workspace, host) returns a builder for the application host serving that configuration, which can be customized before build().await; hosts supplying their own providers and model profiles can instead start with HarnessBuilder::new(workspace, host). Skills are a builder input (skills(HostSkills)): the harness discovers nothing on its own, so an embedder decides whether HostSkills::discover runs. A provider that needs a login reports it as a typed LoginRequired whose remedy names the host’s own auth login command (host, or the program passed to Config::login), including in a session’s request errors; a LoginFlow signs in through a host-supplied LoginPresenter rather than the terminal.

The configuration-backed builder carries the configured modes and selects the configured default. mode(name) selects another, and capabilities(set) limits what modes can grant; build() rejects a selected mode the modes do not declare, whichever was set first. A builder without modes gives the root agent that capability set directly, and no mode applies. SessionHandle::selection(model, mode) issues the Selection a submitted message or a continued turn carries, rejecting a provider/model or mode the session does not have; omitted selections retain the active model and mode. A mode change applies to the root agent from the boundary that consumes it, not retroactively to children it already started. A session runs the harness’s modes and capability ceiling, whatever it ran under before. A reopened session reports modes the configuration redefined or removed in warnings() and changes nothing while viewed, nor when calls such as rename, record_status or cancel_job activate it. The next work that runs the root (a prompt, continue, job delivery or run_script) decides its mode once: the selected one, else its own as configured now, or the default mode once its own is gone (without a default mode, it keeps running its own edition). A message’s ModelChanged and ModeChanged are journaled in one transaction with its MessageCommitted; a script’s precede the script. Each ModeChanged or AgentStarted whose definition differs from that mode’s latest journaled one records a new edition, which the journal keeps for auditing. SessionHandle::changes_mode(mode) reports whether the root’s next message in mode would change what it runs.

Each SessionEvent::TitleSet records its TitleSource: Prompt, User or Generated. SessionHandle::set_title(title) gives an automatic title to a session that has neither a title nor a first prompt to take one from, and leaves any other alone. run_script titles nothing: the terminal titles a session its script starts with the script’s path, and a headless --script leaves the session untitled. rename(Some(title)) sets the user’s title, and rename(None) journals a TitleCleared that returns the session to its automatic title. title().await reads the title the session list shows, as a SessionTitle with its text and TitleSource: the user’s newest title unless cleared since, otherwise the newest Prompt or Generated title, otherwise the first text the user sent the root agent, as a Prompt title.

Before building, hosts can supply policy and question handlers, additional tools, and an embedded shim catalog. A Policy answers Approval::Decided for what it settles by itself and Approval::Ask for what it asks someone, asking nothing until that future is polled. A call that may not ask anyone, because a path it names outside the workspace does not exist, drops an Ask unpolled and is refused with PolicyDecision::refused(), the reason a person’s denial should carry so the two cannot be told apart. A remote call whose paths would need nothing of their own inside the workspace is requested before they resolve, as it would be once they resolve inside it, without asking anyone: a Decided allowance starts its operation in the flight that resolves them, saving a round trip, and should they resolve outside, the call is requested again with what they need. Core Config loading does not load .env; environment setup belongs to the host (the CLI performs its own startup loading).

The builder defaults to <workspace>/.skyhook/sessions. HarnessBuilder::session_root is passed through unchanged: a relative path is relative to the process working directory, not the workspace.

Persona and prompt templates

A host keeps its persona and mode instructions as embedded Tera templates, which the library renders for each agent. skyhook::templates! embeds each named file from the invoking crate’s src/prompts, as a Source::Template, rendered by Tera, or a Source::Verbatim, such as a script shown to the model, included as written and never parsed. A file’s final newline is not part of it, so an include can sit mid-line. Templates::with(sources, &sample) registers them beside the library’s templates, which they can include by name, for a serializable section type H.

Prompts::host(&templates, &section, persona) and HarnessBuilder::prompts give a session the host’s section, fixed for the session, and its persona template, placed in every agent’s system prompt after the built-in role text and before the runtime’s workspace, tool, capability and mode instructions. Templates are named by a TemplateName, the name they are registered under. A mode whose instructions is Instructions::Template(name) is told that template; configuration spells only text, and dump config leaves a template out. Each template renders from the agent’s context (role, available_depth, capabilities, mode, context, job_view) with the section’s fields as top-level names, when the agent’s contract is fixed: Prompts::edition renders a mode’s instructions for an agent entering it.

The journal keeps what rendered: a mode’s edition records its instructions’ text, and an agent’s prompt as sent. A resumed agent keeps its recorded prompt until a mode change rebuilds it, and a reopened root whose mode now renders otherwise warns of a changed mode. One whose mode no longer renders for it opens all the same, warning with the error, which the work that next runs the root in that mode returns.

Registration refuses a template that reads a top-level name its context does not define, counting the names its includes read, so a misspelled setting fails at registration rather than rendering as false. Names nested in a value (capabilities.agents) are not checked.

Host state

HarnessBuilder::host_state(Arc<dyn HostState>) lets the host add its own section to an agent’s runtime state. The harness asks for the section before each request and before a compaction summary, places it inside the state block beside the date, live jobs and todos, and journals it with the state. It is asked with the host’s tables in the session (its session_schema, so only the host’s own sessions have a section) and the agent, so it can read what the host keeps in the session and answer per agent. The host renders the text itself; None adds nothing to that request. Use it for facts an agent needs current, such as a workflow’s identity, policy and progress, rather than prefixing them to the user’s first message. Keep it to the agents that act on it: the state changes between requests, so every character of it is input a provider’s prompt cache cannot reuse.

HostState::events gives an agent news from the host’s own ordered log instead: what it holds for the agent after since, the HostCursor the agent’s last host event went through, or from its start. A cursor is any non-negative i64 position (HostCursor::try_from), stored as it is. The harness asks only as a request is about to be made, so a host event never starts a turn, reopens an answered one, keeps an invocation open or ends a wait: it joins the job events delivered with that request, as {"kind":"host", …view} with the view the host built (HostView::try_from an object naming no kind of its own), and commits in one transaction with its cursor. Each event is given once, across retries, compaction and reopening; an interrupt during the read commits nothing, and a failed read fails the request (HarnessError::HostEvents). The default gives none.

Session origin and host capabilities

HarnessBuilder::new(workspace, host) names the application creating a session. HostName (in skyhook::identity) is nonblank; choose a stable tag such as the binary’s name, not a session title or mode. Tags do not change the session root: hosts share <workspace>/.skyhook/sessions unless they explicitly override it.

SessionHandle::host() and SessionStore::host() expose the persisted origin; SessionSummary::host, SessionStats::host, and SessionEvent::SessionStarted::host retain it for listing, accounting, and journal exports. resume_session may open another host’s session for inspection; SessionHandle::is_view_only() identifies that case, and every call that would change the session fails with HarnessError::HostMismatch { session, host }. Host tags prevent accidental cross-application activation, not access by other processes with filesystem write permission.

Declare application-specific capabilities with HarnessBuilder::host_capabilities. Declaration alone does not grant authority: include Capability::Host(name) in the ceiling and the modes that need it, just like built-ins.

use skyhook::tool::policy::{Capability, HostCapability, HostCapabilityDeclaration};

let verdict: HostCapability = "security.verdict".parse()?;
let builder = builder.host_capabilities([HostCapabilityDeclaration {
    name: verdict.clone(),
    title: "Decide verdicts",
}]);
let options = ToolOptions::default().requires(Capability::Host(verdict));

Capability::title names a capability for the user: a built-in label, a host capability’s declared title, or the name of one the given declarations leave out, such as another host’s. The terminal shows a product’s capabilities under the titles its Identity declares.

Names have exactly two components, <namespace>.<name>, each starting with a lowercase ASCII letter and continuing with lowercase letters, digits, or underscores. build() rejects undeclared host names in the ceiling, any mode, native tool requirements, or MCP requirements with HarnessError::UndeclaredHostCapability. Host capabilities use the existing mode, ceiling, delegation subset, and tool gates.

Host observation API

SessionHandle::store() is the session’s journal. Its observe() returns an Observation: the session’s live part, an ObservationSnapshot, and a receiver of the updates after it, sharing an atomic revision boundary. It copies only what the session holds live, so it costs the same however long the session is, and a host may call it whenever it needs a fresh start. Its applied() is the newest record the session has applied, without observing. The snapshot holds:

  • applied, the newest record it folds, after which every record arrives as an update, and last_activity, when the newest record that is the session’s activity was journaled.
  • requests, each agent’s newest request, with its lifecycle phase, outcome and usage.
  • jobs, the jobs the session holds: their owner, call arguments, state, failure, current invocation, and when that invocation ran. A job’s update arrives just before the record that moved it. RuntimeEvent::JobsUnheld names the jobs the session let go of, which the snapshot drops; a job’s last update is its final view until a record moves it again.
  • activity, each agent’s current activity, with when its turn began (or, once it is no longer busy, when that turn ended); an agent that stops running, as a parked child does, gets an update with none.
  • views, what the records fold into beside the committed state: responses, the live responses keyed by agent and logical request (their streamed blocks in arrival order, then the authoritative blocks once the response has ended; an agent’s responses are its latest turn’s, and one that settled without committing, failed or interrupted, stays until the agent’s next agent request, as a reopened session also shows it); context, the context gauge, each agent’s occupancy as its last committed response reported it, cleared by a checkpoint; and entries, how many entries each agent’s transcript holds.
  • usage, the usage each agent’s requests reported.

Apply updates in revision order with ObservationSnapshot::apply. Once the session no longer runs (viewed, failed or closed), the snapshot reads every request, response, job and turn it left going as interrupted at its last activity. apply returns what an update changed beyond what it carries: entry, the ordinal its record took in its agent’s transcript (none for a record the snapshot already folds); stopped, the jobs and requests read as interrupted that way, which no update of their own reports; requests, the requests its record changed; superseded, the request of its agent that a newer one replaced, as it left it; fact, what the fold decided of its record that presenting it reads (a session::Fact: the request an assistant message committed under, the message whose call a result answered, or that a failed turn ended on its request’s failure); and unheld, the jobs the session let go of, as they left them.

RuntimeEvent::OutputChanged { job, invocation } reports that a run captured output after its output was last read, by any reader; it carries no output. Read it with inspect_output_with_captures. No further one is posted for that run until its output is read again or the run finishes, whose job update reports the final output.

RuntimeEvent::ResponseChanged { agent, request } reports that a response streamed after it was last read; it carries no deltas. Read the response as it streamed so far with SessionStore::response(agent, request) and replace it in views.responses; a read may run ahead of updates still queued, which fold after it. No further one is posted for that response until it is read again, a record of its agent applies, or a new observation is taken. Live responses are provisional, not additional committed messages. A new attempt of the same logical request resets its live response without removing durable attempt records. On receiver lag, obtain a fresh observation and replace both the snapshot and receiver, then read again the pages on display; continuing with only one can leave a gap or apply stale live state.

Reading history in pages

History is read in pages after observing, through the handle’s store() (a SessionStore) and jobs() (a JobManager), each in one snapshot of the journal. A Page is the first or last of a list, or the entries after or before a key, which it never includes:

  • transcript(agent, page, limit) returns consecutive entries of one agent’s transcript by ordinal, with their facts: what presenting them reads beyond them, as the journal leaves it (the requests they make or answer, each answer’s request and when its turn began, the result of each call they made and the calls that started a job, and the failed turns a request’s failure reports), so a host can show any page on its own. PageFacts::observe folds an update’s record and its fact into them.
  • jobs().page(JobScope::Roots(owner) | JobScope::Children(parent), page, limit) returns an owner’s jobs that do not nest under a parent (JobEnvelope::nests: a job its owner’s script issued), or a parent’s children whoever created them, in id order; jobs().views(ids) returns jobs by id.
  • requests(agent, page, limit) returns an agent’s requests as the journal leaves them.
  • agents() returns every agent the session started as the records that say what a host shows of it (its start, latest model and mode changes, latest todos and the latest record that ended a turn), when the turn that record ended began and ended, when its open turn began, and its owner job, read through through: a summary’s records repeat any update through it.
  • failed_after(agent, record) says whether an agent journaled a failed turn after a record.

A page sees at least what the observation applied. A host places an update’s record at the ordinal apply reports, counted on from the snapshot’s views.entries: a record at an ordinal a page holds is one the page already shows, and every later one is news. Requests and jobs read as the snapshot holds them where it holds them, and as their page read them otherwise; a page in flight when the session lets a job go may have read it before its final view, which apply hands over in unheld, as it hands over a request a newer one replaced in superseded.

Inspection and host records

inspect_output_with_captures is the host inspection API. It does not claim jobs or consume agent notifications. Its files name each file a field of the job is kept in. cancel_job is the separate operation that requests cancellation. warnings and mcp_servers expose startup diagnostics and MCP discovery outcomes without inserting diagnostics into model context or writing directly to a terminal. record_status likewise records host-facing status, not a user message.

TodoItem and TodoStatus are exported by skyhook::session. Hosts projecting checklists from records apply SessionEvent::TodosReplaced and the reconciled todos in SessionEvent::Compaction checkpoints in sequence. Both replace the owning agent’s entire list; child-agent lists remain independent.

Interruption, continuation, and shutdown

prompt and prompt_with_options submit input and wait for its turn. interrupt stops active turns while retaining child jobs for continuation, and returns how many turns and unstarted child agents it stopped, and calls it withdrew from waiting on the resume hook. If it stopped any turn or agent, job deliveries start no turn until continue_turn_with or new input: they stay pending for that request. An interrupt also hands back input no agent has taken yet: a pending prompt returns Interrupted, and each QueuedPromptReceipt from enqueue_prompts resolves Interrupted. Queued prompts are checked when a request boundary takes them, all of them as one batch. A batch the session refuses fails the turn, whose AgentFailed record says why, and waits with it: its receipts stay pending, each prompt can still be withdrawn (QueuedPromptCancellation::is_retained tells such a prompt) until continue_turn_with takes the batch to try again under its selection, together with anything queued since. It checks the batch as a request boundary would before it changes anything, and from then on the root runs it as a turn: a batch those checks or the selection refuse waits again unchanged, together with anything queued meanwhile, and the call returns why. One that an interrupt stops first also waits again unchanged, but the interrupt hands back what was queued meanwhile (Interrupted), as it does any input no turn has taken. An interrupt leaves a waiting batch waiting; a prompt hands it back (Interrupted), and so does an interrupt that overtakes the refusal itself, after which the root rests unless a turn is still open. Closing the session drops it. Explicit job cancellation is non-resumable. continue_turn_with continues failed or interrupted work without duplicating its input and can select a model or mode for the continued root turn. It always restarts the interrupted or failed children first; a root turn or batch refused afterwards returns why without undoing that. Its ContinueOutcome distinguishes a root answer from resumed children and reports whether the selection applied: only a continued root turn applies it, and restarting children does not imply that a waiting or live root also ran. continue_turn uses default options and returns the root answer, or an empty string when there is none.

HarnessBuilder::resume_hook registers a ResumeHook whose resumed(&ExtensionDb) runs once per launch for each of the host’s own sessions with its tables that it reopens, before the first prompt, enqueue_prompts, continue_turn_with or run_script; a session only viewed never runs it, nor does one this launch created. SessionHandle::resume_work runs it on its own, for work the host prepares before sending it. A failure refuses that work with HarnessError::Resume (the first queued prompt says why, the rest of its batch resolve Interrupted), and the next work calls it again. An interrupt withdraws every call still waiting on it, even one whose hook succeeded or failed as the interrupt landed: each returns Interrupted, starts nothing, and counts in what interrupt returns. The interrupt leaves its turns continuable as any interrupt does. A hook the interrupt cut short is dropped and runs again for the next work; one that finished does not. shutdown withdraws the calls waiting on it in the same way and returns only once each call’s hook has ended, so nothing the hook does follows it.

Use Harness::resume_session to reopen durable state. The session opens to view: it journals nothing, and its observation reads it stopped at its last activity, until the first call that changes it, such as a prompt, continue_turn_with, a script, a status, a title or a job cancellation. That call first prepares the root agent; if that fails, for example because its provider cannot open a conversation, the call fails and the session stays viewed. Otherwise the runtime reconciles interrupted work in one transaction before starting agents. Shutting down a viewed session stops nothing and journals nothing: it closes the session, releasing it for another open, and later calls that would change it are refused. Work the previous process left open is recorded as ending when that process last did something, so reopening a session is not activity; record times therefore need not increase with sequence. It opens fresh provider contexts and does not reuse old network resources. A root turn that failed or was interrupted before the session closed can still be continued. A root that closed idle with job deliveries pending resumes interrupted too, so continue_turn_with or new input delivers them. Journaled agent settings remain the baseline, subject to restrictions imposed by current host configuration. A session whose root’s recorded model is no longer configured still opens and activates, and warnings says so: calls that only write, such as a title, a status or a job cancellation, work as usual. Only running the root fails, with HarnessError::UnknownModel and before anything is journaled: a script, or a direct prompt, a continuation or an enqueue_prompts call of which no prompt names a configured model. A selection naming one replaces the model, as does SessionHandle::activate_on, which a viewed session journals in the commit that activates it. Job deliveries that would wake the root before then begin a turn that fails as any failed turn does, journaled, and stay pending for the input that names a model. A child whose own model is gone restarts on the root’s, journaled as a model change; with the root’s gone too, its restart fails alone.

Session database formats are clean breaks (crates/schema/src/session.sql sets the current one, 32): earlier formats are not migrated and cannot be resumed; retain a compatible Skyhook version to inspect them, or start a new session.

Await SessionHandle::shutdown() before releasing the host’s session owner. Shutdown stops runtime producers, drains accepted job and journal work, and closes MCP and remote resources. It interrupts the session as a crash would: child agents still running end interrupted and can be continued once the session is resumed, and other running jobs are cancelled. Once it has begun, new prompts, continue, host scripts, new jobs, and input that would restart a finished job are refused with SessionError::Refused; input to a running job and answers to its questions are still accepted. The journal remains available so the host can append a final status after observing shutdown errors; await that append, then SessionHandle::close(), which releases the session so it can be opened again at once rather than once every handle has dropped; closing a closed session does nothing. Closing also prevents retained output handles from writing to the session; already saved output remains readable. Dropping the last SessionHandle without shutting down closes the session as a crash would leave it and stops its agents and jobs; resuming it settles what was running. A session closed with nothing journaled, such as one whose new_session caller gave up, is removed. A write the session journal cannot take stops the session as a crash would: the call that met it, calls it cut short and every later call return SessionError::JournalFailed with the first cause; shutdown and close report it too and still release the session. Its observation reads the phase as failed and otherwise shows what reopening the session would; an observation attached before then no longer follows it once it folds that phase, and observes again. SessionHandle::phase tells whether the session still runs and journals. A session belongs to the Tokio runtime that created or resumed it: use it only from that runtime, and keep the runtime running until the session is closed.

Embedded shim catalog

The library’s shim catalog is empty by default. Supply remote::EmbeddedShimCatalog through HarnessBuilder::shim_catalog, or to launch::startup::prepare, to enable remote execution. The binaries embed their own catalog; library hosts do not inherit their artifacts.

EmbeddedShimCatalog::from_embedded_assets accepts names of the form platform-arch (for example, linux-aarch64), skipping names with an extension and refusing any other, and a loader that returns a named artifact’s bytes. The catalog calls the loader when a connection first needs an artifact, and keeps one read of it: each artifact of the destination’s declared os, to learn what may be installed there, and the one for the destination’s platform and architecture, which it deploys as read. A missing matching artifact produces an explicit deployment error. See remote transport and shims for build, packaging, and deployment behavior.

Reading a session archive

SessionStore::read_records(root, id).await returns every record, in sequence order, from a read-only database snapshot without acquiring the session’s writer lock: an explicit export of the whole journal. A live owner may continue writing; archive inspection neither takes ownership nor resumes unfinished work. SessionStore::is_open(root, id).await reports whether a store in any process holds the session. It takes the session lock shared for an instant; an open racing it retries once before failing with AlreadyOpen. SessionStore::summary(root, id, owner).await reads a session list row without decoding the session, checking a product’s own tables when owner names the session’s host and schema, including its title as SessionStore::title reads it, in last_millis the time of its newest record that SessionEvent::is_activity (closing a session is not), and, in stopped, the failed or interrupted turn that resuming the root agent would continue, if any. stopped reads only the root’s journaled turns, so a session that closed idle with job deliveries pending has none, yet resumes interrupted. SessionStore::stats(root, id).await reads, the same way, the statistics skyhook stats reports: aggregates over the whole journal, its requests read a page at a time, so its memory does not grow with the session.

The SQLite layout is versioned. Opening a database validates its identity and version; there is no migration or compatibility layer for earlier layouts.

Before its first connection the library turns off SQLite’s allocation statistics for the process, whose global mutex serialises parallel readers. That also disables SQLite memory accounting and heap limits for any other SQLite user sharing the process; such a user must not start SQLite before the library’s first connection opens.

Reconstructing model calls

The journal records inputs at the shared Provider boundary, not codec-specific request bodies or authentication headers:

  • model_context stores a ModelContext: the purpose, named model-profile snapshot, assembled system segments (including harness instructions and location), tool descriptions and schemas, and optional response schema. Its template() derives the history-free ModelRequest, including the model ID, reasoning setting, and output limit. Context records describe request settings, not the lifetime of a ProviderContext resource.
  • model_requested identifies one frozen logical request before its first invocation. It references the context record and stores the checkpoint it opens with, its history as the agent’s commits through a message sequence (a summary that overflowed resumes from a later one), tail as exact inline messages, and history_lifetime. Retries refer back to this request using model_attempt_started, with separate failure/interruption or completion outcomes. Ordinary requests reuse a context record while their settings remain applicable; summarization has a separate context with its structured response schema.
  • compaction stores the exact replacement message, retained original message references, covered frontier, the summary attempt that produced it, the reported occupancy that triggered it (none after an overflow), and reconciled owner todos. History and todos become active together after persistence.
  • Runtime state and job-event content are stored structurally and rendered for the model on reconstruction, so a request replays the text the model was sent. A reconstructed context carries, before each response since its checkpoint or the agent’s latest mode switch, the state the request that produced it sent; codecs decide whether to send it.
  • Reconstruction resolves those references and inline values. It does not consult current configuration, live jobs, or the current compaction renderer. Runtime state and job events are rendered by the current state renderer and job-view serialization, which are therefore part of the session format: a change to either is a database version bump. Failed and interrupted requests keep their recorded inputs; usage identifies the originating request, including summary requests and failed attempts.

SessionStore::reconstruct_model_request(sequence).await returns the provider/model name the request was issued under and the reconstructed ModelRequest for a model_requested sequence, read from the session’s journal. It checks the request’s context (its agent’s newest for that purpose), checkpoint and history bound, and that an agent request follows a result for every call its agent made, as an append does, so other records fail with a ReplayError. Attachments and tool images reference content-addressed blobs by SHA-256; load_blobs(&mut request, &mut cache) on the same store loads their contents for provider encoding, reusing and then keeping exactly this request’s blobs in cache. Both need an owning SessionStore; unlike read_records, opening a store acquires the session’s writer lock. Reconstruction reproduces Skyhook’s provider-neutral input, not an API-specific wire encoding or a replay of the external call.

The ModelRequest contract preserves the typed context entries and history_lifetime cache hints. See history, transient state, and caching for their semantics and provider rationale.

Remote transport and shims

Remote execution changes where an operation runs, not who owns the agent or job. Provider calls, agent loops, policy decisions, job state, saved output, and session blobs remain owned by the Skyhook host. A shim runs individual operations and streams their output back; it does not create a session database or run a second agent harness.

Responsibility boundaries

  • Target resolution selects a validated route and execution workspace. SSH configuration comes from target definitions, not the user’s or system’s SSH configuration.
  • RemoteManager owns the session’s connection pool: one connection per route, shared by calls in every workspace along it. It coordinates shared startup, invalidation, and shutdown.
  • ConnectionFactory supplies the byte stream and lifetime owner. The backend handles SSH authentication and OpenSSH processes, WinRM connections, platform probing, and shim deployment; it does not implement job supervision or saved-output storage.
  • The common client performs the shim handshake and runs typed operations on the shim’s machine. The host’s tools render their events into the job’s output exactly as they render a local call’s.
  • The worker (skyhook-worker) performs operations and reports typed facts; it runs no tool, renders no text and asks for no permission. A relayed SSH or WinRM stream is one of its operations. The shim binary itself only reads its arguments, checks its own hash, prunes the shims its install replaced and serves one connection.

This division keeps transport-specific code below the tool/job boundary: a tool runs the same operation whether its target is the session host or a connection.

Protocol

A host and a shim exchange typed frames over one byte stream, the shim’s standard input and output.

  • Handshake. The client’s first frame is Hello, and the worker either reports what it is (its platform, time zone, and the authorization root it resolved) or refuses, naming the setting it cannot use.
  • Calls. Every operation is a call. Its ID associates its events, input, cancellation and end, so any number of calls share the connection as independent streams, and none waits for another.
  • Flow control. A call’s events and its input each run at most one window of frames ahead of their acknowledgements, so a slow reader at either end bounds what the other buffers for that call alone.
  • Large frames. A frame too large to send whole, such as a large inline write, travels in pieces on its call’s stream, other calls’ frames between them. No tool’s data is limited by a frame’s size, and no call’s large frame holds up another’s.
  • Workspaces. The first call in a workspace has the worker resolve it (the Workspace operation), once for the connection: it joins a job’s workspace as written to the target’s, and refuses one it cannot use as it would the connection’s root. The target’s configured workspace is separately the authorization root, so a per-call working directory never redefines the target’s permission boundary.
  • Contained calls. A call the host approved in advance for paths inside the authorization root carries the paths it names. The worker resolves them, and when every one resolves inside the root it performs the operation on those resolutions in that same call. Otherwise it holds the operation and answers with the resolutions; the host approves the call as any other, then resumes or cancels it. Containment is the one decision a worker makes for the host.
  • Ending. Dropping a call cancels it on the worker and takes back what the client had not begun to send of it; a call whose request was not yet sent is never sent. The client ends a connection, and the worker stops that connection’s calls and acknowledges the end only once all their work has returned and the processes they started are killed, so nothing a connection started is still changing files when its end is acknowledged or the shim exits. A worker whose client departs without ending, or whose output fails, stops its calls the same way.

A peer that breaks this contract, for example with a contained call whose operation names other paths than those it resolves, fails the connection with a typed protocol::Violation.

Connection lifecycle

Connection startup is shared by the callers of a route. Cancelling one waiter stops its wait, and the last waiter to leave stops the startup; redefining a target on the route stops it too, and its callers plan again. Transport or protocol failure during execution discards the pooled connection so later work establishes a new one. It does not transparently replay the failed tool operation; output a tool already captured remains inspectable.

Output too large for the session stays on the target. A shim keeps a fetched body over 4 MiB, and a command’s stream past its first 4 MiB, in files under ~/.cache/skyhook/spill/<session id>/ ($XDG_CACHE_HOME when set; %LOCALAPPDATA%\skyhook\spill\<session id>\ on Windows), beside its own shims directory. The host chooses the limit and each file’s name; the shim creates the directory for its user alone, stages the file and publishes it only whole, and reports it as it resolved there; a directory whose resolved path is not Unicode keeps nothing. Each write to a staged file is blocking work the connection counts, so none outlives the connection’s end. A write its file took before a deadline ended the command’s reading is in the file published and in the counts reported with it; if that write fails, the stream is lost. While a command whose stream it is keeping runs, the shim reports the stream’s latest bytes and the lines counted so far: at most the tail it reports at the end, at most as often as the host asks, and only when the report before was taken, so a slow connection never holds the command’s output up. A stream that ends while its command runs on is reported once more, and that report waits to be taken. A read of a text file past the host’s limit counts the file’s bytes and lines before it sends any, stopping at a NUL byte, at bytes that are not UTF-8 or once the read is dropped, so the host learns the size of a text file it leaves where it is. A later page of such a file, or of a stream the shim kept, is a read operation that starts at the page’s first line, which the shim finds, so nothing before that line crosses the connection; the shim stops looking for the line once the page is dropped. A read that needs the whole field reads the file from its start.

Dropping the last owner of a pooled connection ends it. Session shutdown cancels startups, admits no new ones, and ends each connection once the connections its shim carries as their origin have ended, so a shim finishes ending, killing the SSH processes it started and deleting the shells it opened, before the origin’s end stops the stream it runs on. It waits for startup and connection work before the backend releases session-owned authentication resources, and is done once the SSH processes and shells root itself started are killed and deleted.

Origin versus jump hosts

Routing decides where a connection starts: on root or on the shim of the destination’s origin. Targets listed through via are native ProxyJump hops of that SSH process, not additional shim workers; a WinRM destination has none and is never one. A remote origin’s shim can start SSH, or run a command over its own WinRM client, and relay the stream over the existing host connection, while the host still runs the destination’s protocol client and supervises its jobs. Deployment travels that stream too: the host probes the next hop and uploads its shim from its own catalog, so an origin needs no shim binaries. A relayed connection retains its origin connection for as long as it lives.

A WinRM stream is a command in a WinRS shell: its standard input and output carry the bytes, as an SSH session’s do, and once it ends its exit status and the start of its error output explain a failure, as SSH’s own diagnostics do. Dropping the stream deletes its shell, one still being created once the service has made it, and a connection’s end and a session’s shutdown each wait for the shells they opened to be deleted. That wait has one bound from the drop, which what was left of a shell’s creation and its deletion share, and it is the time a host allows an origin’s end beyond its own.

Shim deployment

The target’s declared os chooses the language of the commands that deploy and start its shim: POSIX sh, or Windows PowerShell 5.1 started from cmd.exe, the shell of both Windows OpenSSH and WinRS, so one set of commands serves both transports. The probe’s answer is checked against the declaration: a shell that runs the declared system’s commands and names the other system, as a POSIX shell on Windows does, fails the connection before anything is installed. An installed shim needs no such check, since the digest in its name is that of a shim built for the declared os.

A connection starts with one command, which starts the first shim of the declared os that is installed and matches its digest, and otherwise prints a probe of the platform. A shim writes a fixed preamble before its first frame, so the host tells a started shim from a probe and skips whatever the shell printed before it, such as a login script’s output. After a probe, the host uploads the platform’s shim, which is verified before it is installed, and starts it: a connection takes one command once its shim is installed and three before.

A shim is installed as a digest-named file: ~/.cache/skyhook/shims/<sha256> (under $XDG_CACHE_HOME when that is set), or on Windows %LOCALAPPDATA%\skyhook\shims\<sha256>.exe. A shim that starts serving removes the other shims there built for its platform that no connection has checked for a day, and the uploads an interrupted install left there a day ago or more.

Authentication

Each credential origin authenticates with the agent it inherited: root’s own SSH_AUTH_SOCK, or the agent forwarded to a remote origin’s shim. Only an origin without one lazily owns a private ssh-agent, which it starts when a route loads a key or forwards an agent; a route offering only agent keys uses it only while it already runs. Root’s private agent is session-owned; remote origins manage theirs inside the shim. Once the session shuts down, its agent is never started again. A connection forwards its agent only for a forward_agent target. A Windows origin starts no private agent; see agents.

A private agent’s socket is made in a private directory under XDG_RUNTIME_DIR when that is set and writable, otherwise under the temporary directory, and under /tmp when neither gives a path short enough to bind.

Hops without a password run in BatchMode, so a connection that would need a password, a keyboard-interactive answer, a key passphrase or a host-key confirmation fails, and OpenSSH’s own reason is the connection error. An SSH process has at most one hop with a password: the registry refuses a target whose connection, the target and its via chain up to its origin, would need two, since telling two prompts on one terminal apart would mean reading their text, and the route an origin receives cannot express two.

The hop with the secret offers only OpenSSH’s password method (with key, only that key), so no server writes to the terminal its process is given. Skyhook types the password once, at the terminal’s first output, without reading it; a hop that never prompts is never typed. That output is always the secret’s prompt, since no hop asks about a host key: Skyhook writes each hop’s StrictHostKeyChecking and UpdateHostKeys from the target’s options, ask becoming yes and no, and user and system configuration set neither. Output after the answered line kills the process and fails the connection, reporting the answered prompt. A root origin reads the password once per connection attempt; a remote origin reads it for each SSH process it starts.

A WinRM connection reads its password, and a ca file or Kerberos configuration, on the machine that connects: once per connection attempt on root, and for each relayed command on a remote origin, never kept.

Processes Skyhook starts for tools get no terminal: a command that asks for a password, such as sudo without cached credentials, fails by itself. Askpass and display variables Skyhook inherited reach those processes unchanged.

Building and packaging artifacts

Shims are built explicitly, never as a side effect of building the applications. just build-shims builds every shim with Cargo’s dev profile; just build-shims-release uses the size-optimised, stripped shim-release profile. One shim binary per platform serves every protocol that platform uses. It is cross-compiled with cargo zigbuild for every target in the justfile’s shim_targets and staged into target/shims/ as <os>-<arch>, replacing the previous variant. just setup installs cargo-zigbuild and the shim targets; Zig itself must be installed separately.

The applications discover staged artifacts without checking which build profile produced them. Debug builds (just build) read the directory live, so rebuilding shims needs no rebuild of the applications; a running application keeps one read of each shim. A staged shim built from other sources than the application fails its connection at the first frame either end cannot decode, so rebuild the shims after changing the protocol. Release builds (just build-release) include the bytes at compile time and are self-contained; they rebuild the applications when a staged shim’s bytes change or the set of staged shims does. Debug shim artifacts are substantially larger than release artifacts.

Of the staged files named *-*, one with an extension is skipped, and any other must name a supported platform as <os>-<arch> or the catalog fails. A missing or empty staging directory yields an empty catalog; connecting to a remote target then reports an explicit missing-shim error, distinct from an unsupported remote platform. Library hosts inject their own embedded catalog rather than inheriting the binaries’ catalog.

Git contains source only, not prebuilt shim binaries. To build a native shim without Zig or UI dependencies:

cargo build -p skyhook-shim

This Cargo command builds the binary but does not stage it into target/shims/. See development setup for the recipe list, including the combined shim and application build.
