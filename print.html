Skyhook

Skyhook

Skyhook is a provider-neutral coding agent with a terminal interface and a programmable JavaScript workflow runtime. Use it interactively, automate work in headless sessions, or embed its Rust library in your own application.

Skyhook supports OpenAI Chat Completions and Responses, Anthropic Messages, Codex/ChatGPT subscriptions, and compatible local model endpoints. Tools work in local workspaces and on SSH targets. The agent can call tools directly or use scripts to coordinate jobs and child agents through the same permissions and saved-output system.

  • Everyday use: learn the terminal interface, session management, and permissions.

  • Development: see setup, architecture, and embedding.

Installation

Skyhook runs on Unix and is built from a source checkout with just. Rust 1.89 or newer is required. SSH support needs static Linux shims, which are cross-compiled with Zig; install Zig yourself and make zig available on PATH (or set CARGO_ZIGBUILD_ZIG_PATH). just setup installs the remaining Rust-side tooling (cargo-zigbuild, cargo-nextest, mdBook) and both musl targets.

git clone https://github.com/kryesh/skyhook.git
cd skyhook
just setup
just install   # release shims and both applications, installed into ~/.local/bin

This installs skyhook, the general-purpose coding agent, and skyhook-security, the security research companion. Both support the terminal interface and headless execution and embed the same SSH shims. Make sure ~/.local/bin is on PATH.

For a local-only build without Zig, run just build-release instead and use target/release/skyhook or target/release/skyhook-security. just build builds both applications in target/debug. SSH use without an included shim returns an explicit missing-shim error.

Both applications use the ordinary Skyhook provider configuration and credentials. The companion also reads security.yaml; use security.example.yaml as a starting point and adjust its model assignments to match your config.yaml. See security configuration for discovery rules and research settings.

See development setup for contributor commands and shim builds for the build matrix, artifact layout, and native shim-only builds.

Your first session

After installing Skyhook, create a configuration directory. The default location is $XDG_CONFIG_HOME/skyhook or ~/.config/skyhook:

config_dir="${XDG_CONFIG_HOME:-$HOME/.config}/skyhook"
mkdir -p "$config_dir"

Create config.yaml in that directory with a provider and model you can access. For example:

providers:
  openai:
    codec: "responses"
    dialect: "openai"
    base_url: "https://api.openai.com/v1"
    api_key:
      env: "OPENAI_API_KEY"
    models:
      default:
        model: "gpt-5.6"
        max_context: 1050000
        max_output: 128000

Use a model identifier supported by your account and set its token limits explicitly; Skyhook does not detect them automatically. You can choose smaller budgets. For model limits, other providers, a keyless local server, or Codex OAuth, see providers and models and authentication.

From a source checkout, you can instead copy the comprehensive example and edit it before running:

cp config.example.yaml "$config_dir/config.yaml"

The full example configures several providers; remove unused providers and models or supply their required credentials.

Start from the project directory you want to work on:

export OPENAI_API_KEY=...
skyhook --prompt "inspect this repository"

Skyhook opens a full-screen terminal interface. --prompt submits an initial message; --script workflow.js starts a JavaScript workflow in the same interface. Both remain open for inspection and follow-up input after the work finishes. These interface modes require an interactive terminal. Use skyhook batch with -p/--prompt or -s/--script for headless execution with redirected input/output support and automatic exit; see Headless execution.

An unused startup draft creates no saved session. The first sent message or explicitly run script creates the session. Use --workspace PATH to select another workspace. Normally, <workspace>/.skyhook/config.yaml overlays the selected user configuration, entry by entry. Use --config path.yaml to load only that file instead, with no user/workspace config merging. See configuration layering, including its workspace trust boundary.

To inspect configuration or available skills without a session or API credentials:

skyhook dump config  # Effective YAML on stdout; diagnostics/source paths on stderr.
skyhook dump skills  # Winning skills, frontmatter, and asset tree.

Both return nonzero on errors; skills can still list valid entries when other entries fail. See dump for compatible options. After a session, skyhook stats SESSION_ID reports its token usage, model requests, delegation, and tool calls (see stats).

Actions with effects outside the workspace require approval. See permissions and capabilities before using --approve-all; it bypasses tool approvals, not authentication prompts.

Next, learn the terminal interface, session and context behavior, or headless execution. All command-line options are summarized in the CLI reference.

Terminal interface

Conversation and inspector

User messages appear on the right and assistant messages on the left. Tool previews show their remote execution target after the tool name, such as exec @lab-monitoring; local calls omit @root. Expand a tool call to inspect its arguments, output, or failure details. Scripts, commands, file content, and diffs have syntax highlighting. Click an expanded body to collapse it, or drag to select text. Copying code preserves its contents without visual padding or newlines added by wrapping. Language-labelled code blocks in messages and reasoning receive syntax highlighting once their closing fence arrives; open blocks keep a consistent plain code style while streaming.

The agent tree appears above the composer while children are active or a child agent is being viewed. Click an agent to inspect its conversation without mixing its output with other agents. Each agent and tab retains its reading position and expanded rows. Agents using the wait tool show Waiting rather than Running tools. Tree rows show @target for remote agents and their own token totals, context usage and time: output · input (uncached) · context · time. The time is how long a busy agent’s current turn has run; once it isn’t busy, how long a child ran its job, or how long the root agent’s last turn took. Agent call previews show the child’s target even while queued or running; an omitted target inherits the caller’s target. Completed final replies identify the model that answered in a footer below the reply, with how long that response took and, when tool rounds came first, how long the whole turn took.

The composer always sends to the root agent. While root is busy, Enter queues a follow-up for its next model request, without interrupting the current request or tools. It does not wait for the entire turn to finish. /queue edits/removes input that has not yet been consumed. Selecting a queued message to edit pauses automatic queue delivery and moves it into the composer; merely opening the queue or deleting an item does not pause it. While the edit is open, nothing queued is sent, including messages held for /retry, whatever else happens. Submitting the edit puts it back in its place, however the messages around it change meanwhile, and the messages behind it go with it when the queue resumes; Enter on an empty draft, or /resume, discards the edit and leaves the message as it was. Interruption, a failed turn, submission or delivery errors, and session-start failures also pause queue delivery; a failed turn’s error is shown in the conversation. /resume clears that pause, as does normal composer Enter (even with an empty draft); slash commands do not automatically resume the queue. If Skyhook cannot write a session’s journal, that session stops as if the process had crashed: its queued input is dropped and its conversation shows why. It stays open to read until you close it, and reopening it continues from what was saved. Queued input lives only in the running interface: it is not saved with the session. Each open session keeps its own queue, which keeps delivering while you look at another session and is discarded when its session is closed.

/retry continues failed or interrupted turns without duplicating their original prompts, and resends, as one batch on the bottom bar’s model and mode, queued messages a failure or interrupt paused; a queue paused while you edit a message stays paused. After a session interruption it resumes all interrupted children automatically, regardless of which agent is selected. Parents with pending waits stay in those waits. On a reopened session that has not run anything yet, /retry always starts it and continues whatever it left unfinished, or reports that there was nothing. Automatic model retries display the attempt number, a countdown to the next attempt, and the latest diagnostic in one error block. Error blocks expand to the error, its first lines when it is long, which copying or exporting the block gives whole: a final failure starts expanded and a pending retry collapsed, while /details and exports expand them all. Partial output from the failed attempt clears when the next attempt starts, and partial output a failed or interrupted turn left clears when the agent’s next turn begins, as reopening the session shows it; successful replies have no retry labels. Retries continue until success or cancellation for transient model failures.

The inspector provides Conversation, Requests, and Jobs tabs. Switching agents keeps the selected tab, while reading positions and expanded rows remain separate for each agent and tab. However long a conversation grows, its whole history scrolls and the scrollbar spans all of it: what is far from view is read as the view nears it, with Loading… at its edge until it arrives, and it arrives without moving what you are reading. Drag the scrollbar to move through the history quickly. Requests include compaction requests, numbered from 1 for each agent, with when each was sent, token summaries, and how long each took; transient retries appear under the same request and number, which reads Retrying while the next attempt is pending. Full request bodies are available in the session log, not rendered in the UI. Status messages, such as interruptions and errors, appear in the conversation and are saved with the session, but are not sent to the model. Startup warnings (skills, configuration, connections and MCP servers) describe this installation rather than the session, so the terminal shows them but does not save them. Unsaved notices appear where they arrived in the conversation and scroll away as it grows. Feedback on an action, such as an attached file, an export, or a setting that could not be saved, shows briefly on the notice line instead. An export finishes even if you switch away from its session meanwhile.

Job output is paged and searchable without acknowledging the agent’s pending notifications. Select a job and press o for output fields, regex search, and the next page; c asks to confirm, then requests cancellation (useful for background jobs, since interrupting already cancels the foreground tool). Intermediate child-agent messages and terminal job notifications appear as expandable Job event cards. Earlier progress messages remain readable after the job completes or resumes. Child-agent messages and answers, and question prompts and option descriptions, render as Markdown, both in cards and in the question prompt. Remote output becomes available as it is transferred to the host. An expanded job card loads its output while it is on screen and follows what a running job writes.

Provider-supplied reasoning streams in a separate expanded block and collapses when answer text starts or the response finishes. Click a multi-line block or press Enter when selected to reopen it, including after resuming a session. Single-line reasoning stays inline without an expand/collapse control and is not selectable, even when it wraps in a narrow terminal. A heading or wholly bold or italic line followed by a blank line starts a new reasoning section, titled by that line and collapsible like any multi-line block; only the section still streaming stays expanded. A title with nothing under it stays inline. Spinners indicate that work is still active, and a counter at the end of the row shows for how long. The working indicator counts the whole turn, across model requests and tool rounds; streaming reasoning counts from its request. Running tool calls count up and keep their duration once finished; expanding one shows when it started. A running tool waiting for input keeps its status symbol while its counter runs, and a retry counts down to its next attempt. Copied and exported text includes finished durations but not running counters.

Model selection and UI state

Models are named provider/model and listed in configuration declaration order. For a new session, selection uses --model, then the most recently submitted configured model, then default_model, else the first model of the first provider. The starting mode is chosen the same way: --mode, then the mode of the most recently submitted message if it is still configured, then default_mode. Batch jobs ignore the remembered mode. /model (or Ctrl+X M) selects the model for subsequent user messages in the current session. Selection stays in the UI until a message is sent; cancelling the picker or leaving without sending does not change the session’s recorded model. Each submitted message captures its model, including queued messages. Queued messages are submitted together as one batch, in order, including their attachments. The batch cannot be split across requests; the last message’s captured model is used for that request. A batch is saved whole or not at all: if the session cannot take its model, mode or attachments, the turn it reached fails with why, queue delivery pauses, and every message in it stays queued for /retry, which tries the batch again on the model and mode the bottom bar shows, in place of the ones the messages captured; messages already on their way join the batch. Removing a message from the queue withdraws it, unless /retry is already submitting it. Once every held message is withdrawn, the batch no longer waits: a turn the batch began rests with nothing to continue, while one it stopped mid tool loop stays failed and /retry continues it without the batch. Interrupting while /retry sends the batch returns its messages to the queue, paused: nothing is sent until you resume the queue, submit another message, or /retry. A session closed before then drops the batch. Tool follow-ups, retries, compaction, and /retry retain the active turn’s model. The bottom bar shows the choice for the next message; reply footers identify the model that actually answered. Resumed sessions retain their last applied model, unless --model names another: the session switches to it at startup, before any message or startup script, rather than for the next message as /model does. /models remains an alias for /model. A session whose recorded model is no longer configured still opens, with a startup warning, and is never moved to another model on its own. A message sent to it stays queued and the model picker opens: the model chosen there becomes the session’s, then the message is sent. Children whose own model is gone restart on it too.

The interface stores the last submitted model and mode and the sidebar setting in the workspace’s .skyhook/state.json, beside its sessions, without changing the model configuration. Session titles are saved with their history.

A sidebar beside the conversation shows the application’s name, then the session’s title; click the title to rename the session. Below, it lists the MCP servers the viewed agent can use, with their startup status, and the viewed agent’s todos, with the viewed agent’s capabilities pinned to its bottom. For the root agent of a new session these are what the mode of the next message grants, so cycling modes changes them. Once the root agent runs, choosing a mode for the next message that changes what it runs, including its own mode after the configuration redefined it, previews the change: a green + marks a server that mode would add, and a server it would remove is greyed out. A section with nothing to list is left out, title included. The sidebar is shown by default; Ctrl+X B or /sidebar toggles it. Host-defined capabilities show the titles their product declares; a foreign session’s recorded capabilities fall back to their namespaced names. Long labels are shortened with …. A foreign view-only session shows Recorded capabilities, not grants from the current product’s modes or MCP configuration, and its title cannot be renamed. Terminals narrower than 100 columns hide it without changing the saved setting.

The bottom bar uses this format:

default · openai/fast (gpt-5-mini) · 3f9c2a7d…       8.4k · 200k(31.2k) · 42% (54k/128k)

The left side is the mode, the configured provider/model name with its API model ID in parentheses when the two differ, the working directory (prefixed view-only for another product’s session), and the session ID. The statistics are session output tokens, session total input tokens (uncached input), and the selected agent’s context occupancy as the last response that reported its prompt counted it (tokens/model capacity). Session totals include children and compaction; a count a provider did not report adds nothing. Context includes instructions, tools, history, runtime state and that response; it is not cumulative usage. It appears as — until a response reports its prompt, including after compaction.

Submitting a new prompt rejects any pending question batches; those batches can no longer be reopened. Commands have no terminal, so password prompts from SSH and from sudo in commands (locally or on a target) appear as authentication prompts. The typed answer stays out of the conversation, but it goes to whichever process asked, and a command the agent runs can ask too and capture it. As a hint, each prompt names the program that appears to have asked and, when it runs under one, the job: for example Requested by /usr/bin/ssh or Requested by sudo (running as uid 0) in job 12. A program running as another user, such as sudo, shows only its name and user, since its executable cannot be read. This is best-effort attribution, not proof of who asked or where the answer goes: a command started by a genuine program, such as an SSH ProxyCommand, can ask in that program’s name and receive the answer. Answer only prompts you expect from the work you asked for, and treat one that names a program you don’t expect (a script, a shell, Skyhook itself) or an unknown program as raised by the agent’s command. For background questions and authentication prompts, Esc cancels the request; cancelled requests cannot be reopened. Authentication prompts take priority over questions, permissions, and menus; interrupted question drafts resume afterward.

Renaming opens a prompt of its own, ahead of pending questions and permissions, with the title you set ready to edit, or empty while the title is automatic; the composer and its draft are left alone. Enter saves the title, and saving it empty returns the session to its automatic title. Esc cancels the rename. A draft has nothing to rename until its first message is sent.

Typing enters text-editing mode, where ←/→ moves the cursor; Tab switches between editing and question navigation. Enter confirms an answer and advances to an unanswered question; switching alone never submits. The mouse wheel scrolls the text or choices beneath the pointer. Drafts remain intact while answering questions or inspecting details. Question choices are suggestions: you can select one, optionally add a comment, or provide a free-form answer. For answering agent questions from a script, see jobs and agents.

Product-provided views and actions

An embedding product can add read-only tabs after the built-in inspectors. Cycle them with the same tab shortcuts or click their headers. Their data refreshes in the background, so loading a view does not block typing, switching sessions or resizing the terminal. A view that takes the whole screen may keep the agent tree: in a column beside it on a terminal at least 100 columns wide, headed by how many agents run and in which modes, or below it on a narrower one. There, Tab and Shift+Tab move between the view and the agents, ↑/↓ step through the agents without leaving the view, and clicking an agent or pressing Enter on it opens its conversation, as choosing it from the Agents palette does.

Headless execution

Use skyhook batch with exactly one prompt or script:

session_id=$(skyhook batch -p "Review this repository" --capabilities read,agents)
skyhook batch -s workflow.js --approve-all
skyhook batch -p "What does this service do?" --mode readonly
skyhook batch --resume "$session_id" -p "Summarize the findings"

A batch job runs in the default mode, in the one --mode names, or with the exact --capabilities list. Headless mode does not require a terminal or read answers from stdin. It creates or opens the session, prints only its session ID followed by a newline to stdout, and flushes that line before executing the prompt or workflow. It then exits automatically. The ID lets external programs locate and follow the normal session logs under <workspace>/.skyhook/sessions. Headless mode uses only the selected workspace’s history, just like the terminal UI. Resumed runs print the existing session ID.

Assistant output, script console output/results, startup warnings, and execution diagnostics remain in the session logs; they are not printed to stdout or stderr. The process exits successfully when the submitted operation and shutdown succeed. On failure or interruption it exits nonzero and prints the error to stderr; stdout still carries only the session ID. A failure before a session can be opened produces no session-ID line. If Skyhook cannot write the session journal, the session stops as if the process had crashed: the error says so, and no final status is recorded. Explicit --help and --version retain their normal output. Headless mode is not a line-oriented conversation over stdin.

The submitted root turn or workflow defines completion. A workflow must explicitly await background work it needs completed; outstanding jobs are cancelled, and child agents interrupted, during shutdown. Interrupt and termination signals also trigger cleanup and journaled status rather than a terminal prompt.

A batch job never has human interaction. Root ask is unavailable (also inside scripts and with bg:true). Child agents can still ask their owning parent agent. Operations requiring human approval fail immediately; ordinary automatically allowed operations still work. --approve-all (or config approve_all: true) bypasses tool approvals but does not enable questions, SSH passwords/passphrases, or host/agent confirmation prompts. SSH credentials that work without a prompt can still authenticate.

exec never has stdin connected or a controlling terminal, so ordinary /dev/tty prompts cannot stop the job waiting for terminal input. SSH and sudo password prompts are rejected even when inherited SSH_ASKPASS or SUDO_ASKPASS settings request another prompt helper or the targets capability is disabled. Existing SSH_AUTH_SOCK credentials are preserved unless the configured target-authentication setup replaces them. Remote commands apply the same capability restrictions. This is still not an OS sandbox against deliberately programmed subprocesses that establish their own external interaction mechanisms.

See the CLI reference for argument combinations and permissions for the capability/approval distinction.

Sessions and context

Session lifecycle

Startup and /new open an empty draft without creating a session or its files. The session is created when you send the first message or explicitly run a script; leaving an unused draft behind does not create an empty saved session. Resuming an existing session still opens it immediately.

Use --resume SESSION_ID to reopen a session. The CLI stores session logs and looks for saved sessions only in <workspace>/.skyhook/sessions, where --workspace selects the workspace (default: the current directory). It does not search parent or sibling workspaces. Sessions written by an incompatible earlier session format cannot be reopened and are left out of /sessions, as are a product’s own sessions whose product data, such as Skyhook Security’s research, an incompatible earlier version wrote.

Skyhook’s file tools never open a database this process holds open: searches skip an open session’s session.db, session.db-wal and session.db-shm, and reading, replacing or removing them, or removing a directory that contains them, is refused, since closing any handle to such a file would release the database’s locks. A session opening while a file tool reads its files waits briefly for the read to finish. To inspect a live session from outside, open it read-only without its shared memory index changing, for example sqlite3 'file:.skyhook/sessions/<id>/session.db?mode=ro&readonly_shm=1'.

The terminal keeps several sessions open at once. /new opens a draft beside the current session, and /sessions lists the open and saved sessions: the current session first, then the other activated sessions, those still working first, then every other session by most recent activity. An open session is activated once it has run here: a new session from its first message, a reopened one from the first action that changes it. Activated sessions are shown in bold. Opening a session and closing it again with nothing running does not count as activity. The current session is marked >. Open sessions show their live status, and saved ones how they would resume: idle, interrupted, or failed. Opening a saved session changes nothing in it until you act on it, by sending a message, continuing it, or anything else that is saved with it; notices about it meanwhile are shown, not saved. A session closed idle with results still waiting for its main agent is listed and opens as idle, as described below. A lock marks a session that was held open when the list was shown, by another Skyhook instance or because it was still closing here. Choosing one that was closing here opens it once it has closed; one another instance holds cannot be opened until that instance closes it, and choosing it says so. A saved session whose status cannot be read shows no status symbol. Each row’s id, event count, mode, last activity time, and creating host sit at the right. When a row is too narrow, they give way from the left, id first and host last, so titles keep at least 30 columns; longer titles are cut short with …. Choosing an open session switches to it, choosing a saved one opens it alongside. Sessions you switch away from keep working, and the notice line reports when one of them has a pending question or permission request or has failed. A session you switch away from with nothing running, nothing waiting on you, and nothing typed or queued is closed, so other Skyhook instances can open it; it stays in the list as a saved session. /close shuts down the current session only; quitting shuts down all of them.

Sessions created by another Skyhook product are labelled with their host and view-only in history and the terminal header. You can inspect agents, requests, jobs and saved output, copy text, and export the conversation. The composer, rename, model/mode selection, continuation, interruption and job cancellation are unavailable; reopening and closing never activate these sessions. Use the creating product to continue or change them.

A session is named after the first message you send it. Rename it with /rename (Ctrl+X L) or by clicking its title in the sidebar. A title you set stays until you change it, whatever the session does later, and renaming starts from it; renaming a session with an automatic title starts empty, and saving an empty title returns the session to its automatic title. A session without a title is listed by its first message. Model selection and UI state are described in the terminal guide.

Interrupting a session stops active model requests and cancels foreground tools, scripts, and questions. Nothing asks a model again until you continue with /retry or send new input: results that arrive meanwhile wait, and reach their agent with its next request. A response already recorded when the interrupt lands stands. Delegated child agents, including ones that had yet to start, retain their conversations and continue with /retry; parents waiting on their work keep those waits. Sending new input breaks those waits at every depth: the session proceeds, and each retained child remains interrupted in the background, where /retry can still continue it. Cancelling a job an interrupted agent is waiting on lets that agent go on with the result. Background jobs otherwise keep running, except those owned by a cancelled script. Explicit job cancellation stops work for good. Closing a session interrupts it the same way and cancels its other running jobs: child agents that were running, or already interrupted, can still be continued after it reopens, as can a delegation it stopped before the child started, which asks for approval again. Closing a session does not change its last activity time: as after a crash, work that closing cuts short ends when the session last did something. A session whose journal Skyhook cannot write stops the same way, as if its process had crashed, and reopens as one would.

Child agents must finish or cancel their owned work before completing. The root agent may leave background services running while the session remains open, but they do not survive shutdown or a process restart. On resume, unfinished jobs are marked interrupted and job IDs are not reused. Requests, jobs, and tool calls the previous process left running are recorded as ending when it last did something, so their durations stop there and reopening a session does not change its last activity time. Retained child agents can be resumed; ordinary process and tool jobs cannot. Pending child replies and job notifications remain available after resume and reach their agent with its next request: reopening a session does not start one. A session reopened with any waiting for its main agent resumes interrupted once it runs, so /retry delivers them as a new message would. See jobs and agents for delegation, notifications, and cancellation from scripts.

Conversation compaction

Skyhook uses the current model to summarize older conversation when context grows large. The continuation is intended to preserve the task, instructions, plans, findings, unfinished work, and where to resume. Recent conversation and the original calls for active work remain in context; historical tool calls are not executed again. Compaction also reconciles the agent’s todo list against the conversation without changing child-agent lists.

A successful model response triggers automatic compaction when:

U = input tokens + cached input tokens + output tokens
U >= 0.9 × (max_context - max_output)

This is the completed response’s reported usage, not cumulative session usage. Skyhook does not estimate token counts, so without reported usage there is no automatic trigger. Compaction runs before executing tool calls from that response. The summarizer sees the entire latest response and its pending calls, explicitly marked as not yet executed. It reconciles the current todo list with the conversation and any pending todo changes; its reconciled list takes priority over direct pending todo replacements. Those direct replacements fail as superseded, so they cannot overwrite that list. Todo reads and replacements invoked through scripts run normally; a scripted replacement can update the reconciled list. The original calls and their results are included in the first normal post-compaction request; the summary does not consume those future results. If compaction fails, the turn ends and those calls are recorded as not executed. A text-only response returns at once; the compaction it triggers runs before the agent’s next model request, also after the session is closed and reopened. A compaction that is interrupted, or whose summaries could not be used, stays due and runs again before the agent’s next request, for example when you continue. One that fails for another reason, such as a provider error, is not tried again, and the next request is sent without it. Switching model or mode clears a due compaction: from then on, the new model’s reported usage decides.

The provider still decides whether a request fits. A recognized context-overflow error can trigger compaction and retry, including for an oversized initial request or new tool output. Normal requests keep the configured max_output. Compaction requests can use a smaller output limit when less context space remains, and a summary the provider rejects as too large is retried with half the output reserve, then with about the older half of the summarized history left out. After an overflow, compaction keeps only the latest exchange beside the summary. The context meter in the terminal shows the last reported occupancy. Configure model limits to match the endpoint you use.

Compaction does not execute tools. It can retain selected job results as well as recent conversation; full saved results remain accessible through jobs. Older details depend on the summary: original messages remain in the session log, but there is no agent-callable history tool. A validated summary can still be incomplete or inaccurate.

Invalid, truncated, cancelled, or unsaved summaries leave the preceding context and todos active. Every valid, successfully persisted summary installs a checkpoint and its reconciled todos, even if the replacement context is not smaller. The terminal reports compaction start, the reported occupancy that triggered it, and failures without printing the summary. Eligible compaction failures, such as a truncated or invalid summary, have a bounded retry policy, separate from transient model failures, which retry until success or cancellation. A refused summary is not retried. See model failure recovery.

For persistence and request reconstruction internals, see library architecture and embedding.

Permissions and capabilities

Approval policy

--approve-all or approve_all: true bypasses approval prompts. Subject to the granted capabilities, the default CLI auto-allows reads and agent operations, as well as writes inside the root workspace. Execution, HTTP requests, SSH access, target changes, and writes outside the root workspace require approval. When the interactive capability is granted, questions and authentication prompts (SSH, and sudo in commands, locally or on targets) appear in the interface. Otherwise operations needing human input fail immediately; approve_all bypasses tool approvals but never restores questions or authentication.

Filesystem tools and command cwd accept absolute paths or relative paths including ... The workspace is a base directory, not a security boundary. Filesystem path authorization and human approval are distinct: the default CLI read policy auto-allows reads even when their canonical paths are outside the workspace. Do not rely on a confirmation prompt to protect outside-workspace reads. Outside-workspace writes require confirmation, and remote access has its own approval requirements. Permissions name paths as text, so an operation whose permission names a path or workspace that is not valid Unicode is refused rather than approved under an approximate name.

A path counts as outside the workspace when resolving it leaves the workspace: it ends outside, or passes through an outside directory or symbolic link on the way, even if it ends back inside. Whether such a path exists is revealed only once its operation is approved. When it does not exist, the operation is refused without a prompt, exactly as if the user had denied it, unless the approval policy would allow the operation without asking; then it fails as not found. A missing path inside the workspace fails before approval. On the session host, a child agent’s workspace is checked like a path when the child starts: outside the workspace, it follows the rules above; inside, it need not exist yet, and a write that creates parent directories can create it. On another target the workspace must already exist, and resolves there when the child starts. The child works in the directory its workspace resolves to, and its relative paths resolve from there. On the session host, its job shows the workspace joined to the agent’s workspace, with any .. kept. remove refuses the root workspace, the agent’s workspace, and any directory containing either.

Choose Allow once to approve only the current operation. When offered, Allow proposed scope saves the displayed grant for later operations while the session stays open; reopening the session asks again. Inspect Details before granting it. Path grants apply only to the approved target and access mode. Directory grants cover descendants; read and write grants remain separate. Process execution remains subject to confirmation on each invocation. These defaults apply to the CLI; library hosts can supply a different approval policy.

Approval controls and pending/granted approval details remain user-facing. Agents see an ordinary queued job while authorization is pending. A prompt is withdrawn once nothing waits for it, as when its operation is cancelled or its session stops. A denial preserves its reason and marks the rejected operation with code: "permission_denied"; it does not undo work that a containing script already performed. Agents must not circumvent a denial through another tool or route. For programmatic failure handling, see the JavaScript response contract.

Modes

A mode is a named permission preset. The root agent runs in one mode at a time:

# The mode a new session starts in; "general" when omitted.
default_mode: "readonly"

modes:
  readonly:
    capabilities: ["read", "network"]
    instructions: "Investigate and report. Do not change anything."
    hint: "Look things up without changing anything"

  # Built in, and listed first. Declare it only to change what it grants.
  general:
    capabilities: ["read", "write", "exec", "network", "agents", "mcp"]

capabilities is required, and default_mode must name general or a declared mode. Optional instructions are added to the system prompt of an agent running in the mode; they guide the model, whereas capabilities are enforced. An optional hint offers the mode to agents starting a child: the agent tool lists each hinted mode whose capabilities the caller holds itself, with those capabilities and the hint. A mode without a hint cannot be given to a child. A workspace config that declares a mode replaces the whole definition of a user-config mode with that name; modes it does not name are kept, in declaration order.

--mode NAME selects the starting mode; without it the terminal starts in the mode last used in that workspace, and a batch job in default_mode. In the terminal, Tab/Shift+Tab in the composer (or /mode) choose the mode the next message is sent in; the footer shows it. Cycling modes only makes that choice: it never changes the session. A change takes effect with that message and forfeits the provider’s prompt cache for the next request. Child agents keep what they start with: the capabilities and instructions of the mode their parent chose for them, or otherwise the capabilities their parent holds and no mode instructions. Background jobs and scripts already running keep their capabilities too. A session can only hold capabilities that some configured mode grants, and MCP servers start under that union, so switching modes never starts or stops a server. Approvals granted earlier stay granted but cannot be used while the mode lacks their capability.

A resumed session continues in the mode it was last in, as the current configuration defines it: the configuration decides what a reopened session’s modes grant, more or less than before, and a batch session reopened in the terminal gains interactive. Opening a session whose modes the configuration has since changed or removed shows a warning and changes nothing, and neither do renaming it or cancelling a job. The change applies with the next work that runs the root agent: a prompt, retry, continue, script or job delivery. It is recorded together with the message that work commits, or just before a script starts. A root agent whose mode was removed moves to the default mode. Child agents it already started keep what they started with, within what the configuration still allows. The session’s history keeps every definition of a mode it used, so earlier entries still show what they ran under. Because general is always present, redeclare it with a narrower list if the terminal should never be able to switch to its default capabilities. Continuing a failed or interrupted root turn also applies a newly chosen mode.

Capabilities gate both tool discovery and invocation, including JavaScript. Approval policies and cached grants cannot restore a missing capability. Ungated orchestration tools remain available even with an empty set. These gates are not an OS sandbox: allowing exec lets a command access files or the network independently of the corresponding built-in tool gates. Disabling network removes fetch, not model-provider traffic or trusted MCP transport setup; disable mcp to prevent MCP connections. Per-server MCP requirements are additional gates, not grants.

See headless execution for noninteractive commands and authentication, execution targets for route approvals, and MCP for trusted server startup and per-server gates.

Sessions retain the application that created them, separately from their title and mode. Other applications can inspect them and read their statistics from the shared session directory, but cannot activate, rename, or otherwise change them. Reopening a session in its creating application is required to resume work.

Execution targets

Include "targets" in a mode’s capabilities (or a batch job’s --capabilities allowlist) to grant the target capability. It is not enabled by default. Without it, agents cannot use target-management tools or select another target, including from JavaScript. The external_agent example below also requires ssh_agent; see agents.

Targets are named entries in the top-level targets mapping, and session tools can add or replace targets without modifying YAML. Skyhook never reads SSH configuration files: a target’s host, user, port, authentication, and options come only from its own definition. Aliases, ProxyJump, identities, and other settings in ~/.ssh/config or /etc/ssh/ssh_config do not apply.

When user and workspace config are layered, a workspace entry replaces the whole target with the same name; it does not inherit user SSH, authentication, or routing settings. Targets with other names are retained. Repeat any required settings in the replacement entry.

targets:
  bastion:
    type: "ssh"
    host: "bastion.example.com"
    ssh:
      user: "gateway"
      external_agent: true

  build:
    type: "ssh"
    host: "build.internal"
    workspace: "/srv/project"
    via: "bastion"
    ssh:
      auth:
        kind: "key"
        path: "~/.ssh/build_ed25519"

  database:
    type: "ssh"
    host: "db.internal"
    origin: "build"
    ssh:
      # Reach the host through a gateway using the deploy user's own SSH key on build.
      options: { ProxyCommand: "sudo -n -u deploy ssh -W %h:%p gateway.internal" }

The built-in root is the session host—the machine running the main Skyhook process. It is not configured as a target and always identifies that machine, including when an agent’s current target is remote. Named targets declare their transport with type; "ssh" is the only transport.

Routing: origin and via

  • origin names the target that starts the SSH connection; it defaults to root. Key paths and agents belong to the origin.
  • via names a target to jump through with native ProxyJump, within that same connection. Jump hosts need no shim. A via target must have the same origin, so its key paths are never interpreted on another machine. Omit via, rather than naming the origin, to connect directly from the origin.

Both may be set: origin: "build" with via: "gateway" makes build run SSH through gateway, where gateway also has origin: "build".

Registering targets never connects to them; registrations are session-wide.

await tool.target_add({name: "database", type: "ssh", host: "db.internal", origin: "build",
  ssh: {auth: {kind: "key", path: "~/.ssh/database"}}});

Agents

By default, Skyhook uses a private SSH agent on each origin for keys loaded during the session. An external_agent target instead uses the agent its origin inherited in SSH_AUTH_SOCK: on root, the one Skyhook was started with; on a remote origin, the agent forwarded to that origin’s connection. A chain of external_agent targets therefore keeps using the same external agent.

Each connection forwards the agent it authenticated with, so remote Skyhook commands receive it in SSH_AUTH_SOCK, allowing commands such as git, ssh, and ssh-add to use the same identities. Private agent state is discarded when its origin’s session or connection ends and is not restored when resuming a session.

Targets whose route includes an external_agent hop, including configured ones, require the ssh_agent capability. Without it they are invisible: targets omits them, selecting them or naming them in via or origin fails as an unknown target, target_add cannot replace them, and target_add does not offer ssh.external_agent. With it, connecting requires approval of that route (listing its origin and external_agent hops). Adding an external_agent target with target_add is approved separately from later connecting to it.

target_add requires the write capability as well as targets. It also requires the exec capability and its approval when it sets ssh.options, because options such as ProxyCommand can run commands. Configuration files are trusted like MCP commands.

Passwords, key passphrases, keyboard-interactive challenges, host confirmations, and agent confirmations appear in Skyhook’s interface, including prompts from SSH started on a remote origin; each names the target being connected to and, when it is remote, that origin. Target configuration cannot enable prompts in a noninteractive session. skyhook batch has no authentication prompts; invocations without an interactive terminal must use it and fail operations that require input; --approve-all does not approve authentication prompts. Secrets are never included in tool results or session logs.

Using targets

Use targets to list each target’s host, type, via, and origin without connecting. Registering a target does not change the agent’s location.

Target-aware tools, including agent, use these rules:

  • Omitting target uses the calling agent’s target and current workspace.
  • Setting target: "root" uses the session host and its configured session workspace.
  • Setting another named target uses its configured workspace, except that explicitly selecting the calling agent’s current named target retains that agent’s workspace override.

Workspace-inheriting tools such as write, replace, and remove use the calling agent’s target and workspace without accepting a target selector; a write source names its own target, so a file can be copied between machines. Host/session tools such as jobs, todo, wait, and targets still run on the session host. agent selects a child’s future execution location; launching the child and running its provider remain host operations. An explicit agent.workspace takes precedence over the selected base; relative overrides resolve against that base.

Diagnostics identify the operation and its subject, with the execution target when applicable. A working-directory override is separate from the target’s configured workspace: an absolute cwd must exist on the selected machine, not on the session host. A connection, session-storage, or saved-output inspection failure is not necessarily a failure of the command on the remote machine.

Prefer these named targets to manually running ssh. A tool that needs an SSH route requests approval before any probe, authentication, or shim deployment. A route grant applies across tools and workspaces, so reconnecting an unchanged route needs no new approval. Changing a target or any hop in its route invalidates every grant naming it, whatever the resource, and stops connections still starting over the old route; an operation waiting for approval or a connection is planned again and asks about the new definition. An operation already running over the old route finishes there, but any further approval it asks for is refused.

JavaScript orchestration and the session log stay on the host; nested tool calls use the selected target and workspace. For remote execution internals and shim builds, see remote transport and shims.

Instructions and skills

Instructions

Skyhook loads at most one user instruction file and one file in the exact resolved workspace directory. It does not walk workspace ancestors for instructions. --workspace PATH selects that workspace; --config selects only YAML configuration and does not suppress instruction discovery.

Within each directory, filenames are checked in this order:

  1. AGENTS.md
  2. agents.md
  3. Agents.md
  4. AGENTS.MD

The first existing filename is selected. If reading it fails, Skyhook does not try a lower-priority spelling in the same directory. A readable empty file counts as selected, so it does not trigger fallback either. An instruction file must be a regular UTF-8 file of at most 1 MiB; a larger file or one that is not a regular file is skipped with a startup warning, and other read failures stop startup.

For user instructions, Skyhook first checks $XDG_CONFIG_HOME/skyhook, then falls back to $HOME/.config/skyhook if the first location is absent or fails. It never loads both user files. If no fallback succeeds, all non-missing user-file errors are reported. Missing optional files are fine; an unreadable selected workspace file is an error.

For example, on a case-sensitive filesystem:

$XDG_CONFIG_HOME/skyhook/agents.md  # Selected user file if AGENTS.md is absent.
$HOME/.config/skyhook/AGENTS.md     # Not loaded when the XDG selection is readable.
/project/AGENTS.md                 # Not loaded for workspace /project/app.
/project/app/AGENTS.md             # Selected workspace file, even if empty.
/project/app/agents.md             # Ignored when AGENTS.md exists, even if unreadable.

User instructions are supplied before workspace instructions, with their source identified. If both locations select the same file, it is loaded only once. Root and child agents share these instructions.

Host-owned skills

Host-owned skills are exposed through the skill tool, which is offered only when at least one skill was discovered. Unlike instructions, skill discovery reads ~/.agents/skills and .agents/skills directories along the workspace ancestry, with the nearest workspace definition winning when names collide. Discovery happens at startup; restart Skyhook to discover newly added skills. A skill directory contains SKILL.md and optional supporting files, conventionally grouped in scripts/, references/, and assets/:

.agents/skills/release/
├── SKILL.md
├── assets/
│   └── logo.png
├── references/
│   └── template.md
└── scripts/
    └── release.py

Skill YAML frontmatter may contain arbitrary metadata, but its values must be JSON-compatible: mappings with string keys, sequences, strings, booleans, finite numbers, and null. Duplicate or non-string keys, custom tags, non-finite numbers, and YAML << merge keys are rejected. Anchors and aliases are supported with bounded expansion. A description must be a string; a skill with any other non-null description is skipped with a warning.

Loading and copying assets

The examples below assume the release skill layout shown above.

All skill arguments are optional and nullable; native calls supplying null behave like calls omitting those fields. Without name, the call lists available skills; path requires name.

await tool.skill(); // {kind: "list", skills: [{name, description}]}
await tool.skill({ name: "release" }); // Complete SKILL.md, assets tree, and location
await tool.skill({ name: "release", path: "references" }); // Directory subtree
await tool.skill({ name: "release", path: "references/template.md" }); // Original text
await tool.skill({ name: "release", path: "assets/logo.png" }); // Attached image

Results have a kind discriminator: list, skill, directory, text, image, or binary. Base skill results contain location, complete content, and, when the skill has other files, an assets text tree that includes nested files but excludes the already-loaded root SKILL.md. Directory results use the same tree format, rooted at the selected path. Trees mark symlinks without descending through them. Long trees and asset text are saved in full and can be paged using jobs.

Text assets (including JSON, YAML, source code, and SVG) are returned unchanged, never executed. Supported raster images are attached with metadata, and one that does not decode is an error. Other binary files return metadata rather than raw binary or base64 content. Paths inside a skill must be relative and cannot escape its root. Use path: "." to browse the root.

Skills live on the session host. location is {path, target: "root"}, the skill directory’s absolute path there, so ordinary tools can reach its files. target is included only for agents with the targets capability; an agent on a remote target without it cannot reach the session host, so its results have no location. Copy an asset with write’s source, which also delivers it to an agent working on a remote target:

const { location } = (await tool.skill({ name: "release" })).unwrap();
await tool.write({
  path: "tmp/release.py",
  source: { path: `${location.path}/scripts/release.py`, target: "root" },
});

An agent on the session host can omit target.

A mixed-file test workspace includes its hidden .agents/skills/mixed-assets/ directory. Its tests exercise native calls, explicit nulls, asset discovery, UTF-8 and binary files, image attachments, and path containment.

Security research

skyhook-security is a companion application built from the same library and terminal host as skyhook. It researches a selected part of a target: a codebase, or without source a deployed service or API, a network daemon or a binary, recording the flaws it finds, how each entry point reaches them, the vulnerability candidates they support, reviews, and empirical validation attempts. It is not a sound static analyzer: a flaw, route or candidate is a research hypothesis, not proof that a path is executable or a vulnerability exists. Reports identify assumptions and coverage gaps.

Configuration

The companion reuses the ordinary user and workspace config.yaml: providers, model settings, credentials, execution targets, and MCP servers are not copied into another file, and skyhook auth manages the same credentials. Additional settings live in security.yaml, with the same user-directory discovery and workspace overlay rules; the workspace file is .skyhook/security.yaml. --security-config PATH selects one explicit security file and disables discovery for that file alone; --config PATH independently selects the ordinary configuration. skyhook-security dump config shows the effective shared configuration with security modes, model hints, and merged MCP entries applied, without opening a run or session. The embedded modes’ instructions render for each agent, so the dump leaves them out.

Model assignments refer to the configured provider/model names, not the identifiers sent to a provider. A model can serve several roles, and several models can serve one role. Assignments become model-selection hints rather than mandatory bindings: orchestrators choose appropriate models when delegating, and unassigned models are not offered as explicit delegation choices. The roles are orchestrator, explorer, validator, environment, poc, and reporter; a role is not a mode name. A session that starts with no role hints configured reports it as a diagnostic.

# Replace these names with entries in your ordinary config.yaml.
models:
  main/reasoner:
    roles: [orchestrator, validator]
    hint: Prefer for complex cross-component reasoning.
  local/coder:
    roles: [explorer]
    hint: Prefer for focused code exploration.

shortlist: high

The first configured orchestrator model is the companion’s default model; an explicit --model or the remembered model takes precedence. The root agent always runs in the orchestrate mode: --mode and batch --capabilities are refused, and the terminal offers no mode switch; children take their modes from the agent tool.

shortlist is the CVSS 4.0 severity a candidate needs to enter review; it defaults to high. CVSS keeps an authenticated-user flaw with limited impact below that line, so set shortlist: medium for web and other logic-heavy targets where such findings matter. The severity a candidate is assessed at is the impact if its unresolved conditions hold, so uncertainty never lowers it. workers is how many agents the orchestrator’s scheduler runs at once (default 6). It is the default for a new run; the run keeps what it started with, and a later launch’s --workers can change it. It guides the agents and is not an enforced cap. live decides whether agents work against a running target, probing it and demonstrating findings: ask, yes or no; omitting it asks interactively and defaults to no in batch mode. See security.example.yaml for the complete shape.

A question agent settling a premise the code alone cannot decide may, under a live policy, run a bounded experiment or measurement in a recorded environment, or have a child run it, and decide the premise from what it observed against its control.

How far a child may delegate is set by its launch’s depth. The embedded templates launch coordinators (sweep, probe, validate, poc) with depth 2 and every other mode with depth 1, so any agent can delegate part of its work or a focused check when it is more than it can cover well; agents may choose otherwise.

Research pipeline

The root orchestrator drives the pipeline through delegated research modes; the research store holds one graph of what the agents found and derives the work each part of it still owes; nothing is planned. target maps the code, binaries and interfaces into components, mapping what it cannot read by what its material shows, and records the deployment premises your request settles, each actor’s intended capabilities among them, and each interface in scope under a short name; when your scope includes dependencies, it records each locked version a published advisory affects as a flaw at its manifest entry. Under a live policy, when the map records interfaces, the orchestrator arranges an environment serving them before paths, under ask once you approve its scope. paths has a sources child record the entry points of each file and of each interface an environment serves, each on the path its flow matches or one of its own up to its handoff, then relinks the sources, path premises and candidate actions of paths sharing a handoff onto one path and extends each through the components it reaches.

After paths, one scheduler runs every phase together within workers: each subject starts as soon as its own prerequisites are met rather than when a whole phase ends. Ready work starts in pipeline order — sweeps and probes, settles and chains, assessments, reviews, tests, reports — and later work waits only on earlier-stage work, ready or running, that touches it; unrelated later work fills the remaining slots. Settles and chains go out in bundles: one child takes every ready entry of its phase that shares a node with the first. Work on a node that running work is about waits for it, so one agent works a node at a time and the next starts with its findings in view.

A child working a task is told, with its next request, of what other agents changed of what its work rests on since it began: each change once, as a digest per changed subject (how many changes, the latest, their kinds, and the newest few with the nodes each moved most), so it can re-read them before deciding. Its own changes and its helpers’ are left out, and the root, which works no task, is told nothing.

The research graph holds nodes of a few kinds, each with a title and a body:

  • A component is implementation, by the files and named interfaces it owns; its body notes its concurrency: what runs its code, the state it shares, and what serialises access to it.
  • A source is one entry point an actor drives, with its location and trust (untrusted, authenticated, local or privileged); a location has one source, so recording another there returns the one recorded, and merging a source frees its location for the source it merged into. A read of state an attacker-driven flow writes, such as a stored record or session, is a source too, trusted as its least-privileged writer; configuration read at startup is trusted as the operator, and a CI job others can trigger as whoever can trigger it.
  • A path is an ordered flow of steps through components, each at a location with a note, from the sources that share it.
  • A premise is a prerequisite: internal state or logic a flaw needs to reach unintended state, or a path needs to carry input there. A failing premise contradicts the candidates resting on it. It is code-scoped, about the target’s own logic and decided by reading or observing it, or deployment-scoped, decided by you, and holds, fails, or is undecided.
  • A flaw is a local defect at a location in a component, with an optional CWE, the premises it depends on, and a status: suspected, confirmed (a verified defect with no chain to an observable consequence found so far) or refuted.
  • A candidate is an ordered chain of flaws to an observable vulnerability, its first flaw its root, through its actions: the paths its scenario performs, in order, the first where the attacker starts. A path may repeat, as in a race with itself. Candidates sharing a root flaw are its group, tested and reported together; a candidate merged into another adds, after the other’s own actions, each path it performed as often as it did beyond the other.
  • A finding is a root flaw’s report.

A location is a code region (file and lines, in its function), an address range of a binary image at its link base (in its symbol), or an operation of a recorded interface in that interface’s own terms (a route template, a method, a message type), at one of its fields when narrower. A location names an interface, never an address, so it stays the same across deployments. Evidence is a location with a stance on one node: it supports, contradicts or gives context; one made in an environment names it. Contradicting evidence after a premise’s decision or a flaw’s refutation disputes it and owes its settle or chain again; an edit of its substance since reads it as undecided or suspected until it is decided or judged again. Any agent may raise a candidate, a flaw or a premise at any time, left unsettled for the work that checks it (except a deployment premise your request settles), and merge a duplicate of any kind but a finding into the node it repeats, which takes its edges; restating what is recorded changes nothing. A source, path or component recorded in error is retracted with set_status and a note: it shows as retracted but owes no work, holds none back and leaves every count, and the premises a retracted path relies on stand in no candidate’s chain, until marked recorded (a path unswept) again. Retracting or restoring a path owes the reviews and reports of the candidates performing it again.

Candidates are assessed with a CVSS 4.0 base vector (CVSS-B) scored for the impact if every premise of its chain holds; the native scorer applies the shortlist threshold. A build option, configuration or deployment other than the default, or a race window the attacker must win, makes Attack Requirements present and is a premise. Attack Vector, Privileges Required and the other exploitability metrics come from what the attacker must hold or face before the first action, plus anything a later action needs that no earlier action supplied; access or privilege gained during the scenario is never a prerequisite. A score rests only on what the candidate’s premises establish: a condition that would raise a metric becomes its own candidate, the same chain with that condition as a premise, so the root’s report leads with whichever validates. A review records validated (every premise holds), disproved (a chain flaw is refuted or a code premise fails), excluded (a deployment premise fails, so the deployment keeps a real finding out of reports) or unproven (a premise stays undecided). A verdict counts while nothing it judged changed after it, and an unproven one only while a premise of its chain is undecided: a premise decision or dispute owes the review again, and a material change of the candidate, its chain, a path it performs or a source entering one owes the assessment again too. A candidate’s confidence is conjectured while a premise of its chain is undecided or contradicts it, established otherwise, confirmed while a positive verdict stands, and demonstrated once its settling test (its latest test that is not pending, recorded at its latest verdict) is confirmed and its chain uncontradicted. A validated candidate no more severe than a demonstrated one of its group is noted rather than tested.

Deployment premises stand for what only you can answer. target records the ones your request settles as holding or failing. One raised later and left undecided is never settled by an agent: it holds back the reviews resting on it and is listed in the synthesis as asked. When the scheduler returns, the orchestrator puts the asked premises, and those an unproven candidate rests on, to you as one question, records each answer as the premise holding or failing, which sends their candidates back to review, and runs the scheduler again.

The synthesis a scheduler run ends with lists the work each phase owes and has running, each exhausted subject with its last agent’s reply, the deployment premises asked of you, the candidates left unproven with their undecided premises, the components no path reaches, and the interfaces paths without code wait on an environment for (under live: no, every interface such a path enters on). After each return the orchestrator also has a question agent review the loose ends it lists, the premises of exhausted settles and those an unproven candidate rests on: each is settled, given what would settle it, or reopened. Exhausted work is terminal: the orchestrator closes the run once a pass changes nothing, with nothing owed or held, everything asked put to you, and that review moving nothing. It then always writes the current reports out and lists exhausted work as incomplete and each root flaw without a current report as having none. Every agent that records a conclusion (a premise decided, a flaw judged, a verdict, a test result) checks the code around it for flaws or candidates it implies. All of this is agent-discovered evidence and analytical conclusion, not a symbolic proof or a substitute for empirical validation.

Runs and sessions

Each security session is one analysis run: the session keeps the run’s research beside its journal, so a review today can be followed by environment preparation, empirical validation, and reporting later, in the same session, without repeating discovery.

skyhook-security --prompt "Focus on request routing and access control"
skyhook-security runs            # list security sessions; -w DIR selects another workspace
skyhook-security runs SESSION    # the run as the Research tab shows it, every section open in full

# Continue a run: resume its session.
skyhook-security --resume SESSION --prompt "Extend the analysis to the admin interface"

The orchestrator runs the stages your instructions call for: a new session analyzes the workspace from target selection onward, and a resumed one continues from its records, whether the instructions extend the analysis, prepare an environment, validate, test or rewrite reports. Fresh work is always owed; settled or exhausted work is owed again only once something it rests on changed. A resumed run keeps its shortlist threshold, live policy and workers; a --workers flag resizes it once its work resumes, and --live applies only to a new session, so it is refused with --resume. A headless resume is refused only when the run’s own policy is ask, whatever the configuration says. Only the root agent knows the live policy, and under no every agent’s instructions leave out live work. The shortlist threshold is applied by the store alone; no agent is told it.

In the terminal, a new session opens with a scope panel at the top of the root agent’s conversation: the shortlist threshold, the live policy, and the workers, prefilled from security.yaml, flags, then the defaults. Edit it while writing the instructions in the composer: Shift+Tab moves between the fields and the composer, ←/→ change a choice, digits edit the workers. The first message sends the panel’s values with it; with no instructions the session starts with “Analyze the workspace.” Once the run has started the panel stays in view, frozen; a session that fails to start leaves it editable for the next try.

The Research tab (] from Jobs, or click its header) takes the whole screen below the tab strip. It opens on a dashboard of the run: its threshold, live policy and workers, the synthesis, a pipeline showing where each phase stands (what it owes, has running and has exhausted), and panels for coverage (sources, paths swept and unswept, uncovered interfaces, components reached or mapped only, premises undecided, asked and disputed, flaws by status), candidates by status, and the tasks running and exhausted in each phase. Below it, sections list the candidates, findings, paths, tasks, flaws, premises, components and sources as the session records them; unswept paths come first, and each path, premise, flaw and candidate shows what it owes and its last task, and opens to its latest tasks. Tasks are listed newest first with their phase, subjects, state (as their agent’s job stands), and when they began and ended; a task opens to its brief, its agent’s reply and the records the agent wrote. Click a section’s header, or choose it with ↑/↓ and press Enter, to open it; a record opens the same way to its detail, a candidate to its whole scenario: actions, chain, premises, assessment, verdict, tests and evidence, with an assessment or verdict that no longer stands marked stale. A candidate whose demonstration is under way shows as proving, and as test abandoned once the agent running it ended without recording an outcome. An open section lists its first 50 records, most relevant first; its last row loads 50 more. The page scrolls as one, updates while agents work, and keeps what you opened. While agents run, they stay in view beside the page on a wide terminal, or below it on a narrow one; click one to open its conversation.

The orchestrator receives the run’s state with each request: run, live policy, workers, the plan’s line (such as “owed: 4 sweep, 2 settle; 3 running; exhausted: 1 chain; asked: 1; uncovered: 1”), and the artifacts directory. The agents it starts receive no run state; their briefs name the IDs of their work, and each agent that runs or builds anything gets a working directory of its own under artifacts/, so parallel work never collides. A new session (Ctrl+X N) starts as the command line would, on the model selected where it was opened when the command line’s configuration offers it, and otherwise on its default.

For automation, batch takes the same choices as flags over the security.yaml defaults:

skyhook-security batch --prompt "Review the HTTP header parser" --live no --shortlist medium
skyhook-security batch --resume SESSION --prompt "Review the upload paths" --workers 2

The run’s files live in its session’s directory under .skyhook/sessions/: test artifacts belong under artifacts/, and the current reports are written under reports/. Sessions share .skyhook/sessions with skyhook, so skyhook stats covers them; a session created by the other application opens view-only (see sessions).

Live work and reporting

Live work is any interaction with a running target: probing it, settling or reviewing what only observation decides, and demonstrating findings. It happens only in an environment, a running instance an agent prepared (a container started from a binary or image) or a deployment you authorised, which records the interfaces it serves and their addresses. A prepared environment is a template: each agent copies it into its own working directory and runs its own instance there. A deployment cannot be copied, so its instructions say how agents share it, and are the rules of engagement: addresses, identities by reference, rate, what live work may change and must leave alone, and the window. Under ask the orchestrator records an environment for a deployment only once you approve its scope; under yes it takes the scope from your request, never broader. The store schedules around environments and enforces nothing: Skyhook’s approvals do, fetch per origin and exec per invocation. exec is not a sandbox, and batch live work needs approve_all; with live: yes against production, that is your choice.

Under live: no no live work is owed: interfaces are never probed, and paths on them are listed as uncovered, while a binary is still analysed by reading its disassembly. Under yes or ask a path without source code is probed once an environment serves its interfaces; a probe that needs what its environment lacks, such as an identity, leaves the path unswept for a later environment.

Under live: no no demonstration is owed. Under yes or ask each validated scenario that is not noted owes one until a test settles it, its root group’s most severe first; with ask, an interactive run asks after analytical review which findings to demonstrate, and each one declined is recorded as such. Declining does not reject a finding: its report remains confirmed and empirically untested, with the reason. A PoC agent makes an environment change the scenario’s premises admit itself, through an environment agent when the change is reusable; an environment recorded within its work is prepared for its candidate, without making its test owed again. A test waiting on you is recorded as pending and stays owed until you resolve what it waits for, which lets it resume; one the environment cannot run is recorded as unavailable and reported as untested with its reason. An inconclusive run is not a result: the PoC agent refines its approach, delegating helpers as it needs, until it confirms or disproves the scenario. A test is recorded as failed only with evidence that the scenario does not work as formulated, which goes on the chain flaw or premise it bears on: that evidence sends the candidate back to review, and the scenario is reported, or withdrawn, by the verdict review then records. A test other than a declined one stands only while the verdict it tested, the latest when its work began, is its candidate’s latest: a new verdict, such as a re-validation after its actions or chain changed, owes a test of its own, even one recorded while the test ran. An unavailable or failed test is owed again once a later environment is recorded for its candidate or for none in particular; a declined one stands, across new verdicts too, until you ask for it. A confirmed test stands while its chain is uncontradicted. A race, a check apart from its use or a measured difference such as timing is demonstrated over a fixed number of trials with a control run as often, both success rates in the test’s note, a measured difference confirmed only beyond a threshold stated before the runs; a win that needed the window widened counts only when the window exists in the unmodified build, with the rate without widening reported. A confirmed test is expected to record an attack artifact and a control run on the same build, each a distinct regular file under the run’s artifacts/ directory reached without a symbolic link; the report shows a confirmation that lacks one. Execution uses ordinary approvals and capabilities: prefer a disposable container or a deliberately configured target, and keep live validation within the authorized environment.

A root flaw is reported once its group owes no assessment, review or test, by a report agent who writes one markdown report: summary, analysis, impact, remediation, reproduction citing test ids and artifacts, and a section per other scenario. The report is owed again whenever what its scenarios rest on changes after it was written. reports/ holds only the current reports, rendered from the run’s store; each root flaw with one has a folder, reports/<root>/:

  • README.md: front matter, the title, a generated table of the scenarios (candidate, paths, chain, vector, score, severity, status, confidence and test), then the reporter’s report;
  • finding.json, the machine-readable record the Markdown is rendered from;
  • test-<id>/ for each scenario’s settling test: its artifacts under attack/, control/, observation/, harness/ and notes/ by their own names (numbered -2, -3 when two share one), with test.md, test.json and SHA256SUMS.

reports/index.md and index.json list every current report with its severity (the most severe of its scenarios) and its headline scenario’s own severity, score, vector and confidence, labelled apart since a demonstrated headline may be less severe than an untested variant. reports/hardening.md, linked from the index while it has entries, lists the confirmed flaws no report covers, with each one’s title, location and CWE, in two groups: those no validated candidate holds, with why no chain was found, which are not scored or tested; and those whose most severe validated candidate is assessed below the run’s threshold, with that candidate and its severity. None are reported, and index.json lists them under hardening, each with its reason. Every page opens with a small front matter its text repeats, and links only by relative path. The orchestrator writes reports/ out with research generate once it closes the run: a root’s folder is replaced in one step when what renders has changed, a stale root’s folder and anything else placed there is removed, and a generation with nothing changed changes nothing. An artifact is copied only while it matches the digest its test recorded; one that changed keeps the root out of reports/ and is reported.

Configuration overview

Skyhook uses YAML configuration. The files are not rewritten when the terminal remembers a model.

File selection and layering

With --config path.yaml, Skyhook loads only that file. It does not search for or merge user or workspace configuration, even if the explicit file fails to load. The contents are always parsed as YAML, regardless of the filename suffix.

Without --config, Skyhook:

  1. Tries $XDG_CONFIG_HOME/skyhook/config.yaml, when that environment variable is set.
  2. On any read, YAML parse, or structural error, tries $HOME/.config/skyhook/config.yaml. At most one user file is selected; the two user files are never merged.
  3. Overlays <resolved workspace>/.skyhook/config.yaml if it exists. --workspace PATH selects the workspace; otherwise it is the invocation directory. No ancestor workspace configurations are loaded. An unreadable or invalid workspace file is an error.

Automatic discovery uses only config.yaml, not config.yml or config.toml; there is no TOML fallback.

Missing optional user files are fine: a complete workspace-only configuration can be used. A broken user file is not silently treated as missing if no fallback succeeds. The effective configuration must be valid; defaults are applied after merging.

The workspace file overlays the user file key by key, and each key’s value is replaced whole. The exception is the named maps providers, modes, targets, and mcp. These merge by name, and each entry comes whole from the last file that defines it. A workspace entry replaces the user entry of the same name without inheriting its omitted fields, and entries with other names stay available. For example, a workspace providers.openai must repeat the dialect, endpoint, credentials, and every model it keeps. A replaced entry keeps its position in the user file’s order. Entries only the workspace defines come after the user’s.

An explicit null is a value, not a deletion: providers: null or providers.openai: null makes the configuration invalid rather than removing entries.

Example: user models, workspace targets

Keep providers, with their models, in the selected user config.yaml:

providers:
  openai:
    codec: "responses"
    dialect: "openai"
    base_url: "https://api.openai.com/v1"
    api_key:
      env: "OPENAI_API_KEY"
    models:
      default:
        model: "gpt-5.6"
        max_context: 1050000
        max_output: 128000

targets:
  bastion:
    type: "ssh"
    host: "bastion.example.com"

  build:
    type: "ssh"
    host: "old-build.internal"
    via: "bastion"
    ssh:
      auth:
        kind: "key"
        path: "~/.ssh/old-build"

Then use this <workspace>/.skyhook/config.yaml:

modes:
  general:
    capabilities: ["read", "write", "exec", "targets"]

targets:
  build:
    type: "ssh"
    host: "new-build.example.com"
    workspace: "/srv/project"

The effective configuration retains providers.openai, with its default model, and targets.bastion. A named mode or target is replaced whole, not merged: modes.general grants exactly the listed capabilities, and targets.build uses the new host and workspace, with default authentication/routing behavior: neither the old key nor via: "bastion" survives. If a route or key is needed, repeat it explicitly in the workspace entry.

Trust boundary: workspace configuration is full configuration, not a restricted project hint. It can change approvals, modes, provider credential commands, and MCP server startup. Review it before starting Skyhook in an untrusted checkout.

YAML syntax and strings

Each file must contain a single YAML document with a mapping (object) at its root. Empty or comment-only documents, null roots, and sequence or scalar roots are rejected. An empty mapping ({}) is a valid no-op workspace overlay, but an empty effective configuration is invalid.

Values must be JSON-compatible: mappings with string keys, sequences, strings, booleans, finite numbers, and null. Duplicate keys, non-string keys, custom tags, non-finite numbers, multiple documents, and YAML << merge keys are rejected. Anchors and aliases are supported with bounded expansion. YAML merge keys are unrelated to Skyhook’s file layering.

Use indentation for nested settings, not dotted table headers. Quote values that must stay strings, especially numeric-looking SSH options and environment values: ServerAliveInterval: "15" and WORKERS: "4", not unquoted numbers. Actual numeric settings such as max_context remain numbers.

For multiline instructions or shell-command strings, a literal block scalar preserves line breaks:

modes:
  readonly:
    capabilities: ["read", "network"]
    instructions: |-
      Investigate and report.
      Do not change anything.

|- omits the final newline; use | if the string should end with a newline. Folded blocks (> or >-) turn ordinary line breaks into spaces, so use them only when that is intended. MCP start_command remains a sequence of argument strings, not a shell-command block.

Migrating from TOML

Manually convert the contents of each old config.toml to YAML, then rename it to config.yaml. Replace table headers with nested mappings and key = value assignments with key: value; keep the same configuration keys, values, and model declaration order. Check quoting and multiline string whitespace rather than only changing punctuation. Update explicit --config paths too. Renaming alone does not convert TOML, and Skyhook does not convert files automatically or fall back to the old format. Use skyhook dump config to validate and inspect the effective YAML.

Paths and environment

Relative MCP cwd values resolve against the directory of the source file defining that value. A user-defined cwd keeps its user-file base when other MCP fields are overlaid; a workspace-defined cwd uses the workspace config’s directory (<workspace>/.skyhook), not the workspace root. An MCP server without cwd, from either file, starts in the session workspace rather than the directory skyhook was launched from.

The CLI always stores and discovers sessions in <workspace>/.skyhook/sessions, including headless execution and resume. It does not search other workspaces or honor session_root overrides. Remote paths resolve on the selected execution target. The workspace is a base directory, not filesystem isolation.

The CLI loads .env from the invocation directory, with existing process environment variables taking precedence. Neither --workspace nor --config changes that location. See authentication.

Inspect without starting a session

skyhook dump --workspace /path/to/project         # Same as dump config
skyhook dump config --workspace /path/to/project --approve-all
skyhook dump config --config ./standalone.yaml    # Explicit file only

These commands write resolved effective YAML to stdout and source paths/diagnostics to stderr. They apply defaults and applicable CLI policy overrides without requiring API credentials, starting MCP servers, or making network requests. Exit status is zero for a valid dump and nonzero if valid configuration cannot be produced. See dump for selectors and incompatible options.

Configuration areas

  • Providers and models: named API connections, full model IDs, context/output limits, reasoning replay, and connection recovery.
  • Authentication: environment variables, secret-manager commands, .env, and Skyhook-owned Codex login.
  • Permissions and capabilities: approve_all, modes, and their exact capability allowlists.
  • Execution targets: SSH destinations, origins, routing, and authentication.
  • MCP servers: trusted local server startup and imported tools.

Providers and models

A provider entry names an endpoint and the models served through it, under models. Everywhere a model is chosen or recorded—--model, the /model picker, the agent tool, default_model, session history and skyhook stats—it is named provider/model from the two keys, so neither key may contain /. The model field inside a profile is the identifier sent on the wire and stays free-form. default_model selects the model a new session starts with when neither --model nor the model last submitted in the workspace chooses one; without it, the first model of the first provider is used.

Every provider names a dialect, the server’s wire conventions. Each model selects a codec, either directly or from its provider’s defaults: chat_completions, responses, or messages. The codec is the API family; base_url names the shared API root and Skyhook appends /chat/completions, /responses, or /messages for the selected model. Different models on one provider may use different supported codecs:

Provider defaults and model settings

Request settings are flat: put shared defaults beside models, and model-specific values directly beside model.

Missing model settings inherit from the provider. Explicit values win even when they are false, [], or a setting’s usual default. Lists replace inherited lists rather than append. Under OpenRouter’s routing, only declared members change: a model’s order replaces the inherited order while an undeclared allow_fallbacks still inherits. The same leaf-by-leaf inheritance applies to access_programs and image_limits: {} inherits its leaves, rather than clearing the object.

Every request setting in the table above reads the same way, apart from lists. Left out, it inherits, and with nothing to inherit takes its default. An explicit null sends nothing: organization: null removes the organization header, routing: null removes routing preferences, reasoning_summary: null requests no summaries, and a placement selection of null places nothing. A setting that always sends something, such as state_role or reasoning_effort, refuses null; leave it out to take its default. Lists, such as LiteLLM’s tags, refuse null too: [] is the empty list. A placement selection’s list of locations is never empty; null is how it places nothing. Provider-only settings differ: startup_timeout_secs: null, for one, takes the default.

Every model must have codec, and LiteLLM models must also have upstream, after inheritance. A provider may omit either if every model supplies it. Defaults and compatibility checks apply to each effective model, not to the provider defaults in isolation. Unknown fields, provider-only fields under a model, fields for another dialect, and unsupported codec/setting combinations are rejected. API keys, credential-command caches, and connection resources remain shared by all models in one provider instance, regardless of their request settings.

Service tier

service_tier selects the backend’s tier ID, such as priority, flex, or ultrafast, on any dialect and codec, as a provider default or beside model. It is unset by default and sent exactly as written: Skyhook does not translate client aliases such as fast. Check that the endpoint and model accept the tier before selecting it. Faster tiers can cost more or use more of a subscription; see ChatGPT speed.

Responses settings

Any dialect serving codec: "responses" accepts two optional settings, as provider defaults or beside model. A backend serving Responses need not accept them; check that the endpoint, model, and account support a setting before selecting it. Other codecs refuse a selection, so a model that switches away from Responses must clear inherited ones with null.

  • reasoning_summary is the detail of the reasoning summaries requested: "auto" (every dialect’s default), "concise" or "detailed", or null to request none.
  • access_programs.cyber requests a cybersecurity access program: standard, daybreak_blue, or daybreak_red; unset by default. The model and account must be eligible for the program; it does not grant entitlement, and other safeguards still apply. Some models take a different wire value from the approval it needs: gpt-6-astra and gpt-6.1-sol take daybreak_blue but require Daybreak Red entitlement. See the Daybreak guide.

Explicit caching

explicit_caching: true, as a provider default or beside model, switches a chat_completions or responses request to explicit prompt caching (prompt_cache_options: {mode: "explicit"}) on every dialect but codex, which refuses the setting: the backend caches only at the breakpoints Skyhook marks, never on the changing runtime state, so later requests can reuse the prefix. Both mark the end of the stable history and the point where each earlier request’s history ended, and Chat also the stable system prompt, up to four breakpoints a request: the newest history boundaries are kept. A dialect that already marks breakpoints with cache_control on Chat (openrouter, and litellm behind anthropic) places the same marks with that field. On openrouter Responses, cache_ttl applies to automatic caching only; explicit marks are cached for the backend’s default lifetime. Neither marks the history of a request with no reusable prefix, such as compaction. Left unset, the backend’s automatic caching is unchanged. messages refuses the setting. Check that the endpoint and model support it; see the prompt-caching guide for supported models and pricing.

astra:
  model: "gpt-6-astra"
  max_context: 1050000
  max_output: 128000
  service_tier: "priority"
  access_programs:
    cyber: "daybreak_blue"
  explicit_caching: true

Image limits

Images of up to 8 MiB are stored as attached, except that an animation, and any GIF, is stored as a PNG of its first frame (an APNG’s default image, which may lie outside its animation), re-encoded as a smaller JPEG if that PNG would exceed 8 MiB. An image with very large dimensions can be refused when attached, whatever the model’s limits. Before a request, an image whose longest edge or encoded size exceeds the model’s limits is fitted: it is downscaled to the edge limit, keeping its aspect ratio, and re-encoded as PNG (unless it is a JPEG) if that is within the size limit; otherwise it is re-encoded as JPEG and made smaller until it fits. An image within the limits is sent unchanged, the stored original is kept, and the model is not told that an image was fitted. An image that cannot be fitted, such as one whose stored data no longer decodes, is sent as a short note saying so, and the request proceeds. Each dialect sets defaults:

Dialectmax_edgemax_bytes
anthropic8000 px7.5 MiB (10 MiB as base64)
openai, codex6000 px8 MiB
compatible, litellm, openrouter4096 px3.5 MiB

image_limits replaces either limit, as a provider default or beside model; a limit left out keeps the default, and image_limits: null restores both. max_bytes is at most 8 MiB, since no image is stored larger, and max_edge at most 65535 px, the largest JPEG; a larger value reads as that maximum. The limits are per image: a service rule that depends on how many images a request holds, or on their total pixel area, is not applied. Changing a model’s limits from its dialect’s defaults changes the images earlier reasoning saw, so signed reasoning from before the change is not replayed afterward.

local:
  model: "vision-model"
  image_limits:
    max_edge: 2048     # longest edge, in pixels
    max_bytes: 2097152 # encoded size, in bytes

Placement selections

A server that deviates from its dialect’s presets can select placements at either level:

providers:
  local:
    codec: "chat_completions"
    dialect: "compatible"
    base_url: "http://127.0.0.1:8000/v1"
    output_limit: "max_tokens"                   # or null for none
    reasoning_replay: "reasoning"                # the assistant-message key; or null
    cache_key:                                   # one location, a list of them, or null
      - body: "cache_salt"
      - header: "x-session-id"
    models:
      thinker:
        model: "served-name"
        max_context: 131072
        max_output: 32768
        reasoning_effort: "reasoning_effort"
        output_limit: null                      # Send no output limit.

The selectable dimensions are output_limit, reasoning_effort, reasoning_replay and tool_stream (Chat Completions only), cache_key, and user_id. Every one but cache_key is a field path. Each selection names one location or a nonempty list of distinct locations, and the value is written at every one. A selection left out inherits, and with nothing to inherit keeps the preset for the model’s effective codec and dialect settings; an explicit null places nothing. Changing codec does not discard inherited selections: set null for any the new codec has no place for, or replace them.

A field path is dot-separated (metadata.user_id); cache_key and user_id carry the conversation identity. Paths must not name a field the codec writes itself (such as model or messages) or one the dialect adds (such as OpenRouter’s routing provider and models), and no two may overlap, including one inside another (reasoning and reasoning.effort), within one selection or across two. A cache_key header must not be accept, content-type, or a header the codec sends itself (such as anthropic-version on messages). A reasoning_replay field moves the provider’s replay to other keys in the same form. Messages requires an output limit, so output_limit: null is refused there, as is reasoning_effort: null everywhere.

Context and output budgets

Every model profile requires max_context and max_output. Both must be positive, and max_output must be smaller than max_context. Prompt/history, reasoning, and generated text share the context window. Automatic compaction is triggered by a response whose reported input, cached input, and output tokens reach 90% of max_context - max_output; it does not estimate the next request. Compaction precedes tool execution, or, after a final answer, the agent’s next request. The summarizer sees the pending calls, and their results reach the first post-compaction request intact; a pending todo replacement is superseded by its reconciled list. A max_output of at least 50% of max_context produces a startup warning for that model, whether or not it is selected: reserving that much output space leaves most of the window unused for input. The configuration remains valid. Normal requests retain their configured output limit; compaction requests reduce it when necessary to fit the remaining context space. Use the model’s published limits or your server’s actual configured limits, whichever is lower. You can deliberately choose smaller budgets for cost, latency, or available memory. However, using Skyhook with less than approximately 128k tokens of max_context is not recommended: instructions, tool definitions, conversation, and compaction all need room. This is guidance, not an enforced minimum.

state_mode controls how per-request runtime state (date, active jobs, and todos) reaches the model. dynamic (the default) sends a fresh state with each request; the model sees only the current one. persist keeps each state in the conversation, at the cost of keeping every one in context until compaction; a state the latest kept one already shows is not repeated. Use it for models that bind signed reasoning to the exact earlier conversation (such as Claude Fable 5.1) when the provider cannot hide earlier state, for example Claude reached through a Chat Completions or Responses proxy. Use it too where a large state (many jobs or todos) defeats prompt caching: chat_completions and responses cannot hide an earlier state, so under dynamic each request leaves out the previous one’s, and a provider that reuses only where an earlier request ended, as codex does, then reuses little of the history. none sends no runtime state, except to a compaction summary, which needs the current todo list to reconcile it. See runtime state for what the model receives.

Runtime state is the harness speaking, so it never appears as tool output. A dialect’s state_role selects how it is sent:

  • system uses the protocol’s harness role: a system message on messages, a system or developer message on chat_completions, and a developer message on responses. Through anthropic, or litellm with an Anthropic upstream on messages, a dynamic state is a turn-scoped system message: the model reads it for one request, and afterwards it costs no input tokens but stays in the conversation, so models that bind thinking to the exact earlier conversation (Claude Fable 5.1, Opus 5.5, Sonnet 5.5, Haiku 5.5) keep it with dynamic state. It needs a model that supports mid-conversation system messages (Claude Opus 4.8 and later, Fable, Sonnet 5.5, Haiku 5.5; not Sonnet 5). Other dialects send plain system messages and drop superseded state, as user does. On messages, a state with no valid place, such as right after an assistant turn, is not sent.
  • user sends state as user content, joining the user turn before it or as a turn of its own, for servers without a harness role mid-conversation, such as many open-model chat templates. Superseded state is then dropped, which changes the end of the conversation between requests. During a tool loop each state is a new user turn, so a chat template that keeps reasoning only for the latest user query drops the loop’s earlier reasoning after it, whatever the state_mode. For such models, enable the template’s option to keep earlier reasoning (Qwen’s preserve_thinking, for example).

anthropic defaults to system, as does litellm for messages behind an Anthropic upstream; openai and codex always use it, and compatible, openrouter and every other litellm combination default to user. Changing a provider’s state_role changes the conversation earlier reasoning was produced in, so that reasoning is not replayed afterward. Through anthropic, or litellm with an Anthropic upstream on messages, set reasoning to a level other than off on models that bind thinking: only then does Skyhook ask the service to drop a thinking block whose earlier conversation changed, rather than reject the request.

Model failure recovery

For every provider, transient/network failures retry until success or cancellation, with no attempt limit. This includes connection failures, interrupted streams, timeouts, rate limits, temporary server errors, an expired command-sourced credential (authentication), and a response with neither visible text nor a tool call, such as reasoning alone. Other authentication, billing (exhausted quota, credit, or spend limit, however the service reports it), invalid-request, and malformed-response errors stop the request instead of retrying. So do refusals, and a response cut off at max_output with nothing to act on, which reports that the output limit was reached.

A valid server Retry-After hint—delay-seconds or an HTTP-date—sets the delay, even when it exceeds 30 seconds. Past dates mean no delay; malformed or ambiguous headers fall back to the default backoff. Without a valid hint, delays grow exponentially: 1s, 2s, 4s, 8s, 16s, 30s, then remain at 30s. The backoff restarts when a new request is prepared, including after compaction. Cancellation interrupts the wait.

Retries resend the same request: queued input and notifications wait until that response completes. Completed tools are not rerun, and partial tool calls from failed attempts are never executed. The failed partial response is discarded. The interface and session records may show retry status, but agents receive only the successful response or a terminal failure.

Context-window overflow triggers compaction rather than resending an oversized request indefinitely. Recovery stops after three context failures for one response; an invalid summary also has a separate three-attempt limit. Transient failures during summarization follow the same unlimited retry policy and do not consume either limit.

This prevents duplicate Skyhook tool execution, not duplicate provider inference: the provider may have processed the interrupted request, and additional usage may be incurred. Usage reported before interruption is retained; unreported provider usage remains unknown. Retries also cannot guarantee that tools hosted by the provider will not repeat side effects.

Reasoning history and local-server compatibility

On chat_completions and responses, a model’s reasoning is an effort level: none, minimal, low, medium, high, xhigh or max. On messages it is a thinking mode (off or adaptive) or an effort level under adaptive thinking: low, medium, high, xhigh or max. A value the codec does not accept is refused when the configuration loads, with the accepted values listed.

Responses and Codex automatically request reasoning summaries, even when no model reasoning effort is configured. Anthropic requests summarized thinking when reasoning enables thinking; with reasoning unset, the model’s default applies and may omit thinking text. Skyhook displays only the reasoning text or summaries the service returns, not otherwise-private reasoning. Support varies by provider, model, and compatible server.

Skyhook saves returned reasoning and automatically reuses it with the same API and model. Signed or encrypted reasoning is reused only with the same provider, endpoint, and configured routing or tenant identity; switching to another configuration omits it from requests without deleting the saved history. Readable reasoning is reused across those changes. A proxy changing the upstream behind an unchanged alias cannot be detected automatically. Signed thinking cannot be reused across compaction or mode switches. Visible summaries cannot replace private reasoning state the service requires. Reasoning the service did not sign or encrypt is still replayed, until signed or encrypted reasoning from the model appears in the context; from then on only that is sent. Services that accept only reasoning they signed or encrypted never get the rest: anthropic, openai and codex on responses, and litellm behind Anthropic and on responses.

Standard Chat Completions has no portable request-side reasoning field. Compatible Chat providers replay their returned reasoning under reasoning_content by default. Ordinary Chat responses without reasoning do not acquire an invented reasoning field. A server that spells the key differently selects it with reasoning_replay: "reasoning"; reasoning_replay: null keeps reasoning local. The openai dialect never replays on Chat, since the official API rejects unknown message keys; litellm behind an anthropic or bedrock upstream replays the thinking blocks the proxy returns, and openrouter replays its reasoning_details; signed ones are bound to the exact conversation like Messages thinking. A response with readable reasoning_details keeps those as its reasoning, in place of any plain-text reasoning it also streamed; a response without them keeps its plain text, which openrouter replays under its reasoning field. Once signed reasoning appears in the context, only signed thinking blocks are sent, a turn’s reasoning_details are sent whole, in order, only if one of them is signed, and plain-text reasoning stays local. Responses and Messages replay native reasoning automatically; a Responses reasoning item that restates its summary as content, or the reverse, is kept once, as its final item states.

Reasoning is replayed with its owning assistant turn, including turns that only call tools; it is never merged into answer text or fabricated <think> tags. Server-side tool and reasoning parsers/templates must be configured appropriately; Skyhook does not infer them from model names. Chat requests send max_output as max_completion_tokens; a server that only honours max_tokens sets output_limit: "max_tokens".

Connection timeouts

Every provider accepts positive startup_timeout_secs and read_idle_timeout_secs settings (both default to 600 seconds). Startup is a deadline for each HTTP attempt, while read-idle resets after each response-body chunk. For example:

providers:
  local:
    codec: "chat_completions"
    dialect: "compatible"
    base_url: "http://127.0.0.1:8080/v1"
    startup_timeout_secs: 600
    read_idle_timeout_secs: 600

Each retry gets fresh deadlines, so these settings do not limit the total time spent on a response. Cancel the request to stop waiting; the server may continue processing if it does not honor disconnects. See model failure recovery for retry behavior.

skyhook dump config writes the resolved timeouts, so a dump shows the defaults an entry left implicit.

Authentication

API keys and environment files

Any configured value that may hold a secret—api_key and an entry’s fixed headers—takes one of three forms: a literal, env: NAME to read an environment variable, or command: "..." to run a command:

providers:
  anthropic:
    codec: "messages"
    dialect: "anthropic"
    base_url: "https://api.anthropic.com/v1"
    api_key:
      env: "ANTHROPIC_API_KEY"
    # Alternatively:
    # api_key: "sk-ant-..."
    # api_key:
    #   command: "op read 'op://Private/Anthropic/api-key'"
    headers:
      x-title: "skyhook"
      x-proxy-token:
        env: "PROXY_TOKEN"

A literal secret is stored in plain text in the configuration file, and skyhook dump config prints it. Prefer env or command for secrets. api_key and headers are provider-only: all models in that provider instance share their credential resources, even when their codecs or request settings differ. A LiteLLM virtual key is sent as a bearer token for every codec, including messages.

Environment-variable values the provider sends are resolved when it is built and must be present and nonblank. They are used as they are, not trimmed: a value with a trailing newline fails, naming the provider and field. A command runs only on the first model request that sends its value, not when configuration is loaded or a conversation is opened. A successful command’s stdout is decoded as UTF-8 and trimmed of leading/trailing whitespace and newlines, then cached in memory for that provider instance. All its models, concurrent requests, and child conversations share the cache; a new process or provider instance resolves the value again. Failed commands are not cached and may be retried on a subsequent request. When the server refuses a cached value with HTTP 401, the value is discarded and the next request runs the command again. If the refused value had been accepted before, as when a short-lived token expires, the model request is retried automatically; a value refused on its first use fails the request. Empty output, invalid UTF-8, output that is not a valid header value, and nonzero exits fail the request without including command output in the error. Stdout is limited to 64 KiB. Commands run before the HTTP startup timeout; there is no separate command timeout. Cancelling the invocation terminates the command’s immediate child process, but does not guarantee termination of any descendants it launched.

Commands are trusted host configuration, executed with /bin/sh -c, inheriting Skyhook’s process working directory and environment, not an agent’s workspace or remote target. They do not run through tool approval. Standard input is closed and standard error is discarded; use a noninteractive secret-manager command that writes only the key to stdout. Do not put literal secrets in command strings or commit them to configuration files.

At CLI startup, Skyhook loads .env in the invocation directory before constructing providers. Existing process environment variables take precedence. A missing file is ignored; Skyhook does not search parent directories, the --workspace directory, or the configuration file’s directory. Loaded variables are also inherited by credential commands and other local child processes. Neither inherited host environment variables nor .env values are automatically forwarded into remote target processes; remote commands use the remote machine’s environment. Managed SSH routes disable SendEnv, SetEnv, and X11 forwarding. Local SSH authentication/proxy helpers still use the host environment; Skyhook’s SSH-agent forwarding is configured separately.

For example, in the directory from which you run skyhook:

ANTHROPIC_API_KEY="your-key"

Keep .env out of version control and restrict its file permissions. The CLI supports normal dotenv quoting, comments, export declarations, and variable interpolation. A malformed or unreadable file fails startup without printing its contents.

Codex subscription login

A codex provider uses Skyhook-owned OAuth credentials, one login per provider. Name the provider as it is configured: for a provider named codex, run skyhook auth login codex for browser authorization or skyhook auth login codex --headless for device authorization. skyhook auth status codex reports that provider’s local login status without contacting the service, so it cannot tell whether the service still accepts the login. skyhook auth status codex --check also presents the credentials to the service with the provider’s headers, refreshing them first if a request would, and reports the plan and rate-limit use it returns. It fails when the provider is not logged in or the service rejects the credentials. The check reads the account’s usage, which runs no model and spends no quota; that endpoint is not publicly documented by OpenAI, so what it reports may change. Several codex providers can sign in to different accounts or issuers independently. Login does not require the provider to have models.

When the provider sets auth_url, login and token refresh use that issuer instead of https://auth.openai.com. base_url likewise replaces the ChatGPT backend root, https://chatgpt.com/backend-api. Requests go to codex/responses beneath it, and --check to wham/usage, so a mirror serves both beneath one root. auth_url must use HTTPS (HTTP only on a loopback host) and carry no credentials, query, or fragment; a path prefix is kept. Skyhook never imports, reads, or modifies the official Codex client’s credential files.

Credentials are kept in a credentials/ directory next to the configuration file that defines the provider, as <provider>.json. For a provider in the user configuration that is ~/.config/skyhook/credentials/ (or under $XDG_CONFIG_HOME/skyhook). For a provider the workspace configuration defines, it is <workspace>/.skyhook/credentials/; keep that directory out of version control. For --config path.yaml, it is beside that file. Skyhook creates the directory when you first log in, readable only by you, and refuses to use one that grants any access to other users. Checking status or starting a session creates nothing there, except a missing lock file beside saved credentials.

To sign a provider out, delete its credentials/<provider>.json while no session is using it. Nothing is revoked on the server, so this is also how to clear credentials for a provider you have removed from your configuration.

A provider name becomes a file name, so it must contain no NUL character and be at most 250 bytes. On a case-insensitive file system, such as macOS by default, names that differ only in case (Work and work) share one credentials file; give such providers distinct names.

Stored credentials are bound to the issuer that granted them. When a provider’s issuer differs, requests fail without sending them and name the command that signs it in again. That command selects the provider’s configuration file with -c, so it signs in the same entry the session used wherever you run it.

MCP servers

Configure Model Context Protocol servers in the top-level mcp mapping, with one named mapping per server. It defaults to empty: no MCP connections, tools, or MCP prompt guidance are added unless servers are configured. Skyhook supports stdio and Streamable HTTP; legacy HTTP+SSE transport is not supported.

mcp:
  files:
    transport: "stdio"
    start_command: ["my-mcp-server", "--root", "/srv/project"]
    capabilities: ["read"]
    cwd: "mcp-work"                  # Relative to its config file's directory; default: workspace.
    env: { LOG_LEVEL: "warn" }        # Environment overrides for the launched process.
    startup_timeout_secs: 30         # Default; must be a positive integer.
    call_timeout_secs: 120           # Default; must be a positive integer.

  service:
    transport: "streamable_http"
    url: "http://127.0.0.1:8080/mcp"    # Full MCP endpoint, not an API root.
    capabilities: ["read", "write"]
    headers:
      Authorization: { env: "MY_MCP_AUTHORIZATION" }
    # Optional local startup fallback, only when the endpoint is unreachable:
    # start_command: ["my-http-mcp-server", "--port", "8080"]

Connections and credentials

start_command is an argument vector, not shell text; its first element must name a nonempty executable. Stdio requires it and rejects url and headers. Streamable HTTP requires an absolute HTTP(S) url. It connects first, and only starts the optional command if the endpoint is unreachable—not on authentication, protocol, or other server errors. cwd and env apply only to start_command; HTTP connections without a startup command must omit them. Relative cwd is resolved against the directory of the source configuration file that defines the value, not the agent workspace. Each server entry comes whole from one file, so a user server’s cwd is relative to the user file’s directory and a workspace server’s to <workspace>/.skyhook. Without cwd, the command runs in the session workspace, whichever file defines the server; MCP commands always run on the session host, never on a remote target. Timeouts must be positive whole seconds. Unknown settings and invalid transport combinations are rejected. Environment values must be strings; quote numeric-looking values such as WORKERS: "4".

HTTP headers maps header names to values in the forms a provider’s headers take: a literal, env: NAME, or command: "...". The complete value is sent as the header (for example, MY_MCP_AUTHORIZATION can contain Bearer ...). Invalid or repeated header names, blank values and invalid literals are refused with the configuration. An environment value is read, and a command run, when the connection starts; a missing, blank or invalid value, or a failed command, prevents that server’s connection from starting. Prefer env or command for secrets, and do not put them in start_command arguments or literal env values.

Trust and permissions

Trust boundary: configured startup commands are trusted configuration, including commands from a workspace .skyhook/config.yaml overlay. Review workspace config before use. They run during session startup without a model tool-approval prompt, only on the local root/session host—not on selected SSH targets. Only configure commands and endpoints you trust. Child agents share the session’s MCP connections rather than starting their own servers.

The session must hold the global mcp capability before any MCP server is launched or contacted, and before any MCP tool can be exposed or invoked. Each server’s capabilities sequence defaults to [] and adds requirements to that global gate. Valid names are read, write, exec, network, targets, ssh_agent, agents, interactive, and mcp. An agent must hold all listed capabilities to see or call a server’s tools; otherwise those tools are hidden from both the model catalog and JavaScript access. Servers whose requirements exceed the session’s capabilities are not contacted or launched at all. This is a host-configured gate, not an inference from server annotations. Nonempty lists also request those permissions through the normal approval policy, scoped to the MCP server/tool rather than a filesystem workspace. The implicit global mcp requirement is availability-only and introduces no approval prompt. approve_all never bypasses missing capabilities. An omitted or empty per-server list requires only global mcp and produces no permission prompt. MCP transports do not implicitly require exec or network; startup commands and endpoints remain trusted host configuration.

Using imported tools

Skyhook imports tools only, not MCP prompts or resources. At startup it initializes each server and discovers its tools, then freezes that catalog for the session lifetime; later catalog-change notifications do not add or replace tools. A server that fails startup/discovery is warned about and skipped rather than preventing the session from starting. The terminal interface’s sidebar shows each server’s startup status.

Imported tools are available to the model and through tool builders inside script. Use the exact advertised name and schema rather than deriving them from the server’s tool name. Names usually look like mcp_filesystem_write_file, but may have a suffix to avoid conflicts. Arguments may appear at the top level or under an arguments object so they do not conflict with common Skyhook arguments such as bg. Tools with invalid or unsupported input schemas are warned about and skipped individually.

Call a tool with tool[name](...) or its fluent builder. Calls return the common JobView envelope; the MCP payload (content, plus optional structuredContent and isError) is in .result. Images use the usual saved-output image handling, and server-reported errors retain their output in failed jobs.

Calls pass through the same cancellation and background-job machinery as builtins. Skyhook bounds discovery sizes and each message a server sends, at 64 MiB; a larger stdio message is discarded, the call it answered ends at its call timeout, and the server keeps serving other calls. Skyhook does not replay a call with an uncertain outcome after a connection failure. Cancellation cannot undo effects that already occurred on the server.

Scripting introduction

Every script call gets a fresh JavaScript environment. Run the example below from a Skyhook source checkout (or adapt the paths to your project). Tool calls are lazy: reusing one builder executes it once, while constructing an equivalent new builder creates a new call:

// Every direct JavaScript call is a JobView; use unwrap for the native payload.
const packageFile = (await tool.read({ path: "Cargo.toml" })).unwrap();
const matches = (await tool.search({ pattern: "TODO", path: "src" })).unwrap();

// Fluent setters accept the same arguments; each setter returns a new builder.
const readme = (await tool.read().path("README.md")).unwrap();

// Builders can be awaited independently (and can still be batched with Promise.all).
return { packageFile, matches, readme };

A workflow file runs in the same runtime:

skyhook --script workflow.js
# Run headlessly and exit when the workflow and shutdown finish:
skyhook batch --script workflow.js

There is no Node.js environment or recursive script call. Calls use the same tool schemas, capabilities, approvals, and saved-output behavior as direct tool calls. Read the JavaScript reference for supported globals, serialization, concurrency, result wrappers, and failure handling.

For delegation and background work, continue with jobs and agents. The tool reference, HTTP reference, and saved-output reference describe the individual contracts.

Jobs and agents

Delegation and child input

Child agents retain their conversation for follow-up work. Send instructions with tool.job(id).send({value: instructions}); the returned JobView completes, without a result, once the input is accepted. A running child receives the input at its next model-request boundary, without interrupting its current request or tools. Children do not need receive() for these updates.

A retained child whose job is completed, failed, or interrupted resumes under the same job and agent identity, including after a session restart. New instructions are appended to its existing conversation. Explicitly cancelled children and non-agent jobs cannot be resumed. jobs({job}) then exposes the latest run’s saved result, not an archive of earlier results; the child conversation and messages already delivered to the parent remain intact. A final reply whose completion the parent had yet to receive when the child resumed, as when input races that reply, arrives as a message event instead, unless a script already received it as the call’s result.

After a session interruption, retry resumes every retained failed/interrupted child without selecting them individually. A child-only retry leaves a parent waiting on work untouched and does not add a root model request. Retrying without an instruction continues the same history without adding a synthetic message.

A child’s result is {messages?, reply}: reply is its final reply. A background child’s earlier visible text replies arrive as message events without waiting for the child job to finish. Events carry kind: "message", the child job id, optional name, and text. They reach the parent at a model-request boundary, not by interrupting an in-flight request. Pending messages survive session restart. Reading a background job’s output does not consume its message events.

Message delivery does not mean the child has finished: completion also requires its owned work and queued inputs to be resolved. A completed background child’s notification carries the final reply in .result.reply; earlier replies are not concatenated into it. A foreground child’s earlier visible replies are not message events: its result saves them in messages, oldest first, each {text, at} with at the RFC 3339 UTC time it was made. Like any large result, a long messages is shortened in the call’s view and listed in presentation.truncated; read the rest with jobs({job, field: "/result/messages", index}). Replies a session restart cuts off from a call whose child still ran arrive as message events. messages is absent when there are none. The parent cannot make another model request until its foreground calls return.

When a child asks, the model’s own foreground call blocked on it moves to the background, so the model’s turn goes on and it can answer. That call is either its own agent call, which returns the child’s job:

{"id": 12, "state": "waiting_input", "presentation": {"notice": "This child agent asked a question, ..."}}

or its foreground script call, when the script’s tool.agent(...) waits on the child, which returns the script’s job, {id, state: "running", presentation: {notice}}. The script keeps running, and its completion arrives as a job event. A script’s own tool.agent(...) call never moves: in a foreground or background script it keeps waiting until the child finishes and resolves with the child’s result.

The question goes to the child’s parent agent, the agent whose model or script made the call, never the script itself or a further ancestor. It arrives as the same job event a background child’s question produces, after the replies the child made before it, as message events, in the same delivery: a parent parked in wait wakes for it. A child the model’s own call let go of is then a background job: its later replies arrive as message events and its completion as a job event. A script’s tool.agent(...) result saves in messages only the replies not delivered as message events. Nothing repeats a reply.

Child names are scoped to their caller: A and B may each create a child named worker, but all scripts owned by A share A’s child-name scope. A child retains its name even after termination; send follow-ups to its existing job instead of launching a duplicate. A launch that created no child holds no name: of two launches taking one name at once, the first to start its child keeps it.

Each model-facing ask contains one {id, prompt, options?} question; independent concurrent calls are merged by the runtime. A child question batch changes its stable agent job to waiting_input; answer that job with tool.job(id).send({value: answer}) in a script. For a merged batch, use tool.job(id).send({value: {question_id: answer, another_id: answer}}); the keys are the IDs included in the waiting job’s questions output. Each answer can be a string (a suggestion label or free-form text), or {"answer": "selected label", "comment": "user text"} for a suggestion with a non-whitespace comment. A single question returns that value directly; a merged batch keeps each value under its question ID. Root-agent questions go to the host interface instead of a parent agent. ask also accepts optional bg (boolean, default false). With bg: true, the call returns job metadata immediately so the agent can continue independent work. Use jobs({job}) to inspect the pending question and eventual answer; the ask job also accepts tool.job(id).send({value: answer}). Omitting bg or passing false keeps the usual foreground wait. Multiple outstanding child question batches are combined on the stable agent job; parents may answer a subset keyed by question ID, and unanswered questions remain pending. IDs must be unique across that child’s outstanding questions. Background questions are still owned jobs: children must await or cancel them before finishing.

agent accepts an optional depth delegation budget. It defaults to zero, making the launched child a leaf. The value must be less than the caller’s own available depth; once no depth remains, agent is omitted from both model tools and script bindings. Its optional workspace accepts relative or absolute directories for both local and remote children. Relative overrides resolve against the workspace selected by the target rules. Children receive a fresh conversation, shared session instructions and host-owned skills, and their parent’s active model, including model switches and restored session selections. An explicit child model overrides the inherited model, and mode runs the child in a mode in place of the caller’s capabilities. Both take only entries configured with a hint, and mode only those granting nothing the caller lacks; an input with nothing to offer is absent. This applies equally to local children, remote children, and deeper descendants. Agents on the same target share files; a workspace override creates no filesystem isolation. Children must finish or cancel all owned jobs and descendants before their agent job completes. Only root agents may leave background services running after answering.

Job lifecycle and cancellation

Background-capable tools accept an optional bg argument. Calls use the common JobView contract; a background launch reports the job as launched, running and without a result, even if it has already finished. A loaded literal null result is result: null. Cancellation returns target-job metadata in .result. A child question has state: "waiting_input"; jobs({job}) returns its stable question IDs and text in presentation.question, regardless of its size.

Jobs normally follow queued → running → completed, optionally cycling through waiting_input → running; failed, cancelled, and interrupted are terminal alternatives. A jobs({job}) read acknowledges the question or result it returned, suppressing duplicate automatic notification; an outcome that arrives after the read is still notified. Explicit reads remain repeatable, and jobs itself never waits; see waiting for background work. Unanswered questions do not expire. Send answers to the stable child-agent job ID.

Cancellation cascades through descendant jobs and agents and terminates managed command process groups locally and remotely. It is a request: use jobs({job}) to confirm termination. Deliberately detached processes and unreachable remote hosts limit cleanup. Command timeouts are optional; omission or null means no deadline. Explicit timeouts of 1–3600 seconds terminate execution, retaining captured output. A nonzero command exit is a normal result; see tool result shapes for process payloads.

Job names

agent, exec, and fetch accept an optional name describing the work. Names must use lowercase kebab-case: start with a letter, then use lowercase ASCII letters, digits, and single hyphens between nonempty words. Examples include inspect-config, run-tests, and build-v2. Names are descriptive labels and do not replace job IDs. Tool job names need not be unique; child-agent names must be unique within their caller’s scope, as described above.

return tool.exec({command: ["cargo", "test"], name: "run-tests", bg: true});

Names appear in active-job state, job envelopes (including notifications and inspection), and durable job records. They survive session resume. Omitted or null names leave jobs unnamed; invalid names are rejected before execution. JavaScript builders also support .name("run-tests").

Waiting for background work

Launch with bg: true, do independent work, then yield for events and inspect status. wait resolves when the agent can act: if other foreground work is still running, it keeps waiting; otherwise any pending event resolves it. Each notification resolves a given caller’s wait once, without consuming the notification content. The next model request receives the accumulated events together. A wait timeout ends the wait, not the job. A child must finish or cancel all owned work before it can finish; root background services remain managed by the live session. In headless mode, shutdown cancels and drains outstanding work, so workflows must await work they need completed.

const job = await tool.exec({command: ["cargo", "test"], name: "run-tests", bg: true});
let status = await tool.jobs({job: job.id});
while (["queued", "running", "waiting_input"].includes(status.state)) {
  await tool.wait({timeout: 300});
  status = await tool.jobs({job: job.id});
}
return status;

To request cancellation, use await tool.job(job.id).cancel() and inspect the job until its state is terminal. Wait events can concern other jobs; they do not prove this job finished. See saved job output for inspection and pagination, and runtime state for todos and active-job snapshots.

JavaScript runtime

Supported globals and concurrency

The runtime exposes:

  • Date, RegExp, Map/Set, Proxy/Reflect, and BigInt;
  • ArrayBuffer, DataView, and typed arrays, including Uint8Array.fromBase64, .fromHex, .toBase64(), and .toHex();
  • performance.now() for measuring elapsed milliseconds;
  • await sleep(ms) for asynchronous waits, resolving to undefined. The delay must be a number of milliseconds from 0 to 2147483647, as for JavaScript timers; fractional values are accepted, and any other value throws a TypeError at the call. Sleeps stop when the script is cancelled, and unawaited sleeps do not keep it alive;
  • new WorkPool(concurrency).map(items, worker) and .run([fn1, fn2, ...]) as async iterables yielding {index, value} results in completion order, or {index, error} for a task that threw; remaining items continue. run requires exactly one array of functions, each called with no arguments—not variadic arguments. Invalid run arguments, and a map worker that is not a function, throw before any task starts. Early iterator closure stops scheduling and drains running work;
  • .feed(next, worker, {wake}) for work that becomes ready over time: whenever a slot frees it calls await next(running, free) (a Map of running keys to their items, and how many slots are free), starts the returned items whose key (a string or number) is not already running, and yields {key, item, value} or {key, item, error} as each completes. Items beyond the free slots wait and start, in order, before next is called again. It ends when nothing is running and next starts nothing. An optional wake function (such as receive) is called while work runs and raced alongside it: each value it resolves yields {wake: value}. A wake still pending when the feed ends is released, so the input it would have taken goes to the next receive();
  • await receive() waits for the next JSON value sent to the script’s own job ID with tool.job(scriptJobId).send({value}); the script must be launched with bg: true. Values arrive in order. Calling release() on a receive you no longer await hands its value, taken or not, to the next receive(). This is script input, not child-agent input: agents receive owner updates automatically.

For example, pass the task functions to run in one array:

const results = [];
for await (const {index, value} of new WorkPool(2).run([
  async () => 1,
  async () => 2,
  async () => 3,
])) {
  results.push({index, value});
}
return results;

Memory limit

Each script call has a 512 MiB (536,870,912-byte) QuickJS allocation limit. This covers runtime-managed memory, including JavaScript objects, strings, and JavaScript-created ArrayBuffer and typed-array storage. Freed memory restores capacity; the limit is not a cumulative allocation, execution-time, or token budget.

An allocation that exceeds the limit throws an out-of-memory error. Scripts can catch it; an uncaught error fails the call. Keep headroom for temporary allocations during result conversion and serialization.

This is not a total process-memory limit. Rust-side tool results, host bookkeeping, and other native allocations are outside the budget, and concurrent script calls each have their own allowance.

Saved output and serialization

Read or search saved command output with tool.jobs({job: commandJobId, field: "/result/stdout"}). A jobs read returns the existing JobView for that job; it does not add another wrapper. Field-selected output is a job view, not a raw string: the page is in presentation.preview, as lines of text, elements or members of JSON, or query matches, with pagination metadata alongside it. Field, pagination, search, and query selections omit image attachments; whole-output reads can attach saved images.

JobView response contract

Direct model calls and JavaScript tool calls return the same JobView envelope:

id?: number
state?: string
result?: JSON
error?: string
meta?: JobMetadata
presentation?: Presentation

Tool results omit absent fields and empty lists at every level. Scripts read a field the response’s schema declares but it lacks as null: r.id, r.state and r.meta are null on an ordinary completed call, and an absent stdout is null. The model’s views stay sparse. Fields inside a previewed or paged jobs({job}) result are not filled, since a preview may omit them.

A completed call with nothing more to read or resume (no truncation, page, capture, question, notice, or retained child that input resumes) omits id and state. result is the native tool payload. It is present exactly when the job has a result, and a loaded literal null result stays result: null. A tool with nothing to return, such as tool.job(id).send, completes without a result. meta is absent on an ordinary successful foreground call. Background handles, listings, inspections, and failures carry meta with what the caller does not already know: tool and name except in the response to the caller’s own foreground call, parent, target, and workspace only when they differ from the calling agent’s own, and code for a denial. A pre-admission failure lacks id, as does a call the runtime could not make at all: a tool that is no longer available, or a call interrupted while the session was not running, is answered with this same failure shape.

presentation is absent when a successful foreground response has no truncation, page, capture, question, or notice. When present, it groups preview, shape, truncated, captures, question, and notice, each present only when it has content, and precedes result. Read a text page as r.presentation.preview.lines and a question as r.presentation.question, {questions}. Presentation never shortens a question. A script never sees a question its tool.agent(...) child asks: the call keeps waiting for the child’s result while the question reaches the script’s agent as a job event, and a foreground script’s own call moves to the background so that agent can answer (see delegation). Truncation entries keep their source paths rooted at /result/....

JavaScript receives complete data; model views may shorten fields as described in saved job output. A returned tool response keeps its complete fields whole in the script’s own preview; a value taken out of it, such as response.result, is shortened like any other returned value. Tool descriptions give a call’s response as JobView<T>: the envelope, with the native result T at .result. A successful jobs({job}) read of a failed target is still a successful tool invocation returning that failed JobView; response.unwrap() checks the observed job state and can therefore throw for that view.

response.unwrap() and native results

Use response.unwrap() synchronously when a completed native payload is needed:

const data = (await tool.read({path: "README.md"})).unwrap();

It returns response.result when the response is completed (an absent state means completed), or null when the job has no result, and throws for failed or pending responses; the thrown error has error.response containing the envelope and error.output equal to its .result, plus error.job and error.code when the response has an id or denial code. The method is non-enumerable and runtime-only: Object.keys, JSON serialization, logging, returning, and saving the envelope retain plain JSON. Nested payloads, JSON copies, and receive() values are not decorated, and there is no built-in tool.unwrap helper.

jobs({job}) reads already return views, so inspect their presentation.preview, presentation.captures, or pagination rather than unwrapping them. Operational tool failures are failed views rather than JavaScript throws; programmer, serialization, receive, and sleep errors still throw.

Before returning results, convert BigInt values to strings, dates with .toISOString(), and typed arrays with Array.from(bytes), .toBase64(), or .toHex(); they fail with their path otherwise. The runtime does not provide Node.js APIs, fetch, URL, TextEncoder/TextDecoder, or setTimeout/setInterval. Scripts cannot import modules, including the runtime’s own.

Script results and failures

Every script result payload is {value: <JavaScript return>, console?: <captured text>, failure?: <details>}. Scripts without a return have value: null, silent scripts have no console, and failure is absent unless a failure has details. In a script JobView, the payload is at /result and its return is at /result/value; logs are at /result/console.

console.log(...values) captures space-separated text, formatting objects as JSON. A running script’s captured text can be inspected with tool.jobs({job: scriptJobId, field: "/result/console"}). These inspections read the currently available output; they do not subscribe to future writes or wait for script completion.

There is no fixed console-capture size cap. Disk capacity and I/O failures still apply. Automatic previews can shorten displayed output without discarding captured output; use paging, search, or queries to inspect more. The 16 MiB limit applies to JavaScript source, not console capture.

On a script execution failure, the saved script payload is {value, console?: <captured text>, failure?: <details>}, where value is null unless only the returned value’s conversion failed; the enclosing JobView is failed and carries its error: the thrown error’s message and stack, or the JSON of any other thrown value. The message leads with the error’s name unless it is plain Error. Stack frames are skyhook-script:line:column positions in the submitted body, or end of source for a syntax error where input ended early; frames outside the body are left out. Console text belongs to the script result, not job metadata.

failure holds a thrown error’s other properties: its cause and enumerable properties, such as the job and code of an unwrapped failed response, whose full view tool.jobs({job}) reads. It is absent when there are none, so use the enclosing JobView’s state and error to determine whether execution failed. Automatic previews can shorten it.

Returned values convert to JSON:

  • As in JSON.stringify, an undefined member is omitted, and a top-level undefined or an undefined array element becomes null.
  • Promises, builders and other thenables anywhere in the value are awaited.
  • An Error becomes an object of its name, message, cause and other properties.
  • An unpaired surrogate in a string becomes U+FFFD.
  • Anything else that is not JSON is a problem at its path, such as $.items[2]: non-finite numbers, BigInts, functions, symbols, cycles, objects other than plain objects and arrays, unpaired surrogates in keys, nesting deeper than 100, and a member whose getter throws or whose promise rejects, reported with its error’s message.

Conversion runs after the body returns, so the body’s own try/catch cannot catch its problems. A value with problems still fails the script, with an error listing them by path, but its saved value keeps everything else, with null in place of each problem; captured console text is kept as on any failure.

Tool arguments convert the same way when the builder is made, so a failure throws at the call: undefined properties are omitted, while undefined array elements, promises, builders, Errors and unpaired surrogates fail.

Builder execution and policy

Builder setters and object arguments accept the same inputs; omitted values receive the tool’s normal defaults. Use .set(key, value) to select an argument by name, for example tool.read().set("path", "README.md"). Unknown .set keys throw a TypeError; calling a nonexistent fluent setter produces the usual JavaScript method-call error.

Awaiting a builder executes it immediately. Returning builders recursively executes independent branches concurrently. Only returned values expand: inside the body, await {a: builder} awaits the object, not its members, so await each builder or use Promise.all. Calls use the same capabilities, approvals, path access checks, and saved-output behavior as direct tool calls. Scripts cannot invoke the script tool recursively.

Failed tools retain any partial output (including captured process output on timeout) in the failed JobView’s .result; JavaScript operational failures do not reject the builder promise. Use response.unwrap() when failures should throw rather than be handled as data. Programmer and serialization errors are not operational tool failures and still reject/throw.

See scripting introduction for lazy-builder examples and jobs and agents for background work and child input.

Built-in tools

read, search, glob, exec, fetch, write, replace, remove, script, targets, target_add, skill, jobs, wait, ask, todo, and agent. Calls use the common JobView envelope; native payloads are in .result. skill is offered only when skills were discovered.

exec({command}) runs a string with /bin/sh -lc, or an array as a program and arguments without shell parsing: exec({command: "cargo test 2>&1 | tail"}) or exec({command: ["cargo", "test"]}).

jobs() lists the current agent’s active jobs, excluding the listing call and its containing script. jobs({all:true}) includes completed history. A listing returns {jobs, older}: the newest limit jobs (100 by default), oldest first, and how many older ones it left out, omitted when none were. The listing payload is in the envelope’s .result. jobs({job}) reads that job’s saved output and status immediately; it never waits for new output or completion. It returns the existing queried view, not another wrapper, and accepts the output selections field and limit, with start, offset, pattern, and context for text, or index and query for JSON. all cannot be combined with job, and the other selections require job unless they restate their defaults. Scripts also control jobs with tool.job(id).send({value}) and .cancel().

Use wait({timeout?: seconds}) (or await tool.wait(...) in scripts) to yield until an agent event or a timeout, then inspect the relevant jobs. The returned view’s .result is {reason, waited_s}: reason is "event", "timeout" or "cancelled", and waited_s counts the whole seconds waited. A cancelled wait is a failed view that still carries this result. Omitted or null timeout waits indefinitely; a supplied timeout must be a positive integer number of seconds. An event does not guarantee a particular job has completed; inspect its current status. See waiting for background work for when a wait resolves.

See the JavaScript response contract for response.unwrap(), serialization, and operational-failure behavior. In this reference, tool.jobs({job}) and other inspection calls return views for reading their presentation fields; use the task-specific contracts below for their payloads.

Reading and replacing text

read({path}) reads only regular files. A file is text when it is valid UTF-8 without NUL bytes; any other file is attached if it decodes as a supported image (PNG, JPEG, GIF or WebP) and rejected otherwise. replace({path, old, new, count?}) edits files of at most 64 MiB, both before and after the replacement; old and new together are at most 4 MiB, as is write content.

Creating files with write

write({path, content}) atomically creates or replaces a UTF-8 file, creating missing parent directories first, for example write({path: "reports/run/summary.md", content: "..."}). As in the operating system, .. cannot follow a directory that does not exist yet, so missing/../file fails.

write({path, source: {path, target?}}) copies another file’s bytes exactly, including binary files of any size. Supply exactly one of content or source. The destination is always in the caller’s target and workspace. The source is read on its own target: the caller’s when target is omitted, or the named one, which requires the targets capability and follows the same workspace rules as any target selection. One approval covers reading the source, connecting to its target, and writing the destination, except that a remote source path outside that target’s authorization root is approved separately when its target requests it. Contents stream in chunks, through the session host when either end is remote, and the destination is replaced only once the whole copy has arrived. For example, an agent on a remote target can copy a file from the session host with write({path: "tool.bin", source: {path: "/srv/tools/tool.bin", target: "root"}}).

HTTP requests with fetch

fetch is an HTTP request tool, available directly and as tool.fetch(...) in scripts. It runs on the selected execution target: DNS, TLS, proxy discovery, uploads, and downloads all happen there. Relative paths use that target’s workspace; no files are implicitly copied between machines. Like exec, it supports name, bg, cancellation, and saved job output.

// Read a web page as markdown, without its HTML boilerplate.
const page = (await tool.fetch({url: "https://example.com/article"})).unwrap();

// Send JSON to an API. HTTP 4xx/5xx are responses, not tool failures.
const response = (await tool.fetch({
  url: "https://api.example.com/items",
  method: "POST",
  body: {kind: "json", value: {name: "example"}}
})).unwrap();

// Duplicate query parameters and request headers are supported.
const search = (await tool.fetch({
  url: "https://api.example.com/search",
  query: [["tag", "rust"], ["tag", "http"]],
  headers: {Accept: "application/json"}
})).unwrap();

// Send a file as the raw request body, without base64-encoding it in model context.
const upload = (await tool.fetch({
  url: "https://api.example.com/upload",
  method: "PUT",
  headers: {"Content-Type": "application/gzip"},
  body: {kind: "file", path: "dist/archive.tar.gz"}
})).unwrap();

// Save a download on the execution target. Existing files are preserved unless overwrite:true.
const download = (await tool.fetch({
  url: "https://example.com/archive.tar.gz",
  save_to: "archive.tar.gz",
  max_bytes: 104857600,
  timeout: 300
})).unwrap();

// Explicitly opt out of certificate validation for a development HTTPS server.
// This permits untrusted certificates and enables interception; never use casually.
const development = (await tool.fetch({url: "https://localhost:8443/health", insecure: true})).unwrap();

Request options

Only url is required. method defaults to GET and accepts standard methods and valid custom HTTP method tokens. query is an ordered array of string pairs, appended to any existing URL query. The default User-Agent is Skyhook/<version>; an explicit User-Agent header overrides it. Header values can be strings or arrays of strings. auth accepts {kind:"bearer",token:"..."} or {kind:"basic",username:"...",password:"..."}; arbitrary authentication schemes can use headers. Do not combine auth with an Authorization header or embed credentials in URLs.

body has exactly one tagged source:

  • {kind:"text",value:"..."} for UTF-8 text.
  • {kind:"json",value:...} for any JSON value, including null.
  • {kind:"form",fields:[["key","value"],...]} for URL-encoded forms with repeated keys.
  • {kind:"base64",value:"..."} for inline binary data.
  • {kind:"file",path:"..."} for a regular-file upload as the raw request body.

Multipart form-data encoding is not supported. File bodies can set their media type through the Content-Type request header; they are not interchangeable with multipart uploads.

Responses and extraction

Responses include the status, the received byte count (size), the elapsed milliseconds (duration), and a tagged body: page, unreadable, json, text, base64, file, or empty. Followed redirects add their history (redirects), whose last location is the final URL. Response headers is absent by default; set include_headers: true to return a map of repeated header values. This option does not affect the headers request-header map.

response_format chooses how an inline body is returned:

  • auto (the default): HTML is read as markdown (below). A textual body that is JSON is read as that value, following the JSON output rules: the body is then {kind: "json", value}. A body served as HTML that does not begin like HTML is textual, so JSON labelled as HTML is still read as JSON. Other textual bodies are decoded into body.text, and binary bodies, including any that open with control bytes text never holds whatever their media type, are base64 in body.data.
  • readable: like auto, but reads any textual body served as HTML as a page, and also reads a body as HTML when it looks like HTML but was served as another media type, such as text/plain.
  • text: any body decoded as text exactly as sent, including HTML and JSON.
  • base64: the response entity bytes.

HTTP decompression is automatic; these are not raw wire bytes. Character decoding honors BOMs, HTTP charsets, and HTML meta charsets where applicable. Without an Accept header, auto sends text/html,application/xhtml+xml,application/json;q=0.9,*/*;q=0.8, as a browser asks, so sites that answer other requests with an empty page or a non-HTML variant return their HTML, while APIs that serve no HTML still return JSON; readable sends text/html,application/xhtml+xml;q=0.9,*/*;q=0.8. save_to saves the response to a file on success instead of embedding the payload, creating missing parent directories, and ignores response_format. Errors or cancellation do not replace an existing destination.

HTML is returned as {kind: "page", title, byline?, site_name?, language?, scope, markdown}. scope is article when the page has a readable main article, and markdown holds only that article. Otherwise it is page, and markdown holds the whole page body without scripts, navigation, form controls, footers, and hidden elements. Markdown keeps headings, absolute links, lists, code blocks, and tables with a header row, but not images embedded as data; other tables read as their text. A table cell spanning several columns or rows is repeated in each, so every value stays under its header. Extraction does not execute JavaScript or fetch linked assets. HTML that cannot be read is returned as {kind: "unreadable", reason, text} with its decoded source in text. reason is too_large (over 10 MiB of HTML, 50,000 elements and parse errors, 256 levels of nesting, or 20 MiB built while converting it), no_text (for example a page rendered by JavaScript), or parser_failed. Extraction never fails the call: the status, headers, and redirects are always returned.

Automatic job presentation may shorten a result over its preview budget: the body, and also long header values and redirect lists, recording what it cut; retrieve the complete saved payload using jobs({job}) fields such as /result/body/markdown, /result/body/text, /result/body/value, /result/body/data or /result/headers. JavaScript calls still receive the complete payload for processing.

Limits and failure diagnostics

The default total timeout is 30 seconds, connect_timeout is 10 seconds, and max_bytes is 10 MiB. The response limit can be raised to 100 MiB; total uploads are also capped at 100 MiB. Timeouts must be between 1 and 3600 seconds and max_redirects cannot exceed 20. Limits apply while streaming, including to decompressed data; exceeding a limit fails rather than reporting an incomplete body as successful. Model-visible preview truncation is independent: retrieve saved results with jobs({job}). Cancellation and timeouts cannot undo server-side effects, and requests are not automatically retried.

Transport and processing failures are ordinary failed jobs with no result: in scripts, a failed JobView rather than a rejected promise. The error names the operation in progress (for example send HTTP GET https://example.com, receive HTTP response body, or the download path), then the cause: an I/O kind with its OS error code when the failure carries one (such as connection refused (OS error 111)), or a fixed message such as the TLS handshake failed or response exceeds max_bytes. A failure after the request was sent notes that the request may have executed; a save_to failure that left its destination untouched also reports that it is unchanged, unless it created directories to hold it, which remain. Failure messages never copy underlying error text, query strings, credentials, headers, or bodies; URLs are reduced to their origin. A response’s duration is measured inside fetch on the execution target; it does not include SSH startup or initial tool approval.

HTTP 4xx/5xx responses still complete normally: a 405 establishes HTTP connectivity, not successful ingestion. Permission denial and cancellation retain their separate semantics.

Redirects, proxies, and security

redirects is safe by default (follow GET/HEAD), follow to follow other methods too, or manual to return the redirect response. max_redirects defaults to 5. Changed origins require authorization; cross-origin requests do not inherit sensitive request headers, and HTTPS-to-HTTP redirects are rejected. Redirect method rewriting follows HTTP conventions; 307/308 preserve method and body. proxy selects an explicit HTTP proxy; otherwise fetch uses the target’s proxy environment. insecure defaults to false. Setting it to true disables HTTPS certificate validation for that invocation only; it does not disable authorization or permit HTTPS downgrade redirects.

All requests require the network capability and approval, not just filesystem read permission. File uploads additionally require read, and downloads require write, including paths inside the workspace. Loopback and internal-service URLs are supported; this is a general-purpose network tool, not an isolated browser or a network sandbox. Returned content is untrusted data. There is no ambient shared cookie jar: set Cookie explicitly and use include_headers: true to inspect repeated Set-Cookie headers when needed. Arguments, response bodies, and headers can contain secrets and are subject to the normal session/job persistence rules; do not assume HTTP credentials are omitted from session records or that insecure makes authentication safer.

Saved job output

Tools execute once and save their complete results. File reads capture snapshots; subsequent retrieval does not reread changed files. Search and glob capture their complete result sets. There is no configured capture-size cap or automatic eviction; storage failures are reported as failures, with retained partial output marked incomplete.

Tool result shapes

See the JavaScript JobView response contract for the envelope, metadata, presentation group, and unwrap() behavior. This page focuses on saved output and the task-specific payloads below. A failed or pending view remains an ordinary response.

Search and glob patterns filter eligible files without overriding hidden-file or ignore settings. Nulls in tool payloads are preserved; fields a tool has no value for are absent. Process results contain exit_code, or signal when a signal killed the process, and the stdout and stderr streams that produced output; scripts read an absent stream as null. A stdout holding JSON is read as that JSON; see JSON output. Completed agent calls return their complete answer string without automatic truncation. Child questions return {questions:[{id,prompt,options?}]}.

Directory reads return grouped entries with file sizes, for example: {kind:"directory",entries:{files:[{name:"main.rs",bytes:4096}],directories:["lib"]}}. Groups are files, directories, symlinks, and other, with sorted names; empty symlinks and other groups are absent, and scripts read them as null. Search returns {matches:{"src/main.rs":["12: matching text"]}}, preserving source whitespace. An empty search result has matches: {}. A matched line longer than 1 KiB comes back as the text around its match, ending (line truncated, N bytes). A file or directory the search cannot read is skipped and listed, as skipped: [{path, reason}] with reason unlisted, unopened or unread; the other files’ matches stay, and matches is then incomplete. targets returns each target’s routing and authentication metadata; fields a target does not set are absent. target_add completes without a result. All defaulted input fields are optional in tool schemas.

By default, hidden entries (including .git) and ignored files are excluded. hidden: true includes hidden entries, while no_ignore: true independently disables ignore files. Searches rooted in subdirectories inherit ancestor ignore rules; explicitly requested paths remain accessible.

Diagnostics

Diagnostic messages identify the failed operation and its subject, such as a path, argument, job, or output field. Workspace-operation failures include the applicable execution target; host/session failures are not attributed to the caller’s remote target. “On session host” is shown when the viewing agent is on a different target and omitted for an agent on the host. Inspecting a remote job’s saved output does not connect to that machine: a retrieval failure concerns saved output, while a retrieved execution error retains the original operation’s context.

Structured job diagnostics are rendered for the viewing agent, exposing target aliases only when that viewer’s capabilities permit them. This is not a general redaction guarantee for saved output. A jobs output read made with broader capabilities saves its already-rendered view as ordinary JSON. Later reads of that saved snapshot with narrower capabilities retain the earlier JSON unchanged, as do reads of script results that copy it. Arbitrary returned JSON is not inspected for diagnostics or target aliases, and already-committed model messages are not rewritten.

An error does not by itself establish that an operation had no effects. A command may have started before output capture failed, a file replacement may have committed before a durability check failed, and a recursive removal may have deleted some entries. Messages distinguish known pre-execution failures from known or uncertain later effects. Do not automatically retry a mutation merely because its result is a failed job.

Outcome distinctions still matter: a nonzero process exit is a completed command result, an HTTP error status is a normal HTTP result, and a wait timeout ends only that wait. A read of a missing or inaccessible path is a failed job like any other tool failure, except that a missing path outside the workspace is refused like a denial unless the approval policy allows the operation without asking (permissions). Policy denials, operating-system access failures, cancellation, and interrupted execution remain distinct.

JSON output

Process stdout and MCP text content blocks are checked once when the job finishes, and a textual HTTP body when it arrives. When the whole text is one JSON object or array, or two or more objects or arrays in a row (JSON Lines, or concatenated output such as jq prints by default), the value replaces the text; a sequence becomes an array. stdout and MCP text then hold the value, and stdout’s result type reads string | object | JSON[]; an HTTP body becomes {kind: "json", value} (response_format: "text" keeps it as text). Scripts and the model both receive the value, and page or query it as JSON.

The text stays text when it is anything else (a lone number or string, or JSON with other text around it), is unfinished (cut off or cancelled output), nests deeper than 64 levels, repeats an object key, or holds a number that double-precision floating point cannot represent as written. A number qualifies when the shortest decimal that reads back as its nearest double has the same value as written: 0.1, 1.0 and 1e30 do; integers above 2^53 such as 9007199254740993, over-precise decimals, and out-of-range numbers such as 1e400 do not.

Automatic previews

JavaScript receives complete result data. The model’s automatic view of a finished result is a preview:

  • Text fields, strings reached only through objects of at most 100 members, such as stdout, file content, or body.text, each keep at most 200 lines or 16 KiB (16384 bytes), whichever comes first, counting UTF-8 content bytes before JSON escaping. Together they keep at most 64 KiB; later strings are shortened like everything else.
  • Command streams, the stdout and stderr text fields of exec, keep both ends within those limits: their first whole lines, up to 60 lines and 30% of the bytes, then a marker line such as … lines 61–4860 omitted …, then their last whole lines, up to 140 and the bytes the first lines left. The marker line is not part of the output and is not counted. A stream whose last line alone is over those bytes keeps only its start, like other text fields. An exec response a script returns keeps both ends of its streams in the script’s result too.
  • Everything else shares one 8 KiB preview budget, which also counts the shape and truncation records below. When it is exceeded, strings keep their first 256 bytes; if every element then fits, all are kept. Otherwise arrays keep their first elements, with one count shared by every array at any depth: the largest that fits, and at most 10. Objects with more than 100 members keep their first members in source order the same way; smaller objects keep all of theirs, or when that does not fit, none. When even a single sample does not fit, strings get shorter, then deeper levels are left empty. Values holding complete fields keep the path to them.

Fields a tool declares complete are never shortened and are not counted: skill instructions, child agent answers, and the job views jobs reads return. Errors and child questions sit outside result and are also complete, including those of tool responses a script returns. A response can therefore exceed the budget; it does not limit response size.

presentation precedes result. When arrays or objects were cut, presentation.shape describes the whole result: objects list each member’s shape under its own name, and a member only some objects have includes absent, as in "boolean|absent"; arrays are [count, element], with "min..max" when lengths vary and [0] when always empty; types that vary are joined as "string|null", or {"|": [...]} when one is a container; objects with more than 100 members read {"*": value, "#": count}. A shape over half the budget collapses its deepest levels to "{…}" and [count, "…"].

presentation.truncated lists each cut in its own unit:

  • {field, total_lines, next_start, next_offset?} for a string, with the exact position to continue from; next_offset is present only when that position is inside a line.
  • {field, total_lines, next_start, tail_start} for a command stream shown around a marker line: lines next_start up to, but not including, tail_start were left out.
  • {field, shown, total_elements, kept?} for an array.
  • {field, shown, total_members, kept?} for an object.
  • {field, cuts} for further cuts within field, beyond the first 32 listed.

kept lists the index ranges shown, as [[first, last], ...], when a complete field inside an array or object keeps an element beyond the leading ones; such records are always listed. Reading a cut array or object continues at its first value not shown. Finished jobs with incomplete captures include an Output incomplete; captured fields remain readable with jobs({job, field}). notice. These rules also apply after session resume and to completed remote jobs.

Script result presentation

The enclosing script’s .result is {value, console?, failure?}; silent scripts have no console. Ordinary tools have no console field. Existing JobViews such as tool.jobs({job}) reads are not wrapped again.

Presentation never changes the full saved return value. Default script output retrieval returns the composed script payload; explicit field selections read saved script data. Logging and returning the same data explicitly produces both outputs.

Paging, searching, and querying

Explicit jobs({job}) selections return a view whose presentation.preview is one page of the selected field, in that field’s own unit:

FieldSelectorsPage
Text: a string, a number, boolean or null, or a capture that is live or unfinishedstart, offset, limit, pattern, contextlines, total_lines, next_start, next_offset
A JSON object or arrayindex, limitelements or members, total_elements or total_members, next_index
A JSON object or array, queriedquery, index, limitmatches, total_matches, next_index

Using another unit’s selectors is rejected with an error naming the field’s kind; selectors that only restate their defaults (start: 1, offset: 0, context: 0, and index: 0 without query) select nothing, so they are accepted with either kind of field. Job metadata is never truncated.

// Read part of a text field, search it, and continue a long line.
jobs({job:42, field:"/result/stdout", start:300, limit:80})
jobs({job:42, field:"/result/stderr", pattern:"(?i)error|warning", context:2})
jobs({job:42, field:"/result/stdout", start:22, offset:54, limit:100})
// Page a JSON array, then continue at the returned position.
jobs({job:42, field:"/result/stdout/items", index:200, limit:50})
// Select within JSON.
jobs({job:42, field:"/result/stdout", query:"$.items[?@.status.phase == 'Failed'].metadata.name"})

field is a JSON Pointer: /result/content selects a file snapshot, /result/stdout and /result/stderr select process streams. For scripts, /result/console selects captured console text and /result/value selects the JavaScript return; append pointer segments for nested data, for example /result/value/items. The empty pointer "" selects the whole saved output, the members of {"result": ...}. limit is 1–1000 lines, values, or matches (default 100). Output inspection returns immediately; it does not wait for new output.

Text pages

start is one-based (default 1); offset is a zero-based UTF-8 byte offset within that starting line (default 0). context is 0–20 surrounding lines (default 0), and positive context requires pattern. Pages hold up to 32 KiB of JSON-encoded line content; field is omitted when it is the field the model asked for. next_start is absent when no continuation remains, and next_offset is present only when the next position is inside a line. lines has one entry per returned line (or fragment of an oversized line): a string for a plain read, and {line, text} with the one-based source line number for a search. Empty fields have zero lines; a final unterminated line counts, and a trailing newline does not add an empty line.

Pages prefer whole lines; oversized lines are split at UTF-8 boundaries. The page budget may return fewer lines than limit: use the returned position rather than computing start + limit. Offsets beyond a line or inside a UTF-8 character are rejected. A start past the available lines returns an empty page with the total. Regex matching is case-sensitive unless inline flags override it. Matching supports lines up to 64 MiB and reports an explicit resource error for larger lines; ordinary paging can still read those lines.

For closed fields, a missing next_start means no selected content remains. For running fields, total_lines describes currently captured output, and the numeric next position can be retried after yielding with wait, even when no content is currently available. Unavailable output omits total_lines; known empty output retains zero. Repeat the field, regex, and context when continuing a search; overlapping match context is reconstructed from saved text. Live searches defer incomplete lines and context windows until more output arrives or capture closes. A wait timeout never stops the original job.

JSON pages

index is the zero-based first element or member (default 0). A page holds whole consecutive values in source order within 32 KiB, member names and text included, so it may return fewer than limit: continue at next_index, which is absent at the end. A first value that is not whole within the page is sampled as a preview is, within the page budget, with the page’s shape and truncated records at that value’s own pointers, for scripts and the model alike; select those pointers to read further into it. A member name longer than the page budget is still shown whole.

Queries

query is a JSONPath (RFC 9535) query over the selected JSON field: $ is that field. Filters can use length(), count(), value(), and regular expressions with match() (the whole string) and search() (any part). Matches are {at, value} in document order, duplicates included, where at is the match’s pointer in the saved output, ready to use as field. They page by index like elements, with total_matches counting all of them. Numeric comparisons use double precision. When nothing matches, the page carries the queried field’s shape, which shows the member names a query can use.

A query reads the selected field’s JSON into memory, up to 64 MiB of JSON text; a larger field is rejected, so query a field within it. This limits a query’s input, not its evaluation: once it starts, a query runs to completion, and queries that repeat selectors can produce many duplicate matches.

Persistence and live output

Reads are repeatable and survive session resume. Finished jobs with retained partial output have an Output incomplete; captured fields remain readable with jobs({job, field}). notice, including when viewing the final captured page.

The view’s presentation.captures lists captures that are not a finished part of the result: live, unfinished, or abandoned output, even without a structured result:

[{"field":"/result/console","complete":false}]

complete: false means the capture is still live or incomplete; in particular, a partial JSON capture must not be treated as a valid JSON value. Select a descriptor’s field to page or search its retained bytes as text. Capture descriptors survive failures, cancellation, and session resume even when there is no structured result containing those fields. Empty or absent result fields are not fabricated to represent partial captures.

Local captures, including script console output, can be read while running. Remote captures become available as they are transferred; inspecting already-transferred output does not require reconnecting to the remote machine.

The TUI’s automatic output view shows the structured result and previews any available captures not represented there. This exposes both process streams while live and preserves stderr and exit status on completion. While a job runs, each capture shows its latest lines, up to 20 within a page’s bytes, and follows them as output arrives. Explicit field, page, and search selections remain selected; choose automatic output in the Saved output menu to return to automatic viewing. The menu lists up to 100 fields one level below the one shown, from the page of it shown, starting with the result’s fields and captures, and the field above it; more fields shows the field from where the list stops, so the menu lists the rest.

Recorded model requests keep the previews, pages, and notifications the model actually saw; they are not regenerated from saved output.

Todos and runtime state

Todo lists

Every agent has an ordered advisory todo list. todo() reads the caller’s list; todo({items:[...]}) replaces the whole list and completes without a result; an empty array clears it. Each item has text and a status of pending, in_progress, or completed. Multiple items may be in progress. Unfinished items do not prevent an agent from finishing.

Any agent allowed to delegate can seed a child with agent.todos. The task prompt remains required; seed items use the same {text, status} format as todo.items and appear in the child’s runtime state before its first model request:

return tool.agent({
  prompt: "Implement the requested change and report the validation results.",
  name: "implement-change",
  todos: [
    {text: "Inspect the implementation", status: "in_progress"},
    {text: "Make the change", status: "pending"},
    {text: "Run relevant checks", status: "pending"}
  ],
  bg: true
});

The child owns subsequent edits. Ancestors can inspect a descendant with todo({job: childJobId}), including after it finishes; items and job cannot be combined. Inspection is available once the child has initialized; a queued launch may not have a list yet. Reads return {items}. An agent without todos has an empty list. Inside the child, progress can be updated with the same tool:

return tool.todo({items: [
  {text: "Inspect the implementation", status: "completed"},
  {text: "Make the change", status: "in_progress"},
  {text: "Run relevant checks", status: "pending"}
]});

Lists persist with the session, including completed and interrupted child lists. Resume preserves recorded statuses. For Rust host observation, see embedding.

Per-request state snapshot

The model profile’s state_mode controls whether and how the model receives a fresh <skyhook_state> snapshot with each request.

The snapshot shows the host’s current local date, active jobs, and the caller’s todo list. Empty job and todo sections are omitted. This is a compact model-facing view, not the JSON returned by job or todo tools; scripts should use those tools to inspect state. Dynamic snapshots are still recorded with model requests; this mode is not a data-retention control. It does affect prompt caching: see state_mode for when persist keeps more of the history cached.

Reading job progress

Job rows identify the job, parent, tool, optional name, state, age, and child-agent progress. Directly visible jobs have - as their parent; nested active child agents identify their immediate parent job. Ordinary tool jobs are not shown as nested children.

age_s is elapsed whole seconds since creation, including time queued or waiting for input. Child-agent jobs report the child’s selected target and workspace once initialized. Location overrides are shown only when they differ from the snapshot’s current execution location. Omitted locations refer to that current location, not to the parent row’s overrides. Targets are omitted when target capabilities are unavailable.

Child-agent turns and tool_calls counters describe that agent alone, not its subtree:

  • A turn is a complete, recorded assistant response, including responses containing tool calls. Failed or incomplete attempts, retries, and compaction requests do not add turns.
  • Tool calls count jobs launched by that child, including calls inside its scripts, but not work owned by its descendants.
  • Counters remain cumulative across retained-child follow-ups and session resume.

Todos retain their original order, including completed items. For example:

<skyhook_state>
date:2026-09-05
jobs: job parent tool name state age_s turns tool_calls
7 - exec run-tests running 12 - -
8 - agent review running 9 2 3 workspace="/home/user/review"
9 8 agent - waiting_input 4 1 0
todos:
completed:
  "Inspect the implementation"
in_progress:
  "Make the change"
pending:
  "Run relevant checks"
</skyhook_state>

Here, job 9 uses the snapshot’s current location, not job 8’s workspace override. With no active jobs or todos, only the date remains.

Security research product

skyhook-security owns its layered security.yaml (loaded by the shared layered loader), embedded research modes replacing presets whole (their instructions and the persona are templates rendered for each agent with the run’s live policy in its context, so only a run that may work against a running target reads the live parts), model-role hints, native tools, a report writer, and research tables it keeps in each of its sessions’ own session.db beside the journal as a session extension. A session is the run: it records the run as it opens, with the live policy it keeps, and a resumed session continues it. The run’s test artifacts and current reports live in subdirectories of the session directory. The security guide describes the research behaviour; this section covers how it is held.

The root agent receives the run’s facts as host state with each request; the agents below it get none, and the facts they need travel in their briefs. The facts summarise the run’s work in counts; the synthesis with each exhausted subject’s tasks and reply is read only on request. Running and exhausted work depend on the state of agent jobs, which changes without a research write, so every cached read that touches them (the facts, which host state and the Research page share, and the page’s open tests) keys on a journal watermark, the latest job transition or finish, beside the store’s write generation; what the run holds keys on the generation alone. The Research tab renders those facts as a page of typed blocks, which the host lays out once per page, disclosure and width and only turns its spinners as it draws.

The store is one graph. Every object is a node of one kind (component, path, source, premise, flaw, candidate, finding) with a title and a body; a per-kind detail table shares its id, and a composite key to node(id, kind) makes the schema guarantee a detail row’s kind. Edges are tables between detail rows: a path’s ordered steps through components and its sources, the premises a flaw or a path relies on, and a candidate’s ordered chain of flaws, whose first is its root, and its ordered actions, the paths its scenario performs from where the attacker starts; a chain’s flaws are not bound to an action. Ordered edges keep positions 0..n-1 through the writes that move them. A duplicate of any kind but a finding merges. A merge repoints every edge of the merged node to the survivor, but a merged path keeps its steps and a merged candidate its chain and actions as history, the survivor appending after its own actions each path the merged one performs as often as it does beyond them; a merged source gives up its detail row, so only live sources hold locations. merged_into is one hop, so readers never resolve merges on edges; an id argument naming a merged node resolves to the survivor at the boundary. Inventory recorded in error is retracted rather than deleted: a path’s one status is unswept, swept or retracted, and a source’s or component’s recorded or retracted. A retracted node keeps its edges and shows as retracted, but every queue, coverage count, synthesis list and derived standing reads only recorded sources and components and unretracted paths: a premise a retracted path relies on owes it no settling look and stands in no chain of a candidate performing it. A status set back restores it.

A location is a supertype in the same shape: a kind and a detail row sharing its id, for a code region, an address range of a binary image (link-base addresses stored by their bit pattern, their span checked in Rust) or an operation and field of a named interface. Each is recorded once per key, and sources, flaws, premises, path steps and evidence each hold one location of any kind; a location holds one live source, so recording a source where one is already recorded returns that one, and a merged source’s location is free for the survivor or a new source. A component owns its interfaces by name as it owns its files, and an environment records the interfaces it serves with their addresses; evidence naming an environment is an observation made there.

Every write is one event in one audit log, by the journal’s agent row, with the actor’s note, and event_node names each node it bears on with the strongest of three ordered effects: concerns, standing or changed. A write names its direct marks, and one rule carries them along the graph as it stands after the write: a premise moves the standing of the flaws and paths relying on it, a source passes its effect to the paths it enters, and a flaw or path passes its effect to the live candidates chaining or performing it. Some marks stand on their node alone: a candidate taking or losing a flaw as its root marks that flaw alone, so its other candidates are re-owed only when the flaw itself changes, and a status set on a path, source or component marks that node alone, with a source’s paths, so it moves only their sweeps; but a path retracted or restored moves its standing along the graph, since its premises leave or rejoin its candidates’ chains. A chain is edited whole through its candidate; a flaw joining or leaving it at another place is only concerned, and a chain’s work also rests on the verdicts of the candidates holding its flaw and on the chain edits it joins or leaves, so a disproval or a leave releases the flaw with fresh tries. Results are recorded in place and stamped with the event that recorded them (candidate.assessed, candidate.reviewed, a finding’s reported, and the decided or judged of a premise’s or flaw’s latest status, restated or not); nothing counts revisions. An assessment, verdict, report, flaw judgement or test’s verdict recorded within a task of its phase on its subject stands on that task’s basis rather than on its own event, so another agent’s change after the task began owes the work again.

What each phase’s work on a node reads is its phase’s arm of one relation, generated per phase with the node bound in every arm so it seeks by node (bearing): standing or changed events for a sweep, settle, chain or report (the root’s and each current member’s), those and the environments for any candidate serving one of its sources’ interfaces (any such one when they sit on none) for a probe, but none recorded within a probe, changed events for an assessment, all but test records for a review, and verdicts, assessments, test records and environments for a test. event_node holds its event’s kind, and its effects are indexed without test records, which arms read from test, so a walk down a node’s effects never visits its tests. Every arm leaves out what was recorded within a task of that phase on the node: event_task names the tasks an event’s agent and the agents above it held when it was recorded, so a phase’s own work, its helpers’ included, never moves what it rests on. Two events are never left out: a merge, which work on the survivor rests on whoever made it, and a pending test’s record, which a test resumes rather than repeats. A basis is that relation’s latest event, or the node’s latest while the relation has none, so owed work always rests on one; work is owed while its result predates its basis, or, for an unproven verdict, once no premise of its chain is undecided, and a notice is one of its events after a task began. Candidate standing (candidate_state) and confidence are derived views over those results, the chain’s flaw and premise statuses, and the root group’s demonstrations. A premise’s or flaw’s status counts once set at or after its latest material edit or merge into it, but those made within its own settle or chain (premise_state, flaw_state); an edit since reads it as undecided or suspected again, so its settle or chain is owed again. A test records the verdict it tested, and one settling test per candidate (settling_test: its latest that is not pending when that is a decline, which stands across verdicts, or else its latest recorded at its latest verdict) decides its demonstration, its testing’s settlement and what its report states; finding_scenario is the validated and noted members a root’s finding reports.

Scheduling is derived; nothing is planned. Work started is a log: a task belongs to the journal job of the agent that began it (an agent without a job cannot begin), and its task_node rows name each subject with its basis, several for a bundle; the keys pin a subject’s kind to its phase’s. A task has no end of its own: its state is the job’s job_status, whose index of live jobs is what live work is read from, never the task log’s history; its work is done when its subject is no longer owed. A subject is offered while its phase owes it, no task of it is live, and fewer than two of its tasks began at its current basis; startable pages the offered entries in pipeline order, leaving out what running work holds and later work an earlier ready bundle touches, and admitting tests by the live policy, approvals and unblocked pending tests. A path is swept when a recorded source entering it sits in code and probed otherwise, and a probe is owed only while the launch does live work and an environment for any candidate serves every interface its sources sit on, or its sources sit only in binaries. Test selection reads each root group’s facts once per statement, and only for the groups of the subjects a read can list; a page reads the subjects past its cursor in windows that double until it fills. The orchestrator’s scheduler keeps only its own run’s launch replies: an entry launched twice at one basis is passed back as spent, which the one exhaustion predicate every queue and hold shares compares with the phase’s current basis as it does a task’s. The synthesis counts owed, running and exhausted work, the undecided deployment premises a review waits on, the candidates standing unproven with their undecided premises, the components no path reaches, and the interfaces unswept probed paths wait on. An environment recorded beneath a test task is for that test’s candidate unless it names another.

An agent with tasks is told of others’ changes as a host event: for each subject of its job’s tasks, the bearing relation’s events after the task began and after its cursor (for a subject merged away, from the merge that retired it on), which leaves out those the agent or one beneath it recorded. Each changed subject gets one digest, never omitted: the event count, the latest event and the kinds seen, with its few newest events and their strongest marks, so a delivery is bounded by subjects times recent events; the latest event read is the cursor. Nothing is stored: the subscription is the task log. An agent found with nothing to be told is skipped until research is written again.

reports/ is a projection of the findings that report their scenarios as they stand, which the orchestrator’s generate renders from the store alone: a folder per root, replaced in one step when what renders changed, holding the reporter’s markdown beneath a generated scenario table and a folder per stated test whose artifacts are copied only while they match the digest the test recorded, beside a hardening list of the confirmed flaws no report covers, read in the same snapshot as the findings: each holds no validated chain, or only chains validated below the run’s threshold. The host capabilities security.research, security.verdict and security.test gate every research write, security.scheduled beginning assigned work, and security.coordinate scheduling and report generation; the store refuses nothing but boundary parsing, unknown ids and integrity, so unwanted work is prevented by not scheduling it. Read-only tool actions, the host state and host events run on the session’s read pool beside its one writer, whose research callers take turns without holding a thread; an action whose work is mostly files (recording a test, generating reports) runs outside that turn, its transactions still taking the writer one at a time.

Configuration and provider entries

config loads and layers configuration, admits it, resolves model selections, and builds the model catalog; it does not interpret provider entries. Typed LayeredConfig schemas share one loader for discovery, whole-entry merging and diagnostics; only the main Config schema interprets provider and MCP provenance, stamping every provider with its defining file (ConfigHome), beside which its Skyhook-managed credentials live. provider::dialect owns the entries (RawProviderConfig, ProviderSettings, ProviderModels): each dialect module declares its provider-only Options (connection rules and any Skyhook-managed Login) and its inheritable request settings. Request defaults and model settings are typed partial declarations (provider::settings) that keep inheritance intent until admission resolves each model into a complete, independently validated codec and transport profile. The shared Request also carries service_tier, a body field on every codec, explicit_caching for Chat and Responses, and the Responses-only selections (reasoning_summary, access_programs); admission refuses an effective one on any other codec, and a dialect refuses one its service does not take (Codex refuses explicit_caching). Each dialect’s Responses preset declares its summary default. Its image_limits replace the per-image limits each dialect declares in its profile.

Provider boundary and lifetime

provider::Provider is a shared factory. open_context(id) creates an independently owned ProviderContext for one conversation without making a model request; invoke(&mut self, request) returns an owned asynchronous response stream that does not borrow the context. A startup failure is the stream’s first and only item. Providers may send the context identity as cache-affinity metadata. Custom providers implement both traits. The three inference API families live under provider::codec: each codec encodes requests and decodes native streams under a typed dialect that names the conventions varying between servers of that family (field placements, tool-name rules, schema constraint, replay spelling, terminal-event shape), while the codec keeps the correctness rules and reads error bodies with its API’s own codes. Vendor modules under provider::dialect own provider-only settings, the codecs they speak and the dialect presets for each, credentials, and the transport conventions (fixed headers, per-turn session headers, body fields the vendor takes whatever the codec, and typed readers that map their servers’ own error codes and wording onto error kinds); configured models run through provider::http::HttpProvider. Shared request, message, and response types live under provider::protocol.

Each model runs as its own HttpProvider at its codec’s endpoint under the shared API root; the models of one provider build share its HTTP client, credential sources, command generations, and OAuth state.

Images are admitted only when they decode whole (media::Image) through image’s own decoders, with an allocation limit that also covers an animation’s canvas, and turned upright by their EXIF orientation. The journal keeps a still PNG, JPEG or WebP as attached; an animated PNG or WebP, and any GIF, is kept as its decoded default image or first frame, fitted to the stored size. An HttpProvider context fits each image a request references to its profile’s limits once, and keeps the outcome (media::Prepared) while the context still references the image: a fitted copy, or the reason none could be made. Codecs read these through a read-only view and encode a copy with its own format, or an omitted image as a text part giving the reason, so an image that cannot be fitted never fails the request. Only a fault in Skyhook’s own fitting work, such as a panic, fails it, as ProviderErrorKind::Internal.

The runtime retains the provider context across turns, tool work, questions, retries, and compaction. A child whose invocation has resolved, with nothing left for it to take, parks: its loop and context are released, and the input that resumes it opens a fresh context under the same identity from its history. A model change prepares its replacement before committing the selection and preserves journal history. Reselecting the current model keeps the current context. A mode change also replaces the prompt and tool surface and invalidates earlier bound reasoning. A host’s persona renders into every agent’s prompt; a resumed agent keeps its recorded prompt until a mode change rebuilds it. Resume opens a fresh provider context under the same context identity, or none for a root whose model the configuration no longer has: the session still activates for writes, and only running the root fails with UnknownModel until a selection, or activate_on, which journals the switch in the activation commit, moves it to a configured model. A child whose own model is gone restarts on the root’s committed model, journaled as it starts. continue restarts retryable children in one commit, then claims and admits the root’s held batch in one step, so nothing withdraws from it meanwhile and a refused batch is held again unchanged while the children run on.

Prompt text is embedded Tera templates (prompts). An agent’s prompt renders when its contract is fixed, as it starts or changes mode, from its typed context (role, available depth, capabilities, mode and the skyhook_context location), to which a host’s Prompts add the fields of its own section. One render path serves both: a mode whose instructions are a host template (Instructions::Template) renders them for the agent entering it into an Edition, the text the journal records; the system prompt then places the host’s persona, rendered for the agent, that text and the workspace’s instruction files around the library’s parts, and the journal keeps the prompt as rendered. A journal holds text, never a template name, so resume and replay need no templates, and drift compares the mode as it renders now for the reopened root with its recorded edition. A host’s Templates register beside the library’s; each template is checked against its context, refusing a top-level name it does not define: a host’s read the agent’s context and the section’s fields, and only the system template reads the parts placed around an agent’s context. A script a template shows the model is a verbatim source, included as written.

Each harness is built for one identity::HostName, the application creating sessions; the session stores that origin and exposes it through its summary, stats and SessionStarted. Another host’s session can be opened for reading, and the activation boundary refuses to run or change it with HarnessError::HostMismatch. Host identity does not partition the shared session root.

A host’s ResumeHook (agent/runtime/resume.rs; its contract is in embedding) is ordered by the core. Each call waiting on it joins a set in the core, in the change that also arms what leaves it, so a call abandoned as it joins leaves too. An interrupt empties that set in the same change that stops turns, counting what it withdrew, and so does the shutdown transition. A call is let in only by leaving that set in a core change after the hook finished, whether it succeeded or failed, so an interrupt that lands as the hook finishes still withdraws it.

The session owns the durable conversation (session::Message): user text and attachments, job events (child replies and presented job views), parent input and compaction summaries, assistant items, tool results, and the agent’s state (date, live jobs, todos, and a host-supplied section) as a message of its own. Providers receive it rendered: state becomes a context state entry and job events runtime text, so the provider layer knows nothing about jobs or todos, and those renderers are part of the session format.

Providers receive complete provider-neutral requests; they do not privately replay failed submissions. A response_schema must be transmitted as a structured-output constraint or rejected with InvalidRequest, not silently ignored or replaced with prompting. Input images must be encoded or rejected explicitly; generated image outputs are not supported. Reasoning replay carries provider/model provenance: replay from another model or API is omitted from encoding, and so is sealed (signed or encrypted) replay from another provider configuration, without deleting the durable transcript.

History, transient state, and caching

A ModelRequest carries its context as one ordered list of typed entries: messages, and runtime state the harness wrote, with how long the state stays in the model’s view (StateLifetime). A profile’s state_mode sends each request’s own state (current, dynamic), commits it to the conversation unless it equals the latest committed one (persisted, persist), or omits it (none). Everything before the first current state is a prefix later requests extend under the same context settings until compaction replaces it. Only a state whose request produced no response later drops out of it, since nothing is bound to it.

The journal records each request’s tail. The projection gives each committed response the state its request sent, the request of the attempt that completed with it, and later requests send it again before that response as superseded state, back to the latest checkpoint or mode switch (where bound reasoning ends). A superseded state never reaches the model, so the model always reads only the latest dynamic state. Each codec places state in its dialect’s StateRole: the protocol’s harness role, or user content where a server has none mid-conversation; never inside tool output. A Messages dialect may make system-role state turn-scoped, which lets that codec resend superseded state hidden from the model and keep the conversation unchanged for reasoning bound to it; every other placement omits superseded state, so the wire request stops extending the previous one where that state was, which persist avoids. A state not followed by a response or the end of the context is omitted everywhere: its request produced nothing bound to it.

history_lifetime communicates cache reuse without prescribing a provider implementation:

  • extends is the default: later requests extend this history.
  • detached marks one-off settings, such as a compaction summary request, with no reusable history prefix under those settings.

Messages, Chat dialects that send cache_control, and Chat and Responses under explicit_caching (prompt_cache_options: {mode: "explicit"}, marked with prompt_cache_breakpoint) mark cache breakpoints: the cached segments of the system prompt (on Messages and Chat), the end of the history prefix, and the point before each earlier assistant response in it, where each prior request’s prefix ended, so that prefix stays reusable. Each dialect caps the breakpoints of one request, system segments included, at four by default, the documented limit of each codec’s API (four cache breakpoints on Messages, four cache writes per explicit-cache request on Chat and Responses); over the cap, the oldest history breakpoints are left out, and a request whose system segments leave no room for its history is refused. Responses sends cache_control top-level instead, so the server places the breakpoint itself, and only under automatic caching; Chat and Responses otherwise use automatic prefix caching. A detached request marks no history, and the current state and the rest of the request carry no marker. Responses sends every tool output as a text-block array in explicit mode, so it can carry a marker; Chat gives that form only to a tool output it marks.

Request, response, and recovery lifecycle

  1. At a request boundary, the runtime applies accepted input and model/mode selections, every batch queued by then committed with its selection as one submission, refreshes history from the journal, and builds the request. Shared settings are recorded in model_context; model_requested freezes the exact history range and inline tail.
  2. Each provider invocation gets a model_attempt_started record for that logical request. The stream carries display-only Deltas for blocks, cumulative Usage snapshots, and one terminal End holding the Completion: the complete items in position order and how the response ended (an answer, tool use, or a cut). Only a completion built for tool use carries tool calls, so nothing else can authorize execution. LiveResponse gives the runtime and observers the same provisional view of the deltas until the end arrives. Observers then see each response settle as committed or failed, keyed by the journal sequence it produced.
  3. Only an accepted response becomes model-visible history. Its message, usage, and outcome commit together before tool dispatch. The response’s calls are then planned concurrently and their jobs created together, in call order, in one commit: after a crash either every job of the response exists or none does, and a call that fails planning settles without a job and without affecting its siblings. Each tool result commits as its call finishes; request projection merges results back into the original call order. This preserves completed work after a crash without making completion order part of the next model request.
  4. Once a tool exchange is closed, the runtime can compact history or build the next request. An agent with no further work returns to its idle loop rather than discarding its context, until, as a child, it parks.

The session core keeps each agent’s newest request with its RequestPhase, the calls its responses left without results and whether its input awaits the model; that is what turns, activity, resume settlement and the observation read, and session::Turns folds each agent’s turns. The fold also decides what presenting a record reads beyond it (session::Fact): the request an answer committed under, the call a result answered, and that a failed turn ended on its request’s failure. The core folds requests and each agent’s state as records commit, and writes their rows, with what it decided of answers and failed turns, in that transaction, so request pages, statistics, the session list, agent summaries, compaction’s retention and opening a session read lifecycles from those rows rather than deriving them again.

The core admits every command by the session’s SessionPhase (viewing, running, shutting down, failed, closed) in one table in session/core/phase.rs, which also decides when what a command journals is dated. A reopened session is only viewed until the first call that changes it activates it (agent/runtime/reopen.rs), and shutdown stops a session as a crash would (agent/runtime/lifecycle.rs); the host contract for both is under interruption, continuation, and shutdown.

Interrupt, continue and new input read three facts the core keeps, and nothing else: the session’s flow (open or paused), each agent’s turn (Turn in agent/runtime/agents.rs), and whether each child invocation has begun. stop_turns, redirect and interrupt_tree in agent/runtime/lifecycle.rs decide each agent from them. A busy turn an interrupt stops stays stopping until its loop has unwound the work it took: nothing claims it, or what it would hold, and continue and new input wait for that (settle_interrupts), so one agent never runs two commands at once. The host’s observation is a display, never an input to that decision.

Transient recovery belongs to the runtime, not the provider or transport. It classifies normalized ProviderErrorKind values rather than error-message text: rate limits, timeouts, transport failures, and unavailable servers repeat the frozen logical request. Input and selection changes wait for the next request boundary. The failed stream is dropped before backoff; server retry hints take precedence over capped exponential delays. Recovery remains cancellable and continues until success or interruption. A failure is journaled with its retry and backoff, so a request never reads failed while it retries, and one a crash leaves retrying reopens interrupted.

A retry starts a fresh live response while retaining the attempt audit records and any reported usage. A stream that fails or closes before its end never authorizes tool execution, and transient recovery does not rerun completed tools. An expired command-sourced credential is transient: the provider discards it on a 401 and the retry fetches a fresh one, and so is a completed response with no nonblank text or call, unless it is a refusal or an output cut. Other authentication failures, invalid requests, and protocol errors do not enter this retry loop. Context-window recovery and unusable compaction summaries have their own bounded recovery path; a checkpoint that breaks a journal invariant is not retried. Which cut or empty responses commit is decided in agent/runtime/turn.rs.

Compaction and context accounting

The journal is authoritative; compaction replaces the model-visible projection, not old records. Automatic compaction is decided from a completed response’s reported occupancy, at 90% of max_context - max_output. Skyhook estimates no token counts: every size it uses is one a provider reported. Summarization is a separate journaled request with a structured response schema and no callable tools. Its checkpoint installs the replacement history and the reconciled todos in one commit, which is refused when it would overwrite newer todo state, and replay uses the stored continuation rather than rerunning the summary.

An agent’s context (agent/runtime/context.rs) opens with its history, read from the journal by index: its latest checkpoint with the retained sources, then its records after the frontier folded by Projection::apply, the fold that goes on to apply the records the core feeds it, and reads its history again after a checkpoint. The occupancy it compacts for is the core’s. Compaction retains from that history, with indexed reads of the agent’s requests completed since its checkpoint and of the exchanges its live calls opened, so neither reads the whole journal. agent/runtime/compact/ owns the summary request and how it shrinks after an overflow (mod.rs), the retained tail (retention.rs), and the checkpoint (checkpoint.rs). The user-visible behavior is under conversation compaction, and the durable reference contract under model-call reconstruction.

Tools, jobs, and execution

ToolRegistryBuilder registrations are typed; only MCP tools register a server-supplied JSON schema. Typed registrations generate input and output schemas, and a unit registration completes its job without a result; registry metadata also supplies compact result documentation to the model and JavaScript runtime. Both call paths use the same executor, capability checks, authorization coordinator, and job supervision rather than separate tool implementations. Every call is admitted once, before authorization: a typed registration may declare an admission step that turns its parsed input into the value its handler receives, so its checks run at the boundary rather than in the handler. The admitted value names its path arguments, which are resolved in place, and derives its permissions, so an inadmissible call never asks for approval. It may also choose the schema its job’s result follows, which presentation and scripts read and tool descriptions leave out, for a tool whose result shape varies by action. Path admission (tool::path) resolves a requested path where the call runs: relative to the workspace, through existing symbolic links, as the tool will use it (an existing entry, a write target, or a removal). The resolved path, not the spelling the caller gave, is what the call asks permission for, over the exact file or a directory’s descendants. A relative path continues the workspace’s own resolution, so every entry looked up on the way counts. A path refused outside the authorization root (one that does not resolve, or a removal of the root, the workspace or a directory holding either) is asked for as the path it would be, under a decision that may not ask anyone, and fails only once allowed, so no prompt or error reveals what lies outside. The host planner and a remote worker assemble an invocation’s permissions by one rule, and a capability the caller lacks makes the tool unavailable rather than denied.

Capability::Host(HostCapability) extends the built-in permission vocabulary with namespaced namespace.name identifiers a host declares on its builder; ceilings, modes, native tools and MCP requirements may only use declared names, and every authorization gate treats them like built-ins. The journal records capability names as data, so another host’s names read back without its declarations. The session database is format 30; formats are clean breaks without migration.

The executor coordinates host-owned jobs and their persistence. A job’s lifecycle (queued, awaiting approval, running, waiting for input, finished), its startup lease and its single completion owner live in job/lifecycle.rs and job/supervisor.rs. A tool may declare a source argument, a TargetPath on any target: the executor selects its location like a tool target, authorizes the read with the call, and opens it for the call’s context. A host tool whose input places its job elsewhere, such as a child agent’s target and workspace, has that location selected before the job exists, so every view of the job reports it; a local workspace is resolved and authorized there as one of the call’s paths, while a remote one is only resolved where its worker starts. A job shows that workspace as written, .. kept and no link followed, so no view of it reveals or misstates what lies outside; the job runs where it resolves. The local invocation layer (tool::invocation) admits typed arguments and runs operations without requiring a session database. The SSH shim reuses that layer for remote built-ins while the host retains job ownership, policy decisions, and saved output, so remote workers never become second agent runtimes. See remote transport and shims for connections, streaming and shutdown.

Tool failures are structured diagnostics: a typed cause plus the operation, subject, site, known local effects, and, as a separate fact, whether a sent request may have executed, which only the sender raises, as it sends. Tools annotate facts; tool::diagnostic owns the one renderer. Facts chosen nearest the failure win, and each boundary (planning, dispatch, remote result ingestion) only fills what is still unset: a failure carries a partial context in process and is resolved once, when it is persisted, sent over the wire, or rendered. A worker’s reported site is always rebound to the destination of the connection it arrived on. Diagnostics are persisted with the job and rendered per viewer; saved job output describes what a viewer sees.

Saved output and model-visible presentation are separate. A finished result is saved once, as a compact document with its large parts in captures (job/output/saved.rs), and read back through bounded streaming readers (job/output/json.rs). The large parts are written before the finish, staged: no reader lists them until the finish that references them commits, so that transaction stays small whatever the result’s size. A finish that prepares its output again, as a stale finish retries, replaces what it staged before at the same field, and opening a session removes those a finish never committed. JavaScript receives complete results, while the journal retains the exact previews delivered to the model. Saved job output documents the user-facing limits.

Each script runs in a fresh QuickJS runtime (tool/javascript) with a 512 MiB engine allocation limit set before context creation. This does not cap Rust-side bridge or job memory; allocation failures use ordinary JavaScript error handling. Its runtime is embedded ES modules (tool/javascript/js), compiled to bytecode once per process and instantiated per script; the submitted body is compiled separately, as its own module, so failure reports can keep only its frames. One conversion turns tool arguments and returned values into JSON at the host boundary (bridge.rs), and the host fills a response’s declared absent fields with null there, from the schema its job stores, which also declares its presentations (job/output/projection.rs).

Child messages and job notifications commit to the parent’s history together with their acknowledgment, as a model call’s result does with the outcome it reports, so an event that never reaches committed history stays pending for delivery (agent/runtime/wait/delivery.rs, job/delivery.rs). A host’s events join only the delivery before a request, read under the turn’s cancellation: the agent’s cursor is journal state, a pointer from agent_state to the message holding its latest host event, moved by that commit, and nothing that decides whether an agent has work to take or a wait has resolved reads them. A foreground child’s replies stay queued for its call instead. Its completed result saves them: the finish drops them from the queue, and journals only while the replies queued are those its prepared output saves, preparing the output again otherwise (job/lifecycle.rs). A call let go of before it returns, or returning anything else, leaves them to delivery (job/entry.rs). A question is the owner’s, whoever waits on the job: while it is pending, it and the replies queued before it are pending for the owner together, and a foreground wait keeps waiting for the outcome. Folding the ask record also releases the model-level foreground call blocked on the job, the job’s own or that of the script whose calls wait on it, which then returns the job unfinished, presenting and acknowledging neither (job/persistence.rs, job/delivery.rs). A child’s final answer stays its job’s result until its owner acknowledges that completion; a restart before then supersedes the result and queues the answer as a reply (job/entry.rs), which a read of the superseded result, such as a script’s own call, acknowledges in place of the restarted invocation’s delivery. A job’s read holds the result in the change that captures it, before its output is collected: until that job ends, the reply is held from its owner’s notifications, and a notification read before a hold landed commits nothing. What a waiting job asks is part of its phase, each question by the ask job waiting for its answer: an ask’s end retires its question in the same commit, which asks the rest again or lets the job run on, and a reply is accepted into each ask’s mailbox at most once, so a repeated reply answers nothing again (job/questions.rs).

Process tools leave stdin unconnected, capture stdout and stderr, and detach from the controlling terminal (tool/builtins/process.rs), so a program that prompts uses the session’s askpass helper, backed by the host’s sensitive prompt handler. Without the Interactive capability, a call gets a rejecting helper instead. OpenSSH and sudo run a Skyhook binary as that helper, so every binary calls remote::askpass_main() first: it answers the prompt and exits when started in that role and returns otherwise. The helper, its environment and prompt attribution are described under authentication and prompt isolation.

Session core and transaction boundaries

Each durable session is one SQLite database, session.db, holding the append-only, normalized event ledger beside its blobs, saved job results and captures; session/schema.sql documents the tables and the few JSON columns. Closing any descriptor of a file releases every POSIX lock the process holds on it, SQLite’s included, so one registry under one lock (db::live) records both each database the process has open (its file, -wal, -shm and -journal, by identity and by name) and every handle another in-process opener holds (fs::OpenFile, by identity). An opener refuses a live database’s file and registers its handle under the lock; a database registers before SQLite opens it, waiting at most the busy timeout for handles on its files to close; replacing or removing a file decides and acts under the lock, and removing a tree reserves it under the lock, so no database registers inside it, then removes it outside; walks pass over live files. Each open session has one core thread (session/core/mod.rs) that owns the only writer and the one in-memory fold of what live work reads of the journal (each agent’s newest request, the resident jobs and agents, todos and targets, the next sequence and the last activity, never the records themselves) and, never journaled, each running agent’s turn and inbox and every registered wait.

Commands run on that thread in order. Each plans against the current state: a Plan names the entries it journals, the output it saves with them, and what it changes live. The writer journals them in one transaction, validating each record by index against the journal ahead of it, so no append reads the whole journal. In that transaction it folds them into the state, refusing a transition the state does not admit, and writes the current-state rows of the jobs, requests and agents they changed; the ledger stays the only source of history and exports. No reader sees the state ahead of the journal or a record the state does not reflect, and a rule a concurrent change can break, such as the stale-todos check on a compaction checkpoint, is decided against the state it commits to.

The commands already queued when the core takes one run with it as a group, and one sync of the write-ahead log after the last makes the group durable; the core never waits for more to arrive. Each command still plans against the state the ones before it leave and commits its own transaction, so a refused plan leaves the rest of the group as it would be without it. What a command leaves to happen once it commits, such as its reply, the waits it resolves and its deferred effects, runs after the sync: until then the state and observers may reflect a commit, but nothing the session does in response has happened. A failed sync stops the session; each command of the group that committed, and any drain or close behind it, reports that failure. A stopped session holds what reopening it reads, so a transaction that failed leaves nothing of its fold. A committed record is shared, not copied, by the observation stream, the agent contexts and every observer, and an agent’s context is fed only the records of its own agent that its history folds.

One user-visible operation is one plan. A submission is admitted when its messages commit, a queued batch commits with its model and mode selection in one transaction, and the commit that ends a turn also closes the calls it left without results and journals the failure that ended it, right ahead of the turn’s end, which is how the request ledger tells a turn that failed on a request from one that failed before any. The core’s turn state is the single authority for model work: an interrupt changes it in the core, and every commit that starts work (a request, a model attempt, a response, a delivery, queued input, a compaction, or a job a model call starts) is refused unless the agent’s turn is busy. A turn’s cancellation token decides nothing; it only aborts the I/O in flight, such as a provider stream or a process.

A registered wait declares the agents and jobs it reads, and decides from the state alone before it takes anything. A change decides again only the waits whose agents or jobs it touched, repeating while what they take touches more, and every wait on a session-wide change (phase, flow, activation or a resume withdrawal); each agent’s activity is likewise read again only when the change touched that agent.

Resident set

The core holds only the resident set, so what it holds and what a change, a request or a tool call reads of it are bounded by live work, not by the session’s history. A job is resident while it is unfinished or interrupted, has a delivery or a reply pending, is a child that input can resume, or launched a resident job; the resident jobs are indexed by owner and by parent. A job let go of keeps a cancellation requested of it that the journal does not record for the rest of the session, so a job created under it is cancelled whenever it is made; a reopen forgets it. Every agent’s state is held; its contract and the children it has started are held while it is the root or its loop runs, and read from the records its state names as its loop starts. A job that leaves the set is let go with its indexes and handles: a job holds its input mailbox and cancellation token only while it can still run, and what runs an agent job again is built only as it restarts. Whatever addresses a job by id reads it as the core last held it, from its status row, which is final once the core lets the job go. Opening a session reads the state rows and a few counts by index; nothing is folded from history.

Parking

A child’s loop runs only while it has something to do or something to deliver to. Once its invocation has resolved, its turn is idle or failed with nothing queued or held, it owns no live, interrupted or pending job and none of its children runs, it parks in the change that finds it so. The next change that needs it (input to its job, a continue that restarts it, or the restart of a job it owns) starts its loop again, and that of each parked child above it, in that same change, so an agent never runs two loops and none parks between that check and the work it was started for. It starts as its journal leaves it: under the contract it ran under, with the children it started, stopped on its failure if its last turn failed, and with a fresh context opened at a request boundary under the same identity, so continue and input go on as they would have had it never parked. A child whose job was cancelled, or whose cancellation was requested, is not started again, and its name stays its owner’s. A cancellation requested of a finished child’s job itself (the jobs tool or the host’s cancel_job) is journaled, so it holds after a reopen too; a reopen forgets one that an interrupt, an abandonment or a close requested of a finished descendant.

Log and reads

The ledger is only appended to: triggers refuse updates and deletes on every ledger and dictionary table. A write the journal cannot take stops the session as a crash does. No commit checkpoints the log, since a pass would hold the commits behind it while it syncs the database file: a thread with its own connection copies the log into the database every so many commits, without blocking the writer or a reader, except that once the log has grown well past its bound under commits that never pause, one pass holds the writer so the log can start over. A read holds its snapshot for that read alone, so the log stays bounded by what commits between passes plus what commits during the longest read. Closing a session copies the log into the database and empties it without waiting for a reader; frames a reader still holds stay for the next open to recover. A writer lock excludes competing session owners, not read-only inspection.

Reads that do not belong to the core, such as job output, the blobs a request sends, an agent’s history, history pages, request reconstruction, the title, the session list, statistics and exports, run on read-only connections, each in one snapshot, so they never wait on the writer’s transactions; a session held in memory reads through its writer’s connection instead. A session keeps a fixed few read connections, each on a thread of its own, and a read waits for one rather than opening another. Reads are async, and one waiting for a connection holds no thread. The core reads on a connection of its own, so its reads never wait behind other reads. The pool and the turn it takes are db primitives; the journal and the security store each supply how their readers open. The CLI host turns SQLite’s allocation statistics off for the process at startup (db::configure_process): counting takes one global mutex, which would serialise readers that otherwise run in parallel. The library never changes process-wide SQLite state on its own.

Observation

Observation is a host view of durable records, the jobs the session state folds from them, and live state; it is not a second source of conversation history or job state. An observation copies only what the core holds live: the phase, each agent’s newest request and activity, the resident jobs, the responses of each agent’s latest turn, context gauges, and each agent’s transcript length and usage. It costs the same however long the session is, and since the core reports the jobs it lets go of, an observer holds what the core holds. History is read in pages on read-only snapshots, by index. A page reads at least what the observation applied, and every later record is an update at the next ordinal of its agent, so a host placing updates by ordinal misses nothing and repeats nothing; a lagging host observes again and reads its pages again, never the history. Live updates the journal does not carry, such as streamed deltas and capture notices, never wait on the core’s commands, its state lock or the database, only on the observation’s lock, which a commit takes after COMMIT to fold its records into the views and publish them, and a subscriber holds while it copies the views. A capture write notifies observers of its run once, then again only after something reads that run’s output or the run finishes; a streamed delta likewise notifies observers of its response once, then again only after something reads that response or a record of its agent applies, or a new observation copies the views. A burst of writes or deltas costs a bounded number of updates, so a token stream alone never makes an observer lag.

Source: agent runtime, providers, tools, and sessions.

Terminal history window

The terminal shows the viewed agent’s tab from a window of its history, so drawing reads only memory and what the terminal holds is bounded by the view, not by the history. Each tab is one run of a list loaded a page at a time from either end: the conversation’s entries by ordinal, keeping only the kinds it can show, so a run of records that never show costs reads but nothing held, each page with the facts presenting it reads, which later updates extend, so an entry shows the same whatever else is loaded; requests, an owner’s jobs, and a card’s children. Loads run off the event loop, at most one in flight above the view and one below, and land as work; what is not loaded past either end of the run shows as a loading row. The conversation’s scrollbar spans the transcript’s records, each entry’s rows its own record and records that show nothing none, so what loads or is let go moves it only when a load finds an end of the transcript, which the entry nearest that end then reaches; a list’s spans the rows it loaded. What streams after the last record spans one record more, as its reply will once committed, so the thumb moves through a long reply as it streams. Rows that show no record lie where the next one starts, and a position there finds the first of them, so the start of the track shows what precedes the first entry. The track maps a position to the record there, whatever the view shows. A position beyond the run (the scrollbar, Home, End) reads there instead, at once, in a window of its own: what the one it replaces had in flight lands unused, and until the position is laid out, scrolling moves it rather than the rows shown. A reading position is an anchor (an entry key and rows into it, and the tab’s own entry it belongs to: a transcript entry, a request or a root job, or the start or end where it belongs to none), never a row, so it is found again whatever a new page, width or recovered observation lays out; the children still to read where it belongs load whatever their distance, and it is given up only once a page read where it lies shows it is not there. Entries beyond a fixed budget on either side of those the view needs (what it shows and those up to the next entry each way that shows, so scrolling reaches the next row) are let go with what presenting them read, and with the outputs of the cards they show. A job the session lets go of, and a request a newer one replaces, keep the view they were left with while the window shows them, whatever order that and the pages reading them arrive in. A frame lays out only what the window holds, and the sidebar asks the session what the viewed agent holds only once an agent’s start or mode change, or the chosen agent or mode, changes it, so a frame never waits on a commit. A session out of view keeps only its live part, its agents’ summaries and the job output selections chosen.

Terminal transcript selection

The terminal lays out transcript entries into rows. Each row’s layout separates what it paints as decoration (wrap continuations, code padding, disclosure glyphs, spinner gutters, diff markers, table borders and padding) from the source text it shows. A row’s source is described by spans: which logical line they belong to, which bytes of that line’s text, and which bytes of the row show them. A table cell is a logical line of its own, so the fragments of a wrapped cell share one line. Spans also keep the source that a row shows differently or not at all, such as a cell’s trimmed separators, a replaced wide grapheme, or an empty cell.

A selection is anchored to source, not to rows: each end is an entry key, a logical line identity within that entry, and a byte in that line’s text. Line identities come from the source and do not depend on width, but they are identities only. A Markdown line is identified by its source position; within a tool document, also by all the text before its Markdown block. A tool document or plain line after an entry’s header is identified by all the text before it, so inserting a line gives every line below it a new identity; the header’s own text is the entry’s state, so it takes no part. Document order is the order in which the layout first shows each line, which reads a table’s cells row by row even when their fragments interleave on screen. Endpoints, copying and highlighting all read the same spans. Copying joins each selected line’s parts in that order, one line per table cell. Each layout of an entry orders its lines once, when a selection first needs them, so dragging across a long entry reads only the rows of the lines it selects.

Whenever entries are laid out again (new text, a reply settling, a resize), the selection is re-resolved against the new rows. It survives only if its endpoints still exist and the text they select is unchanged; otherwise it is dropped rather than moved to other text.

Source: rendering.

Embedding

The skyhook crate is the Rust library. Hosts supply configuration, a workspace, model selection, and interaction handlers rather than depending on terminal UI state. See library architecture for responsibility boundaries and the internal request lifecycle.

Layered host configuration and model hints

Config::resolve(workspace, explicit).await loads the main config.yaml without building providers or looking up credentials. Hosts with another YAML schema use the same loader through config::resolve_layers::<T>(workspace, explicit).await, implementing config::LayeredConfig on their own deserializable type:

use std::{collections::BTreeMap, convert::Infallible};
use serde::Deserialize;
use skyhook::config::{LayeredConfig, resolve_layers};

#[derive(Default, Deserialize)]
#[serde(default, deny_unknown_fields)]
struct HostConfig {
    profiles: BTreeMap<String, Profile>,
}

#[derive(Deserialize)]
#[serde(deny_unknown_fields)]
struct Profile {
    description: String,
}

impl LayeredConfig for HostConfig {
    type Error = Infallible;
    const FILE_NAME: &'static str = "host.yaml";
    const NAMED_ENTRIES: &'static [&'static str] = &["profiles"];

    fn missing() -> Option<Self> {
        Some(Self::default())
    }
}

let loaded = resolve_layers::<HostConfig>(workspace, explicit_host_config).await?;
let host_config = loaded.config;

Discovery selects the first usable user file: $XDG_CONFIG_HOME/skyhook/<FILE_NAME>, then $HOME/.config/skyhook/<FILE_NAME>. Rejected candidates remain in loaded.report; their fields never enter the configuration. The workspace’s .skyhook/<FILE_NAME> overlays that file, or can stand alone. A malformed workspace file is fatal. An explicit path disables all discovery, even workspace resolution, and must exist.

NAMED_ENTRIES lists top-level maps whose entries replace same-named entries whole while keeping other names; every other top-level value is replaced whole, and defaults apply after merging. A schema’s admit_layer validates each candidate file and the effective document; LayerSources::entry names the file behind a named entry for source-relative paths. The generic loader does not interpret providers or mcp; those belong to the main Config schema.

Omitting missing() requires a discovered file. Returning defaults permits absent discovered files, but never hides rejected files or a missing explicit path; the defaults still undergo admission. Empty YAML, null, and non-mapping documents are always invalid. LayerResolutionError names the schema file and retains its ConfigReport through report().

Before sealing a Config, hosts can edit a configured model’s profile through model_profile_mut(&ModelRef), which returns ConfigError::Model for an unknown provider or model. Clearing a hint removes that model from the choices offered to agents, not from the configured catalog. Hosts can also assign the public default_model: Option<ModelRef> before calling into_runtime(), which validates the selection. Edits affect the new runtime generation only, not previously sealed configurations.

Sharing the CLI and terminal

The skyhook-cli crate is the shared host. A product implements Product with an Args type implementing clap::Args, a Command implementing clap::Subcommand (NoArgs and NoCommand for unused extension points), and an Identity: the HostName its sessions are tagged with, the tables it keeps in them (see below), display name, about text, the placeholder shown in an empty conversation, a state_file path relative to .skyhook for that product’s remembered model, mode and sidebar setting, a RootMode (Switchable, or Fixed to keep the root in the configured default mode and refuse --mode), a Theme, and the HostCapabilityDeclarations its modes grant, which the host declares on every session the product opens, another host’s included. A theme is a UI palette of semantic roles (surfaces, emphasis, strong, accent, success/warning/error) plus a syntax palette of explicit Rgb colours for highlighted code; a product usually supplies its own UI palette and keeps SyntaxPalette::DEFAULT so code reads the same in every product. Its session arguments work at the root, under batch and for dump config; shared auth, dump skills and stats, and its extra commands take only their own arguments. Session history is always .skyhook/sessions. The host reads approve_all from config.yaml itself (HostConfig); it is not a library setting.

A thin binary retains its own global allocator and starts in this order:

fn main() {
    skyhook::remote::askpass_main();
    // SAFETY: no threads or runtime have been started.
    unsafe { skyhook_cli::main(MyProduct) }
}

main is unsafe because it loads the invocation directory’s .env and configures SQLite for the process before starting Tokio, so the process must still be single-threaded; help and version need no .env or configuration.

The extension points are:

  • Product::configure(&self, &mut Config, Args, SessionContext<'_>) returns Configured: the product’s own ConfigReport, which the host renders beside the main configuration’s, and an Arc<dyn SessionFactory>. It edits the resolved configuration before runtime admission (product settings, model defaults, modes, MCP entries); dump config serializes the result and a session runs with it. command handles the product’s own subcommands.
  • SessionFactory::form(&self, SessionContext<'_>) -> Option<ScopeForm> is the scope a new session’s draft is written with (cli::form): choice and integer fields with defaults, and a message used when the draft is submitted empty. The terminal shows it at the top of the root’s conversation beside the composer, sends its values with the first message and freezes it once the session starts; a failed start leaves it editable. The values reach prepare in the context’s Opening::New. Batch runs pass no form.
  • SessionFactory::prepare(&self, HarnessBuilder, SessionContext<'_>) returns HookFuture<'_, PreparedSession>: the customized builder and an Arc<dyn SessionExtension>. SessionContext holds the canonical workspace, headless, and its Opening: New with the form’s answers, if any, or Resume(SessionId). A draft calls it on first submission; the host tags the builder with the product’s host name and tables and calls it only for the product’s own sessions, so a foreign session opens view-only with no extension.
  • SessionExtension::opened(&self, &SessionHandle, SessionContext<'_>) -> HookFuture<'_, ()> runs before the first input; associate a new session with its product resources here, and finish a setup an interruption left undone. A reopened session may only be viewed, so change nothing else. Failure shuts the session down.
  • What this launch changes about a reopened session’s work (as the security product applies its --workers) goes in a skyhook::agent::ResumeHook registered on the prepared builder with HarnessBuilder::resume_hook; the library runs it before that session’s first work (see Interruption, continuation, and shutdown).

Hooks before opened create no sessions and write nothing to stdout; a batch run prints the session ID first. A product that keeps its own data in each session declares it as Identity::tables, an Extension { sql, format, seed } the host passes to HarnessBuilder::session_extension: the harness creates those tables in every session it creates and checks their format on every one of its own it reopens. SessionStore::summary, given the host and its tables, refuses one of the host’s own sessions that check would refuse, so the session switcher leaves it out and --resume refuses it before prepare, as for an earlier session format; other hosts’ sessions are still listed, view-only. The harness hands host state and the resume hook the tables as an ExtensionDb on the session’s own writer and read pool; tools reach them through ToolContext::extension(), and the extension’s terminal hooks through the session (SessionStore::extension()); a write whose commit failed reports Unconfirmed, since it may have committed. Another host’s harness opens such a session without them; ExtensionDb::inspect reads them read-only without opening it. Files of the product’s own go in subdirectories of the session directory. HookFuture is a boxed Send future returning Result<T, cli::Error>.

Per-session terminal views and actions

SessionExtension::views() returns a stable slice of ExtensionView { title, frame }. These tabs follow Conversation, Requests, and Jobs and share their keyboard cycling and clickable headers. ViewFrame::Session draws a view inside the session’s chrome; ViewFrame::Page { agents } gives it the frame below the tab strip, keeping only the footer, any prompt awaiting an answer and, with AgentPane::Live, the live agents: a column beside the page on a terminal at least 100 columns wide, the usual band below it on a narrower one. AgentPane::Hidden leaves them out.

refresh(view, SessionHandle, Disclosed) -> HookFuture<'_, page::Page> loads views()[view] off the UI thread, as the extension’s own session sees it. A Page is a list of typed blocks: Facts (label and value pairs), a Pipeline of stages, Panels of labelled values and meters, and Sections, collapsible tables of records that each open to their detail. Cells carry a Tone, not a colour. The host lays the page out with its own theme, reflowing panels and dropping section columns by priority as the width shrinks, and owns disclosure and scrolling, so a product needs no terminal code. Disclosed says which sections are open, how many of their records to supply (Disclosed::PAGE at a time), and which records are open, each with how many of its detail’s continued entries to supply, likewise a page at a time: supply records and detail only for those, and mark a detail that has more entries than it shows. The host reads the shown view about once a second and again at once when the viewer opens or closes something. Futures must be cancellation-safe. Sanitize untrusted text before returning it.

Foreign sessions remain view-only: the host hides the composer and title editing and withholds the commands that would write, while inspection, transcript copy and export remain available. SessionHandle::host() identifies the recorded origin and is_view_only() reports whether this harness may activate it; library activation checks remain authoritative.

Constructing a harness and session

The configuration-backed entry point is:

let model = config.into_runtime()?.select_model(&name)?;
let harness = HarnessBuilder::configured(&model, workspace, host)?
    .build()
    .await?;
let session = harness.new_session().await?;

into_runtime() admits an immutable configuration generation, including any edits the host made to the Config; select_model(&name) binds the host’s explicit choice, a ModelRef parsed from provider/model, to that generation. Admission and selection precede provider construction, credential lookup, and workspace access. HarnessBuilder::configured(&model, workspace, host) returns a builder for the application host serving that configuration, which can be customized before build().await; hosts supplying their own providers and model profiles can instead start with HarnessBuilder::new(workspace, host). Skills are a builder input (skills(HostSkills)): the harness discovers nothing on its own, so an embedder decides whether HostSkills::discover runs. A provider that needs a login reports it as a typed LoginRequired whose remedy names the host’s own auth login command (host, or the program passed to Config::login), including in a session’s request errors; a LoginFlow signs in through a host-supplied LoginPresenter rather than the terminal.

The configuration-backed builder carries the configured modes and selects the configured default. mode(name) selects another, and capabilities(set) limits what modes can grant; build() rejects a selected mode the modes do not declare, whichever was set first. A builder without modes gives the root agent that capability set directly, and no mode applies. SessionHandle::selection(model, mode) issues the Selection a submitted message or a continued turn carries, rejecting a provider/model or mode the session does not have; omitted selections retain the active model and mode. A mode change applies to the root agent from the boundary that consumes it, not retroactively to children it already started. A session runs the harness’s modes and capability ceiling, whatever it ran under before. A reopened session reports modes the configuration redefined or removed in warnings() and changes nothing while viewed, nor when calls such as rename, record_status or cancel_job activate it. The next work that runs the root (a prompt, continue, job delivery or run_script) decides its mode once: the selected one, else its own as configured now, or the default mode once its own is gone (without a default mode, it keeps running its own edition). A message’s ModelChanged and ModeChanged are journaled in one transaction with its MessageCommitted; a script’s precede the script. Each ModeChanged or AgentStarted whose definition differs from that mode’s latest journaled one records a new edition, which the journal keeps for auditing. SessionHandle::changes_mode(mode) reports whether the root’s next message in mode would change what it runs.

Each SessionEvent::TitleSet records its TitleSource: Prompt, User or Generated. SessionHandle::set_title(title) gives an automatic title to a session that has neither a title nor a first prompt to take one from, and leaves any other alone. run_script titles nothing: the terminal titles a session its script starts with the script’s path, and a headless --script leaves the session untitled. rename(Some(title)) sets the user’s title, and rename(None) journals a TitleCleared that returns the session to its automatic title. title().await reads the title the session list shows, as a SessionTitle with its text and TitleSource: the user’s newest title unless cleared since, otherwise the newest Prompt or Generated title, otherwise the first text the user sent the root agent, as a Prompt title.

Before building, hosts can supply policy, question and sensitive-prompt handlers, additional tools, and an embedded shim catalog. A Policy answers Approval::Decided for what it settles by itself and Approval::Ask for what it asks someone, asking nothing until that future is polled. A call that may not ask anyone, because a path it names outside the workspace does not exist, drops an Ask unpolled and is refused with PolicyDecision::refused(), the reason a person’s denial should carry so the two cannot be told apart. A SensitivePromptHandler answers each SensitivePrompt with a PromptAnswer: Secret for passwords, passphrases and keyboard-interactive prompts, and Confirmed or Rejected for the confirmation kinds (SensitivePromptKind::is_confirmation), which cover host keys and agent key use. A handler error means no answer could be obtained; Rejected is a decision, and so is an answer of the wrong shape for the prompt’s kind. Core Config loading does not load .env; environment setup belongs to the host (the CLI performs its own startup loading).

The builder defaults to <workspace>/.skyhook/sessions. HarnessBuilder::session_root, including an override supplied by Config::session_root, is passed through unchanged: a relative path is relative to the process working directory, not the workspace or configuration file. The CLI selects its own workspace-local session root.

Persona and prompt templates

A host keeps its persona and mode instructions as embedded Tera templates, which the library renders for each agent. skyhook::templates! embeds each named file from the invoking crate’s src/prompts, as a Source::Template, rendered by Tera, or a Source::Verbatim, such as a script shown to the model, included as written and never parsed. A file’s final newline is not part of it, so an include can sit mid-line. Templates::with(sources, &sample) registers them beside the library’s templates, which they can include by name, for a serializable section type H.

Prompts::host(&templates, &section, persona) and HarnessBuilder::prompts give a session the host’s section, fixed for the session, and its persona template, placed in every agent’s system prompt after the built-in role text and before the runtime’s workspace, tool, capability and mode instructions. Templates are named by a TemplateName, the name they are registered under. A mode whose instructions is Instructions::Template(name) is told that template; configuration spells only text, and dump config leaves a template out. Each template renders from the agent’s context (role, available_depth, capabilities, mode, location, job_view) with the section’s fields as top-level names, when the agent’s contract is fixed: Prompts::edition renders a mode’s instructions for an agent entering it.

The journal keeps what rendered: a mode’s edition records its instructions’ text, and an agent’s prompt as sent. A resumed agent keeps its recorded prompt until a mode change rebuilds it, and a reopened root whose mode now renders otherwise warns of a changed mode. One whose mode no longer renders for it opens all the same, warning with the error, which the work that next runs the root in that mode returns.

Registration refuses a template that reads a top-level name its context does not define, counting the names its includes read, so a misspelled setting fails at registration rather than rendering as false. Names nested in a value (capabilities.agents) are not checked.

Host state

HarnessBuilder::host_state(Arc<dyn HostState>) lets the host add its own section to an agent’s runtime state. The harness asks for the section before each request and before a compaction summary, places it inside the state block beside the date, live jobs and todos, and journals it with the state. It is asked with the host’s tables in the session (its session_extension, so only the host’s own sessions have a section) and the agent, so it can read what the host keeps in the session and answer per agent. The host renders the text itself; None adds nothing to that request. Use it for facts an agent needs current, such as a workflow’s identity, policy and progress, rather than prefixing them to the user’s first message. Keep it to the agents that act on it: the state changes between requests, so every character of it is input a provider’s prompt cache cannot reuse.

HostState::events gives an agent news from the host’s own ordered log instead: what it holds for the agent after since, the HostCursor the agent’s last host event went through, or from its start. A cursor is any non-negative i64 position (HostCursor::try_from), stored as it is. The harness asks only as a request is about to be made, so a host event never starts a turn, reopens an answered one, keeps an invocation open or ends a wait: it joins the job events delivered with that request, as {"kind":"host", …view} with the view the host built (HostView::try_from an object naming no kind of its own), and commits in one transaction with its cursor. Each event is given once, across retries, compaction and reopening; an interrupt during the read commits nothing, and a failed read fails the request (HarnessError::HostEvents). The default gives none.

Session origin and host capabilities

HarnessBuilder::new(workspace, host) names the application creating a session. HostName (in skyhook::identity) is nonblank; choose a stable tag such as the binary’s name, not a session title or mode. Tags do not change the session root: hosts share <workspace>/.skyhook/sessions unless they explicitly override it.

SessionHandle::host() and SessionStore::host() expose the persisted origin; SessionSummary::host, SessionStats::host, and SessionEvent::SessionStarted::host retain it for listing, accounting, and journal exports. resume_session may open another host’s session for inspection; SessionHandle::is_view_only() identifies that case, and every call that would change the session fails with HarnessError::HostMismatch { session, host }. Host tags prevent accidental cross-application activation, not access by other processes with filesystem write permission.

Declare application-specific capabilities with HarnessBuilder::host_capabilities. Declaration alone does not grant authority: include Capability::Host(name) in the ceiling and the modes that need it, just like built-ins.

use skyhook::tool::policy::{Capability, HostCapability, HostCapabilityDeclaration};

let verdict: HostCapability = "security.verdict".parse()?;
let builder = builder.host_capabilities([HostCapabilityDeclaration {
    name: verdict.clone(),
    title: "Decide verdicts",
}]);
let options = ToolOptions::default().requires(Capability::Host(verdict));

Capability::title names a capability for the user: a built-in label, a host capability’s declared title, or the name of one the given declarations leave out, such as another host’s. The terminal shows a product’s capabilities under the titles its Identity declares.

Names have exactly two components, <namespace>.<name>, each starting with a lowercase ASCII letter and continuing with lowercase letters, digits, or underscores. build() rejects undeclared host names in the ceiling, any mode, native tool requirements, or MCP requirements with HarnessError::UndeclaredHostCapability. Host capabilities use the existing mode, ceiling, delegation subset, and tool gates.

Host observation API

SessionHandle::store() is the session’s journal. Its observe() returns an Observation: the session’s live part, an ObservationSnapshot, and a receiver of the updates after it, sharing an atomic revision boundary. It copies only what the session holds live, so it costs the same however long the session is, and a host may call it whenever it needs a fresh start. Its applied() is the newest record the session has applied, without observing. The snapshot holds:

  • applied, the newest record it folds, after which every record arrives as an update, and last_activity, when the newest record that is the session’s activity was journaled.
  • requests, each agent’s newest request, with its lifecycle phase, outcome and usage.
  • jobs, the jobs the session holds: their owner, call arguments, state, failure, current invocation, and when that invocation ran. A job’s update arrives just before the record that moved it. RuntimeEvent::JobsUnheld names the jobs the session let go of, which the snapshot drops; a job’s last update is its final view until a record moves it again.
  • activity, each agent’s current activity, with when its turn began (or, once it is no longer busy, when that turn ended); an agent that stops running, as a parked child does, gets an update with none.
  • views, what the records fold into beside the committed state: responses, the live responses keyed by agent and logical request (their streamed blocks in arrival order, then the authoritative blocks once the response has ended; an agent’s responses are its latest turn’s, and one that settled without committing, failed or interrupted, stays until the agent’s next agent request, as a reopened session also shows it); context, the context gauge, each agent’s occupancy as its last committed response reported it, cleared by a checkpoint; and entries, how many entries each agent’s transcript holds.
  • usage, the usage each agent’s requests reported.

Apply updates in revision order with ObservationSnapshot::apply. Once the session no longer runs (viewed, failed or closed), the snapshot reads every request, response, job and turn it left going as interrupted at its last activity. apply returns what an update changed beyond what it carries: entry, the ordinal its record took in its agent’s transcript (none for a record the snapshot already folds); stopped, the jobs and requests read as interrupted that way, which no update of their own reports; requests, the requests its record changed; superseded, the request of its agent that a newer one replaced, as it left it; fact, what the fold decided of its record that presenting it reads (a session::Fact: the request an assistant message committed under, the message whose call a result answered, or that a failed turn ended on its request’s failure); and unheld, the jobs the session let go of, as they left them.

RuntimeEvent::OutputChanged { job, invocation } reports that a run captured output after its output was last read, by any reader; it carries no output. Read it with inspect_output_with_captures. No further one is posted for that run until its output is read again or the run finishes, whose job update reports the final output.

RuntimeEvent::ResponseChanged { agent, request } reports that a response streamed after it was last read; it carries no deltas. Read the response as it streamed so far with SessionStore::response(agent, request) and replace it in views.responses; a read may run ahead of updates still queued, which fold after it. No further one is posted for that response until it is read again, a record of its agent applies, or a new observation is taken. Live responses are provisional, not additional committed messages. A new attempt of the same logical request resets its live response without removing durable attempt records. On receiver lag, obtain a fresh observation and replace both the snapshot and receiver, then read again the pages on display; continuing with only one can leave a gap or apply stale live state.

Reading history in pages

History is read in pages after observing, through the handle’s store() (a SessionStore) and jobs() (a JobManager), each in one snapshot of the journal. A Page is the first or last of a list, or the entries after or before a key, which it never includes:

  • transcript(agent, page, limit) returns consecutive entries of one agent’s transcript by ordinal, with their facts: what presenting them reads beyond them, as the journal leaves it (the requests they make or answer, each answer’s request and when its turn began, the result of each call they made and the calls that started a job, and the failed turns a request’s failure reports), so a host can show any page on its own. PageFacts::observe folds an update’s record and its fact into them.
  • jobs().page(JobScope::Roots(owner) | JobScope::Children(parent), page, limit) returns an owner’s jobs that do not nest under a parent (JobEnvelope::nests: a job its owner’s script issued), or a parent’s children whoever created them, in id order; jobs().views(ids) returns jobs by id.
  • requests(agent, page, limit) returns an agent’s requests as the journal leaves them.
  • agents() returns every agent the session started as the records that say what a host shows of it (its start, latest model and mode changes, latest todos and the latest record that ended a turn), when the turn that record ended began and ended, when its open turn began, and its owner job, read through through: a summary’s records repeat any update through it.
  • failed_after(agent, record) says whether an agent journaled a failed turn after a record.

A page sees at least what the observation applied. A host places an update’s record at the ordinal apply reports, counted on from the snapshot’s views.entries: a record at an ordinal a page holds is one the page already shows, and every later one is news. Requests and jobs read as the snapshot holds them where it holds them, and as their page read them otherwise; a page in flight when the session lets a job go may have read it before its final view, which apply hands over in unheld, as it hands over a request a newer one replaced in superseded.

Inspection and host records

inspect_output_with_captures and jobs().inspect_output_fields are host inspection APIs. They do not claim jobs or consume agent notifications. cancel_job is the separate operation that requests cancellation. warnings and mcp_servers expose startup diagnostics and MCP discovery outcomes without inserting diagnostics into model context or writing directly to a terminal. record_status likewise records host-facing status, not a user message.

TodoItem and TodoStatus are exported by skyhook::agent. Hosts projecting checklists from records apply SessionEvent::TodosReplaced and the reconciled todos in SessionEvent::Compaction checkpoints in sequence. Both replace the owning agent’s entire list; child-agent lists remain independent.

Interruption, continuation, and shutdown

prompt and prompt_with_options submit input and wait for its turn. interrupt stops active turns while retaining child jobs for continuation, and returns how many turns and unstarted child agents it stopped, and calls it withdrew from waiting on the resume hook. If it stopped any turn or agent, job deliveries start no turn until continue_turn_with or new input: they stay pending for that request. An interrupt also hands back input no agent has taken yet: a pending prompt returns Interrupted, and each QueuedPromptReceipt from enqueue_prompts resolves Interrupted. Queued prompts are checked when a request boundary takes them, all of them as one batch. A batch the session refuses fails the turn, whose AgentFailed record says why, and waits with it: its receipts stay pending, each prompt can still be withdrawn (QueuedPromptCancellation::is_retained tells such a prompt) until continue_turn_with takes the batch to try again under its selection, together with anything queued since. It checks the batch as a request boundary would before it changes anything, and from then on the root runs it as a turn: a batch those checks or the selection refuse waits again unchanged, together with anything queued meanwhile, and the call returns why. One that an interrupt stops first also waits again unchanged, but the interrupt hands back what was queued meanwhile (Interrupted), as it does any input no turn has taken. An interrupt leaves a waiting batch waiting; a prompt hands it back (Interrupted), and so does an interrupt that overtakes the refusal itself, after which the root rests unless a turn is still open. Closing the session drops it. Explicit job cancellation is non-resumable. continue_turn_with continues failed or interrupted work without duplicating its input and can select a model or mode for the continued root turn. It always restarts the interrupted or failed children first; a root turn or batch refused afterwards returns why without undoing that. Its ContinueOutcome distinguishes a root answer from resumed children and reports whether the selection applied: only a continued root turn applies it, and restarting children does not imply that a waiting or live root also ran. continue_turn uses default options and returns the root answer, or an empty string when there is none.

HarnessBuilder::resume_hook registers a ResumeHook whose resumed(&ExtensionDb) runs once per launch for each of the host’s own sessions with its tables that it reopens, before the first prompt, enqueue_prompts, continue_turn_with or run_script; a session only viewed never runs it, nor does one this launch created. SessionHandle::resume_work runs it on its own, for work the host prepares before sending it. A failure refuses that work with HarnessError::Resume (the first queued prompt says why, the rest of its batch resolve Interrupted), and the next work calls it again. An interrupt withdraws every call still waiting on it, even one whose hook succeeded or failed as the interrupt landed: each returns Interrupted, starts nothing, and counts in what interrupt returns. The interrupt leaves its turns continuable as any interrupt does. A hook the interrupt cut short is dropped and runs again for the next work; one that finished does not. shutdown withdraws the calls waiting on it in the same way and returns only once each call’s hook has ended, so nothing the hook does follows it.

Use Harness::resume_session to reopen durable state. The session opens to view: it journals nothing, and its observation reads it stopped at its last activity, until the first call that changes it, such as a prompt, continue_turn_with, a script, a status, a title or a job cancellation. That call first prepares the root agent; if that fails, for example because its provider cannot open a conversation, the call fails and the session stays viewed. Otherwise the runtime reconciles interrupted work in one transaction before starting agents. Shutting down a viewed session stops nothing and journals nothing: it closes the session, releasing it for another open, and later calls that would change it are refused. Work the previous process left open is recorded as ending when that process last did something, so reopening a session is not activity; record times therefore need not increase with sequence. It opens fresh provider contexts and does not reuse old network resources. A root turn that failed or was interrupted before the session closed can still be continued. A root that closed idle with job deliveries pending resumes interrupted too, so continue_turn_with or new input delivers them. Journaled agent settings remain the baseline, subject to restrictions imposed by current host configuration. A session whose root’s recorded model is no longer configured still opens and activates, and warnings says so: calls that only write, such as a title, a status or a job cancellation, work as usual. Only running the root fails, with HarnessError::UnknownModel and before anything is journaled: a script, or a direct prompt, a continuation or an enqueue_prompts call of which no prompt names a configured model. A selection naming one replaces the model, as does SessionHandle::activate_on, which a viewed session journals in the commit that activates it. Job deliveries that would wake the root before then begin a turn that fails as any failed turn does, journaled, and stay pending for the input that names a model. A child whose own model is gone restarts on the root’s, journaled as a model change; with the root’s gone too, its restart fails alone.

Session database formats are clean breaks (the current one is named in architecture): earlier formats are not migrated and cannot be resumed; retain a compatible Skyhook version to inspect them, or start a new session.

Await SessionHandle::shutdown() before releasing the host’s session owner. Shutdown stops runtime producers, drains accepted job and journal work, and closes MCP and remote resources. It interrupts the session as a crash would: child agents still running end interrupted and can be continued once the session is resumed, and other running jobs are cancelled. Once it has begun, new prompts, continue, host scripts, new jobs, and input that would restart a finished job are refused with SessionError::Refused; input to a running job and answers to its questions are still accepted. The journal remains available so the host can append a final status after observing shutdown errors; await that append, then SessionHandle::close(), which releases the session so it can be opened again at once rather than once every handle has dropped; closing a closed session does nothing. Closing also prevents retained output handles from writing to the session; already saved output remains readable. Dropping the last SessionHandle without shutting down closes the session as a crash would leave it and stops its agents and jobs; resuming it settles what was running. A session closed with nothing journaled, such as one whose new_session caller gave up, is removed. A write the session journal cannot take stops the session as a crash would: the call that met it, calls it cut short and every later call return SessionError::JournalFailed with the first cause; shutdown and close report it too and still release the session. Its observation reads the phase as failed and otherwise shows what reopening the session would; an observation attached before then no longer follows it once it folds that phase, and observes again. SessionHandle::phase tells whether the session still runs and journals. A session belongs to the Tokio runtime that created or resumed it: use it only from that runtime, and keep the runtime running until the session is closed.

Reading a session archive

SessionStore::read_records(root, id).await returns every record, in sequence order, from a read-only database snapshot without acquiring the session’s writer lock: an explicit export of the whole journal. A live owner may continue writing; archive inspection neither takes ownership nor resumes unfinished work. SessionStore::is_open(root, id).await reports whether a store in any process holds the session. It takes the session lock shared for an instant; an open racing it retries once before failing with AlreadyOpen. SessionStore::summary(root, id).await reads a session list row without decoding the session, including its title as SessionStore::title reads it, in last_millis the time of its newest record that SessionEvent::is_activity (closing a session is not), and, in stopped, the failed or interrupted turn that resuming the root agent would continue, if any. stopped reads only the root’s journaled turns, so a session that closed idle with job deliveries pending has none, yet resumes interrupted. SessionStore::stats(root, id).await reads, the same way, the statistics skyhook stats reports: aggregates over the whole journal, its requests read a page at a time, so its memory does not grow with the session.

The SQLite layout is versioned. Opening a database validates its identity and version; there is no migration or compatibility layer for earlier layouts.

An embedder that runs the library without skyhook_cli::main may call skyhook::db::configure_process() once at startup, before any other thread or SQLite use. It turns off SQLite’s allocation statistics, whose global mutex serialises parallel readers, but it also disables SQLite memory accounting for everything else in the process, so the library never calls it on its own.

Reconstructing model calls

The journal records inputs at the shared Provider boundary, not codec-specific request bodies or authentication headers:

  • model_context stores a ModelContext: the purpose, named model-profile snapshot, assembled system segments (including harness instructions and location), tool descriptions and schemas, and optional response schema. Its template() derives the history-free ModelRequest, including the model ID, reasoning setting, and output limit. Context records describe request settings, not the lifetime of a ProviderContext resource.
  • model_requested identifies one frozen logical request before its first invocation. It references the context record and stores the checkpoint it opens with, its history as the agent’s commits through a message sequence (a summary that overflowed resumes from a later one), tail as exact inline messages, and history_lifetime. Retries refer back to this request using model_attempt_started, with separate failure/interruption or completion outcomes. Ordinary requests reuse a context record while their settings remain applicable; summarization has a separate context with its structured response schema.
  • compaction stores the exact replacement message, retained original message references, covered frontier, the summary attempt that produced it, the reported occupancy that triggered it (none after an overflow), and reconciled owner todos. History and todos become active together after persistence.
  • Runtime state and job-event content are stored structurally and rendered for the model on reconstruction, so a request replays the text the model was sent. A reconstructed context carries, before each response since its checkpoint or the agent’s latest mode switch, the state the request that produced it sent; codecs decide whether to send it.
  • Reconstruction resolves those references and inline values. It does not consult current configuration, live jobs, or the current compaction renderer. Runtime state and job events are rendered by the current state renderer and job-view serialization, which are therefore part of the session format: a change to either is a database version bump. Failed and interrupted requests keep their recorded inputs; usage identifies the originating request, including summary requests and failed attempts.

SessionStore::reconstruct_model_request(sequence).await returns the provider/model name the request was issued under and the reconstructed ModelRequest for a model_requested sequence, read from the session’s journal. It checks the request’s context (its agent’s newest for that purpose), checkpoint and history bound, and that an agent request follows a result for every call its agent made, as an append does, so other records fail with a ReplayError. Attachments and tool images reference content-addressed blobs by SHA-256; load_blobs(&mut request, &mut cache) on the same store loads their contents for provider encoding, reusing and then keeping exactly this request’s blobs in cache. Both need an owning SessionStore; unlike read_records, opening a store acquires the session’s writer lock. Reconstruction reproduces Skyhook’s provider-neutral input, not an API-specific wire encoding or a replay of the external call.

The ModelRequest contract preserves the typed context entries and history_lifetime cache hints. See history, transient state, and caching for their semantics and provider rationale.

Remote transport and shims

Remote execution changes where an operation runs, not who owns the agent or job. Provider calls, agent loops, policy decisions, job state, saved output, and session blobs remain owned by the Skyhook host. A shim runs individual operations and streams their output back; it does not create a session database or run a second agent harness.

Responsibility boundaries

  • Target resolution selects a validated route and execution workspace. SSH configuration comes from target definitions, not the user’s or system’s SSH configuration.
  • RemoteManager owns the session’s connection pool, keyed by resolved route identity and workspace. It coordinates shared startup, invalidation, and shutdown, and tracks startup and reader/drain tasks independently of pool membership and callers.
  • ConnectionFactory supplies the byte stream and lifetime owner. The SSH backend handles authentication, OpenSSH processes, platform probing, and shim deployment; it does not implement job supervision or saved-output storage.
  • The common client performs the shim handshake and routes multiplexed requests, output, authorization checks, and private control messages. The host persists streamed output and images using the same job-output machinery as local execution.
  • The worker reuses the local built-in invocation layer for argument admission and operation execution. Permission requests return to the host’s authorization coordinator. Private services support relayed SSH streams and sensitive prompts without turning them into tool results.

This division keeps transport-specific code below the tool/job boundary and lets local and remote operations share validation and execution behavior.

Connection and request lifecycle

Connection startup is shared by callers using the same pool key. Cancelling one waiter stops its wait, not the shared startup; redefining a target on its route stops the startup, and its callers plan again. Startup failure removes the failed slot; transport I/O or protocol failure during execution discards the affected pooled connection so later work can establish a new one. It does not transparently replay the failed tool operation.

Once connected, request IDs associate output and cancellation with individual operations. SSH cancellation remains best-effort: the client does not await a terminal reply. Already captured output remains inspectable, but final worker diagnostics or structured results may be unavailable. Credit-based flow control bounds queued payload, source-upload, and relayed-stream data. A transport’s lifetime owner retains its underlying process resources; dropping it tears those resources down. A relayed connection also retains its origin connection for the lifetime of the child stream.

Accepted-payload ingestion is tracked independently of pool membership and caller lifetime. Pool eviction does not abort the reader; dropping the last PooledConnection owner cancels routing instead. When routing ends through cancellation or failure, the reader releases the transport owner before draining the finite queue of already accepted payloads. The drain does not require a live socket or further acknowledgements, and the session tracks the reader until it finishes. This protects accepted output, not payloads that never reached the host or a terminal reply the worker has not sent.

Session shutdown cancels startup and routing, fences new startup under the pool lock, and clears the pool. Shared startups and readers use the same session task tracker: a startup registers its reader before its own tracked lifetime ends, so shutdown cannot miss a reader from an in-flight handshake. Shutdown waits for startup and reader/drain work before backend cleanup releases session-owned authentication resources.

Origin versus jump hosts

Routing decides where SSH runs: on root or on the shim of the destination’s origin. Targets listed through via are native ProxyJump hops of that SSH process, not additional shim workers. A remote origin’s shim can start SSH and relay its byte stream over the existing host connection, while the host still runs the destination’s protocol client and supervises its jobs.

Shim deployment

The backend probes the remote platform, selects a matching embedded artifact, and installs it in a digest-named directory under the remote user’s cache. An existing executable is reused only after it matches the expected digest, and an upload is verified before it is installed. The shim starts in the requested workspace. The target’s configured workspace is separately resolved as the authorization root, so a per-call working directory does not silently redefine the target’s permission boundary.

Authentication and prompt isolation

Each credential origin can lazily own a private ssh-agent. Root’s agent is session-owned; remote origins manage theirs inside the shim. external_agent targets use the origin’s inherited agent socket instead. Ordinary processes started by a remote worker receive OpenSSH’s forwarded SSH_AUTH_SOCK; no second forwarding listener is needed.

SSH authentication prompts use SensitivePromptHandler, separate from model questions and tool output. Remote prompts and their typed answers (a secret, a confirmation or a rejection) travel as private control messages, not session events or saved results. OpenSSH is given an explicit askpass helper so the host can handle passwords, passphrases, and confirmations outside the agent transcript; the helper prints a secret to the program that ran it, answers yes to a confirmed host key, and exits nonzero for a rejection. The same helper is offered to sudo as SUDO_ASKPASS, which sudo uses whenever no terminal is available and some DISPLAY is set, so command password prompts reach the host the same way; a placeholder DISPLAY is set only when the process would have none. Since every interactive command receives the helper, a command the agent writes can run it and capture the answer, so each prompt carries its requester for the user to judge. The machine serving the prompt reads that requester from /proc, since its PIDs are meaningful only there. It reads the executable link of the parent of the socket peer, taking the peer to be the helper. A program running as another user, such as set-user-ID sudo, denies that read, so the prompt carries its name and effective UID instead. The attribution is best effort: any process running as the server’s user can connect to the socket itself, so a command started by a genuine program (an SSH ProxyCommand, say) is reported as that program and receives the answer. Prompts on the host also carry the job: the ancestors of the helper are compared with the processes running exec jobs have registered with the job manager. A job that has ended no longer matches. Workers don’t know host job IDs, so their prompts carry only the executable, and missing information leaves the requester unknown rather than failing the prompt. Once the session shuts down, its authentication refuses to start another askpass server.

Each askpass server keeps its helper and socket in a private temporary directory and accepts only peers running as its own user. That directory, like the managed agent’s, is made under XDG_RUNTIME_DIR when that is set and writable, and otherwise under the temporary directory: a socket path must fit the platform’s short limit (sun_path, 108 bytes on Linux and 104 on macOS), which a deep TMPDIR exceeds. When neither gives a socket path within the limit, the directory is made under /tmp, so binding never fails on path length. This prevents other local users from injecting prompts or obtaining answers through the socket; it is not an isolation boundary against other processes running as the same user. Dropping the server cancels its task and removes its temporary files.
